## TL;DR

**M6 owns**, per the frozen record's own repeated citations, three named
things, consistently bundled together across every prior milestone's
deferred-items table:

1. **An async ingestion plane.**
2. **An "Event Lake."**
3. **Population-level policies** (the literally-cited example: adverse
   impact ratio).

Read literally, these sound like three separate, large infrastructure
projects. Read against this codebase's own consistent discipline (no
infrastructure without a real, current case that needs it; no port change
without a second case to justify it; additive-only retrofits), this review
argues they are **one coherent thing with one shared reason to exist**:
population-level policies are structurally incapable of producing a
synchronous, per-event result — they need a population of decisions, not
one — so evaluating them requires an asynchronous plane and a queryable
store of accumulated events, i.e., exactly "async ingestion" and "Event
Lake." This review's central recommendation (§13.1, the highest-stakes call
in this document) is that M6 should build the async plane **that population
policies need**, not redesign the two existing, synchronous, per-event
ingestion routes into something they were never asked to become.

**Nothing else changes.** `POST /v1/ingestion/events` and
`POST /v1/ingestion/events/credit-scorecard` keep their exact current
synchronous contract — a caller still gets a real `IngestionResponse` with a
real per-event `VerdictStatus` inline, unchanged since M0/M2. `Policy`,
`Adapter`, `GovernanceEngine`, and `EvidenceStore.append` are untouched.

**Sixteen ambiguities** are identified below (§13), each with a
recommendation — fourteen from the original design pass, plus two found
only during the subsequent hostile-review pass (§13.15/§13.16). Four are
the highest-stakes calls in this document and are flagged inline: §13.1
(what "async ingestion" actually means, given no one has asked the
existing synchronous contract to change), §13.2 (whether the "Event Lake"
is new storage at all, or a new read pattern over storage that already
exists), §13.3 (whether population-level policies fit inside the existing
`Policy`/`Finding`/`Verdict` machinery or need a parallel port), and
§13.16 (whether a historical population finding is reproducible against
the rules in effect when it was computed, or silently drifts with
whatever `protected_attribute_rules` says today — found during the
hostile-review pass, and this document's most consequential correction).
Skip to §16 for a plain checklist of every decision this review needs your
sign-off on before implementation starts.

## 2. How M6 builds on M5

M0–M5 built an entirely **synchronous, per-event** pipeline:
`Adapter.translate` → `NormalizationService.normalize` →
`GovernanceEngine.govern` (now severity-driven, four-state) →
`EvidenceStore.append` (now signed) → `IngestionResponse`, all inside one
HTTP request. Every `Policy` M0–M5 ever built evaluates exactly one
`DecisionEvent` and returns exactly one `Finding` scoped to it
(`policy_engine/base.py`: *"A `Policy` evaluates exactly one `DecisionEvent`
and produces exactly one `Finding`"*) — a hard, load-bearing constraint
`GovernanceVerdict` and the hash-chained `evidence_chain` payload both
depend on (`GovernanceVerdict.decision_event_id: str`, singular).

A population-level policy — "what fraction of this system's approvals
skew against a protected group over the last 30 days" — cannot be
expressed inside that constraint at all. It needs many events, not one; a
time window, not a request; and it produces a result that doesn't belong to
any single `decision_event_id`. M6 is not a generalization of M0–M5's
per-event pipeline the way M4 generalized M3's single policy to a list, or
M5 generalized M4's static binding to a dynamic one — **it is a genuinely
new, parallel pipeline**, sharing the same normalized data M0–M5 already
produce and persist, but evaluated on a different cadence, by a different
kind of policy, producing a different kind of result. Recognizing that this
is additive alongside the existing pipeline, not a replacement or a
widening of it, is the throughline of every recommendation below.

## 3. Why each piece exists architecturally

**Population-level policies.** A per-event fairness gate (M2's
`DirectAttributeInInputsPolicy`, M4's `HighDebtRatioGatePolicy`) can only
ever catch a *direct* rule violation visible in one decision. Real
disparate-impact analysis — the actual regulatory concern a governance
platform for lending/hiring/etc. decisions exists to catch — is
inherently statistical: a scorecard can pass every per-event rule and
still approve one demographic group at systematically lower rates than
another. Architecture's own repeatedly-cited example, adverse impact ratio
(the "4/5ths rule" from EEOC guidance), is exactly this: a ratio computed
over a population of decisions, meaningless for any single one.

**Event Lake.** Population-level policies need to read many past
`DecisionEvent`s for a system, not the one currently being ingested — a
fundamentally different access pattern (a batch read over a window) than
anything the ingestion path or Admin API does today (both are single-row
reads/writes). Something has to be the durable, queryable substrate that
access pattern runs against.

**Async ingestion plane.** Given population policies cannot run inline
with a single ingestion request (they need to see events that haven't
happened yet, relative to any one request, and reading a large window on
every single ingestion call would revive exactly the "N sequential
sandboxed calls per request" throughput problem M4's own review already
flagged and pointed at M6 to solve, not worsen) — evaluating them has to
happen on its own asynchronous cadence, decoupled from any individual
ingestion request's response.

## 4. Proposed architecture (this review's recommendation)

### 4.1 The async plane is the population-policy evaluation plane — not a redesign of existing ingestion

**The two existing ingestion routes do not change.** No new response
shape, no "pending" status, no polling endpoint, no message broker in the
write path. `POST /v1/ingestion/events` and
`POST /v1/ingestion/events/credit-scorecard` keep returning a real,
synchronous `IngestionResponse` exactly as they do today — nothing in the
architecture record or this codebase's own history asks that contract to
change, and M2 §11.1's "byte-for-byte unchanged" discipline for the
*previous* route every time a *new* one was added is the closest existing
precedent for how this project treats an established route's contract. See
§13.1 for the full reasoning and the alternative reading this review
declined.

**"Async" describes the population-policy evaluation pipeline**: a
separately-invoked process reads a window of already-ingested,
already-normalized `DecisionEvent`s for a system, runs every active
population policy against that window, and persists the results — entirely
decoupled from, and with zero latency impact on, any individual ingestion
request.

### 4.2 The Event Lake is the existing normalized store, read a new way — not new storage

`decision_events` (migration `0003`) already holds `input_features`,
`protected_attribute_refs`, `decision_output`, and `occurred_at` for every
event ever ingested, joined to `model_versions`/`systems` for identity.
Everything an adverse-impact-ratio computation needs to read already
exists, normalized, in Postgres. This review recommends **no new physical
store** — "Event Lake" names a new *batch, windowed read pattern* over the
existing operational tables, not a new table, and certainly not a new
storage technology (object storage, Kafka, a separate analytical database).
See §13.2 for the full reasoning and the real production caveat this punts
on.

**Correction from the hostile-review pass, before implementation:**
`protected_attribute_resolutions` (M2) holds *classification*
(`DIRECT`/`PROXIED`/`WITHHELD`), not the attribute's actual *value* — it
records that `race` is `DIRECT` for a given event, not that this event's
`race` was `"Black"`. Adverse impact ratio groups decisions **by value**,
so the population read must go back to `decision_events.protected_attribute_refs`
(the raw refs) for values, cross-referenced against a ruleset for which
keys are `DIRECT` in the first place. That cross-reference reopens M5
§13.9's named divergence in a new place: does the population read use the
static `classification.py` (what `DirectAttributeInInputsPolicy` uses) or
the DB-backed `protected_attribute_rules` (what `EvidenceStore` uses)?
**Decision: the DB-backed `protected_attribute_rules`.** The batch job
already has full, unconstrained database access — none of the constraints
that forced `DirectAttributeInInputsPolicy` onto the static ruleset
(`Policy`'s zero-argument construction, per M5 §13.9) apply here. Using the
static ruleset would also mean a population finding could silently
disagree with what an admin currently believes is protected, for no reason
but which of two rulesets M6 happened to pick.

This decision has a real consequence, addressed fully in §13.16: unlike
`policy_id`/`population_policy_version` (code identity, deploy-pinned,
naturally stable), `protected_attribute_rules` is live, admin-mutable data
with no versioning or point-in-time history. A population finding computed
against it must **snapshot exactly which classifications it used**, not
just reference the table — see `PopulationFinding.classification_snapshot`
in §4.3 and §13.16's full reasoning.

### 4.3 A new, parallel `PopulationPolicy` port — not a widened `Policy`

**Revised from the first draft, per the hostile-review pass**: `PopulationWindow`
no longer materializes every raw `DecisionEvent` into Python — the one real
policy this milestone ships only needs a `GROUP BY` count per protected-
attribute-value and outcome, which Postgres computes far more cheaply than
loading a window's full row set into memory and aggregating in-process
(see §13.3's revised recommendation). `PopulationWindow` therefore carries
pre-aggregated counts, computed by a single SQL query joining
`decision_events` against whichever attribute names `protected_attribute_rules`
currently classifies as `DIRECT` for the system's domain — and it records
exactly which classifications it used, for the reproducibility reasons in
§13.16:

```python
class PopulationGroupCount(BaseModel):
    """One (attribute_name, attribute_value) group's outcome counts within
    a window -- the unit adverse-impact-ratio-style metrics need, computed
    by one SQL GROUP BY, not assembled from row-level DecisionEvents."""

    model_config = ConfigDict(frozen=True)

    attribute_name: str
    attribute_value: str
    total_count: int
    favorable_outcome_count: int  # e.g. "approved" -- outcome key is policy-specific


class PopulationWindow(BaseModel):
    """One system's decisions over one time window -- the unit a
    PopulationPolicy evaluates. Built by a new population_engine/window.py,
    which reads decision_events.protected_attribute_refs for values and
    protected_attribute_rules for which attribute names are DIRECT (see
    §4.2) -- not persisted itself. classification_snapshot is exactly what
    was read, carried forward so the eventual PopulationFinding is
    self-contained (§13.16)."""

    model_config = ConfigDict(frozen=True)

    system_id: str
    window_start: datetime
    window_end: datetime
    group_counts: list[PopulationGroupCount]
    classification_snapshot: dict[str, str]  # attribute_name -> classification, as read


class PopulationFindingOutcome(StrEnum):
    CLEAR = "CLEAR"
    FLAGGED = "FLAGGED"


class PopulationFinding(BaseModel):
    """One PopulationPolicy's evaluation of one PopulationWindow. Not tied
    to a single decision_event_id -- the entire reason this is a new type,
    not a reuse of Finding. classification_snapshot is copied straight from
    the PopulationWindow that produced this finding -- see §13.16: this
    field, not a live read of protected_attribute_rules, is what a
    signature verifies and what an audit five years from now interprets
    against, regardless of how the ruleset has changed since."""

    model_config = ConfigDict(frozen=True)

    population_finding_id: str
    population_policy_id: str
    population_policy_version: str
    system_id: str
    window_start: datetime
    window_end: datetime
    outcome: PopulationFindingOutcome
    metric_values: dict[str, float]
    classification_snapshot: dict[str, str]  # attribute_name -> classification, as used
    rationale: str
    evaluated_at: datetime


class PopulationPolicy(ABC):
    """Architecture's population-level policy surface -- a distinct port
    from Policy (§7), evaluated on a window of decisions, not one."""

    population_policy_id: str
    version: str

    @abstractmethod
    def evaluate(self, window: PopulationWindow) -> PopulationFinding:
        raise NotImplementedError
```

`Policy.evaluate(event) -> Finding` and `GovernanceEngine` are completely
untouched. See §13.3 for why this review recommends a new port over any
attempt to fit population results into the existing `Finding`/`Verdict`
shape.

### 4.4 One concrete `PopulationPolicy`: adverse impact ratio for `FINANCE`

Architecture's own repeatedly-cited example, computed the standard way
(EEOC "4/5ths rule"): for each `DIRECT`-classified protected attribute
already resolved by M2's machinery, compare the approval rate (read from
`decision_output`) for each attribute value against the group with the
highest approval rate; `FLAGGED` if any ratio falls under 0.8. One
concrete metric, one concrete domain (`FINANCE`, the only one that
exists) — not a general population-metrics framework. See §13.9.

### 4.5 Bindings, lifecycle, and triggering — extending existing mechanisms, not new ones

- **Plugin lifecycle:** `PluginType` gains `POPULATION_POLICY`; a
  `PopulationPolicy` registers/promotes through the exact same
  `plugin_registrations` table and Admin API `promote` endpoint every
  `Adapter`/`Policy` already uses. No new lifecycle mechanism.
- **Binding:** a new `population_policy_bindings` table, keyed by
  `(system_id, population_policy_id)` — **not** `adapter_id`, and **not**
  a reuse of `policy_bindings`. See §13.8 for why this is a real, separate
  decision, not a copy-paste of M5's binding shape.
- **Triggering:** a new CLI, `python -m gov_platform.population.run_policies`,
  mirroring `plugins/seed_registry.py`'s and `audit/verify_chain.py`'s
  existing shape — an explicitly-invoked batch job, not a new daemon or
  in-process scheduler. See §13.4.

**Four implementation-readiness requirements surfaced by the hostile-review
pass, binding on whoever implements this even though none change a
numbered decision:**

- **Windows are fixed, calendar-aligned, and closed in the past** —
  e.g. always "yesterday's full UTC day," never `[now() - 30d, now())`. A
  rolling window recomputed fresh on every invocation has no stable
  identity, makes the uniqueness constraint in §6/§13.13 meaningless, and
  reads right at its own boundary while ingestion is still writing. This is
  now part of the design, not an implementation detail — see §13.13.
- **`PopulationPolicy.evaluate` must run through `run_sandboxed`**, the
  same timeout/exception isolation every other plugin call in this
  codebase (`Adapter.translate`, `Policy.evaluate`, shadow evaluation)
  already gets. The original sketch omitted this; it would have been the
  one unguarded plugin call in the system.
- **The runner must check `plugin_registrations` for `PRODUCTION` before
  evaluating a bound `PopulationPolicy`**, exactly like the ingestion
  route's existing 503 discipline for `Adapter`/`Policy` — the original
  sketch didn't say this explicitly and, as drafted, would have happily run
  a `DRAFT` implementation against real data.
- **A minimum per-group sample size gate.** A group with a handful of
  decisions can produce a mathematically valid but statistically
  meaningless ratio. Below a stated floor, the policy must report `CLEAR`
  with an explicit "insufficient data" rationale, not a `FLAGGED` verdict
  built on noise — this is a governance-correctness requirement, not a
  testing nicety.

## 6. Database schema changes (proposed)

```sql
-- population_policy_bindings: which population policies evaluate which
-- System's decisions -- system_id-keyed (not adapter_id; see §13.8),
-- deliberately separate from policy_bindings.
CREATE TABLE population_policy_bindings (
    id                    TEXT PRIMARY KEY,
    system_id             TEXT NOT NULL REFERENCES systems(id),
    population_policy_id  TEXT NOT NULL,
    lifecycle_state       TEXT NOT NULL,   -- 'ACTIVE' | 'INACTIVE'
    created_at            TIMESTAMPTZ NOT NULL,

    UNIQUE (system_id, population_policy_id)
);

-- population_findings: one PopulationPolicy's result for one
-- (system, window) pair -- never chained into evidence_chain (see §13.5),
-- but append-only for the same evidentiary reason evidence_chain is
-- (see §13.16, revised from the first draft).
CREATE TABLE population_findings (
    id                          TEXT PRIMARY KEY,
    population_policy_id        TEXT NOT NULL,
    population_policy_version   TEXT NOT NULL,
    system_id                   TEXT NOT NULL REFERENCES systems(id),
    window_start                TIMESTAMPTZ NOT NULL,
    window_end                  TIMESTAMPTZ NOT NULL,
    outcome                     TEXT NOT NULL,   -- 'CLEAR' | 'FLAGGED'
    metric_values                TEXT NOT NULL,   -- JSON, matching every other table's convention
    classification_snapshot      TEXT NOT NULL,   -- JSON: attribute_name -> classification, as read at computation time (§13.16)
    rationale                    TEXT NOT NULL,
    evaluated_at                 TIMESTAMPTZ NOT NULL,
    signature                    TEXT,            -- see §13.6; covers classification_snapshot too
    signing_key_id                TEXT,

    -- Revised per the hostile-review pass (§13.13): a window is computed
    -- exactly once. A duplicate insert (an overlapping/retried run) is a
    -- clean no-op, not a race that produces two disagreeing findings for
    -- "the same" window.
    UNIQUE (population_policy_id, system_id, window_start, window_end)
);
```

No changes to any existing table — `decision_events`,
`protected_attribute_resolutions`, `verdicts`, and `evidence_chain` are
read-only inputs to the new pipeline, never written by it.

**Privileges, corrected from the first draft.** `population_policy_bindings`
gets the same ordinary `GRANT SELECT, INSERT, UPDATE, DELETE` treatment as
`policy_bindings` — legitimate, live admin config (which system a policy
currently applies to). `population_findings` does **not**: per §13.16, a
population finding is computed governance output, evidentiary in the same
sense a `Verdict` is, and needs the same append-only guarantee
`evidence_chain` gets (`REVOKE UPDATE, DELETE`), not the mutable-table
treatment this review originally proposed for it. Combined with the
uniqueness constraint above, this makes "silently recomputing" a historical
window structurally impossible — a deliberate recompute (§13.16) can only
ever produce a new, additional row.

**A required index, elevated from "worth considering" in the first draft
to a concrete requirement**: `decision_events` has no index shaped for
"this system's events in this window" today — a population read joins
through `model_versions` to `systems` with no supporting index at all.
Add `CREATE INDEX idx_decision_events_model_version_occurred_at ON
decision_events (model_version_id, occurred_at);` in this milestone's
migration set. A full analytical-store split remains out of scope (§13.2)
— this is the minimum needed for the windowed read this milestone actually
performs not to table-scan.

## 9. Interfaces and abstractions

`PopulationPolicy` (§4.3) is a new, third plugin port alongside `Adapter`
and `Policy` — the first new port since M0. This review treats introducing
it as a real, explicit architectural decision requiring your sign-off
(§16), not a mechanical extension, for the same reason `governing_policy_ids`
and `GovernanceEngine`'s constructor changes have each individually needed
sign-off at every prior milestone. Justification for a genuinely new port
rather than forcing `Policy` to serve double duty: `Policy.evaluate`'s
single-event, `Finding`-per-`decision_event_id` contract is structurally
incompatible with an aggregate result (§2) — this is not a case of two
similar things that happen to differ slightly (where this project's
"three lines beat a premature abstraction" discipline would argue against
a new type), it is two genuinely different kinds of question ("does this
one decision violate a rule" vs. "does this population of decisions show a
statistical pattern") that only coincidentally share the word "policy."

## 12. Expected production-readiness review points

- **The Event Lake is read-only reuse of operational tables not sized or
  indexed for batch/windowed scans.** `decision_events` has no index on
  `(model_version_id, occurred_at)` or equivalent today — a population
  query scanning "every event for this system in the last 30 days" will
  table-scan at real volume. Worth an explicit index in this milestone's
  migration, and worth naming that a real analytical-store split
  (`architecture-mapping.md`'s own §16 row already names this as a later,
  unscheduled milestone) is the actual long-term fix, not solved here.
- **Adverse impact ratio's 0.8 threshold is a hardcoded constant** — the
  same governance smell M2 flagged for its own domain and M4 flagged for
  its debt-ratio constant, now a third instance. Precise provenance
  documentation (this is the EEOC's own 4/5ths guidance, not an invented
  number), not a configuration system, is the realistic fix at this
  milestone's scope.
- **A `PopulationFinding` has nowhere to escalate to** — same
  "`ESCALATE_FOR_REVIEW` verdict that says review me to nobody yet" gap M5
  §12 already named for per-event verdicts, now also true for population
  findings, and arguably worse: there isn't even a severity/escalation
  concept for population findings at all this milestone (§13.10). Named
  explicitly as a real gap `PopulationFinding` inherits from day one, not
  a regression.
- **The batch runner's own operational story is unaddressed** — who/what
  actually invokes `run_policies` on a schedule in a real deployment (cron,
  k8s CronJob, a human) is explicitly out of this milestone's scope (§13.4)
  but is a real gap between "the mechanism exists" and "population policies
  actually run in production."
- **No authentication on two more admin endpoints** — restates the
  standing M5+/M13 gap (§13.14), not a new one, but the pile keeps growing.

## 13. Architectural ambiguities, with my recommendation for each

### 13.1 — What does "async ingestion plane" mean: redesigning the two existing synchronous routes, or building the async plane population policies specifically need? **(the highest-stakes call in this document)**

Options: **(a)** Redesign ingestion itself: the existing routes enqueue a
raw payload to a broker/queue and return `202 Accepted` immediately; a
worker processes translate → normalize → govern → evidence-append out of
band; callers who need the verdict poll a new endpoint or receive a
webhook. **(b)** (recommended) Leave both existing routes exactly as they
are — synchronous, in-request, real verdict in the response — and build
"the async plane" as the separately-scheduled pipeline that evaluates
population-level policies against already-ingested data, per §4.1.

**Recommendation: (b).** Option (a) is a real, breaking contract change to
two routes nothing in this milestone's own citations, nor any prior
milestone's design record, has ever asked to change — `IngestionResponse`
returning a synchronous `VerdictStatus` is exactly the behavior M0 built and
every milestone since has preserved and extended (M2's "byte-for-byte
unchanged" for the prior route at every new-route addition; M5's explicit
`IngestionResponse`-unchanged decision at §13.14). Adopting (a) would also
need to answer a real product question this review has no basis to answer
unilaterally — does any real caller actually need a synchronous ALLOW/HOLD
gate on individual decisions (a plausible "yes" for a live credit
decision) — which is exactly the kind of judgment call this review's own
prior instances (M5 §13.11) have flagged rather than decided alone. Option
(b) delivers the literal, load-bearing part of "async ingestion" that
population-level policies actually require (they cannot run synchronously,
full stop — see §2) without inventing a queue/broker and a breaking API
change nothing has requested. **If this reading is wrong against the real
architecture document** — if "async ingestion plane" is meant literally, as
a redesign of how individual decisions get ingested — that is the one
finding in this review most likely to require a materially different
design, not a parameter tweak, exactly the caveat M5 §13.1 attached to its
own highest-stakes call.

### 13.2 — Is the "Event Lake" new storage, or a new read pattern over storage that already exists? **(second-highest-stakes call)**

Options: **(a)** A new, dedicated store — a separate database, an
object-storage-backed append log, or a message-log technology (Kafka-
adjacent) — decoupled from the OLTP-shaped `decision_events` table, sized
and indexed for analytical/batch scans. **(b)** (recommended) No new
storage: `decision_events` + `protected_attribute_resolutions` (+
`verdicts` for outcome, already available via `decision_output`) already
hold, normalized, everything a population read needs — see
`infra/migrations/0003_create_decision_events.sql`'s actual columns. "Event
Lake" is satisfied by a new *query pattern* (`population_engine/window.py`,
§4.2) over existing tables, not a new physical store.

**Recommendation: (b).** This platform has exactly one deployment
environment and no real production query volume to design a genuinely
separate analytical store against — introducing one now would be the same
"no second case yet" mistake this project has declined at every prior
milestone (M2 declining multi-domain generalization with one domain; M5
declining a rule engine with one aggregation rule), applied to
infrastructure instead of code. Duplicating `decision_events` into a
second store would also create exactly the kind of two-sources-of-truth
problem this codebase has consistently avoided (`shadow_findings` stays
structurally separate from `findings` *because* it's genuinely different
data, not a copy of the same data). The real cost of (b), named honestly:
`decision_events` has no index shaped for "scan this system's events over
this window" today — now a required migration item, not a punt (see §6).

**Revised, hostile-review pass:** the first draft of this section
understated what the read actually needs — see §4.2's correction.
`protected_attribute_resolutions` supplies classification, not value;
the population read needs `decision_events.protected_attribute_refs`
directly, plus a decision (made here, not left open) on which ruleset
resolves DIRECT-ness: the DB-backed `protected_attribute_rules`, not the
static `classification.py`. See §13.15 for the full reasoning and §13.16
for the reproducibility consequence that decision creates.

### 13.3 — Population-level policies: a new `PopulationPolicy` port, or force-fit into the existing `Policy`/`Finding`/`Verdict` shapes? **(third-highest-stakes call)**

Already argued in full in §2/§9. Options: **(a)** (recommended) A new
`PopulationPolicy` port, `PopulationWindow`, and `PopulationFinding` —
structurally parallel to, but never touching, `Policy`/`DecisionEvent`/
`Finding`. **(b)** Reuse `Policy.evaluate(event) -> Finding` by picking one
"representative" `decision_event_id` to attach an aggregate result to (e.g.
the most recent event in the window) — a real option in the sense that it
needs no new port, but a semantic lie: the finding doesn't actually belong
to that event, and any future consumer (a compliance dashboard, M10;
signature verification, M5's existing pattern) that assumes
`decision_event_id` on a `Finding` means "this event caused this finding"
would be silently wrong. **(c)** Widen `Finding.decision_event_id` to
`decision_event_ids: list[str]` — spreads the population concept into the
per-event type everywhere it's used (the hash chain payload, `Verdict`,
every existing repository), for a capability only one new policy type
needs.

**Recommendation: (a).** (b) corrupts the meaning of an existing,
already-relied-upon field; (c) is a real port change to the *existing*,
busiest type in the codebase, imposed on every future per-event `Finding`
forever, to serve a need that's actually orthogonal. A new, small,
narrowly-scoped port that never has to touch `evidence_chain`'s hash-chain
invariants at all is the more consistent architecture — the same reasoning
that kept `shadow_findings` a separate table rather than a new
`Finding.is_shadow` flag (M3 §13.3).

**Revised, hostile-review pass:** the port decision (a) stands unchanged,
but the first draft's `PopulationWindow` shape did not — it materialized
every raw `DecisionEvent` in the window into Python before computing a
ratio that only ever needed a `GROUP BY` count. For the one policy this
milestone ships, that's a correctness-irrelevant but real scalability
mistake: it forces the entire window into process memory for a computation
Postgres can do in one aggregate query. §4.3 now has `PopulationWindow`
carrying pre-aggregated `PopulationGroupCount` rows instead of raw events —
cheap to fix now, before `PopulationPolicy.evaluate`'s signature is
load-bearing across tests.

### 13.4 — What triggers a population-policy run: an in-process scheduler/daemon, or an explicitly-invoked CLI?

**Recommendation: CLI**, mirroring `plugins/seed_registry.py`'s and
`audit/verify_chain.py`'s existing shape exactly
(`python -m gov_platform.population.run_policies`). This platform has zero
always-running background processes anywhere today — `create_app()`'s own
design invariant (`api/app.py`'s docstring) is explicitly that construction
needs no live database and does no background work; introducing the first
daemon/scheduler thread in this milestone would be a meaningfully different
operational model than every module built so far. Real scheduling (cron, a
Kubernetes `CronJob`) is deployment topology — the same class of concern
`docs/architecture-mapping.md` §17 already assigns to M13, not this
milestone.

### 13.5 — Are population findings chained into `evidence_chain`, or a new, parallel, non-chained table?

**Recommendation: new, parallel table (`population_findings`), not
chained**, mirroring `shadow_findings`' existing precedent. The hash chain
computes `record_hash` over a payload containing exactly one
`decision_event`/`verdict` pair, and its append-only, `pg_advisory_xact_lock`
-protected write path is designed around one write per governed decision.
A population finding governs *no single decision* — chaining it would
require either inventing a payload shape the existing verifier
(`audit/verify_chain.py`) doesn't understand, or writing a fake/placeholder
`decision_event_id`, which is exactly option (b)'s semantic problem from
§13.3 recurring one layer down.

### 13.6 — Are population findings cryptographically signed, reusing `audit/signing.py`?

**Recommendation: yes.** `EvidenceSigner.sign(record_hash: str) -> str` is
already a pure function with no dependency on `evidence_chain`'s specific
schema — nothing about it is evidence-chain-specific beyond where it's
currently called from. Signing `population_findings` rows the same way
extends the same authenticity guarantee (§4.3's `M5.md`: "a third party
with the public key can verify a record was produced by this specific
deployment") to a second kind of governance output, for negligible added
code. Flagged as a real, separate decision (not bundled silently into
§13.5) because M5's own design record scoped signing narrowly to
`evidence_chain` specifically — extending it here is this review's
proposal, not an automatic consequence of that prior decision.

**Revised, hostile-review pass — what gets signed, not just whether:** the
payload hashed and signed must include `classification_snapshot` (§4.3),
not just `metric_values`/`outcome`. Without it, "verify this signature"
only answers "have these bytes been tampered with," not "was this computed
from a well-defined, checkable basis" — see §13.16. Also worth stating
plainly: signing without any verifier is exactly the "infrastructure with
zero callers" pattern this review's own §13.12 argued against for the read
API. A minimal `verify_population_findings` path (even just extending
`audit/verify_chain.py`'s CLI shape to a second table) should ship
alongside signing, not be deferred as a follow-up with no committed owner.

### 13.7 — Do population policies get their own plugin-registry lifecycle, or does M6 invent a separate mechanism?

**Recommendation: extend the existing mechanism** — `PluginType` gains
`POPULATION_POLICY`; a `PopulationPolicy` registers, promotes
(`DRAFT`→`SHADOW`→`PRODUCTION`), and is looked up through the exact same
`plugin_registrations` table, `PluginRegistrationRepository`, and
`api/admin/plugins.py` endpoints every `Adapter`/`Policy` already uses. No
second lifecycle mechanism, no new Admin surface for lifecycle
specifically — the same "no second case yet" discipline argues against
inventing a parallel promotion concept for a third plugin kind when the
existing one generalizes for free.

### 13.8 — Population-policy binding: `adapter_id`-keyed like `policy_bindings`, or something else?

This resurfaces M5 §13.1's explicitly-deferred domain/jurisdiction-keyed
question, in a new form. Options: **(a)** Reuse `policy_bindings`, keyed
by `adapter_id` — but a population analysis is naturally about a
*System's* aggregate decisions across however many adapter versions have
produced them over time (a scorecard's `0.1.0`→`0.2.0` retrofit, per M4,
shouldn't reset what "this system's population" means), making
`adapter_id` the wrong grain. **(b)** (recommended) A new,
`system_id`-keyed `population_policy_bindings` table, structurally separate
from `policy_bindings` (different key, different shape, different
question — same reasoning M5 §13.4 already applied to keep
`policy_bindings`/`protected_attribute_rules` apart). **(c)** Finally build
the richer, domain/jurisdiction-keyed binding M5 explicitly declined — but
this platform still has exactly one real domain (`FINANCE`) and zero real
jurisdictions, the identical "no second case" gap M5 cited, so nothing about
M6 actually resolves that gap; reaching for it here would just relocate
M5's declined generalization into a new table instead of building it
honestly when a second domain exists.

**Recommendation: (b).** `System.id` is the correct aggregation grain for
"this system's population of decisions" regardless of which adapter version
translated each one — a `System`-keyed binding is not a re-litigation of
M5's `adapter_id`-vs-`domain` question (that was about which *policies*
govern which *adapter's events*; this is "which system does this
*aggregate* concern"), but it is a new, similar-shaped key decision worth
your explicit attention rather than silent copy-paste from `policy_bindings`.

### 13.9 — Adverse impact ratio: one hardcoded metric/threshold, or a general population-metrics framework?

**Recommendation: one concrete metric** (§4.4), for `FINANCE` only,
threshold `0.8` cited to its real regulatory source (EEOC 4/5ths
guidance) — no configurable-metric DSL, no pluggable statistical-test
framework. Identical reasoning to M4 §13.6's rejection of a configurable
escalation-rule engine with only one aggregation rule to justify one: a
general population-metrics framework is real, and is architecture §10's
Evaluation Framework (M8) — building it a milestone early, disguised as
"just configuring this one metric a bit more," would be reaching for M8's
job.

### 13.10 — Do population findings carry severity/escalation like per-event Verdicts, or stay purely informational this milestone?

**Recommendation: purely informational — `PopulationFindingOutcome` stays
binary `CLEAR`/`FLAGGED`, no severity, no `VerdictStatus`-style escalation
state.** Directly mirrors M5 §13.7's own precedent ("M5 stops at
computing/persisting the four-state status; it builds no review queue or
notification — that's M9"), applied one milestone later to a second kind
of output with the identical problem: there is still no Human Review
Workflow (M9) for *any* escalated output, per-event or population-level, so
building an escalation *mechanism* for population findings now would be
machinery with nothing at the other end, the same anti-pattern named at
every mention of the M5/M9 boundary.

### 13.11 — Does the Event Lake / population read pattern finally trigger the M0/M2-deferred raw-vs-normalized `DecisionEvent` pipeline-stage type question?

**Recommendation: no — still declined, and named explicitly rather than
silently dropped a second time.** `docs/milestones/M0.md`'s original
deferral was conditioned on "a second entry point" existing to inform the
right fix; M2 shipped one and explicitly declined to resolve it anyway
(§11.4: normalized `DecisionEvent` remains the one canonical shape
everything downstream sees). §4.2's proposed `PopulationWindow` reads the
same already-normalized `DecisionEvent` rows `decision_events` already
stores — it introduces no new pipeline stage, no "raw" representation
anywhere near it. The trigger condition this row names still isn't met by
this design. If a future milestone's real raw-payload-auditing need
(distinct from anything M6 does) eventually forces this question, that
milestone should re-open it explicitly — M6 should not be read as having
quietly resolved it just because this document didn't raise it as a
blocker.

### 13.12 — Does M6 add a read endpoint for population findings, or is direct DB access sufficient (the standing precedent for every other Finding/Verdict table)?

M5 §13.7 already accepted that no query-by-status endpoint exists for
per-event Verdicts either ("a query API doesn't exist yet for *any*
status... so this isn't a new gap M5 introduces"). Options: **(a)** Add
nothing — consistent with that precedent, population findings are
queryable only via direct DB access until a real Reporting milestone (M12)
or Compliance Dashboard (M10) needs them. **(b)** (recommended) Add a
minimal, read-only `GET /v1/admin/population-findings[/{id}]`.

**Recommendation: (b), diverging from the pure-precedent answer, for a
reason specific to this milestone.** M2 §2 named the exact failure mode
this review wants to avoid repeating: shipping "infrastructure with zero
callers." Protected Attribute Resolution avoided that fate only because M2
deliberately paired it with a policy that consumes it. Population-level
policies have no analogous in-process consumer — nothing in this codebase
ever reads a `PopulationFinding` except a human deciding whether to act on
one, so *some* retrieval path is the entire point of building this
milestone at all, not an optional nicety layered on top. A minimal
list/get, mirroring every other read-only Admin listing already in this
codebase, is the smallest addition that avoids that failure mode.

### 13.13 — Does the batch runner's read pattern need its own locking against concurrent ingestion writes, and does the run itself need idempotency guarantees? **(reversed from the first draft)**

**The first draft's "no new locking needed" was wrong**, on both the read
side and the write side, and left window semantics entirely unspecified —
found during the hostile-review pass, not a refinement of an already-sound
answer.

**Read side.** `window.py` issues more than one query against tables that
can change between them (`decision_events`, plus whatever
`protected_attribute_rules` lookup §4.2/§13.15 requires). Under plain
read-committed, nothing guarantees those queries see the same snapshot — an
event or rule committed between them can appear in one read and not the
other, silently corrupting a count. This is not the same situation as an
ordinary Admin-API `GET`, which reads one row under one statement; this
reads a *consistent set* across statements. **Recommendation:** wrap
`window.py`'s reads in a single `REPEATABLE READ` transaction.

**Write side and window semantics.** The first draft never specified how
`window_start`/`window_end` are chosen. If the runner computes "the last
30 days from `now()`" on every invocation, windows never align between
runs — there is no stable key two runs of "the same" window could ever
agree on, idempotency is structurally impossible, and a daily cron
produces ~30x redundant, overlapping findings. Worse, nothing then stops
two overlapping invocations (a stuck cron plus a manual re-run — the exact
class of race M3's own review already named for a different mechanism)
from computing and inserting two disagreeing findings for what a human
would call "the same" window. **Recommendation:**

- **Fixed, calendar-aligned, closed-in-the-past windows** — e.g. always
  "yesterday's full UTC day," never a window ending at `now()`. This also
  removes the read-skew risk of a window boundary racing live ingestion.
- **`UNIQUE (population_policy_id, system_id, window_start, window_end)`**
  on `population_findings` (§6) — a duplicate run becomes a clean,
  detectable no-op, not a race that silently produces two answers for one
  window.

This changes §6's schema, not just an implementation detail — see the
updated migration above.

### 13.14 — Does M6 add authentication to its two new admin surfaces?

**Recommendation: no**, restating M5 §13.11's identical reasoning:
consistent with every existing admin endpoint (still none authenticated),
adding it to only the two newest would be inconsistent scoping, not a real
security improvement. Named again, though, because the honest trend across
M5 and M6 is that this gap keeps getting wider (two more admin write/read
surfaces) while staying named `M5+/M13` — worth your explicit attention
that this is now the third consecutive milestone widening a gap this
review keeps flagging rather than solving.

### 13.15 — Which ruleset resolves DIRECT-ness for a population read: the static `classification.py`, or the DB-backed `protected_attribute_rules`? **(found during the hostile-review pass, not in the original draft)**

Options: **(a)** The static, code-defined `classification.py` —
`DirectAttributeInInputsPolicy`'s own ruleset. Deploy-pinned, immutable,
trivially reproducible, but a population job with full DB access reading a
frozen, code-defined copy while `EvidenceStore` reads the live, DB-backed
one (M5's own `protected_attribute_rules`) means the platform now has
*three* places that can disagree about whether an attribute is protected,
not two. **(b)** (recommended) The DB-backed `protected_attribute_rules` —
the same table `EvidenceStore`'s resolution path already consults. No
architectural reason exists to force the population job onto the static
copy; the constraint that forced `DirectAttributeInInputsPolicy` there
(`Policy`'s zero-argument construction, M5 §13.9) simply doesn't apply to
a batch job that already holds a live `Engine`.

**Recommendation: (b).** Consistent with the same table already being the
admin-facing, current source of truth for "what counts as protected" —
using the static copy here would mean an admin adding a new proxy
attribute via the M5 Admin API (the exact scenario that table was built
for) has no effect on population-level analysis at all, silently. The real
cost of (b) is not a flaw in the choice itself but a consequence of what
"DB-backed and mutable" means for a *historical* computation — addressed
in full in §13.16, which this decision directly creates the need for.

### 13.16 — Does rerunning a historical population window reproduce the original result, or recompute using whatever rules are in effect today? **(found during the hostile-review pass — the highest-stakes correction in this document)**

§13.15's decision means a population finding's correctness now depends on
a live, admin-mutable table with no versioning or point-in-time history —
unlike `population_policy_version`, which already pins the policy's *code*
identity per finding, nothing pins the *ruleset* a finding was computed
against. Options: **(a)** Rules-as-of-run-time — always resolve against
whatever `protected_attribute_rules` says right now. Simplest, but a
"historical" finding is a live view wearing a timestamp: re-running last
March's window today can produce a different ratio than what was
originally reported, with nothing in the record distinguishing "the
underlying decisions actually changed" from "an admin edited the ruleset
in the meantime." **(b)** (recommended) Rules-as-of-window-close — a
finding is computed once, and it **embeds** the exact
`(attribute_name -> classification)` pairs used
(`PopulationFinding.classification_snapshot`, §4.3), rather than pointing
at a table that can keep changing underneath it.

**Recommendation: (b).** This mirrors a pattern already load-bearing
elsewhere in this codebase: `evidence_chain.payload` embeds the full
`decision_event`/`verdict`, not just their IDs, specifically so a
historical record's meaning never depends on some other, mutable table
still agreeing with it later. `population_findings` is the first M6 table
to read admin-mutable data the evidence chain never had to (the static
`classification.py` `DirectAttributeInInputsPolicy` uses was deploy-pinned
precisely to avoid this problem) — §13.15's decision makes this the first
real instance of the issue, not a hypothetical.

Concrete implications, since this is a real trade-off, not a free
improvement:

- **Auditability.** A finding is self-contained — interpretable without
  trusting that `protected_attribute_rules` still says today what it said
  when the finding was computed.
- **Evidence signing (§13.6).** The signed payload must include
  `classification_snapshot`. Without it, a valid signature only proves the
  bytes weren't altered, not that "verify this finding" is even a
  well-defined question — two different rulesets could otherwise produce
  identically-shaped, identically-signed-looking records for different
  reasons.
- **Regulatory defensibility.** This is the sharpest consequence. "We
  reported X in March; asked to reproduce it today, our own tool now says
  Y" is a materially worse position under scrutiny than "we cannot
  instantly recompute this" — it makes the platform's own audit trail
  self-contradicting. Point-in-time pinning means the platform can always
  reproduce exactly what it originally reported.
- **A genuine "what-if, recompute under today's rules" capability** is a
  legitimate, different feature (plausibly M8/M10 territory) — explicitly
  **not** built by M6, and not to be conflated with the default,
  point-in-time-pinned record. If ever built, it must produce a new,
  clearly-labeled finding, never overwrite or reinterpret the original —
  a natural consequence of the `UNIQUE` constraint and privilege lockdown
  §13.13/§6 already establish.

This decision does **not** reopen or modify `protected_attribute_rules`
itself (that table is M5-frozen) — the fix lives entirely on the M6 side,
as a defensive snapshot of whatever M6 happened to read, regardless of
whether the upstream table itself ever grows real versioning.

## 14. What M6 owns

1. **A `PopulationPolicy` port** — a new, third plugin surface alongside
   `Adapter`/`Policy`, evaluating a `PopulationWindow` (many decisions for
   one system over one time range) into one `PopulationFinding`.
2. **One concrete population policy** — adverse impact ratio for
   `FINANCE`, the architecture's own named example.
3. **The "Event Lake" read pattern** — a windowed query over the existing
   `decision_events`/`protected_attribute_resolutions` tables; no new
   storage.
4. **The async evaluation plane** — a CLI-invoked batch runner, decoupled
   entirely from, and with zero effect on, the two existing synchronous
   ingestion routes.
5. **`population_policy_bindings`** — `system_id`-keyed, `ACTIVE`/
   `INACTIVE`, admin-managed, structurally separate from `policy_bindings`.
6. **A minimal, read-only Admin API surface** for population findings and
   bindings.
7. **Point-in-time-reproducible findings** — every `population_finding`
   embeds the exact protected-attribute classification basis it was
   computed against (`classification_snapshot`), independent of later
   changes to `protected_attribute_rules`; `population_findings` is
   append-only at the database-privilege level, the same guarantee
   `evidence_chain` has.

## 15. What remains deferred past M6

- **A general Evaluation Framework** (architecture §10, multiple
  statistical tests, pluggable metrics) — M8; M6 ships one concrete metric,
  not the framework.
- **Real scheduling** of the batch runner (cron, `CronJob`, any
  always-running process) — deployment/M13-adjacent, not built.
- **A dedicated analytical store for the Event Lake** — the existing
  operational tables are reused, unindexed for batch scans beyond whatever
  index this milestone adds; a real separate analytical-warehouse split
  remains unscheduled (`architecture-mapping.md` §16).
- **Severity/escalation for population findings** — stay purely
  informational; no `VerdictStatus`-equivalent state (§13.10).
- **Redesigning per-event ingestion into a truly asynchronous, queued
  contract** — explicitly declined this milestone (§13.1); the two
  existing routes are unchanged.
- **Human Review Workflow** consuming either per-event `ESCALATE_FOR_REVIEW`
  or a `FLAGGED` `PopulationFinding` — M9.
- **Compliance Dashboard**, **Monitoring/metrics dashboards** — M10, M7.
- **Encryption at rest and retention** for the two new tables — M11, same
  as every existing table.
- **Authentication** on any endpoint, including M6's two new surfaces —
  still named `M5+/M13`, not claimed here (§13.14).
- **The raw-vs-normalized `DecisionEvent` pipeline-stage type question** —
  re-declined, explicitly, not silently dropped (§13.11).
- **Recomputing a historical window under today's (changed) rules** — a
  legitimate, different "what-if" capability, explicitly not built by M6;
  the default, point-in-time-pinned record is the only thing this
  milestone produces (§13.16).
- **Versioning/point-in-time history for `protected_attribute_rules`
  itself** — that table stays exactly as M5 shipped it; M6 defends against
  its mutability by snapshotting what it read, not by reopening M5's
  frozen schema.

## 16. Decisions requiring your approval before implementation

A plain checklist, each referencing the fuller reasoning above:

1. **[§13.1]** "Async ingestion plane" is read as the async plane
   population-level policies need — the two existing synchronous ingestion
   routes are **unchanged** (recommended), not redesigned into a
   queue/poll contract. The single highest-stakes call in this document.
2. **[§13.2]** The "Event Lake" is a new **read pattern** over the existing
   `decision_events` table (recommended) — corrected from the first draft:
   attribute *values* come from `decision_events.protected_attribute_refs`
   directly, not from `protected_attribute_resolutions` (which only holds
   classification, per §13.15) — not a new physical store.
3. **[§13.3]** Population-level policies get a **new `PopulationPolicy`
   port**, `PopulationWindow`, and `PopulationFinding` (recommended), never
   touching `Policy`/`Finding`/`Verdict`.
4. **[§13.4]** Population-policy evaluation is triggered by an
   **explicitly-invoked CLI** (recommended), not an in-process
   scheduler/daemon.
5. **[§13.5]** `population_findings` is a **new, parallel table**, not
   chained into `evidence_chain` (recommended).
6. **[§13.6]** Population findings **are signed** with the existing
   `audit/signing.py` machinery (recommended), **and the signed payload
   includes `classification_snapshot`**, with a minimal verifier shipped
   alongside — amended from the first draft, which signed only
   `metric_values`/`outcome` and named no verifier.
7. **[§13.7]** Population policies use the **existing plugin-registry
   lifecycle** (`PluginType.POPULATION_POLICY`), not a new mechanism
   (recommended).
8. **[§13.8]** Population-policy bindings are a **new, `system_id`-keyed
   table** (recommended), separate from `policy_bindings`.
9. **[§13.9]** Adverse impact ratio ships as **one hardcoded metric/
   threshold** for `FINANCE` (recommended), not a configurable framework.
10. **[§13.10]** Population findings stay **purely informational** — no
    severity, no escalation state (recommended).
11. **[§13.11]** The raw-vs-normalized `DecisionEvent` pipeline-stage

12. **[§13.12]** M6 **adds a minimal, read-only Admin API** for population

    **fixed, calendar-aligned, and closed in the past**; window-building

    `population_findings` gets a **`UNIQUE (population_policy_id,

    reads resolve DIRECT-ness against the **DB-backed
