## Update: verified end to end against real Postgres (2026-07-26)

Docker Desktop and WSL are now installed. Everything this milestone
originally deferred to "the first CI run" (see the superseded constraint
section below, kept for the historical record) has now actually been run
locally against a real Postgres 16 container, exactly mirroring
`.github/workflows/ci.yml`'s `lint-type-test` and `docker-smoke` jobs:
`ruff`, `mypy --strict`, all 8 migrations, the CI-only role-privilege setup
script, the full pytest suite (including the 22 tests that had only ever
been skip-if-absent), and a full container build + `/healthz` +
end-to-end ingestion smoke test. As predicted, this first real execution
surfaced issues hand-review alone couldn't catch. All were root-caused and
fixed, not worked around:

1. **`db/migrate.py` couldn't connect to Postgres at all.** `create_engine()`
   on a bare `postgresql://` URL makes SQLAlchemy default to the
   `psycopg2` driver — but this project depends on `psycopg` (v3) only;
   `psycopg2` was never installed. Fixed by normalizing bare
   `postgresql://`/`postgres://` URLs to `postgresql+psycopg://` inside
   `migrate.py` itself (`_with_psycopg_driver`), leaving `ADMIN_DATABASE_URL`
   as plain `postgresql://` in CI — required, since `infra/ci/setup_test_role.py`
   hands that same env var straight to `psycopg.connect()`, which needs the
   plain scheme, not a SQLAlchemy dialect suffix.
2. **`infra/ci/setup_test_role.py` couldn't run `ALTER ROLE ... PASSWORD`.**
   Postgres's DDL grammar for that clause requires a string literal, not a
   bind parameter — the parameterized `%s` placeholder was a syntax error.
   Fixed with `psycopg.sql.SQL(...).format(psycopg.sql.Literal(...))`,
   which still escapes the value safely but composes it into the statement
   text client-side instead of sending it as a query parameter.
3. **A flaky test**: `test_body_within_limit_is_not_rejected_by_the_middleware`
   posted the `synthetic_payload_json` fixture unmodified, with its
   hardcoded `source_event_id`. Every other M1 test file already works
   around `decision_events.id` being a permanent, never-truncated primary
   key by generating a unique id per call — this one test hadn't been
   updated to match, so it could only ever pass once per database lifetime
   (it passed on the very first run against a fresh container, then failed
   on every rerun). Fixed to generate a unique id the same way.
4. **Coverage floor (98%) failed on first real run: 92%, not the 98%
   estimated without ever measuring it against live Postgres.** The gap was
   real, not a fluke of measurement: `DecisionEventRepository.get`,
   `FindingRepository.list_by_decision_event`, `ModelVersionRepository.get`/
   `list_by_system`, `VerdictRepository.get`, `verify_chain_from_database`,
   the CLI `main()` wrappers in `verify_chain.py`/`migrate.py`, and
   `migrate.py`'s new `_with_psycopg_driver` helper were all real,
   reachable, previously-untested code paths — added integration tests
   (`tests/integration/test_repositories_postgres.py`,
   `tests/integration/test_verify_chain_postgres.py`) and unit tests
   (`tests/unit/db/test_migrate.py`) exercising all of them. Coverage is
   now 100% except two `abc.abstractmethod` bodies and two `if __name__ ==
   "__main__":` guards, which are unreachable by construction — those are
   now excluded via a `[tool.coverage.report]` `exclude_lines` config
   (standard practice; previously absent from this project).

Test suite is now 105 passed, 0 skipped, 0 failed, 100% coverage, run three
times in a row against the same persistent container with no flakiness.
Migrations are idempotent (`No pending migrations.` on rerun). The
container builds, serves `/healthz`, and completes a real ingestion
end-to-end against Postgres.

## Environmental Constraint (superseded — kept for historical record)

This sandbox originally had no Postgres, no Docker, and no WSL — only
`winget`, which would mean a system-level install on the user's machine not
performed without being asked. Per an explicit choice made before
implementation began, M1 was built as **"CI-verified, locally
skip-if-absent"**: the real Postgres schema, migrations, and repositories
were written to production standard, but anything requiring a live database
connected via a `POSTGRES_URL` environment variable that was unset in that
environment and set for real in CI (a genuine Postgres 16 service container
— see `.github/workflows/ci.yml`). Locally, those tests skipped with an
explicit reason rather than failing or being silently omitted. This
constraint no longer applies — see the verification update above.

**What that meant concretely, at the time:** everything DB-agnostic (the
hash-chain algorithm, `verify_chain`'s core logic, the migration runner's
mechanism, schema validation) had been executed and verified in that
session. Anything requiring a real Postgres connection (the repository
layer's actual SQL, the 8 migration files' real syntax, DB-privilege
enforcement) had been written carefully and reviewed by hand multiple
times, but had **not** been executed against a real Postgres by that
session — see the verification update above for what that first real
execution actually found.

## A Design Issue Caught and Corrected Mid-Implementation

While building `EvidenceStore`'s Postgres internals, `SELECT ... FOR UPDATE`
(the originally planned replacement for M0's in-process lock) was found to
require UPDATE privilege in Postgres — which would have directly conflicted
with `REVOKE UPDATE` on `evidence_chain`, the exact restriction the M1
acceptance criterion requires. This was caught by reasoning through Postgres's
documented privilege model before writing the code, not by running it. Fixed
by using `pg_advisory_xact_lock` instead — a locking mechanism that needs no
table privileges at all. See `evidence_store.py`'s module docstring for the
full explanation. Flagged to the user at the time, per instruction.

## What Was Built

- **System & ModelVersion**, formalized as real entities (`schemas/system.py`,
  `schemas/model_version.py`) with a repository each, replacing M0's bare
  `system_id` string.
- **8 Postgres migrations** (`infra/migrations/0001`–`0008`) establishing
  `systems`, `model_versions`, `decision_events`, `findings`, `verdicts`,
  `verdict_findings` (a join table, matching architecture's "verdict
  aggregates findings" data model even though exactly one finding exists per
  verdict until M4), `evidence_chain`, and the DB-privilege grants.
- **A minimal migration runner** (`db/migrate.py`) — numbered `.sql` files
  applied in order, tracked for idempotency. No Alembic: consistent with M0's
  tooling discipline.
- **A repository layer** (`db/repositories/`) — one class per entity, each
  method taking an externally-supplied `Session` so `EvidenceStore.append`
  can write across six tables in one atomic transaction.
- **`EvidenceStore` reimplemented on Postgres** — same public interface as
  M0 (`append`, `get`, `all`, `EvidenceRecord`), entirely different internals:
  normalized writes through five repositories, `pg_advisory_xact_lock` for
  cross-instance-correct concurrency (replacing M0's in-process-only lock),
  and database-privilege-enforced append-only (`REVOKE UPDATE, DELETE`) in
  place of M0's "no method exists for it" application-layer stopgap.
- **`audit/hash_chain.py`**, extracted from `evidence_store.py` per the
  frozen file list — pure, DB-agnostic, unchanged algorithm from M0.
- **`audit/verify_chain.py`** — the standalone hash-chain verification job,
  pure core logic (fully unit-tested locally, including deliberately
  corrupted-chain fixtures) plus a thin CLI wrapper.
- **Admin API** (`api/admin/systems.py`) — register/list/get a System.
  Explicit registration is stricter than ingestion's auto-provisioning (409
  on duplicate name vs. silent reuse) — different callers, different intent.
- **CI now runs a real Postgres 16 service container** — migrations applied,
  the restricted `gov_platform_app` role enabled via a CI-only script
  (`infra/ci/setup_test_role.py`, no credential ever committed), full test
  suite run with an enforced coverage floor that only lives in CI now (see
  below).

## Final Architecture (as built)

```
src/gov_platform/
  ...(M0 packages, unchanged)...
  audit/
    hash_chain.py       Pure hash-chain primitives (new, extracted)
    evidence_store.py   Reimplemented on Postgres
    verify_chain.py     Standalone verification job + CLI (new)
  db/                   New in M1
    session.py           Engine factory
    models.py             SQLAlchemy declarative models (query-only, never DDL)
    migrate.py             Migration runner + CLI
    repositories/           system, model_version, decision_event, finding, verdict
  api/
    admin/
      systems.py          POST/GET /v1/admin/systems (new)
infra/
  migrations/            8 numbered .sql files (new)
  ci/
    setup_test_role.py   CI-only role/password setup (new)
```

Data flow through `EvidenceStore.append` (unchanged call site in
`api/ingestion/routes.py`): resolve-or-create System → resolve-or-create
ModelVersion → write DecisionEvent, Finding(s), Verdict rows → acquire
advisory lock → compute and write the hash-chained evidence row — all in one
transaction.

## Design Decisions Differing From a Literal Reading of the Plan

Explained in full before implementation began; summarized here for the
record — none required reopening anything already approved:

1. Auto-provision System/ModelVersion during ingestion rather than requiring
   pre-registration — keeps M0's ingestion route completely unchanged.
2. `EvidenceStore`'s constructor takes an `Engine`, not a path — necessary
   for connection-pool sharing with the new Admin API.
3. Schema authority moved to migration files, not `Base.metadata.create_all()`
   — as planned, with the side benefit that `create_app()` no longer needs a
   live database just to construct (SQLAlchemy engines are lazy).
4. Repository methods take an externally-supplied `Session` — necessary for
   cross-table transactional atomicity once evidence spans six tables.
5. Migrations and repositories target Postgres only, no dual-dialect SQLite
   portability layer — matches exactly what was approved, avoids
   unrequested complexity.
6. The coverage floor moved from an always-enforced local gate to a CI-only
   one — a chunk of M1's code is legitimately Postgres-only and cannot
   execute here through no fault of the tests.
7. `pg_advisory_xact_lock` instead of `SELECT ... FOR UPDATE` — see the
   "design issue caught" section above.
