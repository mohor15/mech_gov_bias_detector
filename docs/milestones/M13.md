## Revision note (hostile-review pass)

This document was drafted, then re-read as though written by someone
else, assuming it wrong until proven otherwise — the identical discipline
M6–M12 were each built under. Five findings from that pass are folded in
below, in place, not as a separate errata section, matching the
convention M6/M8/M9/M11/M12 each established. A second, independent
hostile-review pass — a full outside review cross-checking every claim
in this document directly against the current codebase (migrations,
source files, `pyproject.toml`, `tests/conftest.py`,
`.github/workflows/ci.yml`), the identical discipline M11's own second
pass and M12's own second pass were each held to — later found ten
further issues: four of them (items 6–9 below) genuinely blocking (the
kind of "invisible until actually executed" defect M11's psycopg
regression and M12's own two SQL bugs already taught this project to
hunt for before freezing a design, found here before implementation
rather than after), the remaining six real but non-blocking corrections.
All fifteen are recorded in place below, in the order each was found,
matching M12's own precedent of folding a second pass's findings into an
already-corrected document rather than a separate errata section:

1. **Reversed — the auth-check dependency is not applied uniformly as one
   blanket-per-router rule.** The first draft assumed every Admin API
   router could take a single `dependencies=[Depends(require_role(...))]`
   argument at its `app.include_router(...)` call site in `api/app.py`,
   mirroring how centrally that composition root already wires everything
   else. Checked directly against each router's actual endpoint list:
   several mix genuinely different minimum-permission endpoints in one
   file — `api/admin/policy_bindings.py` has both read endpoints
   (`list`/`get`, safe for any authenticated caller) and mutating ones
   (`create`/`activate`/`deactivate`, requiring `ADMIN`); the identical
   mix exists in `population_policy_bindings.py`,
   `protected_attribute_rules.py`, `plugins.py`, `verdict_reviews.py`,
   and `population_finding_reviews.py`. A single router-level dependency
   cannot express this without either over-restricting the read endpoints
   or under-restricting the mutating ones. **Corrected (§5.4):**
   per-route dependencies for every router that mixes permission levels;
   a router-level blanket dependency only for the few routers where every
   endpoint genuinely shares one minimum role (`population_findings.py`,
   `metrics.py` — both entirely read-only; the ingestion router — entirely
   `INGESTION`-or-`ADMIN`).
2. **Reversed — FastAPI's `fastapi.security.OAuth2PasswordBearer` is not
   used, despite being the framework's own built-in convenience for
   exactly this shape of header.** Reconsidered: that helper's name and
   OpenAPI-schema output both imply RFC 6749 OAuth2 semantics (a token
   endpoint, scopes, a defined grant type) this design does not
   implement — using it would misrepresent what this platform actually
   does to any client generating an SDK from the OpenAPI schema, or any
   future engineer skimming the dependency's import line and assuming a
   real OAuth2 flow exists. **Corrected (§5.2):** a plain,
   hand-written `Authorization: Bearer <token>` header parser, named for
   what it actually is.
3. **Amended — token hashing uses stdlib `hashlib.sha256` +
   `hmac.compare_digest`, not `bcrypt`/`argon2`/`passlib`.** The first
   draft reached for a password-hashing library by reflex, the same
   reflex that produces a login form. Reconsidered against what is
   actually being hashed: a 256-bit, cryptographically-random token
   (`secrets.token_urlsafe(32)`, never a human-chosen password), which
   has no low-entropy brute-forceable structure for a slow, adaptive hash
   to defend against — the exact reasoning real API-key systems (GitHub
   personal access tokens, Stripe secret keys, AWS access keys) already
   use in practice. A fast, constant-time-compared SHA-256 digest is
   correct here, and adds no new dependency to a project whose own
   `cryptography` package (already present since M5) is more than this
   specific job needs. See §5.1/§9.
4. **Amended — no refresh-token/access-token pair.** The first draft,
   reaching for familiar OAuth2-adjacent shape again, proposed a
   short-lived access token plus a longer-lived refresh token. Reconsidered:
   this platform has no forcing case for short-lived-token rotation at its
   real, disclosed operating scale (a handful of admin/reviewer principals,
   `docs/milestones/M9.md`'s own review already describing the review
   queue's realistic user base) — the identical "no rotation" restraint
   M5 already applied to the signing key and M11 already applied to the
   encryption key, applied here to a third kind of secret for the
   identical reason: real rotation infrastructure with no concrete forcing
   case is exactly the premature generalization this project's standing
   discipline declines. **Corrected (§5.1/§11):** one long-lived,
   individually revocable opaque token per principal; rotation is
   "revoke and issue a new one," the same manual mechanism this platform
   already accepts for its other two secret types.
5. **Confirmed, not changed — `/healthz` and `/readyz` remain
   unauthenticated.** Checked directly, not assumed: both endpoints exist
   specifically for infrastructure (an orchestrator's liveness/readiness
   probe) that will never carry an `Authorization` header, and neither
   returns any governance-sensitive content — `/healthz` is a bare status
   string, unchanged since M0; `/readyz` (M7) is a boolean derived from a
   database ping. Requiring auth on either would break every existing
   deployment's health-check configuration for zero confidentiality
   benefit. See §5.4/§10.
6. **Blocking, amended — migration `0028`'s own SQL had no `GRANT`
   statement, contradicting its own prose two paragraphs later and
   breaking an unbroken convention.** Checked directly against every
   `CREATE TABLE` migration in this schema since `0009`
   (`protected_attribute_resolutions`, `plugin_registrations`,
   `policy_bindings`, `protected_attribute_rules`,
   `population_policy_bindings`, `population_findings`,
   `verdict_reviews`, `population_finding_reviews` — eight consecutive
   table-creating migrations, no exception): every one grants privileges
   to `gov_platform_app` **in the same file** that creates the table.
   Postgres roles have zero privileges on a new table until explicitly
   granted — there is no ambient default anywhere in this schema. The
   first draft's `0028` SQL (§6) created `principals` with no `GRANT` at
   all, directly contradicting that same section's own prose ("ordinary
   `GRANT SELECT, INSERT, UPDATE, DELETE` privileges") and §5.1/§8's own
   claim that `auth/create_principal.py` needs only the ordinary
   application connection: as originally drafted, the very first
   invocation of that CLI against a freshly-migrated database would fail
   with `permission denied for table principals`. **Corrected (§6):** the
   `GRANT` statement is now part of `0028`'s own SQL, matching the
   unbroken convention exactly.
7. **Blocking, amended — the recommended `AUTH_ENABLED=True` default
   (§13.1) would break this repository's own existing CI on the very
   next run, unaddressed anywhere in the first draft.** Checked directly
   against `.github/workflows/ci.yml`'s `docker-smoke` job: it posts to
   `/v1/ingestion/events/synthetic` with a bare, unauthenticated `curl`,
   asserting `"status":"ALLOW"` in the response, with no step anywhere in
   that job provisioning a principal or attaching a credential. Under
   this document's own recommended default, that exact, currently-passing
   CI step starts receiving `401` the moment this milestone's code is
   deployed — a concrete, checkable regression, not a hypothetical one,
   of exactly the kind M11's own psycopg/migration CI failures already
   taught this project to hunt for before freezing a design.
   **Corrected (§8):** updating `.github/workflows/ci.yml`'s
   `docker-smoke` job to provision a bootstrap `INGESTION` principal and
   attach its token to the ingestion `curl` call is now an explicit,
   in-scope M13 deliverable (§1), not an implicit assumption left to an
   implementer.
8. **Blocking, amended — every existing Postgres-gated test (roughly 640,
   per M12's own Test Statistics) would break under the recommended
   default, with no fixture strategy proposed to prevent it.** Checked
   directly against `tests/conftest.py`: the `test_settings` fixture
   constructs `Settings(DATABASE_URL=POSTGRES_URL or _PLACEHOLDER_DATABASE_URL)`

   `ClaimVerdictReviewRequest`/`ResolveVerdictReviewRequest` declare
   `reviewer: str = Field(..., min_length=1)` as a **required** field on

   in this codebase for a route's request schema to vary by a `Settings`

   422 (not a silent override) if a client-supplied value is present and

## TL;DR

M13 closes the single most repeatedly-named gap in this project's entire
record: every one of the eleven design documents from M2 through M12 has
pointed at "no authentication anywhere" and deferred it, most describing
it as the standing production-readiness finding most likely to matter in
a real deployment. This document's own critical finding (§4.2) is that
"M13," as actually used across those eleven documents, is not one
cohesive deliverable — it is three unrelated concerns (caller
authentication/authorization; deployment-topology hardening — mTLS,
multi-tenancy, multi-plane; and operational scheduling infrastructure for
this platform's three batch CLIs) that only share a number because each
milestone individually ran out of scope to solve whatever cross-cutting
issue it hit and reached for the same unclaimed bucket. **This document
scopes M13 to exactly one of the three: authentication and
authorization** — identifying who is calling this platform's API, and
gating what they may do — the same "smallest architecture that solves
the milestone" discipline every prior milestone has held itself to, and
explicitly re-defers the other two (§4.2, §12.2) rather than silently
inheriting them.

The proposed mechanism is the smallest one that actually closes the gap,
built from parts this platform already has: **opaque, cryptographically-
random bearer tokens, issued by a new CLI (mirroring
`plugins/seed_registry.py`'s and `human_review/backfill_reviews.py`'s own
shape), hashed at rest in one new table, and checked by a new FastAPI
dependency applied at the existing composition root.** No OAuth2 server,
no JWT library, no external identity provider, no session-store
technology, no new dependency of any kind — not even a reuse of the
`cryptography` package M5 already added: the stdlib `secrets`/`hashlib`/
`hmac` modules alone are sufficient (corrected by this document's own
second hostile-review pass, Revision note item 13 — the first draft
overstated what this design leans on), the identical "no infrastructure
without a concrete forcing case" restraint M5 applied to signing-key
custody, M7 to metrics, and M11 to encryption, applied here to a third
and structurally similar problem (a per-principal secret,
operator-provisioned, no rotation, no external key-management service).

**Four callers currently reach this platform, and each needs this design
to answer a genuinely different question, argued in full in §4.1:**
the two ingestion routes (currently fully anonymous — must now present an
`INGESTION`-scoped credential, a real, disclosed break from eleven
consecutive milestones' "ingestion is byte-for-byte unchanged" streak);
the eighteen Admin API endpoints across nine routers (most need `ADMIN`;
a handful are safely read-only for any authenticated principal; three —
`claim`/`release`/`resolve` on both Human Review Workflow routers — need
a `REVIEWER`-or-`ADMIN` role, and are the direct fix for the exact gap
`docs/milestones/M9.md` named as this platform's single sharpest
authentication risk: *"an unauthenticated caller can fabricate a specific,
named person's professional judgment about a real bias finding"*); the
M10 Compliance Dashboard (a browser, needing a session cookie, not a
bearer header a human would have to paste into every page load); and this
platform's six existing CLIs (`db/migrate.py`,
`plugins/seed_registry.py`, `population_engine/run_policies.py`,
`retention/purge_expired_records.py`, `reporting/generate_report.py`,
`human_review/backfill_reviews.py`, `audit/verify_chain.py`,
`audit/verify_population_findings.py`), which **this document recommends
stay entirely outside HTTP authentication's scope** — they already
operate under a separate, pre-existing trust boundary (direct database
credential/filesystem access) this project has repeatedly and explicitly
treated as sufficient (most recently, `docs/milestones/M12.md` §9/§12.13,
in terms this document quotes directly in §4.1.4), and folding them into
an HTTP-auth design would conflate two different kinds of access control.

**This document's own highest-stakes call (§13.1, approved 2026-07-31):
`AUTH_ENABLED` defaults to `True` (fail-closed) — a deliberate, disclosed
break from `FIELD_ENCRYPTION_KEY`'s exact M11 precedent of defaulting to
`False`.** Every predecessor secret-bearing setting in this platform
(`SIGNING_PRIVATE_KEY`, `FIELD_ENCRYPTION_KEY`) defaults to "off, logged
loudly" — but both of those protect *confidentiality/integrity of data
already at rest*, a narrower harm than what an unauthenticated caller can
do today: fabricate ingestion events, silently deactivate a policy
binding that governs real financial decisions, or falsely resolve a
bias-finding review under someone else's name. This document's
recommendation, and why it is not a mechanical repeat of the encryption
precedent, is argued in full at §13.1 — **this was the one recommendation
in this document most likely to warrant a different call than the
pattern the rest of the platform already established**, and was held for
explicit sign-off before implementation, the same way M11 §12.1 and M12
§12.1 each gated their own milestone on one foundational, non-mechanical
decision before proceeding. A second, independent hostile-review pass
found that this recommendation's own "operational break" had two
concrete instances inside this repository itself — this platform's own
`docker-smoke` CI job and its entire existing Postgres-gated test suite
(Revision note items 7–8) — neither named in the first draft. Both are
now addressed as explicit, in-scope M13 deliverables (§1/§5.7/§8), which
is what made this recommendation approvable as stated rather than merely
asserted.

## 1. Scope

**M13 owns:**

- **A `Principal` concept** — a registered caller (human or machine) with
  a name, an assigned role from a small, fixed set, and one opaque,
  revocable bearer credential — persisted in one new table, provisioned
  by a new CLI, never through a self-service HTTP registration endpoint
  (§4.4/§5.1).
- **A fixed, four-value role enum** — `INGESTION`, `REVIEWER`, `ADMIN`,
  `READ_ONLY` — matching this platform's own real, already-observed
  caller shapes (§4.1), not a general-purpose permission matrix (§12.4).
- **A FastAPI dependency (`get_current_principal`/`require_role(...)`)**
  checked on every existing HTTP surface that returns or mutates
  governance-sensitive data: both ingestion routes, all eighteen Admin
  API endpoints, and the M10 dashboard's own three view routes — applied
  at the existing composition root (`api/app.py`), the identical
  centralization pattern every cross-cutting concern in this codebase
  already uses (§5.4).
- **A minimal browser-session mechanism for the M10 dashboard** — one new
  login endpoint that exchanges a bearer token for an `HttpOnly` session
  cookie, and one new logout endpoint, plus a small static login page
  added to `api/dashboard_static/` — reusing the identical principal/token
  mechanism every other caller uses, not a second, parallel auth system
  (§5.5).
- **Closing `docs/milestones/M9.md`'s own named, sharpest gap**: `resolve()`
  on both Human Review Workflow routers stops trusting a client-supplied
  `reviewer` string once a caller is authenticated, sourcing it from the
  authenticated principal's own name instead, with an explicit rejection
  (not a silent override) if a client-supplied value disagrees — no
  schema change, since `reviewer` is already a plain `str` column; a
  call-site change only (§4.5/§5.6).
- **One new, purely additive migration** — a `principals` table, granted
  the same ordinary privileges every other admin-configuration table in
  this schema gets in the same migration that creates it, no `ALTER` of
  any existing table (§6).
- **Two operational updates inside this repository itself, both required
  by, and shipped as part of, the `AUTH_ENABLED` default recommended in
  §13.1** — updating `.github/workflows/ci.yml`'s `docker-smoke` job to
  provision and use a bootstrap `INGESTION` principal (§8), and updating
  `tests/conftest.py`'s `test_settings` fixture so this platform's
  existing ~640-test Postgres-gated suite keeps passing unmodified,
  alongside a small, new, dedicated set of fixtures/tests for
  authentication itself (§5.7). Found missing from this document's own
  first draft by a second, independent hostile-review pass (Revision
  note items 7–8) — not an afterthought, a required part of this
  milestone's own deliverable.

**M13 explicitly does not own** — each backed by a finding in §4, not a
judgment call made unilaterally:

- **Multi-tenancy, multi-plane deployment, and mTLS** — architecture
  §17's own explicit scope, a structurally different kind of concern
  (network/deployment topology, not caller identity) that happens to
  share a citation with authentication only by historical accident, not
  by design intent — see §4.2/§12.2.
- **Real scheduling** (cron, a Kubernetes `CronJob`) for this platform's
  three recurring CLIs — an operator's own deployment-topology concern,
  repeatedly and consistently declined by M6, M8, M11, and M12 alike; no
  finding in this document changes that conclusion — see §4.2/§12.3.
- **Comprehensive request-abuse protection** (rate limiting, streaming
  byte-counting, reverse-proxy request limits) beyond the `Content-Length`
  check M0 already added — named exactly once, at M0, and never repeated
  by any of the eleven subsequent design reviews, unlike authentication's
  eleven-consecutive-citation record; `api/middleware.py`'s own docstring
  already assigns this to "the reverse-proxy / gateway layer," an
  infrastructure concern this repository has never provisioned for
  anything (not even Postgres itself) — see §4.2/§12.5.
- **Key rotation or KMS/HSM-backed custody** for the signing key (M5) or
  the encryption key (M11) — a real, disclosed, still-unassigned gap this
  document does not newly claim; it is adjacent to (both are
  "secret-material lifecycle") but structurally distinct from
  authentication-token issuance, and remains unassigned rather than
  absorbed here — see §12.6.
- **A general-purpose RBAC permission matrix** — a fixed, four-role enum
  is sufficient for this platform's actual, observed endpoint shapes;
  building a configurable permission system now, with zero concrete case
  requiring finer granularity, would be the identical premature
  generalization this project has declined at every prior opportunity
  (M2's resolver staying concrete, M7's fixed metric set, M8's declined
  metrics-registration framework, M12's declined report-type plugin port)
  — see §12.4.
- **Authentication of this platform's own CLIs** — `db/migrate.py`,
  `plugins/seed_registry.py`, `population_engine/run_policies.py`,
  `retention/purge_expired_records.py`, `reporting/generate_report.py`,
  `human_review/backfill_reviews.py`, `audit/verify_chain.py`, and
  `audit/verify_population_findings.py` all keep operating under their
  existing, separate trust boundary (direct database credential and/or
  filesystem access) — see §4.1.4.
- **Self-service registration, password reset, SSO/OIDC federation, or
  multi-factor authentication** — no concrete case for any of these
  exists in this platform's twelve-milestone record; a CLI-provisioned
  opaque token, distributed out of band by an operator, is the smallest
  mechanism that closes the actually-named gap — see §5.1/§12.7.
- **A persisted, queryable audit trail of authentication events** (logins,
  token issuance/revocation, permission denials) — structured logging
  (`observability/logging.py`, unchanged) is sufficient for this
  milestone; a second evidentiary system for access events is a real,
  plausible future need with no concrete forcing case today — see §12.8.

## 2. Relationship to previous milestones

M13 is the first milestone whose entire job is a cross-cutting control
plane over every existing surface, rather than a new capability added
alongside them — closer in shape to M11's "add a control to prior
milestones' output" than to M6/M9's "add a new pipeline." Concretely, it
depends on, and changes the calling contract of, the following
prior-milestone artifacts:

- **`api/app.py`** (every milestone since M0) — the one composition root
  every router, repository, and middleware is already wired through.
  M13 adds one more collaborator (a `PrincipalRepository`), one more
  piece of middleware-equivalent wiring (dependency injection at
  `include_router()` call sites, per the Revision note's first finding),
  and one more `Settings`-driven opt-in flag, following the exact pattern
  `FieldEncryptor` (M11) already established for "build one collaborator
  from a `Settings` value, thread it into everything that needs it."
- **`api/dependencies.py`** (M0–M9) — gains
  `get_principal_repository`/`get_current_principal`/`require_role`,
  the same "route handlers depend on a provider function, never a
  concrete singleton" discipline this module's own docstring has stated
  since M0.
- **`api/middleware.py`** (M0) — `MaxBodySizeMiddleware`'s own docstring
  already names "M13" as the milestone that would own reverse-proxy/
  gateway-layer concerns; this document's own finding (§4.2) is that
  authentication is not that concern, and this milestone does not modify
  `MaxBodySizeMiddleware` or add abuse-protection middleware alongside it.
- **`config/settings.py`** (M0–M11) — gains `AUTH_ENABLED: bool`, defaulting
  to `True` (§13.1, approved and frozen). This is the first `bool` field this project
  has ever added to `Settings` — every existing "off until configured"
  gate (`FIELD_ENCRYPTION_KEY: str | None`, `RETENTION_DAYS_*: int | None`)
  instead uses the value's own `None`-ness as the toggle. That pattern
  doesn't transfer here: unlike a signing/encryption key, there is no
  single per-process secret for `AUTH_ENABLED` to key off of — a
  principal's credential is per-principal, provisioned into the
  `principals` table (§6), not into `Settings` at all — so a bare boolean
  is the correct, structurally-necessary departure, stated explicitly
  here rather than left implicit (corrected by this document's own
  second hostile-review pass, Revision note item 14). `AUTH_ENABLED`
  still inherits `SIGNING_PRIVATE_KEY`'s (M5) "no rotation, no KMS" scope
  boundary for the credential material it gates.
- **`api/ingestion/routes.py`** (M0, generalized at M3) — gains exactly
  one new dependency per generated route. This is the **first** milestone
  to change ingestion's calling contract at all since M2's "two adapters,
  two routes, one shared ledger" design — every one of M4 through M12's
  own architecture-mapping notes has stated some variant of "both
  ingestion routes... byte-for-byte unchanged" as a point of pride. This
  document does not treat that streak as sacred: eleven consecutive
  milestones deferred authentication specifically because ingestion (and
  everything else) was going to need it eventually, not because
  ingestion was meant to stay permanently exempt. See §4.1.1/§10 for the
  full backward-compatibility treatment of this reversal.
- **`schemas/human_review.py`, `db/repositories/verdict_review.py`,
  `db/repositories/population_finding_review.py`** (M9) — `resolve()`'s
  existing `reviewer: str` parameter and its "must match who claimed it"
  conditional-update check (M9's own pre-authentication integrity
  mitigation, explicitly named as *not* a substitute for real auth in
  `docs/milestones/M9.md` §3.3/§9.6) are unchanged at the repository
  layer. What changes is the API layer one level up
  (`api/admin/verdict_reviews.py`/`population_finding_reviews.py`):
  once a caller is authenticated, `reviewer` is derived from
  `principal.name`, never accepted from the request body — see

- **`api/dashboard.py`, `api/dashboard_static/`** (M10) — gains a login

- **`docs/architecture-mapping.md` §17** — the specific, numbered
  citation this document's own scope decision (§4.2) declines to also
  claim; a future milestone inherits it, still unnumbered beyond §17

- **Every CLI's own documented trust boundary** (`db/migrate.py`'s
  admin-credential requirement, `plugins/seed_registry.py`'s and
  `human_review/backfill_reviews.py`'s "explicitly invoked, no HTTP

  connection) — the direct precedent for §4.1.4's conclusion that CLI
  access control is a solved, separate problem this milestone does not
  need to re-solve, and the direct structural template for §5.1's new
  `access/create_principal.py` CLI, which mirrors their exact shape
  (`create_db_engine`, explicit `--database-url`, no daemon).
- **`tests/conftest.py`** (M0–M11) — gains an explicit
  `AUTH_ENABLED=False` override on the existing `test_settings` fixture

  milestone's own new testing need requires, in the same milestone"
  precedent M11 already established for `admin_database_url`/

- **`.github/workflows/ci.yml`** (M1–M12) — the `docker-smoke` job's

Every existing endpoint's *calling contract* changes (a request now needs

argued fully in §10.

## 4. Architectural analysis

### 4.1 What "authentication" must actually cover — four structurally different callers

Unlike every prior milestone, M13 has no single new module to design
around; it has to be checked against every surface this platform has
accumulated across twelve milestones. Four genuinely different caller
shapes exist today, confirmed directly against the current routing table
in `api/app.py` (§2), and each needs a different answer:

**4.1.1 — Ingestion callers.** `POST /v1/ingestion/events/{synthetic,
credit-scorecard}` are, today, fully anonymous: any client that knows a
route exists can post a fabricated `DecisionEvent` and have it
auto-provisioned, governed, and permanently written into the hash chain.
This is the platform's actual highest-blast-radius unauthenticated
surface — every downstream governance judgment (a `Verdict`, a
`Finding`, eventually a `PopulationFinding`) traces back to data an
unauthenticated caller supplied. This document recommends ingestion
require an `INGESTION`-role credential (§5.4), ending the "byte-for-byte
unchanged since M2" streak deliberately, not by oversight (§2).

**4.1.2 — Admin/operator callers.** Eighteen endpoints across nine
routers, ranging from read-only (`GET /v1/admin/population-findings`,
`GET /v1/admin/metrics`) to high-blast-radius mutation (`POST
/v1/admin/plugins/{id}/promote`, `POST
/v1/admin/policy-bindings/{id}/deactivate` — either can silently change
which policy governs real financial decisions on the very next request,
per M3/M5's own "takes effect on the very next request, no restart
needed" design). These need role-gated access, not a single blanket
check — see §5.4's per-router breakdown.

**4.1.3 — Dashboard viewers.** M10's three HTML views are read-only, but
render exactly the governance-sensitive content M10 §6 itself named as
the reason "no authentication yet" stopped being theoretical for that
milestone: which systems have been flagged for bias, which verdicts are
escalated, the human review queue. A browser needs a session mechanism
suitable for repeat page loads without re-presenting a credential every
time — a cookie, not a bearer header a human manually manages. See §5.5.

**4.1.4 — This platform's own CLIs.** `db/migrate.py`,
`plugins/seed_registry.py`, `population_engine/run_policies.py`,
`retention/purge_expired_records.py`, `reporting/generate_report.py`,
`human_review/backfill_reviews.py`, `audit/verify_chain.py`, and
`audit/verify_population_findings.py` all take an explicit
`--database-url` argument and run under whoever has that connection
string — never through this platform's own HTTP surface at all.
`docs/milestones/M12.md` §9/§12.13, describing its own CLI's identical
shape, states this most directly: *"The CLI's own implicit trust
boundary (whoever has filesystem/credential access to invoke it) is the
identical boundary `db/migrate.py`/`population_engine/run_policies.py`/
`retention/purge_expired_records.py` already operate under, not a new or
different one."* This document adopts that same conclusion for its own
new CLI (`access/create_principal.py`, §5.1) and does not add HTTP-style
authentication to any CLI — a database credential already *is* this
platform's access-control mechanism for that class of caller, and has
been since M1. Conflating "HTTP API authentication" with "who holds the
database credential" would be solving an already-solved problem a second,
worse way.

### 4.2 Why multi-tenancy, mTLS, and real scheduling are not this milestone, despite sharing a citation

The Sourcing note above establishes the fact: "M13" has been used for at
least three unrelated concerns. This section argues why they should stay
separated rather than be designed together, since a hostile reader could
reasonably ask "if you're doing M13 anyway, why not close the whole
bucket at once?"

**They solve different problems for different questions.** Authentication
answers "who is calling, and what are they allowed to do" — a property of
a single request, checked once, at the API boundary. Multi-tenancy
answers "whose data is this," a property of the *data model* (which
`System`/`DecisionEvent`/`Verdict` rows a given caller may see at all,
not just which endpoints they may call) — this platform's schema has no
tenant-scoping concept anywhere today (`System.owner` is free-text
metadata, never enforced — see §12.9); building it correctly requires
deciding what a "tenant" even is in this domain (one `System`? one
organization owning several `System`s? one `Policy`/`PopulationPolicy`
governance regime?), a real design question with zero concrete case in
this platform's record to design against, the identical "no second real
domain exists yet" reasoning M5 §13.1 already applied to a structurally
similar question (`System.domain`-keyed Policy Bindings). mTLS answers
"do these two network peers trust each other," a transport-layer,
deployment-topology property completely orthogonal to which human or
API-key is making a request over an already-established connection —
and this platform has exactly one deployment plane today (`infra/docker/`,
"single container, single service," unchanged since M1 per
`docs/architecture-mapping.md` §17), meaning there is no second plane yet
for mTLS to secure trust between. Real scheduling answers "when does a
batch job run," an operational/infrastructure question this project has
independently and consistently declined to build for four consecutive
occurrences (M6 §13.4, M8 §4.1, M11 §5.2, M12 §5.3) with the same
"an operator's own cron/`CronJob` cadence, not this platform's job"
reasoning each time — nothing about adding authentication changes that
conclusion.

**Bundling them would violate this project's own discipline, not
extend it.** Every milestone from M5 onward has narrowed an
over-broad citation to "the smallest architecture that actually solves
it" and named the rest explicitly as still-deferred, rather than
building everything a section's literal text could be read to imply
(M5's narrower Policy Bindings reading, M7's "not Prometheus," M10's
static HTML over an SPA). Treating "M13" as license to build
authentication, multi-tenant data isolation, mTLS, and a scheduling
daemon in one milestone would be the single largest scope expansion in
this project's history, with three of the four having no concrete
forcing case today. This document declines that expansion and ships the
one piece — authentication — that eleven consecutive documents have
already, independently, and urgently justified.

**They are not independent forever — multi-tenancy in particular is a
natural, later consumer of this milestone's own `Principal` concept**
(a tenant boundary could plausibly be expressed as "which `System`s a
`Principal` may act on," once tenancy itself is designed) — but building
that linkage speculatively, before multi-tenancy's own shape is decided,
would be exactly the premature generalization this project's discipline
forbids. Named as a real, plausible future dependency, not built now
(§12.2).

### 4.3 Why not OAuth2/OIDC or an external identity provider

This platform has never integrated an external service for anything —
not for metrics (M7 declined Prometheus/OpenTelemetry), not for its
analytical reads (M6 declined a dedicated warehouse), not for its
compliance exports (M12 declined a document-rendering service). The
identical reasoning applies here: this platform has **one deployment
environment**, no established corporate identity provider it is known to
sit behind, and zero citations anywhere in its record naming a specific
IdP, protocol, or federation requirement. Standing up or integrating an
OIDC provider (Keycloak, Auth0, Okta, an internal SSO gateway) would be
real infrastructure with no concrete forcing case — the same class of
mistake M12 §12.1 argued against for a PDF renderer, applied here to a
much heavier dependency. A self-contained, DB-backed principal/token
mechanism is smaller, requires no new external service, and is
sufficient for the caller shapes §4.1 actually describes. If this
platform is later deployed behind a real corporate SSO requirement, that
is itself a forcing case strong enough to justify federation — and this
design's `Principal` concept (a name, a role, one credential) is a small
enough surface to federate against later without being thrown away, the
same "small, self-contained, not thrown away later" property M12's own
`reporting/` package was built to have relative to `observability/metrics.py`.

### 4.4 Why principals are CLI-provisioned, not self-registered

An HTTP self-service "create an account" endpoint has an unavoidable
bootstrap problem: the very first administrator account has to be
created by *someone*, and that creation step is either itself
unauthenticated (defeating the entire point) or requires a
already-provisioned admin to exist first (impossible on a fresh
deployment). Every secret this platform has ever introduced —
`SIGNING_PRIVATE_KEY` (M5), `FIELD_ENCRYPTION_KEY` (M11), the
`gov_platform_app` database role's own password (M1) — is provisioned
out of band by whoever controls the deployment, never through this
platform's own HTTP surface, and the plugin registry itself
(`plugins/seed_registry.py`) is seeded by an explicitly-invoked CLI run
before the application ever accepts real traffic, per this platform's
own README. A new CLI, `access/create_principal.py`, mirroring that
exact shape, sidesteps the bootstrap problem entirely: an operator with
database and filesystem access (the same access every migration and
every other CLI in this codebase already requires) creates the first —
and every subsequent — principal directly, no HTTP round trip, no
chicken-and-egg. See §5.1.

### 4.5 Why closing M9's "fabricated reviewer" gap needs no schema change

`docs/milestones/M9.md` named, more sharply than any other document in
this project's record until M10, that an unauthenticated caller can
`POST /v1/admin/verdict-reviews/{id}/resolve` with any `reviewer` string
they like — `resolve()`'s own conditional check (`reviewer` must match
whoever `claim()`ed the item) is explicitly documented as "a
non-authentication sanity check... which catches accidental cross-wiring,
not a malicious actor" (`README.md`, Human Review Workflow section).
Once a caller is authenticated, the fix requires no migration and no
repository change at all: `VerdictReviewRepository.resolve`/
`PopulationFindingReviewRepository.resolve` already take `reviewer: str`
as a plain parameter, agnostic to where the caller (the API layer)
sourced that string from. The fix is entirely in
`api/admin/verdict_reviews.py`/`population_finding_reviews.py`: stop
reading `reviewer` from the request body once a principal is
authenticated, and pass `principal.name` instead. `claim()` gets the
identical treatment. This is the smallest possible fix for the specific
gap M9 named — no new column, no new table for review-identity, no
retroactive rewrite of any already-resolved review's historical
`reviewer` value (which stays exactly as originally recorded, the same
"historical record is never silently rewritten" discipline M5 §13.6
already applied to legacy `VerdictStatus` values).

## 5. Proposed architecture (this review's recommendation)

### 5.1 New top-level package: `access/`

Mirrors the exact "a new top-level package only when nothing existing is
a natural home" bar `human_review/` (M9), `retention/` (M11), and
`reporting/` (M12) each had to clear: authentication spans
`api/`-adjacent concerns (a FastAPI dependency) and a pure, DB-agnostic
cryptographic mechanism (token generation/hashing) with no existing
package that naturally owns both. Folding it into `audit/` instead — the
one existing package that already handles this platform's other two
secret types (`signing.py`, `encryption.py`) — was considered and
declined: `audit/` is about evidentiary integrity (proving what happened
is what happened); principal/token handling is about access control
(deciding who may act at all), a genuinely different concern this
project's own single-responsibility-package discipline
(`human_review/`, `retention/`, `reporting/`, each scoped to exactly one
concern) argues against blending into one package. **Named `access/`,
not `auth/`** — corrected by this document's own second hostile-review
pass (Revision note item 10): `auth/` sits immediately adjacent,
alphabetically and visually, to the existing `audit/` package (`hash_chain.py`,
`evidence_store.py`, `verify_chain.py`, `signing.py`, `encryption.py`),
a realistic source of a mis-typed import in a codebase whose own isort
configuration (`known-first-party = ["gov_platform", "tests"]`) groups
them together. The **API path prefix** (`/v1/auth/session`,
`/v1/auth/logout`, §5.5/§7) is a separate namespace with no equivalent
collision risk and is unaffected by this rename.

**`access/tokens.py`** — pure, no DB, no FastAPI import, unit-testable
with no Postgres, the identical shape `audit/hash_chain.py` (M0/M1)
already established for this platform's other pure cryptographic
primitives:

```python
import hashlib
import hmac
import secrets

_TOKEN_BYTES = 32  # 256 bits of entropy -- matches SIGNING_PRIVATE_KEY's own seed length

def generate_token() -> str:
    """A fresh, cryptographically-random bearer token. Never persisted in
    plaintext anywhere -- see hash_token."""
    return secrets.token_urlsafe(_TOKEN_BYTES)

def hash_token(token: str) -> str:
    """One-way digest stored in `principals.token_hash`. SHA-256, not a
    slow/adaptive password hash (bcrypt/argon2/scrypt) -- deliberately:
    `token` is a 256-bit random value with no human-memorable structure to
    defend against offline brute-forcing, the same property that makes a
    fast digest correct for GitHub/Stripe/AWS-style API keys. See
    docs/milestones/M13.md Revision note, item 3."""
    return hashlib.sha256(token.encode("utf-8")).hexdigest()

def token_matches(token: str, token_hash: str) -> bool:
    """Constant-time comparison -- a naive `==` here would leak timing
    information about how many leading hex characters of a guessed hash
    matched, the same class of defect `hmac.compare_digest` exists to
    close."""
    return hmac.compare_digest(hash_token(token), token_hash)
```

**`schemas/principal.py`** — the domain model, deliberately excluding the
token/hash entirely (the same "never round-trip the secret through the
domain model" discipline `encryption.py`'s own callers already hold
themselves to for encrypted column values):

```python
from datetime import datetime
from enum import StrEnum

from pydantic import BaseModel, ConfigDict, Field


class PrincipalRole(StrEnum):
    """Four roles, matching this platform's own real, observed caller
    shapes (docs/milestones/M13.md §4.1) -- not a general permission
    matrix (see §12.4). StrEnum, not `(str, Enum)` -- matches
    VerdictStatus/FindingOutcome/PluginType's own existing convention
    (corrected by this document's own second hostile-review pass,
    Revision note item 12)."""
    INGESTION = "INGESTION"    # POST to either ingestion route
    REVIEWER = "REVIEWER"      # claim/release/resolve on either review workflow
    ADMIN = "ADMIN"            # every mutating Admin API endpoint, plus everything REVIEWER/READ_ONLY can do
    READ_ONLY = "READ_ONLY"    # every read-only Admin API endpoint and the dashboard


class Principal(BaseModel):
    """A registered caller. The token itself is never a field here --
    see access/tokens.py and db/repositories/principal.py; this model is
    what a request handler receives *after* successful authentication,
    never what proves it."""
    model_config = ConfigDict(frozen=True)

    id: str = Field(..., min_length=1)
    name: str = Field(..., min_length=1)
    role: PrincipalRole
    created_at: datetime
    revoked_at: datetime | None = None
```

**`db/repositories/principal.py`** — `PrincipalRepository`, the same
one-class-per-entity shape every repository in this codebase already
follows:

- `create(session, *, name, role) -> tuple[Principal, str]` — the
  **only** place the plaintext token is ever available; returned once, to
  the CLI caller, and never persisted or logged anywhere (mirrors how a
  real API-key issuance flow — GitHub, Stripe, AWS — shows the secret
  exactly once at creation time).
- `get_by_token_hash(session, token_hash) -> Principal | None` — the hot
  path, called on every authenticated request; backed by a `UNIQUE` index
  on `token_hash` (§6) for O(1) lookup, the same "a real, load-bearing
  index for the one new query pattern this milestone introduces"
  discipline M7's/M12's own index-adding migrations already established.
- `revoke(session, principal_id) -> None` — sets `revoked_at`; an
  `UPDATE`, not a `DELETE` (the historical record of who was once a
  principal, and when their access ended, is worth keeping — the
  identical "never destroy, only supersede" discipline this platform
  already applies to a resolved `VerdictReview`).
- `list(session) -> list[Principal]` — for a future minimal
  "list active principals" capability; **not** exposed via any new HTTP
  endpoint in this milestone (§12.10) — CLI-only for now, the identical
  restraint M11 §7/§12.10 already applied to a "new Admin API surface for
  retention/encryption status."

**Revocation is instant and requires no token-holder cooperation** — the
direct, checked benefit of an opaque, DB-backed token over a JWT (Revision
note item 4's underlying reasoning): a compromised or offboarded
principal's access ends the moment `revoke()` commits, with no stateless-
token blocklist to maintain, matching this platform's own real threat
model (M9 §3.3's own "an abandoned claim" scenario already establishes
that this platform's realistic user base is small enough that immediate,
positive revocation matters more than avoiding one indexed lookup per
request).

**`access/create_principal.py`** — the CLI:

```
python -m gov_platform.access.create_principal \
    --database-url "postgresql://postgres:<password>@localhost:5432/gov_platform" \
    --name "jane" --role REVIEWER
# principal created: jane (REVIEWER)
# token (shown once, not recoverable): <the plaintext token>
```

Mirrors `plugins/seed_registry.py`'s exact shape: `create_db_engine`
(§4.1.4's own precedent — this CLI needs the ordinary connection, not an
elevated one, since `principals` is an ordinary admin-configuration
table, not evidentiary, and migration `0028` now grants
`gov_platform_app` the ordinary privileges that connection needs to use
— see §6, corrected by this document's own second hostile-review pass,
Revision note item 6), no `bootstrap_plugins()` call (this tool touches
no plugin registry), explicit `--database-url`, no daemon. A
`--revoke <principal-id>` flag provides the CLI-side complement to
`PrincipalRepository.revoke`.

### 5.2 Bearer-token authentication for API/CLI-style callers

A plain, hand-written header parser (Revision note item 2 — deliberately
**not** `fastapi.security.OAuth2PasswordBearer`), added to
`api/dependencies.py` alongside every other provider function that file
already defines:

```python
def get_principal_repository(request: Request) -> PrincipalRepository: ...
    # identical shape to every other get_*_repository provider in this module

async def get_current_principal(
    request: Request,
    db_engine: Engine = Depends(get_db_engine),
    principal_repository: PrincipalRepository = Depends(get_principal_repository),
) -> Principal:
    """Checks, in order: the `Authorization: Bearer <token>` header (every
    API/CLI-style caller), then the `gov_platform_session` cookie (the
    dashboard, §5.5) -- header takes precedence when both are present.
    Raises AuthenticationError (401) if neither is present, the token
    doesn't match any principal, or the matching principal is revoked."""
    ...

def require_role(*roles: PrincipalRole) -> Callable[..., Principal]:
    """A dependency *factory* -- `Depends(require_role(PrincipalRole.ADMIN))`
    -- returning a dependency that calls get_current_principal and raises
    AuthorizationError (403) if the resolved principal's role isn't one of
    `roles`. Mirrors this platform's own existing `ValueError`/
    `PluginTimeoutError` -> typed-exception -> dedicated-handler pattern
    (api/app.py) rather than inlining a status check in every route body."""
    ...
```

If a deployment explicitly overrides the approved `AUTH_ENABLED=True`
default (§13.1) back to `false`, every route using these dependencies
still functions exactly as it does today — `get_current_principal` is
not called at all when the setting is off, the identical "encryption
disabled means every code path behaves exactly as it did before M11"
precedent `FieldEncryptor`/`NoOpFieldEncryptor` already established,
applied here via a `NoOpPrincipal`-free short-circuit in `create_app()`
rather than a second encryptor-style protocol implementation (auth has
no equivalent "always succeeds, does nothing" useful runtime behavior
the way no-op encryption does — see §13.1 for why this asymmetry didn't
change the approved default).

### 5.3 Two new, minimal exception handlers

Registered in `api/app.py` alongside the existing
`PluginTimeoutError`/`ValueError`/`Exception` handlers, the identical
pattern:

```python
class AuthenticationError(Exception):
    """Raised by get_current_principal: missing, malformed, unknown, or
    revoked credential."""

class AuthorizationError(Exception):
    """Raised by require_role: a real, known principal whose role doesn't
    permit this action."""

@app.exception_handler(AuthenticationError)
async def authentication_error_handler(request, exc) -> JSONResponse:
    return JSONResponse(status_code=401, content={"detail": "authentication required"})

@app.exception_handler(AuthorizationError)
async def authorization_error_handler(request, exc) -> JSONResponse:
    return JSONResponse(status_code=403, content={"detail": "insufficient permissions"})
```

**Uniform, content-free error bodies** — neither handler names which
principal, which role, or which resource was involved, deliberately: a
401/403 response distinguishing "wrong token" from "right token, wrong
resource" would let an unauthenticated caller enumerate which resource
IDs exist, the standard reasoning behind returning identical 401s for
"credential missing" and "credential doesn't match anything" alike.

### 5.4 Wiring at the composition root — per-router granularity, corrected by the Revision note

Applied in `api/app.py`, at each `include_router()` call site, per the
Revision note's first finding — a blanket dependency where every
endpoint in a router shares one minimum role, per-route dependencies
where a router mixes levels:

| Router | Minimum role(s) | Shape |
|---|---|---|
| `health.router` (`/healthz`) | **None** — unauthenticated | Unchanged (§4.1's caveat is orthogonal; see Revision note item 5) |
| `readiness.router` (`/readyz`) | **None** — unauthenticated | Unchanged, same reasoning |
| Ingestion router (`build_ingestion_router()`) | `INGESTION` or `ADMIN` | Router-level blanket — every generated route shares this requirement |
| `admin_systems.router` | `list`/`get`: any authenticated; `register`: `ADMIN` | Per-route |
| `admin_plugins.router` | `list`/`get`: any authenticated; `promote`: `ADMIN` | Per-route |
| `admin_policy_bindings.router` | `list`/`get`: any authenticated; `create`/`activate`/`deactivate`: `ADMIN` | Per-route |
| `admin_protected_attribute_rules.router` | `list`/`get`: any authenticated; `create`: `ADMIN` | Per-route |
| `admin_population_policy_bindings.router` | `list`/`get`: any authenticated; `create`/`activate`/`deactivate`: `ADMIN` | Per-route |
| `admin_population_findings.router` | Any authenticated (entirely read-only) | Router-level blanket |
| `admin_metrics.router` | Any authenticated (entirely read-only) | Router-level blanket |

further role-gated beyond "is a real principal," since no citation
anywhere in this platform's record asks for read-level tenant/role
partitioning within the Admin API (that would be multi-tenancy's job,
§4.2/§12.9, not this milestone's).

### 5.5 Dashboard sessions: one login endpoint, one cookie, no second auth system

The M10 dashboard is a browser client; asking a human to manually attach
an `Authorization` header to every page load is not a realistic UX, and
building a second, parallel authentication mechanism for it would
violate the same "one mechanism, reused" discipline this document holds
itself to elsewhere. Instead:

- **`POST /v1/auth/session`** (new, minimal) — accepts `{"token": "<bearer
  token>"}` in the request body, validates it exactly the way
  `get_current_principal` already does, and on success sets an
  `HttpOnly`, `Secure`, `SameSite=Strict` cookie (`gov_platform_session`,
  value: the same token, so `get_current_principal`'s existing
  hash-and-look-up logic needs no cookie-specific branch beyond reading
  from a different request location) and returns `204`.
- **`POST /v1/auth/logout`** — clears the cookie, returns `204`. Does
  **not** revoke the underlying principal's token (the token may still be
  valid for non-browser use) — logging out of the dashboard and revoking
  API access are different actions; conflating them would surprise an
  operator who also uses the same token from a script.
- **A small, static login page** (`api/dashboard_static/login.html`),
  following M10's own "vanilla JS, `fetch()`, no build step, no
  framework" precedent exactly — a single input field, a submit handler
  that `POST`s to `/v1/auth/session` and redirects to `/dashboard` on
  success, an honest error message on failure (the identical "every view
  renders a visible, honest error state" discipline M10 §4.5/§8.5
  already established for its own `fetch()` failures).
- **The dashboard's existing three views are otherwise unchanged** — they
  already call `fetch()` against the same JSON endpoints this document
  now requires a credential for; the browser's own cookie jar supplies
  that credential automatically on every subsequent same-origin request,
  no client-side JavaScript change needed beyond the new login page and a
  single "redirect to `/login` on a `401` response" check added to each
  view's existing fetch-error handling (already present, per M10 §4.5).

### 5.6 Closing M9's gap: `reviewer` sourced from the authenticated principal

Corrected by this document's own second hostile-review pass (Revision
note item 9) — the first draft's "drops the `reviewer` field... once
`AUTH_ENABLED=true`" left the actual mechanism unspecified.
`ClaimVerdictReviewRequest`/`ResolveVerdictReviewRequest`
(`api/admin/verdict_reviews.py`; `population_finding_reviews.py`'s
identical twin) are **statically-defined Pydantic models — they cannot
change shape at runtime based on a `Settings` value** — so the fix is
not a conditional field, it is one unconditional relaxation plus
explicit handler-level logic:

- **The model change**: `reviewer: str = Field(..., min_length=1)`
  becomes `reviewer: str | None = Field(default=None, min_length=1)` on
  both request models — a backward-compatible relaxation (a stricter
  requirement becoming looser is never a breaking change for an existing
  caller that already always supplies the field).
- **When no principal is resolved** (`AUTH_ENABLED=false`, or no
  authentication dependency wired at all): the handler requires
  `payload.reviewer is not None`, raising the identical `422` Pydantic's
  own `Field(..., ...)` used to raise if it's absent — byte-for-byte the
  current, pre-M13 behavior, just enforced one layer up instead of by
  the model itself.
- **When a principal is resolved** (`AUTH_ENABLED=true`): the value
  passed to `VerdictReviewRepository`/`PopulationFindingReviewRepository`'s
  `claim`/`resolve` is always `principal.name`, never the request body.
  If `payload.reviewer` is present **and** differs from `principal.name`,
  the handler raises `422` (`"reviewer, if provided, must match the
  authenticated principal"`) — an explicit rejection, not a silent
  override, reusing the exact "must match who claimed it" precedent
  `resolve()`'s own repository-level check (M9) already established, one
  layer up, at the API boundary instead of the database. If
  `payload.reviewer` is omitted entirely, nothing was asserted, so
  nothing is silently overridden — the handler simply uses
  `principal.name`.
- `claim()` receives the identical treatment as `resolve()`.

This closes the exact "what the client sent and what gets persisted
silently diverge" footgun the first draft's own vague phrasing left
open, using one Pydantic model in both regimes and reusing an existing,
already-approved mismatch-detection pattern rather than inventing a new
one.

### 5.7 Testing strategy: the existing suite stays auth-disabled by default

Added by this document's own second hostile-review pass (Revision note
item 8) — the first draft never addressed this at all. Checked directly
against `tests/conftest.py`: the `test_settings` fixture builds
`Settings(DATABASE_URL=POSTGRES_URL or _PLACEHOLDER_DATABASE_URL)`, with
no other field overridden, and `api_client` (used by nearly every
integration test that exercises the HTTP layer) is built from it; `ci.yml`'s
own job-level `env:` block never sets `GOV_PLATFORM_AUTH_ENABLED`. Left
unaddressed, `AUTH_ENABLED`'s recommended `True` default (§13.1) would
have made this platform's entire existing Postgres-gated suite (roughly
640 tests, per M12's own Test Statistics) start receiving `401` on every
`api_client` call the moment this milestone's code merged — every one of
those tests would need editing, or the suite would simply fail, neither
an acceptable state to freeze a design around.

**The fix, mirroring M11's own precedent exactly** (that milestone added
`admin_database_url`/`admin_db_engine`/`requires_admin_postgres` in the
same milestone that first needed them, rather than leaving the existing
suite to silently break against a new elevated-credential requirement):

- **`test_settings` is updated to pass `AUTH_ENABLED=False` explicitly**,
  not left to whatever the environment or the new field's own default
  happens to be. This is a one-line change with a large effect: every
  existing test — all ~640 of them — continues to exercise exactly the
  code paths it already does, completely unaware this milestone exists,
  the identical "the bulk of this platform's own test suite should never
  need to know about a cross-cutting concern it isn't testing" principle
  every other opt-in `Settings` field (`FIELD_ENCRYPTION_KEY`,
  `RETENTION_DAYS_*`) already benefits from.
- **A small, new, dedicated set of tests exercises authentication
  itself** — `tests/unit/access/test_tokens.py` (pure, no Postgres,
  covering `generate_token`/`hash_token`/`token_matches`, the same
  DB-independent-first discipline `tests/unit/audit/test_hash_chain.py`
  already established for M0/M1's own pure primitive) and
  `tests/integration/test_authentication_postgres.py` (real Postgres
  round trips: `PrincipalRepository`'s CRUD/revocation behavior,
  `get_current_principal`/`require_role` against a real provisioned
  principal, the `POST /v1/auth/session`/`logout` cookie flow, and the
  `reviewer`-mismatch-rejects-with-422 behavior from §5.6) — each
  constructing its own `Settings(..., AUTH_ENABLED=True)` app instance
  explicitly, rather than relying on the suite-wide default, mirroring
  `@requires_admin_postgres`'s own "opt in per test file, not
  suite-wide" shape.
- **No new pytest marker is introduced** — `@requires_postgres` already
  gates every test that needs a real database; authentication tests need
  nothing further beyond constructing their own `Settings` override, the
  same way any other test that needs non-default configuration already
  does in this codebase (e.g. `tests/unit/config/test_settings.py`-style
  overrides, where they exist).
- **`.github/workflows/ci.yml`'s `lint-type-test` job needs no change** —
  it already runs `pytest`, and the fixture update above is sufficient;
  only `docker-smoke` needs an update, covered in §8.

This keeps the recommended `AUTH_ENABLED=True` **production** default
(§13.1) completely decoupled from this platform's own **test** default,
the same decoupling `Settings`'s own `DATABASE_URL` placeholder value
already relies on for tests that never touch a real database at all.

## 6. Database/schema implications

**One new table, purely additive — no `ALTER` of any existing table or
column:**

```sql
-- 0028_create_principals.sql
CREATE TABLE principals (
    id            TEXT PRIMARY KEY,
    name          TEXT NOT NULL,
    role          TEXT NOT NULL,   -- 'INGESTION' | 'REVIEWER' | 'ADMIN' | 'READ_ONLY'
    token_hash    TEXT NOT NULL UNIQUE,
    created_at    TIMESTAMPTZ NOT NULL,
    revoked_at    TIMESTAMPTZ
);

-- The one query pattern every authenticated request needs, at O(1):
-- already covered by the UNIQUE constraint's own implicit index above,
-- named here so a future reader doesn't add a redundant explicit one.

GRANT SELECT, INSERT, UPDATE, DELETE ON principals TO gov_platform_app;
```

**No `CHECK` constraint on `role`** — corrected by this document's own
second hostile-review pass (Revision note item 11): `grep -rn "CHECK"
infra/migrations/` returns nothing across all 27 existing migrations;
every other enum-backed column in this schema (`verdicts.status`,
`findings.outcome`, `verdict_reviews.status`/`resolution`,
`plugin_registrations.plugin_type`) is plain `TEXT NOT NULL`, validated
only at the Pydantic layer, matching `db/models.py`'s own stated
discipline that migrations define shape, not domain validation. The
first draft's `CHECK (role IN (...))` was a novel pattern with no
precedent anywhere in this schema; `PrincipalRole` (§5.1, Pydantic)
remains the single source of truth for valid values, consistent with
every other enum-backed column in this codebase.

**The `GRANT` statement above is not optional decoration — its absence
in this document's own first draft was a real, blocking defect**,
corrected by this document's own second hostile-review pass (Revision
note item 6): every `CREATE TABLE` migration in this schema since `0009`
grants privileges to `gov_platform_app` in the same file (verified
directly across all eight consecutive table-creating migrations since
then — `0009`, `0010`, `0011`, `0012`, `0014`, `0015`, `0023`, `0024` —
no exception). Postgres roles hold zero privileges on a new table until
explicitly granted; the first draft's SQL omitted this entirely, which
would have made `access/create_principal.py`'s very first `INSERT` fail
with `permission denied for table principals` against a freshly-migrated
database, directly contradicting this same section's own classification
below and §5.1/§8's claim that the CLI needs only the ordinary
connection.

`principals` is an **ordinary admin-configuration table**, the same
privilege class as `plugin_registrations`/`policy_bindings`/
`protected_attribute_rules`/`population_policy_bindings`/
`verdict_reviews`/`population_finding_reviews` (`docs/milestones/M11.md`
§5.3's own six-table classification) — **not** evidentiary, **not**
retention-eligible, ordinary `GRANT SELECT, INSERT, UPDATE, DELETE`
privileges for `gov_platform_app`, now actually present in the migration
SQL above. This is a deliberate, checked classification, not an
oversight: `principals` records *who currently has access*, not a
historical governance judgment about a real decision — revoking a
principal is an operational action with no evidentiary weight the way a
`Verdict`/`Finding`/`PopulationFinding` has, and the row is never
referenced by anything hash-chained or signed. `DELETE` stays granted
for the same reason it stays granted on the six tables M11 already
classified this way, though this design's own `revoke()` method (§5.1)
never calls it, preferring the "never destroy, only supersede" pattern
already established for reviews.

**No existing table is altered.** `verdict_reviews.reviewer`/
`population_finding_reviews.reviewer` keep their existing plain `TEXT`
column, unchanged (§4.5) — this milestone changes *what value the API
layer writes there*, never the column's shape, type, or constraints.

**No index on `principals.name`.** Lookups are always by token hash
(§5.1's `get_by_token_hash`), never by name at request-authentication
time; a future "list principals by name" CLI convenience can use a
sequential scan, bounded by the number of principals this platform will
ever realistically have (a handful to a few dozen — the same "bounded by
real-world registration activity, not per-request traffic" reasoning
`model_versions`' own lack of a `system_id` index already relies on, per
`docs/milestones/M12.md` §6).

## 7. Public API changes

**Two new endpoints, both minimal, both under a new `/v1/auth` prefix:**

- `POST /v1/auth/session` — exchanges a bearer token for an `HttpOnly`
  session cookie (§5.5). No request body beyond the token; `204` on
  success, `401` on an invalid/revoked token.
- `POST /v1/auth/logout` — clears the session cookie. `204` always
  (idempotent whether or not a session existed).

**No new endpoint for principal management** —
`access/create_principal.py` is CLI-only, mirroring
`plugins/seed_registry.py`'s own precedent of "the first-run provisioning
step is a CLI, not an endpoint" (§4.4/§12.10).

**Every existing endpoint's request-side contract changes**: a request
now needs a valid `Authorization: Bearer <token>` header (or, for the
dashboard's three view routes, the session cookie set by the new login
endpoint) once `AUTH_ENABLED=true`, or it receives `401`/`403` instead of
its previous response. **No existing endpoint's response body shape
changes** — every field a client already parses today is byte-for-byte
identical once authenticated; this is a request-authorization change, not
a data-shape change, unlike every other milestone's own "zero API
changes" claims, which were unconditional. See §10 for the full backward-
compatibility treatment.

**One existing request body shape is relaxed, not broken**: `claim`/
`resolve`'s `reviewer` field on both Human Review Workflow routers
becomes optional rather than required (§5.6) — a backward-compatible
change (a stricter requirement loosening is never breaking for a caller
that already always supplies it), corrected by this document's own
second hostile-review pass (Revision note item 9) from an earlier,
unspecified "the field is dropped" description.

## 8. Migration strategy

One purely additive migration (`0028_create_principals.sql`, §6), applied
via the same numbered, idempotent runner every migration since M1 has
used. No maintenance window needed — `CREATE TABLE` takes no lock on any
existing table, unlike M11's own migration `0025` (which needed one for
its `ACCESS EXCLUSIVE` `REVOKE` against this platform's highest-throughput
tables). No backfill, no data migration — `principals` starts empty on
every deployment, fresh or upgraded alike.

**The real migration-strategy risk in this milestone is not the schema
change — it is rollout sequencing**, argued in full in §9/§13.1: flipping
`AUTH_ENABLED=true` on a deployment with zero provisioned principals
would lock out every caller, including whoever is deploying the change,
since no bootstrap credential is baked into the code or the migration
itself (deliberately — a hardcoded bootstrap credential would be a
standing backdoor). The required operational sequence, which this
document states explicitly rather than leaving an implementer to infer:

1. Apply migration `0028`.
2. Run `access/create_principal.py` at least once, provisioning an
   `ADMIN` principal, and record the printed token somewhere durable (a
   secrets manager, not a commit) — the identical "generate it, store it
   yourself, this platform never sees the plaintext again" discipline
   `SIGNING_PRIVATE_KEY`/`FIELD_ENCRYPTION_KEY` already require of an
   operator.
3. Only then set `AUTH_ENABLED=true` and restart the application.

This three-step sequence is the direct analogue of this platform's own
README, which already documents an equivalent ordering constraint for
`plugins/seed_registry.py` ("required before ingestion will accept
anything") — the same shape of "a fresh deployment needs one explicit
provisioning step before the feature it gates will actually work,"
applied here to authentication instead of plugin promotion.

**This repository's own CI needs the identical sequence applied to
itself — found missing from this document's own first draft by a
second, independent hostile-review pass (Revision note item 7), and now
an explicit, in-scope part of this milestone's own implementation, not
a deployment-operator's afterthought.** `.github/workflows/ci.yml`'s
`docker-smoke` job posts to `/v1/ingestion/events/synthetic` with a
bare, unauthenticated `curl`, asserting `"status":"ALLOW"` — under
`AUTH_ENABLED=True`, that step fails on the very next CI run unless this
milestone also adds, to that same job:

1. A step provisioning a bootstrap `INGESTION` principal (mirroring the
   job's own existing "Seed the plugin registry" step, which already
   runs `plugins/seed_registry.py` against the same freshly-built
   container ahead of the ingestion `curl`).
2. Attaching that principal's token as an `Authorization: Bearer <token>`
   header on the existing ingestion `curl` call — the only change to
   that call itself.

The `lint-type-test` job needs no equivalent change — §5.7's
`test_settings` fixture update already keeps that job's `pytest --cov-fail-under=98`
run passing unmodified, since it pins `AUTH_ENABLED=False` for the
entire existing suite regardless of this milestone's own production
default.

## 9. Security implications

- **Credential storage**: tokens are never stored in plaintext anywhere —
  only `hash_token`'s SHA-256 digest is persisted (§5.1). The plaintext
  token exists only transiently, in the CLI process's own memory at
  creation time and in whatever the operator's terminal/secrets manager
  captures from `create_principal`'s stdout — this platform's code never
  writes it to a log, a database row, or a response body a second time.
- **Logging discipline**: `observability/logging.py`'s structured logger
  must never include a raw `Authorization` header value or cookie value
  in any `extra_fields` payload — verified directly against every
  existing `logger.*` call site that touches a request during
  implementation (none does today, since no request-header logging
  exists anywhere in this codebase yet; this is a discipline to hold,
  not a defect to fix).
- **Transport security is out of this milestone's scope, and was always
  out of this platform's scope** — `docs/architecture-mapping.md` §17
  has stated since M1 that this platform assumes an external, unbuilt
  deployment layer for TLS termination; a bearer token or session cookie
  sent over plaintext HTTP is exactly as exposed as `GOV_PLATFORM_DATABASE_URL`
  already is in that same unaddressed gap. This document does not newly
  introduce that risk; it adds one more secret type to an existing,
  already-disclosed transport-security assumption.
- **Timing-safe comparison**: `token_matches` uses `hmac.compare_digest`,
  not `==` (§5.1) — closes the standard timing-attack vector for secret
  comparison.
- **No token expiry, by design (§12.6/Revision note item 4)** — a token
  is valid until explicitly revoked. This is a real, disclosed trade-off:
  a leaked, un-revoked token remains usable indefinitely. Mitigated only
  by operational practice (revoke on suspected compromise, the same
  "manual, operator-driven" mitigation this platform already accepts for
  the signing key), not by any automatic expiry this design builds.
- **`INGESTION`-role tokens are the platform's new highest-value target**
  for a would-be attacker seeking to inject fabricated governance
  events — a genuinely new, disclosed risk this milestone introduces by
  closing the *anonymous*-ingestion gap (§4.1.1) with a *shared-secret*
  gap instead. This is a real improvement (anonymous access is strictly
  worse than credentialed access), not a solved problem — a compromised
  `INGESTION` token can still fabricate events, the same way a
  compromised database credential already can today. Per-`System` or
  per-adapter ingestion credentials (rather than one platform-wide
  `INGESTION` role) would narrow this further; declined for this
  milestone as unrequested granularity with no concrete forcing case
  yet — named as a real, plausible refinement, not built now (§12.11).
- **Interaction with M11 encryption**: `resolution_notes`'s existing
  encryption (M11) and `reviewer`'s new authenticated-sourcing (§5.6) are
  fully independent — the former protects a free-text column's
  confidentiality at rest, the latter protects a plain string column's
  *integrity of origin*. Neither changes the other's behavior; `reviewer`
  remains unencrypted (M11 §4.1 already excluded it, since `resolve()`'s
  own equality check against it cannot survive non-deterministic
  ciphertext — unaffected by this milestone).
- **`principals` itself is not encrypted** — `name`/`role` are
  operational metadata, not evidentiary or personally sensitive in the
  way `resolution_notes` free text is; `token_hash` is already a one-way
  digest, encrypting it further would add cost with no confidentiality
  benefit (a digest reveals nothing about the token it was derived from).
- **`reviewer`-mismatch is rejected, never silently overridden** (§5.6) —
  added by this document's own second hostile-review pass (Revision note
  item 9): if an authenticated caller's request body names a `reviewer`
  that disagrees with their own `principal.name`, the request fails with
  an explicit `422` rather than persisting `principal.name` while
  quietly discarding what the client actually sent. This closes a real,
  distinct integrity gap the first draft's own imprecise "drops the
  field" phrasing would have otherwise left open — a caller silently
  finding out, or never finding out, that their claimed identity for a
  review didn't take effect.
- **A permanent, disclosed residual limitation, not a defect this
  milestone (or any future one) can retroactively close**: historical
  `reviewer` values already persisted before `AUTH_ENABLED=true` first
  takes effect on a given deployment remain exactly as they were written
  — potentially fabricated, per M9's own named risk, and permanently
  unverifiable, since this platform's own "never silently rewrite an
  already-recorded fact" discipline (M5 §13.6) forecloses retroactively
  correcting or flagging them. §5.6's fix closes M9's gap
  **prospectively only** — every `claim`/`resolve` call made after that
  point in a given deployment's history. See §12.

## 10. Production-readiness considerations

- **This is the first milestone whose default value materially changes
  every existing deployment's behavior once flipped on** — every prior
  opt-in setting (`SIGNING_PRIVATE_KEY`, `FIELD_ENCRYPTION_KEY`,
  `RETENTION_DAYS_*`) only changes what happens to *data*; `AUTH_ENABLED`
  changes whether *a request is answered at all*. Getting the rollout
  sequence (§8) wrong genuinely locks operators out of their own
  deployment — this document states that sequence explicitly rather than
  leaving it implicit, the identical discipline M11 §5.4 already applied
  to its own maintenance-window requirement for migration `0025`.
- **Ingestion clients need advance notice and a provisioned credential
  before `AUTH_ENABLED=true` is flipped on an existing deployment** — any
  automated system currently posting to either ingestion route will
  start receiving `401`s the moment this setting changes, with no
  backward-compatible fallback. This is a real, disclosed operational
  break, not a silent one.
- **This repository's own CI is exactly such an "automated system,"
  and is not exempt** — found by a second, independent hostile-review
  pass (Revision note item 7), not the first draft: `.github/workflows/ci.yml`'s
  `docker-smoke` job is itself an unauthenticated ingestion client that
  would fail under the approved default. §8 now makes updating that
  job an explicit, in-scope part of this milestone, and §5.7 makes the
  equivalent update to `tests/conftest.py` explicit for the rest of the
  suite — the operational break named above is no longer an unquantified
  abstraction, it is two concretely-identified, concretely-fixed
  instances plus a general warning for any other deployment's own
  automated ingestion clients this document cannot see.
- **No token expiry means no automatic recovery from a forgotten
  revocation** — an offboarded reviewer's token remains valid until
  someone remembers to run `--revoke`. A real, accepted operational gap,
  not a new one relative to how this platform already handles the
  signing/encryption keys (also never auto-rotated).
- **An operator may still explicitly override the approved default to
  `AUTH_ENABLED=false`** (§13.1) — doing so reproduces today's
  fully-open platform exactly, a fresh deployment behaving identically to
  every deployment before M13, the same "nothing happens until
  explicitly configured" shape `FIELD_ENCRYPTION_KEY`/`RETENTION_DAYS_*`
  already have when left unset. This override remains available and
  deliberately not removed, but is no longer what a fresh, unconfigured
  deployment does by default — §13.1's approved decision is `True`.
- **No metrics/dashboard visibility into authentication activity** — no
  "failed login attempts" or "active principal count" signal is added to
  `GET /v1/admin/metrics` (M7) or the dashboard (M10) by this milestone;
  a real, plausible operational-visibility gap, declined for lack of a
  concrete forcing case, the identical restraint M8 §13.14 already
  applied to review-queue-depth metrics.
- **Interaction with the M0 `MaxBodySizeMiddleware`**: unaffected — that
  middleware inspects `Content-Length` before any routing or dependency
  resolution runs, so it continues to reject oversized requests
  regardless of whether they carry a valid credential, the correct
  ordering (reject the cheap way first).

## 11. Backward compatibility

- **Every existing response body shape is unchanged** — a successfully
  authenticated (or, if `AUTH_ENABLED=false`, any) request receives
  exactly the JSON this platform already returns today, field for field.
- **Every existing endpoint's request-side contract changes once
  `AUTH_ENABLED=true`** — this is the one genuine, disclosed break in
  this platform's entire milestone history: eleven consecutive documents
  claimed "zero API changes" or "byte-for-byte unchanged," and this one
  cannot make that claim. It is named plainly, not minimized.
- **No pre-M13 database row needs to change shape, be migrated, or be
  reinterpreted** — `principals` starts empty; every other table's
  existing rows are read and written exactly as before.
- **`reviewer`'s historical values are never rewritten** (§4.5/§6) — only
  new `claim`/`resolve` calls, made while `AUTH_ENABLED=true`, source
  this value differently; a permanent, disclosed residual limitation for
  anything already recorded, not something a later fix can close (§9,
  Revision note item 15).
- **`claim`/`resolve`'s `reviewer` request field becomes optional, not
  removed** (§5.6/§7) — a caller supplying it exactly as before still
  works identically when `AUTH_ENABLED=false`; only an authenticated
  caller whose supplied value disagrees with their own identity sees new
  behavior (a `422`, per §5.6/§9). No existing, correctly-behaving caller
  is broken by this specific change.
- **The dashboard's existing three views need no JavaScript rewrite**
  beyond the addition of a login page and a `401`-triggers-redirect check
  already compatible with M10's own existing fetch-error-handling
  pattern (§5.5).
- **This platform's CLIs are entirely unaffected** — none of them calls
  the HTTP API, so none of them is subject to this milestone's new
  requirement (§4.1.4).
- **This repository's own CI and test suite are explicitly updated as
  part of this milestone, not left as an unstated assumption** (§5.7/§8,
  added by a second, independent hostile-review pass — Revision note
  items 7–8): `.github/workflows/ci.yml`'s `docker-smoke` job gains a
  bootstrap-principal step, and `tests/conftest.py`'s `test_settings`
  fixture pins `AUTH_ENABLED=False`, so this platform's own existing
  ~640-test suite continues passing completely unmodified.

## 13. Architectural ambiguities, each with a recommendation and justification

### 13.1 — `AUTH_ENABLED` default: `False` (opt-in, matching M11's precedent) or `True` (fail-closed, a deliberate break from precedent)? **(the highest-stakes call in this document — approved 2026-07-31, now a frozen architectural decision)**

**Decided: (b), `True`.** Approved as stated below; this section is
preserved as the record of the choice and its reasoning, the same
"keep the approved argument in place, not rewritten after the fact"
discipline this project has held every prior gating decision to (M10
§4.1, M11 §12.1, M12 §12.1). The two options that were weighed:
**(a)** Default `False`, mirroring `FIELD_ENCRYPTION_KEY`'s exact M11
shape — a fresh deployment behaves exactly as every deployment before
M13 did, and an operator must explicitly opt in, in full awareness of
the three-step rollout sequence (§8). **(b)** (**approved**) Default
`True` — a fresh deployment, or an upgrade with no
`GOV_PLATFORM_AUTH_ENABLED` set, refuses every request except
`/healthz`/`/readyz` until at least one principal exists, forcing the
rollout sequence (§8) rather than merely documenting it.

**Why (b), with a disclosed, real cost.** This is not a mechanical
repeat of the encryption precedent, and this document did not treat it
as one: `FIELD_ENCRYPTION_KEY`/`RETENTION_DAYS_*` defaulting to "off"
only weakens *confidentiality of data already written* or *retention
hygiene* — real but bounded harms. An unauthenticated caller today can
fabricate governance-relevant ingestion events, silently deactivate the
policy binding governing real financial decisions, or falsely resolve a
bias-finding review under a real person's name — the exact harms eleven
consecutive design documents named as this platform's single sharpest
standing risk, sharper than anything M11 was built to address.
Defaulting `AUTH_ENABLED` to `False` would have meant this milestone
closes the gap only for whichever operator remembers to flip the
setting — the same failure mode that produced eleven consecutive "still
open" citations for encryption's own analogous gaps before M11 finally
closed them, except this time for the platform's most consequential
exposure. **The real cost of (b), stated plainly:** it breaks every
existing deployment's ingestion clients and Admin API callers the
moment this milestone's code is deployed, until the §8 rollout sequence
is completed — a deliberate, disclosed, one-time operational break, not
a silent one, accepted in exchange for never having a window where an
upgraded deployment is auth-capable but still wide open by default.

**A second, independent hostile-review pass tested this recommendation
against the one codebase where its cost could actually be measured —
this repository's own CI and test suite — and found the cost real but
fully containable, not merely asserted to be worth paying.** The
original "real cost, stated plainly" paragraph above was abstract;
checked directly, that cost had two concrete instances inside this
project itself: `.github/workflows/ci.yml`'s `docker-smoke` job (an
unauthenticated ingestion `curl`) and `tests/conftest.py`'s
`test_settings` fixture (feeding roughly 640 existing tests with no
credential). Both are now explicit, in-scope parts of this milestone's
own implementation (§5.7/§8, Revision note items 7–8), not left to an
implementer to discover the hard way, the same "found before freeze, not
after" standard M11's psycopg regression and M12's own two SQL bugs set
for this project. This evidence — not merely the abstract argument
above — is what made (b) approvable as stated, rather than a
recommendation asking for sign-off on an unquantified cost.

**Approved 2026-07-31.** An operator may still explicitly configure
`AUTH_ENABLED=false` for a given deployment if local operational
constraints make the fail-closed default genuinely unworkable (e.g., an
automated deployment pipeline with no step for §8's manual token
provisioning) — that override is not removed, and remains the
documented fallback for a deployment that needs it — but it is no
longer this platform's own default, and choosing it for a specific
deployment is now that deployment's own explicit, disclosed decision to
make, not this design's.

### 13.2 — Should multi-tenancy, mTLS, and multi-plane deployment be designed now, since M13 is "already" the milestone touching auth?

Already argued at length in §4.2. **Recommendation: no** — these remain
explicitly unassigned to any numbered milestone, exactly as architecture
§17 leaves them, rather than informally absorbed into this document
because they share a citation. If a future milestone number is reserved
for them, this document's own `Principal` concept (§5.1) is a reasonable
foundation to build tenant-scoping against, but that linkage should be
designed when tenancy's own shape is decided, not spec'd speculatively
here.

### 13.3 — Should real scheduling (cron/`CronJob`) for this platform's three batch CLIs be built alongside authentication, since both are labeled "M13" in prior citations?

**Recommendation: no**, unchanged from four consecutive prior milestones'
own identical conclusion (M6 §13.4, M8 §4.1, M11 §5.2, M12 §5.3) —
nothing about adding authentication changes the reasoning that real
scheduling is an operator's own deployment-topology concern this
repository has never built infrastructure for (it does not even provision
Postgres itself).

### 13.4 — Four fixed roles, or a configurable permission system?

Options: **(a)** (recommended) Four fixed roles (`INGESTION`, `REVIEWER`,
`ADMIN`, `READ_ONLY`), hardcoded as a Python enum, matching this
platform's own existing convention for every other closed-set domain
concept (`VerdictStatus`, `FindingOutcome`, `PluginType`,
`PopulationFindingReviewResolution`). **(b)** A configurable
permission-matrix system (named permissions, roles as sets of
permissions, admin-editable via a new Admin API surface). **(c)** No
roles at all — a single "authenticated" bit, gating everything
identically.

**Recommendation: (a).** (c) fails §4.1's own analysis directly — an
`INGESTION` credential and an `ADMIN` credential must not be
interchangeable, since a compromised ingestion credential should not
also be able to deactivate a policy binding. (b) is real, general
infrastructure with zero concrete case in this platform's twelve-
milestone record asking for finer-grained or admin-configurable
permissions than the four roles above already express — the identical
premature-generalization pattern this project has declined at every
comparable fork (M2's resolver, M7's fixed metrics, M8's declined
metrics-registration framework, M12's declined report-type plugin port).
A fifth role is one enum value away, whenever a concrete sixth caller
shape actually appears.

### 13.5 — Comprehensive request-abuse protection: build it now, since M0's own citation named it "M13"?

**Recommendation: no.** Named exactly once, at M0, before ten more
milestones existed to potentially re-raise it, and none did — unlike
authentication's eleven-consecutive-citation record, this is a
single-citation placeholder, and `api/middleware.py`'s own docstring
already assigns it to "the reverse-proxy / gateway layer," a piece of
infrastructure this repository has never built (it doesn't build or
provision a reverse proxy, an ingress controller, or Postgres itself —
see `docs/architecture-mapping.md` §17). This document's own
authentication mechanism makes a *future* per-principal rate limit a
coherent, buildable feature (rate-limit by `principal.id`, not by
unauthenticated IP) — a real, plausible follow-on named in §12, not
built here.

### 13.6 — Key rotation/KMS custody for the signing key, encryption key, or this milestone's new authentication tokens?

**Recommendation: still unassigned**, unchanged from M11 §11's own
identical conclusion for the first two; this milestone's own token
mechanism inherits the identical "no rotation infrastructure without a
concrete forcing case" scope boundary, closed only by "revoke and issue
a new one," the same manual mechanism already accepted for the other two
secret types.

### 13.7 — OAuth2/OIDC federation, or a self-contained principal/token mechanism?

Already argued in full in §4.3. **Recommendation: self-contained** — no
external identity provider, no forcing case anywhere in this platform's
record for one.

### 13.8 — Should this milestone persist a queryable audit trail of authentication events (logins, revocations, permission denials)?

Options: **(a)** (recommended) Structured logging only
(`observability/logging.py`, unchanged) — every `AuthenticationError`/
`AuthorizationError` is already logged via this platform's existing
exception-handling pattern (§5.3), with no new persisted table.
**(b)** A new, evidentiary-shaped `auth_events` table, hash-chained or
signed the way `evidence_chain`/`population_findings` are.

**Recommendation: (a).** (b) would be a second audit system, parallel to
`audit/hash_chain.py`'s own — a real, disclosed architectural weight
this milestone's own citation trail never asks for, and no concrete
compliance/forensic requirement in this platform's record names
"who attempted to authenticate, and when" as evidentiary output the way
a `Verdict`/`Finding` genuinely is. A real, plausible future need if a
compliance requirement for access-attempt records ever materializes —
not built speculatively now, the same restraint M11 §12.10 already
applied to its own "new Admin API surface for retention/encryption
status" question.

### 13.9 — Should `System.owner` become an enforced authorization boundary now that principals exist?

**Recommendation: no.** `System.owner` (M1) has always been descriptive,
free-text metadata, never enforced anywhere in this codebase; turning it
into a real access-control boundary ("a principal may only act on
Systems where `owner` matches their own name") is a multi-tenancy-shaped
question (§4.2/§13.2), not an authentication one — it conflates "who is
calling" with "whose data may they see," the exact distinction §4.2
argues these are different problems. Left as pure metadata, unchanged.

### 13.10 — Should this milestone add a new Admin API surface for listing/managing principals, alongside the CLI?

**Recommendation: no**, mirroring M11 §7/§12.10's own identical
conclusion for a retention/encryption status surface — `PrincipalRepository.list`
exists (§5.1) for a future CLI convenience or endpoint, but no HTTP
surface is built this milestone for lack of a concrete forcing case; an
operator with database access can already query `principals` directly
for the same information every other admin-configuration table in this
schema already permits.

### 13.11 — Should ingestion credentials be scoped per-`System`/per-adapter, or one platform-wide `INGESTION` role?

Options: **(a)** (recommended for this milestone) One platform-wide
`INGESTION` role — any principal with this role may post to either
ingestion route, for any system. **(b)** A credential scoped to one
specific adapter or `System`, narrower blast radius on compromise.

**Recommendation: (a), with (b) named as a real, plausible refinement.**
(b) requires deciding how a credential's scope interacts with
auto-provisioning (§1.1 of this platform's own precedent —
`EvidenceStore.append` auto-provisions an unregistered `System` by name)
— a real design question with no concrete forcing case yet, since this
platform has exactly two adapters and no multi-tenant deployment to
motivate per-system credential isolation today. (a) closes the actual
named gap (fully anonymous ingestion) completely; (b) is a genuine future
narrowing, not a blocking requirement for this milestone.

### 13.12 — Should this milestone protect this platform's own CLIs with the same authentication mechanism, for consistency?

Already argued in full in §4.1.4. **Recommendation: no** — CLIs keep
their existing, separate, database-credential-based trust boundary; this
platform has treated database/filesystem access as sufficient
authorization for CLI-invoked operations since M1, and this milestone
does not reopen that settled question.

### 13.13 — A mismatched `reviewer` value on an authenticated `claim`/`resolve` call: reject (`422`), or silently prefer the authenticated identity? **(added by this document's own second hostile-review pass, Revision note item 9)**

Options: **(a)** (recommended) Reject with `422` if `payload.reviewer` is
present and disagrees with `principal.name` — an explicit,
client-visible failure. **(b)** Silently use `principal.name` regardless
of what the request body says, discarding a disagreeing value with no
error.

**Recommendation: (a).** (b) is exactly the undisclosed footgun the
first draft's own imprecise "drops the field" phrasing risked
introducing: a client that still believes it is asserting who is
resolving a review would have no way to discover that assertion was
silently ignored. (a) reuses `resolve()`'s own existing "reviewer must
match who claimed it" repository-level check (M9) at the API boundary
instead, a pattern this platform has already approved and shipped once;
introducing no new kind of validation, only a new place it runs. The
cost is a caller must stop sending a now-redundant field once it
switches to relying on authentication — a one-time, disclosed
integration change for any caller that adopts the new credential,
not a standing ambiguity.
