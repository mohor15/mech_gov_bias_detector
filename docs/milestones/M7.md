- **`observability/metrics.py`** — `check_db_reachable`,
  `get_system_health_metrics`, `get_governance_health_metrics`,
  `get_metrics`; `SystemHealthMetrics`/`GovernanceHealthMetrics`/`MetricsResponse`.
  The staleness query is the specified `LEFT JOIN` anchored on `ACTIVE`

  the shadow/production disagreement join goes through
  `plugin_registrations` exactly as specified (§4.2, point 4), with a

  `findings(evaluated_at, policy_id, outcome)`,
  `population_findings(population_policy_id, system_id, evaluated_at)` —
  no existing table altered, per §6/§13.13.
- **No sandbox-timeout counter, no change to `plugins/sandbox.py`** —
  §13.11's reversal, honored exactly: a process-local metric was never
  built.
- **No dashboard, no UI, no new authentication** — §13.2/§13.10, as
  designed.

## Production-Readiness Review

Performed after implementation, before freeze — mirroring M0–M6's own
finalization passes.

**Finding (fixed): a migration comment containing a colon directly
followed by a word is parsed as a bind parameter, even inside a SQL
comment.** Migrations `0017`–`0019`'s first drafts explained the index's
purpose using phrases like "since :since" — `db.migrate.apply_migrations`
applies each file via SQLAlchemy's `text()`, which scans the *entire*
string for `:name`-shaped placeholders regardless of SQL comment syntax,
so this failed with "a value is required for bind parameter" before the
`CREATE INDEX` ever ran. Fixed by rewording every affected comment to
spell out "a given timestamp" instead, with an explicit warning left in
migration `0017` for whoever writes the next one.

**Finding (fixed): `ruff`'s B008 rule doesn't recognize `Query(default=None)`
as the safe FastAPI idiom for every parameter type.** Verified directly,
not assumed: the identical call already in this codebase
(`api/admin/population_findings.py`'s `system_id: str | None = Query(default=None)`,
M6) passes `ruff check` cleanly, but the same call shape for
`since: datetime | None` in the new `api/admin/metrics.py` was flagged —
ruff's bugbear exemption logic distinguishes by the parameter's annotated
type, not just the call. Fixed the same way this project already fixed
the identical false positive for `Depends` — `pyproject.toml`'s own
`[tool.ruff.lint.flake8-bugbear] extend-immutable-calls` — by extending
it to include `fastapi.Query` too, rather than scattering a
`# noqa: B008` on one line.

**Finding (fixed): an unreachable database could hang `/readyz` for well
over a minute instead of failing fast.** Found by actually connecting to
a bad host:port during implementation, not by reasoning about it in the
abstract: `psycopg`/libpq's default connection behavior on a silently-dropped
route (not a fast "connection refused") retries for the OS's full
TCP-retransmission timeout. An unbounded readiness check is worse than no
readiness check — the one thing it must never do is take longer to fail
than the orchestrator polling it is willing to wait. Fixed in
`db/session.create_db_engine` (a bounded `connect_timeout`, benefiting
every consumer of the shared engine, not just `/readyz`), not narrowly in
`check_db_reachable` alone.

**Finding (fixed): the readiness/reachability check proved connectivity
and authentication, but not the thing its own docstring claimed.**
`check_db_reachable`'s first implementation ran a bare `SELECT 1` — a
query that touches no table at all, so it would report "reachable" even
for a `gov_platform_app` role that could authenticate but had every table
grant revoked, which is a real, distinct failure mode from "can't
connect." Fixed to read one row from `systems` (the smallest table, and
the one every ingestion request already touches first via
auto-provisioning) instead, so the check actually exercises a real table
grant, not just a network path.

**Reviewed, no issue found:**
- **`/v1/admin/metrics` under a genuine database failure**, verified
  directly against a real unreachable database (not assumed): falls
  through to `api/app.py`'s existing generic exception handler and
  returns a clean `500`, exactly as designed (§7) — deliberately
  *not* mirroring `/readyz`'s `503`. (`TestClient`'s default behavior
  re-raises server-side exceptions instead of converting them, for
  debugging convenience — verifying this required
  `TestClient(app, raise_server_exceptions=False)` to see the real,
  production-equivalent response; worth knowing for anyone else
  debugging this class of thing later.)
- **`db_latency_ms`'s real meaning.** It reflects whichever connection
  the pool happens to hand back — a fresh connect or an already-warm
  pooled one — not a steady-state query-latency signal. Not a defect,
  but worth naming explicitly for whoever consumes this field later
  rather than leaving it to look more precise than it is.
- **Three separate connection checkouts per `/v1/admin/metrics` call**
  (one in `check_db_reachable`, one `Session` for system-health queries,
  one for governance-health queries) rather than one shared connection.
  Not a correctness issue, and consistent with this milestone's own
  explicit "no caching, no premature optimization" scope decision
  (§13.6) — a reasonable, low-priority future consolidation, not a gap
  found late.
- **The new `connect_timeout` applies to every consumer of
  `db.session.create_db_engine`** (the app, `population_engine/run_policies.py`,
  both `audit/verify_*` CLIs) — checked that this is a strict improvement
  for all of them (previously unbounded, now bounded), not a narrowly-scoped
  fix with an unreviewed side effect elsewhere. `db.migrate` and
  `infra/ci/setup_test_role.py` build their own connections separately and
  are unaffected, which is correct — they are ops-time tools outside the
  request path `/readyz` protects.

**Named, not fixed — deliberate scope boundaries, not gaps found late:**
- No authentication on the two new endpoints (§13.10) — the fourth
  consecutive milestone widening this gap, restated, not newly
  discovered.
- No caching/materialization of metrics (§13.6), no dashboard/UI
  (§13.2), no sandbox-timeout signal (§13.11) — all deliberate, all
  named at design time, all confirmed present exactly as scoped.

## TL;DR

**M7 owns**, per the (thin) frozen record, two named things under one
architecture section (§9, "Monitoring"):

1. **System- and governance-health metrics** (and, per the same sentence,
   "dashboards" — see §13.2, the second-highest-stakes call in this
   document, on why this review recommends M7 build the former and
   explicitly not the latter).
2. **A real readiness check** — `api/health.py` already names this
   precisely: verifying Evidence Store *writability* and (now that they
   exist) adapter/source *reachability*, replacing `/healthz`'s current
   liveness-only placeholder, which has been explicitly flagged as
   incomplete since M0.

Read against six milestones of this project's own consistent discipline
(no infrastructure without a real, current case that needs it; a fixed,
named set of concrete things over a configurable framework; additive
retrofits that never silently change an existing endpoint's contract),
this review's central recommendation is: **M7 ships a small, fixed set of
governance- and system-health counters exposed over a new, DB-query-backed
JSON metrics endpoint — not a Prometheus/OpenTelemetry stack, and not a
UI** — plus a new `/readyz` endpoint alongside the unchanged `/healthz`.
This is the direct architectural sibling of M6's own "Event Lake is a new
read pattern, not new storage" call (§13.1, this document), applied to
metrics instead of population windows.

**Seventeen ambiguities** are identified below (§13), each with a
recommendation — fourteen from the original design pass, plus three more
found during a subsequent hostile-review pass (§13.15–§13.17). Two are
the highest-stakes calls in this document: §13.1 (does "Monitoring" mean
a real metrics-infrastructure stack, or a minimal, DB-backed endpoint
consistent with this platform's established minimalism) and §13.2 (does
M7 build any dashboard/UI at all, given its own citation says
"dashboards" in the same breath as M10's own name, "Compliance
Dashboard"). The hostile-review pass's own most consequential finding is
§13.11's reversal: a process-local timeout counter that silently produces
wrong numbers under the exact horizontal-scaling scenario this platform's
own architecture names as a real future concern. Skip to §16 for the
plain approval checklist.

## 1. What M7 is exactly responsible for

Both citations, read together, name two genuinely different kinds of
"health":

1. **System health** (operational). Is the platform itself functioning:
   can it reach Postgres, is the Evidence Store actually writable (not
   just "the process didn't crash"), are adapters/sources reachable. This
   is `api/health.py`'s own explicitly-named gap, unresolved since M0's
   own finalization review flagged it and deferred it.
2. **Governance health** (meta-level, about what the platform is
   observing, not about the platform's own uptime). Aggregate signal
   about the governance decisions themselves: how many verdicts landed
   in each status, how often each policy flags, how often population
   findings flag, how much shadow policies disagree with production ones
   — none of which has any query surface today. Every milestone since M4
   has named and declined "a query API for verdicts/findings by status"
   as out of scope (M5 §13.7 explicitly: *"a query API doesn't exist yet
   for any status... isn't a new gap M5 introduces"*); M7's own citation
   is the first milestone whose stated job requires building one.

**What M7 explicitly is not**, read against every other architecture
section's own citation: a general, pluggable Evaluation Framework
(architecture §10) is M8 — M7 exposes metrics *about* verdicts and
findings, it does not add new ways of computing them. The Compliance
Dashboard (architecture §11) is M10 — see §13.2 for the full boundary
argument. The Human Review Workflow (architecture §12) is M9. Periodic
report generation (architecture §14, Reporting) is M12. Encryption/
retention is M11. Authentication on any endpoint, including whatever M7
adds, remains the standing `M5+/M13` gap this review does not close
either (§13.10).

## 2. How M7 builds on M6

M0 through M6 built five real, persisted signal sources with no shared
read surface over any of them: `verdicts`/`findings` (per-event, M0–M5),
`shadow_findings` (per-event, shadow-only, M3), `evidence_chain`
(hash-chained ledger, M1/M5), `population_findings` (per-window,
system-scoped, M6), and `plugin_registrations`/`policy_bindings`/
`population_policy_bindings` (operational/admin state, M3/M5/M6). Every
one of these is currently readable only by direct database access or, for
a handful, by fetching individual rows through an Admin API with no
aggregation. M7 is not a new pipeline stage and not a new plugin port —
unlike M6, which added a genuinely new, parallel computation (population
policies producing new findings), **M7 adds no new domain computation at
all**. It is purely a new *read* surface over data every prior milestone
already produces, plus one new, narrowly-scoped health check. This is the
first milestone since M1 that plausibly needs zero new persisted domain
state — worth naming as a real, distinguishing characteristic of this
milestone's shape (see §13.5's schema recommendation).

M6's own "Event Lake" precedent (§13.2 of that milestone: *"no new
storage — a new read pattern over existing tables"*) is the direct
architectural template this review recommends reusing here, one layer up:
metrics are a new read pattern over `verdicts`, `findings`,
`shadow_findings`, `population_findings`, and `plugin_registrations` —
not a new metrics-store technology.

## 3. Why each piece exists architecturally

**System-health / readiness.** `/healthz` has returned a hardcoded
`{"status": "HEALTHY"}` regardless of database state since M0 — a
known-and-named gap, not a new discovery. A real deployment behind an
orchestrator (Kubernetes, ECS) uses a readiness probe to decide whether to
route traffic to an instance at all; an instance that can't reach Postgres
should stop receiving ingestion traffic, not accept it and fail every
request. This is the same "fail loud, not silent" discipline `EvidenceStore`
already applies to a mid-transaction resolution failure (M2 §10) — a
readiness check is the operational analogue at the process-health level.

**Governance-health metrics.** A governance platform whose only way to
answer "how many decisions has this system flagged this week" is a raw
SQL query against production is missing the actual point of the
platform's own stated purpose — the same argument M2 §2 made for why
Protected Attribute Resolution needed a real consumer, not
infrastructure nobody calls, applied here to the *aggregate* view of
every governance decision this platform has made so far.

## 4. Proposed architecture (this review's recommendation)

### 4.1 A new `/readyz` endpoint, additive — `/healthz` stays exactly as it is

`api/health.py`'s own docstring already frames this as an *addition*
("a readiness check... is explicitly called out as a gap to close"), not
a redefinition of what `/healthz` means. `/healthz` keeps its current,
tested, zero-dependency contract (process liveness only); `/readyz` is
new, checks a cheap DB round trip (see §13.7 on why this is a read check,
not a write), and returns `503` if the database is unreachable. This
mirrors the exact discipline every prior milestone has applied to an
existing endpoint's contract (M2's "byte-for-byte unchanged" for the
prior ingestion route; M6's unchanged `IngestionResponse`) — applied here
to `/healthz` specifically, which is the one endpoint every real
deployment's orchestrator already depends on.

**Revised, hostile-review pass — the "adapter/source reachability" half
of `/readyz`'s own cited scope, named rather than silently dropped.** The
first design draft's `/readyz` only checked database reachability,
silently narrowing `api/health.py`'s own two-part citation
("Evidence Store writability *and* ... adapter/source reachability")
without saying why — inconsistent with this project's own standing
discipline of naming every deferral explicitly rather than letting one
quietly disappear (the same discipline that makes M2's, M5's, and M6's
own deferred-items sections trustworthy at all). The honest reason:
neither first-party `Adapter` has a real external dependency to check
today — `CreditScorecardAdapter`'s own docstring states plainly "there is
none to connect to yet." Checking "adapter/source reachability" against
zero real sources is vacuous, not deferred scope. `/readyz` is therefore
database-connectivity-only *for now*, named as a real, temporary scope
narrowing (not a silent one) — revisit the moment a first-party `Adapter`
gains a genuine external dependency (a live upstream API, a message
queue) to check.

### 4.2 A single, read-only, DB-query-backed metrics endpoint — not a metrics-store technology

**Recommendation: `GET /v1/admin/metrics`, a plain JSON aggregate,
computed on demand from existing tables via SQL, no new persisted
state.** Not Prometheus text format, not OpenTelemetry, not a metrics
database — this platform has one deployment environment, no established
scraping infrastructure (`docker-compose.yml` provisions nothing metrics-
related), and no second case to design a real metrics-store integration
against, the identical "no second deployment environment to design
correctly against yet" reasoning M5 §13.8 already applied to signing-key
custody. See §13.1 for the full options considered and why this is the
recommended middle ground: richer than nothing, far short of a real SRE
stack this platform has no operational need for yet.

**A fixed, named set of metrics — not a configurable/extensible
framework.** Mirrors M4 §13.3's rejection of weighted aggregation and M6
§13.9's rejection of a general population-metrics framework: no second
metric-definition case exists yet to justify a plugin surface for
metrics themselves.

Proposed concrete metrics, grounded in what already exists and has no
query surface today:

- **System health**: DB reachability + latency (feeds `/readyz` too);
  `evidence_chain`'s latest sequence number (a coarse ingestion-volume/
  liveness signal — see the hostile-review-pass correction below on how
  this must be computed); plugin counts by `(plugin_type, lifecycle_state)`
  (how many `ADAPTER`/`POLICY`/`POPULATION_POLICY` registrations are
  `DRAFT`/`SHADOW`/`PRODUCTION` — direct visibility into rollout state
  `api/admin/plugins.py` today only exposes as a flat list); each active
  `PopulationPolicyBinding`'s most recent `population_findings.evaluated_at`
  (a **staleness** signal — "when did this binding last actually run,"
  the natural operational question M6's own batch-job design raises and
  never answers itself — see §13.12, and the hostile-review-pass
  correction below on the join direction this actually requires).
- **Governance health, over a bounded recent window** (see §13.15's
  correction — the first design draft omitted this entirely): verdict
  counts by `status`; finding counts by `(policy_id, outcome)`;
  population finding counts by `(population_policy_id, outcome)`;
  shadow-vs-production disagreement rate.

Not proposed: per-request tracing, latency histograms, anything requiring
instrumentation inside the request path itself beyond what structured
logging (M0) already captures — a real APM concern, no milestone has
named it, not manufactured here.

**Revised, hostile-review pass — four corrections to the metrics
themselves, found before implementation:**

1. **Governance-health metrics need an explicit time window — the first
   draft's own motivating example ("how many decisions has this system
   flagged *this week*," §3) already assumed one, but §7/§8's proposed
   endpoint and response shape never actually specified or exposed it.**
   `verdicts`, `findings`, and `population_findings` are unbounded,
   append-mostly tables with no retention policy (M11 not built) — an
   all-time `COUNT(*) ... GROUP BY status` gets slower, without limit, for
   as long as this platform runs. `GET /v1/admin/metrics` now takes a
   `?since=<ISO 8601>` query parameter (default: the last 24 hours,
   matching the index in §6), and every governance-health count is scoped
   to `created_at`/`evaluated_at` `>= since`. See §13.15 and the revised
   §7/§8 below.
2. **`evidence_chain`'s "length" must never be computed as `COUNT(*)`.**
   Postgres has no fast row-count path under MVCC — `COUNT(*)` on an
   ever-growing table is a full table scan, and gets slower forever. The
   correct, already-established query
   (`EvidenceStore._latest_hash`'s own pattern: `ORDER BY sequence_number
   DESC LIMIT 1`, or equivalently `MAX(sequence_number)`) is O(log n) via
   the existing primary-key index. The field is renamed
   `evidence_chain_latest_sequence_number` (not `..._length`) specifically
   so its own name doesn't invite a future implementer to reach for
   `COUNT(*)` — see §13.16 and the revised §8 below.
3. **The staleness query (§13.12) must `LEFT JOIN` from active
   `population_policy_bindings`, never aggregate starting from
   `population_findings`.** A binding that has never once produced a
   finding — the single most important case this metric exists to catch
   — would be silently absent from a `GROUP BY` over `population_findings`
   alone, rather than surfaced as `staleness: null` (never ran). See
   §13.17.
4. **`shadow_disagreement_rate_by_policy`'s actual join path is more
   intricate than the flat response field suggests, named here rather
   than left to be discovered at implementation time.**
   `shadow_findings` has no `policy_id` column — only
   `plugin_registration_id` (a foreign key to `plugin_registrations`).
   Computing this metric requires: `shadow_findings JOIN plugin_registrations
   ON shadow_findings.plugin_registration_id = plugin_registrations.id`
   to recover `(plugin_id, version)`, then a second join back to
   `findings` filtered to the `PRODUCTION` registration sharing the same
   `plugin_id` (`policy_id`) family, matched on `decision_event_id`, to
   get the outcome the shadow candidate is actually being compared
   against. Not a blocking issue — the data to do this exists — but
   asserting the metric as a one-line `dict[str, float]` without naming
   this join path risked it being underestimated at implementation time
   the way M6's own first draft underestimated `PopulationWindow`'s real
   query cost (see `docs/milestones/M6.md` §13.3's revised note).

**Reviewed, no issue found, but stated explicitly rather than left
ambiguous:** the metrics endpoint issues several independent aggregate
queries (one per metric category), not one transaction under a fixed
isolation level the way `population_engine/window.py` uses `REPEATABLE
READ` for its own multi-statement read. This is a deliberate choice, not
an oversight — a monitoring endpoint answering "roughly how is the
platform doing right now" tolerates brief cross-metric skew under
concurrent writes the same way any real metrics system (Prometheus
included) does; unlike M6's `PopulationWindow`, nothing here is persisted
as an evidentiary record whose internal consistency could later be
audited or signed. `REPEATABLE READ` is deliberately *not* proposed here.

### 4.3 No dashboard, no UI

See §13.2. This platform has never built a UI anywhere — every surface to
date is a JSON API. "Dashboards" in §9's own citation is read as
describing what a *future* consumer (M10's Compliance Dashboard) would
render from the metrics M7 exposes, not a deliverable of M7 itself.

## 6. Database schema changes (proposed)

**None.** Every metric in §4.2 is computed by `SELECT`/`GROUP BY` queries
against existing tables — no new table, no new column. The one concrete,
required addition is **indexes** to support the new aggregate-query
access pattern this milestone introduces, the identical situation M6 §6
was in for its own windowed reads:

```sql
-- Supports "verdict counts by status since :since" -- verdicts has no
-- index shaped for a time-bounded status count today. created_at leads
-- the composite so a `WHERE created_at >= :since` range scan can still
-- use the index to group by status -- see §4.2's revised, now-mandatory
-- time window.
CREATE INDEX idx_verdicts_created_at_status ON verdicts (created_at, status);

-- Supports "finding counts by (policy_id, outcome) since :since".
CREATE INDEX idx_findings_evaluated_at_policy_id_outcome
    ON findings (evaluated_at, policy_id, outcome);

-- Supports "population finding counts by (population_policy_id, outcome)
-- since :since" AND the per-binding staleness query (most recent
-- evaluated_at per population_policy_id/system_id -- see §4.2's revised
-- LEFT JOIN requirement, §13.17).
CREATE INDEX idx_population_findings_policy_system_evaluated_at
    ON population_findings (population_policy_id, system_id, evaluated_at);
```

`evidence_chain`'s existing primary key (`sequence_number`) already
supports `ORDER BY sequence_number DESC LIMIT 1` with no new index — see
§4.2's revised guidance on why this must never become `COUNT(*)`.

The staleness query is a `LEFT JOIN` from `population_policy_bindings`
(filtered to `ACTIVE`) to `population_findings`, aggregated by
`MAX(evaluated_at)` per `(population_policy_id, system_id)` — a binding
with zero matching rows on the right-hand side must still appear in the
result, with `evaluated_at: null`, not be silently absent (§4.2's
revision, §13.17).

No privilege changes needed — every table these queries read already
grants `gov_platform_app` `SELECT` (operational tables) or `SELECT`
(the append-only tables, which already allow `SELECT`). Metrics are
read-only from this milestone's perspective; nothing about `/v1/admin/metrics`
needs `INSERT`/`UPDATE` on anything.

## 7. Public API changes (proposed)

```
GET  /readyz                              -- 200 if DB reachable, 503 otherwise; separate from /healthz
GET  /v1/admin/metrics?since=<ISO 8601>   -- one JSON aggregate; since defaults to now - 24h
```

**Revised, hostile-review pass:** `?since` is new, required by §4.2's
time-window correction (§13.15) — omitted from the first design draft
entirely. System-health metrics (plugin counts, staleness, the evidence
chain's latest sequence number) are **not** windowed by `since` — they
describe current state, not recent activity, so a time filter has no
meaning for them; only the governance-health half of the response is
scoped to the window.

**Reviewed, no issue found, but named explicitly:** if the database is
unreachable, `/v1/admin/metrics` falls through to `api/app.py`'s existing
generic `Exception` handler (a `500`), the same behavior every other
DB-touching Admin API endpoint already has today — deliberately *not*
mirroring `/readyz`'s `503`. A readiness probe's job is specifically "is
this instance safe to route traffic to," which `503` communicates to an
orchestrator; an Admin API call failing because its one dependency is
down is an ordinary server error, the same category every existing
`GET /v1/admin/*` endpoint already falls into on a DB failure. Named here
so the asymmetry reads as reviewed and intentional, not an inconsistency
nobody noticed.

No changes to any existing endpoint's request or response shape —
`/healthz`, both ingestion routes, and every existing Admin API surface
are byte-for-byte unchanged.

## 8. New domain models

```python
class SystemHealthMetrics(BaseModel):
    model_config = ConfigDict(frozen=True)

    db_reachable: bool
    db_latency_ms: float | None
    # Renamed from evidence_chain_length (hostile-review pass, §13.16):
    # the old name invited a COUNT(*) implementation -- a full table scan
    # on an unbounded, ever-growing table under Postgres's MVCC storage.
    # Always MAX(sequence_number) / ORDER BY ... DESC LIMIT 1 (O(log n)
    # via the existing primary key), never COUNT(*).
    evidence_chain_latest_sequence_number: int
    plugin_counts: dict[str, dict[str, int]]  # plugin_type -> lifecycle_state -> count
    # binding id -> last evaluated_at, or None if that ACTIVE binding has
    # never produced a finding at all -- requires a LEFT JOIN from
    # population_policy_bindings, never an aggregate starting from
    # population_findings (§13.17), or a never-run binding is silently
    # absent instead of showing None.
    population_binding_staleness: dict[str, datetime | None]
    # Process-local only if ever implemented -- see §13.11's reversal.
    # Deferred out of M7 entirely; field removed from this milestone's
    # response shape.


class GovernanceHealthMetrics(BaseModel):
    model_config = ConfigDict(frozen=True)

    window_start: datetime  # hostile-review pass, §13.15 -- was missing entirely
    window_end: datetime
    verdict_counts_by_status: dict[str, int]
    finding_counts_by_policy: dict[str, dict[str, int]]  # policy_id -> outcome -> count
    population_finding_counts_by_policy: dict[str, dict[str, int]]
    # See §4.2's revised note: shadow_findings has no policy_id column of
    # its own -- computed via plugin_registration_id -> plugin_registrations
    # -> the PRODUCTION registration sharing the same plugin_id, matched
    # to `findings` on decision_event_id.
    shadow_disagreement_rate_by_policy: dict[str, float]


class MetricsResponse(BaseModel):
    model_config = ConfigDict(frozen=True)

    system: SystemHealthMetrics  # current state -- not windowed
    governance: GovernanceHealthMetrics  # scoped to [window_start, window_end)
    computed_at: datetime
```

Deliberately flat, deliberately not persisted — `MetricsResponse` is a
read-time view, the same relationship `EvidenceRecord` has to
`GovernanceVerdict`, except with no backing row at all.

## 12. Expected production-readiness review points

- **Metrics computed on-demand, per request, with no caching.** A
  monitoring scraper polling `/v1/admin/metrics` every few seconds would
  put real, avoidable aggregate-query load on the primary OLTP database —
  the identical class of concern M6 §12 named for the unindexed windowed
  read, now for a query pattern with a much shorter expected polling
  interval. The indexes in §6 keep individual queries cheap; they do not
  prevent a naive, too-frequent polling client from adding load no
  milestone has designed a caching layer for.
- **`/readyz` must stay cheap.** An orchestrator can call a readiness
  probe every few seconds; if it runs a heavy aggregate query instead of
  a trivial connectivity check, the readiness check itself becomes a load
  source. §13.7 argues for a plain connectivity check, not a real write —
  worth restating here as the concrete operational reason, not just an
  architectural preference.
- **No authentication on `/v1/admin/metrics`** — the same standing gap
  M5 and M6 both named, arguably relevant again here: aggregate
  governance-health numbers ("12% of this system's decisions were
  `RECOMMEND_HOLD` this week") are themselves a compliance-sensitive
  signal about a real system, closer in kind to M6's own
  `population_findings` exposure than to M3's plugin-lifecycle listing.
- **A fixed metric set with no versioning story.** Adding a new metric
  later is easy (additive); changing what an existing metric *means*
  (e.g., redefining "disagreement rate") has no migration story for a
  consumer that started depending on the old definition — worth naming,
  not solved here, the same "no data migration, no data corruption"
  discipline `schemas/verdict.py`'s permanent legacy enum members already
  established for a different kind of meaning-change.

## 13. Architectural ambiguities, with my recommendation for each

### 13.1 — Does "Monitoring" mean real metrics infrastructure (Prometheus/OpenTelemetry), or a minimal, DB-backed endpoint? **(the highest-stakes call in this document)**

Options: **(a)** A real metrics stack — a Prometheus client library,
a `/metrics` endpoint in Prometheus text exposition format, possibly
OpenTelemetry tracing. This is what "Monitoring" means in most real SRE
contexts, and is the technically "correct" long-term answer for a
production governance platform. **(b)** (recommended) A plain JSON
aggregate endpoint, computed on demand via SQL, no new dependency, no new
infrastructure. **(c)** Structured-log-only — extend `observability/logging.py`
with periodic counter log lines, no new endpoint at all, relying entirely
on an operator's own external log-aggregation stack to build metrics from.

**Recommendation: (b).** This platform has exactly one deployment
environment (`infra/docker/docker-compose.yml` provisions nothing beyond
the app container itself) and no established scraping infrastructure to
integrate with — introducing Prometheus/OpenTelemetry now would be
designing against a deployment topology this project has never had a
real case for, the identical "no second deployment environment" reasoning
M5 §13.8 already applied to signing-key custody and M6 §13.2 applied to
a dedicated analytical store. (c) under-delivers on the "governance-health
metrics" half of §9's own citation — a metric only visible by grepping
logs is a much weaker deliverable than a queryable endpoint, and this
platform already has a JSON-API-only precedent for every other read
surface (the Admin API), which (b) is consistent with and (c) is not.
**If a real ARCH-GOV-002 document specifies an actual metrics/tracing
technology**, that is the one finding in this document most likely to
require a materially different design, not a parameter tweak — flagged
as prominently as this review's sourcing note already requires.

### 13.2 — Does M7 build any dashboard/UI, or is "dashboards" entirely M10's job? **(second-highest-stakes call)**

`observability/__init__.py`'s own citation names "metrics/dashboards" in
one breath, and `architecture-mapping.md` §11 separately names "Compliance
Dashboard" as M10. Options: **(a)** M7 builds a real UI (even a minimal
one — a server-rendered HTML page showing the metrics from §4.2).
**(b)** (recommended) M7 builds no UI at all; "dashboards" in §9's
citation is read as describing what a *future* consumer (M10) renders
from M7's metrics, not something M7 itself delivers.

**Recommendation: (b).** This platform has never built a UI anywhere in
six milestones — every existing surface is a JSON API, a deliberate,
consistent architectural choice (`api/app.py`'s composition root has no
templating engine, no static-file serving, nothing UI-adjacent at all).
Introducing the first UI in this platform's history as a side effect of
"Monitoring," rather than as M10's own, explicitly-named, dedicated job
("Compliance Dashboard" — a name that already claims the UI), would mean
M7 quietly absorbing M10's actual reason to exist, the identical mistake
M4 §13.1 already declined for M4/M5's boundary and M6 §13.1 declined for
the ingestion-redesign question. A `MetricsResponse` JSON body is exactly
the shape a real dashboard (M10) would consume — M7 producing it and M10
rendering it is the cleaner division of labor, matching how M6 produces
`PopulationFinding` data with no consumer of its own beyond a minimal
read API. **If this reading is wrong**, this is the second most likely
finding in this document to require a different design.

### 13.3 — Readiness check: modify `/healthz` in place, or add a new `/readyz`?

**Recommendation: add `/readyz`, leave `/healthz` byte-for-byte
unchanged.** `api/health.py`'s own docstring already frames the
readiness check as an addition, not a redefinition. Every prior
milestone's own discipline for an *existing*, already-depended-on
endpoint is additive-only (M2's second ingestion route left the first
unchanged; M6's population pipeline left both ingestion routes
unchanged) — `/healthz` is the one endpoint most likely to already be
wired into a real orchestrator's liveness probe today, making an
in-place behavior change here the highest-blast-radius option available
to this milestone. Kubernetes' own liveness/readiness split is the
direct precedent for keeping the two questions ("is the process alive"
vs. "is it ready for traffic") as two separate endpoints, not one
endpoint whose meaning silently deepens.

### 13.4 — Are "system health" and "governance health" one endpoint or two?

Options: **(a)** One combined `GET /v1/admin/metrics` response with both
halves nested (§4.2/§8's proposed shape). **(b)** Two separate endpoints,
`/v1/admin/metrics/system` and `/v1/admin/metrics/governance`.

**Recommendation: (a).** Unlike `policy_bindings`/`protected_attribute_rules`
(M5 §13.4, kept as two tables because they have different keys and
shapes), system- and governance-health metrics share the same audience
(an operator or a future dashboard checking on the platform generally),
the same read cadence, and the same "no new persisted state" nature —
there's no structural reason to force two round trips for what's
naturally one "how's the platform doing" view. Splitting them can happen
later if a real second consumer (e.g., an orchestrator that only ever
wants the system half) demonstrates a reason to.

### 13.5 — A fixed, named metric set, or an extensible metrics-registration framework?

**Recommendation: fixed set** (§4.2), the same "no abstraction without a
second case" discipline M4 §13.3, M5 §13.6, and M6 §13.9 have each
already applied to their own milestone's one new computation. A plugin
surface for metrics themselves (letting a future `Adapter`/`Policy`
author register custom metrics) is a real, plausible future need — with
zero real cases today to design the right extension point against.

### 13.6 — Metrics computed on-demand per request, or precomputed/cached/materialized?

Options: **(a)** (recommended) Computed fresh on every `GET
/v1/admin/metrics` call, via SQL aggregate queries. **(b)** Periodically
materialized (a background job, or a materialized view refreshed on a
schedule) and served from a cache.

**Recommendation: (a).** This is the direct sibling of M6 §13.4's own
"CLI-invoked batch job, not a daemon/in-process scheduler" call —
introducing the first background/periodic-refresh process in this
platform's history to keep a metrics cache warm would be a materially
different operational model than anything M0–M6 built, for a milestone
whose own citation never asked for real-time freshness guarantees a
few-hundred-millisecond query can't already provide at this platform's
current, real scale. Named explicitly in §12 as a real production
caveat if polling frequency ever gets ahead of what on-demand queries can
absorb — the honest, scoped answer, not a preemptively-built cache
nothing has demonstrated a need for yet.

### 13.7 — Does the readiness check attempt a write (proving "writability" literally), or a read/connectivity check?

`api/health.py`'s own docstring says "verifies Evidence Store
**writability**" — read literally, that implies an actual write attempt,
not just connectivity. Options: **(a)** Literal: `/readyz` performs a
real (test) write against `evidence_chain` on every call. **(b)**
(recommended) A read-only connectivity check (e.g. `SELECT 1`, or reading
`evidence_chain`'s latest row) — "writability" read as "the append path
is *available*" (correct privileges, reachable role), not "prove it by
writing something on every single health check."

**Recommendation: (b).** A literal per-probe write would mean every
orchestrator's readiness poll (potentially every few seconds, per
instance, per replica) takes the `pg_advisory_xact_lock` `EvidenceStore.append`
uses and either writes a synthetic row into the permanent, hash-chained,
append-only ledger or requires inventing a separate "test write" path
that doesn't pollute it — both real, avoidable costs and complexity for
a health check, and directly at odds with §12's "readiness checks must
stay cheap" concern. A read-only check that the `gov_platform_app` role's
grants and connectivity are intact is the honest, cheap proxy for
"writes would succeed if attempted" without actually attempting one on
every poll. Flagged because it's a literal-reading deviation from the
cited docstring's exact word, the same category of judgment call M6
§13.1 flagged for its own literal-vs-read interpretation of "async
ingestion plane."

### 13.8 — Where does the metrics endpoint live: under `/v1/admin/`, or a new top-level namespace?

Options: **(a)** (recommended) `GET /v1/admin/metrics`, alongside every
other Admin API surface. **(b)** A new, separate namespace (e.g. `/v1/monitoring/metrics`
or a bare `/metrics`), reflecting that its actual audience (an operator
or monitoring system) is arguably different from "admin" (a compliance/
platform operator managing bindings and rules).

**Recommendation: (a).** Every read-only, admin-facing surface this
platform has ever built lives under `/v1/admin/` (`plugins`,
`policy-bindings`, `protected-attribute-rules`, `population-findings`,
`population-policy-bindings`) — introducing a second top-level namespace
for one more read-only endpoint would be a new organizing principle with
exactly one member, the same "no abstraction for one case" discipline
applied to routing instead of code. A bare `/metrics` (the Prometheus
convention) is declined for the same reason (a) in §13.1 was declined —
it would imply exposition-format compatibility this milestone isn't
building.

### 13.9 — Does structured logging (`observability/logging.py`) change at all?

**Recommendation: no.** `JsonFormatter`/`configure_logging` stay exactly
as M0 built them — this milestone's metrics are computed from persisted
table state, not derived from log lines, so nothing about the logging
pipeline needs to change to deliver §4.2's metric set. If a future
milestone needs log-derived metrics (e.g. request-latency percentiles,
a real APM concern no milestone has named), that's a new, separate
question — not manufactured here.

### 13.10 — Does M7 add authentication to its new endpoints?

**Recommendation: no**, restating M5 §13.11's and M6 §13.14's identical
reasoning: consistent with every existing endpoint (still none
authenticated), adding it to only the two newest would be inconsistent
scoping, not a real security improvement. Worth your explicit attention
that this is now the fourth consecutive milestone (M5, M6, M7) widening a
gap every one of these reviews has flagged rather than solved — at some
point closing it stops being deferrable by "not this milestone's job"
and becomes its own overdue milestone, a judgment call for you, not this
review to make unilaterally.

### 13.11 — Does `plugins/sandbox.py` gain new instrumentation (a timeout counter), or is that deferred? **(reversed from the first draft — hostile-review pass)**

**The first draft's "add a module-level counter" was wrong, not just
incomplete — found during the hostile-review pass, not a refinement of
an already-sound answer.** `run_sandboxed` executes inside whatever
process handles a given request. A plain Python module-level counter is
**process-local** — under the normal, expected way to scale a stateless
HTTP service (`uvicorn --workers N`, or multiple container replicas
behind a load balancer, exactly the horizontal-scaling scenario this
platform's own architecture already names as real future territory,
architecture §17/M13), each worker/replica would hold its own,
independent count. `GET /v1/admin/metrics` answered by whichever
worker happens to handle that particular request would report only
*that worker's* timeouts, silently omitting every other worker's — not
an error, not a crash, just a quietly wrong number with no signal that
anything is missing. Worse: the count resets to zero on every process
restart/redeploy, so even a single-worker deployment's "cumulative"
count is actually "count since last restart," a materially different
and undocumented meaning. This directly contradicts the one property
every *other* metric in this design correctly has: because they're all
computed from Postgres — shared, durable, identical no matter which
worker or replica answers the request — they are automatically correct
under horizontal scaling. A process-local counter is the one metric in
this document that silently breaks that property, and does so exactly
at the scale where a real deployment would actually run more than one
worker.

Options: **(a)** Persist timeout events to a new, small Postgres table
(genuinely new domain state, contradicting §2's own observation that M7
otherwise needs none). **(b)** (recommended) Defer entirely — ship M7's
other metrics with no sandbox-timeout signal this milestone. **(c)** Keep
the in-memory counter, documented loudly as "meaningless under more than
one worker/replica" — technically honest, but knowingly shipping a
metric this platform's own architecture already expects to be wrong
under a documented future scenario is a worse choice than not shipping
it at all.

**Recommendation: (b).** This is the identical "no second deployment
environment to design correctly against yet" reasoning §13.1 and §13.6
already apply elsewhere in this same document — applied here to a
metric's *storage*, not just to the endpoint's own infrastructure choice,
for consistency rather than smuggling in an exception to a principle
this document otherwise holds throughout. `plugins/sandbox.py` stays
completely untouched by M7; a real fix (a durable, cross-process counter)
is real scope for whichever milestone first needs to design correctly
against an actual multi-replica deployment — not invented speculatively
here. `PluginTimeoutError` occurrences remain visible via the existing
structured log line (`api/app.py`'s `plugin_timeout_handler`) in the
meantime — a real, if less convenient, signal that already exists and
needs no code change to keep working.

### 13.12 — Does M7 expose per-binding population-policy-run staleness ("when did this last actually run")?

A genuinely new operational question M6's own design raises and never
answers: since `population_engine/run_policies.py` is an explicitly-
invoked batch job, not a daemon (M6 §13.4), nothing today tells an
operator whether it's actually being run on schedule, or silently
stopped weeks ago. Options: **(a)** (recommended) Include it in
`SystemHealthMetrics` (§4.2/§8) — the most recent `population_findings.evaluated_at`
per active `PopulationPolicyBinding`, letting an operator (or a future
alerting rule) notice "this binding hasn't produced a finding in 9 days."
**(b)** Defer — M7 ships governance-health metrics for findings that do
get produced, silent on whether they're being produced on the expected
cadence at all.

**Recommendation: (a).** This is a direct, load-bearing consequence of
M6's own architecture (an async plane with no built-in scheduling, per
M6 §13.4/§15 — "real scheduling... deployment/M13-adjacent, not built")
— without a staleness signal, a silently-stopped cron entry is
invisible until someone thinks to check by hand. Cheap to add (one more
query over `population_findings`, per §6's index) — **but see §13.17,
found during the hostile-review pass: the query must be a `LEFT JOIN`
from `population_policy_bindings`, not a plain aggregate over
`population_findings`, or the exact failure case this metric exists to
catch is the one case it cannot see.** This directly
closes a gap the immediately-prior milestone's own design explicitly
named as deployment-topology's job, not M6's — this review reads that as
M7's opening, not an unrelated scope grab.

### 13.13 — What indexes does this milestone require, and were they sized against real query shapes?

**Recommendation: the three indexes in §6**, elevated to a concrete
requirement in this document from the start (unlike M6's own first draft,
which under-scoped this and had to correct it during its hostile-review
pass) — `verdicts`, `findings`, and `population_findings` currently have
no index shaped for "count by status/outcome," and every metric in §4.2
needs exactly that shape. Named here explicitly so this milestone doesn't
repeat M6's own documented mistake of treating a required index as
optional in the first design pass.

### 13.14 — Does the M7/M8/M12 boundary need explicit disambiguation the way M7/M10 does?

`architecture-mapping.md` §10 (Evaluation Framework, M8) and §14
(Reporting, M12) are both plausibly adjacent to "metrics" in casual
reading. **Recommendation: name the boundary explicitly, don't just rely
on context.** M8 is about *computing new statistical judgments*
(more population-level metrics, configurable thresholds) — M7 exposes
counts *of* judgments already computed by M0–M6, it computes no new
governance judgment of its own. M12 (Reporting) is periodic,
document-shaped output (the kind of thing compliance teams file, not
poll) — a different cadence and audience than an on-demand JSON endpoint.
Neither boundary is as contested as M7/M10's (§13.2), but naming both
here means a future milestone's own review doesn't have to rediscover
the distinction from scratch, the same service this document's own §14
list already provides for M9/M10/M11/M13.

### 13.15 — Do governance-health metrics need an explicit time window, or is an all-time cumulative count acceptable? **(found during the hostile-review pass)**

`verdicts`, `findings`, and `population_findings` are unbounded,
append-mostly tables with no retention policy (M11 not built, and
`evidence_chain`'s own append-only guarantee means nothing in this
platform's history has ever been deleted). Options: **(a)** All-time
cumulative counts — the first design draft's implicit shape (§4.2/§8
originally had no window at all). **(b)** (recommended) A bounded,
recent window (`?since=<ISO 8601>`, default the last 24 hours),
governance-health counts scoped to it.

**Recommendation: (b).** Two independent problems with (a), found during
the hostile-review pass, not just a stylistic preference: first, it
directly contradicts this same document's own motivating example (§3:
*"how many decisions has this system flagged this week"* — a windowed
question, not an all-time one) — the design as originally drafted
couldn't actually answer the question it used to justify its own
existence. Second, an unindexed-for-this-purpose, all-time
`COUNT(*) ... GROUP BY` over a table with no upper bound on size gets
slower without limit for as long as the platform runs, the identical
class of risk M6 §12 named for an unindexed windowed read, except here
compounding indefinitely rather than being fixable by one index alone —
even a well-indexed all-time scan still touches more rows every single
day this platform stays in production. A recent, bounded window keeps
every query's cost roughly constant regardless of how long the platform
has been running. See the revised §4.2/§7/§8 above for the concrete
`?since` parameter and schema change this requires.

### 13.16 — How is `evidence_chain`'s "length" computed? **(found during the hostile-review pass)**

Options: **(a)** `SELECT COUNT(*) FROM evidence_chain`. **(b)**
(recommended) `SELECT sequence_number FROM evidence_chain ORDER BY
sequence_number DESC LIMIT 1` (equivalently `MAX(sequence_number)`).

**Recommendation: (b), and the field is renamed accordingly** (see the
revised §8: `evidence_chain_latest_sequence_number`, not
`evidence_chain_length`). Postgres's MVCC storage model has no
maintained, O(1) row count for a table — `COUNT(*)` is a sequential scan
proportional to table size, a well-known Postgres gotcha, not an
implementation detail this milestone can afford to leave to whoever
happens to implement it first. `evidence_chain` is, by design,
permanent and never shrinks (M1's append-only guarantee, enforced at the
database-privilege level) — it is exactly the table in this entire
schema where a `COUNT(*)`-shaped mistake compounds the most severely and
the longest. `EvidenceStore._latest_hash` already reads the tail row via
`ORDER BY sequence_number DESC LIMIT 1` for an unrelated reason (finding
the previous hash to chain from) — `(b)` reuses the exact same,
already-proven-cheap access pattern via the existing primary key index,
rather than inventing a second, more expensive way to answer a similar
question. The field rename is deliberate, not cosmetic: a name literally
containing "length" invites exactly the `COUNT(*)` mistake this
recommendation exists to prevent.

### 13.17 — Does the staleness query start from `population_findings` or from `population_policy_bindings`? **(found during the hostile-review pass)**

Options: **(a)** `SELECT population_policy_id, system_id, MAX(evaluated_at)
FROM population_findings GROUP BY population_policy_id, system_id` — a
plain aggregate. **(b)** (recommended) `SELECT ... FROM
population_policy_bindings LEFT JOIN population_findings ON ... WHERE
population_policy_bindings.lifecycle_state = 'ACTIVE' GROUP BY ...` — a
left join anchored on the bindings, not the findings.

**Recommendation: (b).** Option (a) has a real, silent failure mode:
a `PopulationPolicyBinding` that has never once produced a finding —
because it was just created and the batch job hasn't run yet, or
because it's been quietly broken since the day it was created — has
**zero matching rows** in `population_findings`, so a `GROUP BY` starting
from that table never produces a row for it at all. The resulting
`population_binding_staleness` map would simply omit that binding,
indistinguishable from "this binding doesn't exist" to any consumer —
exactly backwards from what a staleness metric is for, which is making
"this is not producing results" *more* visible, not silently dropping
the worst offender from the report entirely. A `LEFT JOIN` anchored on
`population_policy_bindings` guarantees every currently-`ACTIVE` binding
appears in the result, with `evaluated_at: null` read as "never ran, ever"
— the loudest possible staleness signal, not an absence.

## 14. What M7 owns

1. **`GET /readyz`** — a real, cheap, read-only dependency check
   (database connectivity only — "adapter/source reachability" is
   currently vacuous, §4.1), additive alongside the unchanged `/healthz`.
2. **`GET /v1/admin/metrics?since=<ISO 8601>`** — one JSON aggregate of
   system-health (current-state) and governance-health (windowed)
   metrics (§4.2/§8), computed on demand via SQL over existing tables, no
   new persisted state.
3. **Three new indexes** (`verdicts`, `findings`, `population_findings`),
   revised during the hostile-review pass to actually match the
   now-mandatory time-windowed query shape (§6/§13.15).
4. **Population-policy-binding staleness visibility**, via a `LEFT JOIN`
   anchored on active bindings (§13.17) — the direct, load-bearing
   consequence of M6's own async-plane design.

**Not owned, reversed during the hostile-review pass:** a sandbox-timeout
counter — a process-local metric would have silently broken under
horizontal scaling, the one property every other metric in this
milestone correctly has (§13.11). `plugins/sandbox.py` is untouched.

## 15. What remains deferred past M7

- **Any dashboard/UI** — explicitly M10's job (§13.2), not built here.
- **A general Evaluation Framework** (architecture §10) — M8; M7 exposes
  counts of existing judgments, computes no new ones.
- **Periodic/document-shaped reporting** (architecture §14) — M12.
- **Real metrics infrastructure** (Prometheus/OpenTelemetry, tracing,
  latency histograms) — no milestone named yet; declined for this
  milestone per §13.1, revisit if a real second deployment environment
  or a real scraping-infrastructure need ever materializes.
- **Caching/materialization of metrics** — on-demand only this milestone
  (§13.6); revisit if polling load ever demonstrates a real need.
- **All-time cumulative governance-health counts** — deliberately not
  what the default, windowed metric answers (§13.15); a distinct
  "lifetime totals" view, if ever wanted, is a separate, explicitly-named
  addition, not silently conflated with the windowed default.
- **Sandbox-timeout observability** — reversed out of this milestone
  entirely (§13.11); real scope once a genuine multi-replica deployment
  exists to design a durable, cross-process counter against.
- **Human Review Workflow** (architecture §12) — M9, still nothing
  consumes an `ESCALATE_FOR_REVIEW` verdict or a `FLAGGED`

- **Encryption at rest and retention** — M11, unaffected by M7 (no new

- **Authentication** on any endpoint, including M7's two new ones — still
  named `M5+/M13`, now a four-milestone-and-counting gap (§13.10).
- **A metrics-extensibility/plugin surface** — fixed set only this
  milestone (§13.5).

## 16. Decisions requiring your approval before implementation

A plain checklist, each referencing the fuller reasoning above:

1. **[§13.1]** "Monitoring" is built as a **minimal, DB-query-backed JSON
   metrics endpoint** (recommended), not a Prometheus/OpenTelemetry
   stack. The single highest-stakes call in this document, made against
   the thinnest citation record of any milestone so far.
2. **[§13.2]** M7 builds **no dashboard/UI** (recommended) — "dashboards"
   in §9's citation belongs to M10. The second-highest-stakes call.
3. **[§13.3]** A **new `/readyz` endpoint**, additive (recommended);
   `/healthz` stays byte-for-byte unchanged.
4. **[§13.4]** System- and governance-health metrics are **one combined
   endpoint** (recommended), not two — **amended during the hostile-review
   pass**: only the governance half is time-windowed (`?since=`); the
   system half describes current state and is never windowed (§13.15).
5. **[§13.5]** A **fixed, named metric set** (recommended), not an
   extensible metrics-registration framework.
6. **[§13.6]** Metrics are **computed on demand per request**
   (recommended), not precomputed/cached/materialized by a new
   background process.
7. **[§13.7]** The readiness check is a **read-only connectivity check**
   (recommended), not a literal per-probe write against `evidence_chain`.
8. **[§13.8]** The metrics endpoint lives at **`GET /v1/admin/metrics`**
   (recommended), alongside every other Admin API surface.
9. **[§13.9]** `observability/logging.py` is **unchanged** (recommended).
10. **[§13.10]** M7 adds **no authentication** to its new endpoints
    (recommended), consistent with every existing one — now a
    four-milestone-and-counting gap, flagged for your explicit attention.
11. **[§13.11]** **Reversed from the first draft.** `plugins/sandbox.py`
    is **not** touched — no sandbox-timeout counter this milestone. A
    process-local counter would silently produce wrong numbers under
    horizontal scaling (multiple workers/replicas), the one property
    every other metric in this design correctly avoids by being
    DB-backed.
12. **[§13.12]** System-health metrics include **per-binding
    population-policy-run staleness** (recommended) — a direct
    consequence of M6's own async-plane design. See §13.17 for the join
    direction this requires.
13. **[§13.13]** The indexes in §6 are required, not optional — revised
    during the hostile-review pass to match the now-mandatory
    time-windowed query shape (§13.15), not the original, unwindowed
    query pattern.
14. **[§13.14]** The M7/M8 and M7/M12 boundaries are named explicitly
    (recommended), alongside the more contested M7/M10 one.
15. **[§13.15]** **New, found during the hostile-review pass.**
    Governance-health metrics are scoped to a **bounded, recent window**
    (`?since=`, default 24h) — an all-time cumulative count both
    contradicts this document's own motivating example and risks an
    unbounded, ever-slower query with no upper limit on an
    ever-growing, retention-free table.
16. **[§13.16]** **New, found during the hostile-review pass.**
    `evidence_chain`'s size metric is computed via **`MAX(sequence_number)`
    / tail-row read, never `COUNT(*)`** — a classic Postgres full-table-scan
    landmine on an unbounded, permanent table — and the field is renamed
    (`evidence_chain_latest_sequence_number`) so its own name stops
    inviting the mistake.
17. **[§13.17]** **New, found during the hostile-review pass.** The
    staleness query is a **`LEFT JOIN` anchored on
    `population_policy_bindings`** (filtered to `ACTIVE`), never a plain
    aggregate starting from `population_findings` — otherwise a binding
    that has never once run is silently invisible instead of showing the
    loudest possible staleness signal.

this design, in full or with changes to any of the seventeen items above.
