## Revision note (hostile-review pass)

This document has been through a hostile-review pass (assume-it's-wrong-
until-proven-otherwise, the identical discipline M5–M9 each went through
before their own implementations began). Three findings were severe enough
to change the proposed architecture rather than just annotate it, and are
folded in below, in place, rather than kept as a separate errata section —
mirroring exactly how M9 folded in its own hostile-review corrections:

1. **§4.3/§4.4 reversed**: the packaging risk, originally described as
   "the dashboard... silently 404s," is corrected to its actual, verified
   consequence. Starlette's `StaticFiles` raises `RuntimeError` at
   *construction* time — inside `create_app()` itself — when its
   configured directory does not exist, which is exactly what a real,
   non-editable install missing `package_data` declarations produces
   (verified directly: `infra/docker/Dockerfile` runs a non-editable
   `pip install .`, the exact deployment path this risk lives on). A
   packaging mistake here does not make the dashboard unavailable — it
   prevents `create_app()` from ever returning an application object,
   taking `/healthz` down with it, the one endpoint every milestone since
   M0 has treated as an unconditional liveness signal. §4.3 now requires
   the dashboard's `StaticFiles` mount to be constructed inside a
   `try`/`except` in `create_app()`, logging loudly and skipping
   dashboard route registration on failure rather than ever letting a
   non-essential subsystem's packaging defect fail application
   construction itself — the identical "a failure in this non-essential
   subsystem must never take down what matters more" precedent M9 already
   established for its own decoupled review-row creation
   (`docs/milestones/M9.md` §3.4).
2. **§4.3 reversed**: the static assets directory moves from a new
   top-level package (`src/gov_platform/dashboard/static/`) to living
   alongside the router that serves them, under the existing `api/`
   package. The original proposal put the router in `api/` but its
   assets in a brand-new top-level package for no reason this document's
   own §3.2 reasoning would accept — this project only reaches for a new
   top-level package when nothing existing is a natural home (M9's
   `human_review/`, whose standalone CLI tool had no other place to
   live); a dashboard's static files, served by a dashboard router that
   already lives in `api/`, do not meet that bar.
3. **§4.3/§6 reversed**: the field-specific escaping guidance
   (`rationale`/`resolution_notes`/`reviewer`, named as "the" fields
   requiring `textContent`-safe insertion) is replaced with a blanket
   rule — every string value taken from any API response and inserted
   into the DOM must use safe, escaping insertion, with no exception
   list. The original three-field enumeration was not just incomplete, it
   was actively misleading: it invited an implementer to treat everything
   else as safe. `System.name` is a concrete counter-example the original
   list missed entirely — it carries no character or length restriction
   beyond `min_length=1` (`schemas/system.py`), and is auto-provisioned
   directly from the *public*, unauthenticated ingestion endpoint's
   `system_id`/`source_system` fields
   (`SystemRepository.get_or_create_by_name`, established M1), reachable
   by anyone who can call `POST /v1/ingestion/events/{adapter}` — not
   merely an unauthenticated admin endpoint. There is no closed,
   enumerable set of "the risky fields" in a platform where every write
   endpoint is unauthenticated; the requirement has to be unconditional.

Beyond these three, two findings are folded in as amendments — real gaps
that don't change the overall shape of the design but do change its
details:

- **Client-side fetch-failure handling** (§4.3/§6, new requirement):
  nothing in the original design said what `dashboard.js` does when a
  `fetch()` fails or returns a non-2xx status. This matters more here
  than for an ordinary admin tool because of a real coupling: the
  Overview page's metrics and readiness data come from the same database
  `/readyz` is reporting the health of — the moment an operator most
  needs the dashboard to work (a real outage) is also the moment its own
  data source is most likely to be failing. Every view must now render a
  visible, honest error state on a failed fetch, never a silent blank
  page.
- **§7/§8.3 amended, not reversed**: the pagination gap's consequence is
  restated from "a human-facing usability problem" to what actually
  happens at real scale. `population_findings` grows unboundedly by
  design (no retention exists until M11), and §4.1's own chosen approach
  (no DOM virtualization, no windowing library) means rendering tens of
  thousands of rows as one unbroken response is a well-known
  browser-tab-freezing failure mode, not a mild rough edge. The
  underlying recommendation — fixing pagination is M6's/M9's own API
  surface to own, not M10's additive scope to absorb — is unchanged.

Two new ambiguities were discovered during the hostile-review pass and are
folded in at §8.6 (the construction-failure containment mechanism) and
§8.7 (the router's path-prefix registration convention). Neither requires
your sign-off before implementation the way §4.1/§8.1 do; both are this
review's confident recommendations, added for completeness. Every other
decision in this document — the choice of plain HTML/CSS/vanilla JS over
a framework or templating engine (§4.1), the three proposed views (§4.2),
same-origin serving (§8.4), the read-only-vs-interactive question (§8.1),
and everything else not named above — stands unchanged.

## TL;DR

M10 builds `architecture-mapping.md` §11 ("Compliance Dashboard") — the
one deferred item every design document since M5 has pointed at by the
same two-word description ("UI", "dashboard") and never once built. The
citation trail across five milestones is unusually consistent: M7's own
Monitoring milestone explicitly declined to be this ("'Dashboards' in §9's
own citation is read as describing what a *future* consumer (M10's
Compliance Dashboard) renders from M7's metrics, not something M7 itself
delivers" — `docs/milestones/M7.md` §13.2); M9's Human Review Workflow
explicitly declined to be this too ("M10 is the Compliance Dashboard that
would actually render this data for a human" — `docs/milestones/M9.md`
§1/§8). Every milestone from M6 onward computes something a human
eventually needs to *look at*; none of them render it. This platform has
never built a UI in nine milestones. M10 is the first.

Read literally, "Compliance Dashboard" could mean anything from a single
static page to a full single-page-application framework with its own
build pipeline. Read against this codebase's own nine-milestone-long,
extremely consistent discipline — no new external dependency without a
demonstrated need (M0's stdlib-only logging, M8's stdlib
`statistics.NormalDist` over `scipy`), no new abstraction without a proven
second use case, no infrastructure without a real current case that needs
it — this review's central recommendation (§5, the highest-stakes call in
this document) is that M10 should be **the smallest thing that actually
renders what M6–M9 already compute for a human to read**: a handful of
static HTML/CSS/vanilla-JS pages, served from the existing FastAPI app,
fetching data from the JSON endpoints that already exist — `GET
/v1/admin/metrics` (M7), `GET /v1/admin/population-findings` (M6), `GET
/v1/admin/verdict-reviews` and `GET /v1/admin/population-finding-reviews`
(M9) — and **zero new endpoints, zero new database tables, zero new
external dependencies**. No SPA framework, no build tooling, no npm, no
server-side templating engine — none of that is justified by anything
this milestone actually needs to render, and inventing it now would be
exactly the kind of premature infrastructure this project has declined at
every prior opportunity.

The one genuinely new design tension this milestone introduces, not
present in any prior one: this is the first time a human-facing
*rendering* surface, not a script-facing JSON API, exposes governance-
sensitive data (bias findings, escalated verdicts, the human review
queue) — and it is the first milestone for which "no authentication yet"
(named in every design document since M2, M13's still-unclaimed job)
stops being a purely theoretical gap and starts being the single most
consequential thing this document has to say about production readiness
(§6).

A hostile-review pass (see the revision note above) found that this
milestone's own proposed serving mechanism, if implemented as first
drafted, would have reintroduced exactly the class of risk M10 is
supposed to be free of: a packaging mistake in the dashboard's static
assets would have prevented `create_app()` from constructing at all,
taking every endpoint — including `/healthz` — down with it. The
recommendation below has been corrected accordingly: the dashboard's
static-file mount is now explicitly required to fail safely, in
isolation, never the whole application; its assets live alongside the
router that serves them rather than in a new top-level package; and the
escaping requirement for dashboard-rendered data is now unconditional
(every API-sourced string, not a named few) rather than a short list that
invited an implementer to treat everything else as safe.

## 1. Scope (what M10 owns and what it explicitly does not own)

**M10 owns:**

- A small set of **read-only** HTML views rendering data this platform
  already computes and already exposes via JSON: system/governance health
  (M7), population findings (M6/M8), and the Human Review Workflow queue —
  both `VerdictReview`s and `PopulationFindingReview`s (M9).
- The minimal serving mechanism for those views: one new FastAPI router
  (`api/dashboard.py`) mounted in the existing composition root, plus a
  directory of static assets (HTML/CSS/vanilla JS), served from the
  **same** application instance and origin as every existing endpoint.
- Nothing else. No new computation, no new persisted state, no new
  Admin API surface beyond what serves the dashboard's own static
  assets and shell page.

**M10 explicitly does not own**, named here so it is not assumed by
omission — each backed by an existing citation, not a judgment call this
document is making unilaterally:

- **Authentication of any kind**, for the dashboard or anywhere else.
  Still `M13` — the seventh consecutive milestone naming this exact gap
  (M2 through M9), and the first for which the gap concerns a
  human-readable web page rather than a JSON API. See §6.
- **Any new backend computation.** M10 renders what M0–M9 already
  computed and already persisted; it does not add a new metric, a new
  population policy, a new review-workflow state, or a new verdict
  status. If a view needs data no existing endpoint provides, that is a
  gap in a *prior* milestone's API surface, not something M10 quietly
  patches over by inventing a new endpoint (§4).
- **Writing anything.** Whether the dashboard should also let a human
  *act* — claim, release, or resolve a review, directly from the page,
  rather than only view its state — is a real, undecided scope question,
  not silently assumed either way. See §8.1.
- **Periodic report generation** (architecture §14, "Reporting") — M12.
  M7 and M8 already drew this line precisely: "a different cadence and
  audience than an on-demand finding" (`docs/milestones/M8.md` §15). M10
  is on-demand, interactive, browser-rendered; M12 is periodic,
  generated, document-shaped output (e.g. a scheduled PDF/CSV export).
  This document does not blur that boundary by adding any export/
  download capability to the dashboard.
- **Encryption at rest, retention tiers** (M11) — unrelated; the
  dashboard reads through the same `Engine`/repositories every existing
  endpoint already uses, with no new persisted state of its own to
  encrypt or retain.
- **Real-time push, auto-refresh, or a notification mechanism.** M7 §13.1
  and M9 §7/§8 both already declined this for their own read/workflow
  surfaces ("no push mechanism," "the queue is pull-only"). M10's views
  are pull-only too — a human reloads the page; nothing pushes to them.
- **A general "list all Verdicts" or "list all Findings" capability.**
  M9 §4.5 already considered and declined this ("out of scope for M9
  specifically... a plausible small, independent future improvement").
  M10 does not reopen that decision by building a UI that assumes it
  exists — every view this document proposes is backed by an endpoint
  that is *already real* (§4).
- **Pagination on the endpoints it depends on.** A real, newly-surfaced
  risk (§7), but fixing `list_all`/list-endpoint pagination is a change
  to M6/M9's own repository and API contracts, not something M10's own,
  additive scope stretches to cover. Flagged, not silently absorbed —
  see §8.3.
- **Multi-tenancy, multi-plane deployment, mTLS** — unchanged, still
  M13 (architecture §17, `docs/architecture-mapping.md`'s own
  unchanged-since-M1 note).

## 2. Relationship to previous milestones

M0 through M9 built, in order: a governed ingestion pipeline (M0–M2), a
real plugin/adapter registry (M3), policy plurality (M4), policy bindings
and evidence signing (M5), an async population-policy plane (M6), a
read-only metrics endpoint (M7), a second population policy with
admin-configurable parameters (M8), and a review workflow for escalated
verdicts and flagged population findings (M9). Every one of these is a
**JSON API** — this platform, across nine milestones and every admin
surface it has built, has never rendered a single byte of HTML. M10 is
the first milestone whose entire job is presentation, not computation.

This makes M10 structurally different from every milestone before it in
one specific way worth naming precisely: M0–M9 each added a *new kind of
governed fact* (a verdict, a population finding, a review) or a *new way
of reading already-computed facts* (M7's metrics). M10 adds **no new
fact and no new read pattern** — every JSON endpoint it depends on already
exists, unmodified, exactly as M6–M9 left it. M10's only job is to put a
human-readable page in front of data that has been fully computable,
queryable, and (since M7) countable for at least two milestones already,
and in the Human Review Workflow's case, one milestone.

The specific endpoints M10 depends on, and what each already guarantees:

- **`GET /v1/admin/metrics?since=`** (M7, `api/admin/metrics.py`) — one
  JSON aggregate: system-health (current-state: DB reachability, plugin
  lifecycle counts, evidence-chain tail sequence, population-binding
  staleness) and governance-health (windowed: verdict/finding/population-
  finding counts by status, shadow-disagreement rate). Unchanged by M8/M9.
- **`GET /v1/admin/population-findings[?system_id=]`,
  `GET /v1/admin/population-findings/{id}`** (M6, `api/admin/population_findings.py`)
  — read-only, list/get. Unchanged by M8/M9 except an additive
  `parameters_used` field (M8).
- **`GET /v1/admin/verdict-reviews[?status=&severity=]`,
  `GET /v1/admin/verdict-reviews/{id}`** and
  **`GET /v1/admin/population-finding-reviews[?status=]`,
  `GET /v1/admin/population-finding-reviews/{id}`** (M9,
  `api/admin/verdict_reviews.py`/`api/admin/population_finding_reviews.py`)
  — each embeds the full `Verdict`/`PopulationFinding` its review
  references, so a single request already carries everything a rendered
  view needs (`docs/milestones/M9.md` §3.7).
- **`GET /readyz`** (M7), **`GET /healthz`** (M0) — liveness/readiness,
  already JSON, trivially renderable as a status indicator.
- **`GET /v1/admin/systems`** (M1, `api/admin/systems.py`) — already a
  list endpoint; useful as a navigational aid (e.g., a system picker for
  the population-findings view's existing `system_id` filter), not a new
  capability M10 needs to add.

Every one of these already exists, unmodified, and already returns
everything M10's proposed views need (§5). This is the reason §4 below
concludes no new endpoint is required — not an assumption, a direct
consequence of tracing what M6–M9 already built.

## 3. Architectural analysis

### 3.1 What "Compliance Dashboard" can and cannot mean, given this codebase's own history

`architecture-mapping.md` §11 names the component "Compliance Dashboard"
and nothing more — there is no fuller architecture-spec text checked into
this repository to consult beyond that name and the citations every prior
milestone has already built around it (§2 above). Read in isolation, the
phrase is compatible with anything from a single static page to a
full commercial BI product. This codebase's own nine-milestone track
record is the actual constraint, and it is unusually consistent:

- **No new external dependency without a demonstrated, current need.**
  M0 chose stdlib JSON logging over a logging library ("one line of
  JSON-formatting logic does not justify adding one" —
  `observability/logging.py`). M8 chose stdlib `statistics.NormalDist`
  over `scipy`/`numpy` for a genuine two-proportion z-test, specifically
  because the stdlib was sufficient. Every dependency this project has
  ever added (`fastapi`, `sqlalchemy`, `psycopg`, `cryptography`,
  `pydantic`) was load-bearing from the moment it was added — none was
  speculative.
- **No new abstraction without a second, real, concrete use case
  already in hand.** M4 proved `Policy` generalized by shipping a second
  real policy, not by redesigning the port first. M8 proved
  `PopulationPolicy` generalized the identical way. This document does
  not get to skip that discipline just because "dashboard" sounds like a
  green field — see §5.1's rejection of a full SPA framework on exactly
  this basis.
- **No infrastructure ahead of a real, current case for it.** M7 §13.1
  declined a Prometheus/OpenTelemetry stack because "this platform has one
  deployment environment and no established scraping infrastructure to
  integrate with" — the identical reasoning applies to a heavyweight
  frontend build pipeline here: this platform has one deployment
  environment, one small admin audience, and no established frontend
  tooling to integrate with either.
- **Additive, not a redefinition of anything existing.** Every milestone
  since M2 has left every previously-shipped endpoint's shape untouched.
  M10 must be the same: zero changes to any existing JSON response shape,
  zero changes to any existing route.

Given this, "Compliance Dashboard" is read, for this milestone, as: **the
smallest possible human-readable rendering of data this platform already
computes, added without requiring any new dependency, any new backend
computation, or any change to an existing API.** See §5 for the concrete
proposal this reading produces, and §8.1 for the one genuine scope
question (read-only vs. interactive) this reading does not resolve by
itself.

### 3.2 Why this is additive infrastructure, not a new "port"

Unlike `Adapter`/`Policy`/`PopulationPolicy`, there is no plugin
architecture question here at all. A dashboard is not a third-party-
extensible surface — nobody registers a new "dashboard implementation"
the way they register a new `Adapter`. It is first-party presentation
code with exactly one implementation, the same category
`observability/metrics.py`'s query functions and `api/readiness.py`'s
check already occupy. No new `PluginType`, no new registry entry, no new
lifecycle-promotion concept — confirmed by the same reasoning M9 §3.8
already applied to Human Review Workflow's own repositories.

### 3.3 The boundary with M7 (Monitoring) and M9 (Human Review Workflow)

M7 built the data M10 renders for its system/governance-health view; M9
built the data (and the workflow state machine) M10 renders for its
review-queue view. Neither of those milestones' own JSON contracts
changes here — M10 is a **new, additional consumer** of both, the
identical relationship M7's `/v1/admin/metrics` already has to
`verdicts`/`findings`/`population_findings` (a read pattern over
data other code already computes and persists, computing nothing new
itself). Confirmed by direct reading of both endpoints' current response
shapes (§2) — no field either one currently returns is insufficient for
what §5 proposes to render.

### 3.4 The boundary with M12 (Reporting)

Already drawn precisely by M7/M8 (§1, "Reporting" bullet) and repeated
here for this document's own clarity: M10 is **on-demand and
interactive** (a human opens a browser, sees the current state, closes
it); M12 is **periodic and document-shaped** (a scheduled job produces a
static artifact — e.g. a monthly compliance PDF — for an audience that
may never touch the live system at all). The two are not the same
capability at different maturity levels; they are different *products*
for different audiences and cadences. M10 does not add any export/
download/scheduled-generation capability that would blur this line.

## 4. Proposed architecture (this review's recommendation)

### 4.1 Technology: static HTML/CSS/vanilla JavaScript, zero new dependencies — not a SPA framework

**The highest-stakes call in this document.** Three real options:

**(a) A full single-page-application framework** (React, Vue, or
similar), with its own build pipeline (bundler, `package.json`, `npm`/
`pnpm`, a `node_modules` dependency tree entirely separate from this
project's Python dependency management).

**(b) Server-side HTML templating** (Jinja2 — FastAPI's own most common
companion for exactly this purpose), rendering HTML with data already
resolved server-side before the response is sent.

**(c) A static HTML shell plus vanilla JavaScript**, fetching JSON from
the existing endpoints (§2) client-side via `fetch()`, with no build
step, no templating engine, and no new Python or JavaScript-toolchain
dependency at all.

**Recommendation: (c).** This is not a stylistic preference — it is the
direct, mechanical consequence of §3.1's discipline applied honestly: no
view this document proposes (§4.2) needs anything a handful of `fetch()`
calls against already-JSON endpoints and plain DOM manipulation can't
render. Option (a) would introduce this project's first genuinely large
dependency surface (an entire JavaScript ecosystem, a build step, a
`node_modules` tree) for a handful of read-only tables and a status
strip — exactly the kind of infrastructure-ahead-of-a-real-case §3.1
warns against, and a materially larger, harder-to-audit surface for a
platform whose own architecture (§17) still assumes a single container,
single service. Option (b) is a smaller step but still a **new Python
dependency** (Jinja2 is not currently installed anywhere in this
project) for a templating capability this milestone doesn't actually
need — every value M10 renders is *already* JSON at the moment the
browser has it; templating exists to interpolate data into HTML
**server-side**, which only matters if the rendering needs to happen
before the response leaves the server. It doesn't here: the browser can
fetch the JSON and populate the DOM itself, exactly as any API-consuming
client already does. Option (c) requires nothing new in `pyproject.toml`
at all — `StaticFiles`, used to serve the CSS/JS assets, is already part
of Starlette, itself already a transitive dependency of `fastapi`.

### 4.2 Views: three pages, each backed by one existing endpoint family

- **Overview** (`/dashboard`) — system/governance health, rendered from
  `GET /v1/admin/metrics`; a readiness indicator from `GET /readyz`. The
  landing page.
- **Population Findings** (`/dashboard/population-findings`) — a table
  from `GET /v1/admin/population-findings[?system_id=]`, with a system
  picker sourced from the already-existing `GET /v1/admin/systems`.
- **Review Queue** (`/dashboard/reviews`) — two tables, one per subject
  type, from `GET /v1/admin/verdict-reviews[?status=&severity=]` and
  `GET /v1/admin/population-finding-reviews[?status=]`, with the identical
  status/severity filters those endpoints already support exposed as
  simple dropdowns — no new filtering capability invented, only the ones
  M9 already built surfaced as UI controls.

No other view is proposed. A per-event `Finding`/`Verdict` detail view
(beyond what's already embedded in a `VerdictReview`'s response) is
deliberately **not** included — no endpoint exists for browsing verdicts
outside the review-queue context (§1's "no general list-all-Verdicts"
boundary, per M9 §4.5), and inventing one to feed a new dashboard view
would be exactly the "invent functionality not supported by the
architecture" this document's own instructions rule out.

### 4.3 Serving mechanism

- **`api/dashboard.py`** (new) — a plain `APIRouter`, mirroring
  `api/health.py`/`api/readiness.py`'s shape exactly: one route per page
  (`GET /dashboard`, `GET /dashboard/population-findings`,
  `GET /dashboard/reviews`), each returning the identical static shell
  HTML file via Starlette's `FileResponse` — the client-side JavaScript
  (not the route) decides which view to render, based on the current
  path, the same "thin server, client renders" split every other part of
  this recommendation follows. Computes nothing, loads no new data,
  authenticates nobody (§6) — the same "manages facts, never computes"
  boundary every Admin API in this codebase already draws (M6 §1),
  applied here to *serving static bytes* instead of facts.
- **Static assets** (new directory, `src/gov_platform/api/dashboard_static/`
  — `dashboard.js`, `dashboard.css`, and the one shell `index.html`) —
  colocated under the same `api/` package as the router that serves them,
  **not** a new top-level package. *(Corrected by the hostile-review
  pass: the first draft proposed a brand-new top-level
  `src/gov_platform/dashboard/` package for these files while putting the
  router itself in `api/` — an inconsistency with §3.2's own reasoning
  about when a new top-level package is warranted. This project reaches
  for one only when nothing existing is a natural home, the way M9's
  `human_review/` earned its own package for a standalone CLI tool with
  nowhere else to live. A dashboard's static assets, served by a
  dashboard router that already lives in `api/`, do not meet that bar.)*
- **Construction-failure containment — a hard requirement, not a
  judgment call.** *(Added by the hostile-review pass.)* Starlette's
  `StaticFiles` raises `RuntimeError` at *construction* time if its
  configured directory does not exist (`check_dir=True` is its default,
  verified directly against Starlette's own source). Combined with §4.4's
  packaging risk, this means a packaging mistake in a real, non-editable
  install would otherwise prevent `create_app()` from ever returning an
  application object — not a degraded dashboard, a completely dead
  process, including `/healthz`, `/readyz`, and every ingestion and admin
  endpoint this platform has. `create_app()` must therefore construct the
  dashboard's `StaticFiles` mount and register `api/dashboard.py`'s
  router inside a `try`/`except` of their own, logging an error loudly on
  failure and simply not registering the dashboard's routes, while every
  other router and mount in the composition root proceeds unaffected.
  **Rationale:** this is not a new idea invented for M10 — it is the
  exact "a failure in this non-essential subsystem must never take down
  what matters more" precedent M9 already established for
  `_queue_verdict_review`'s own decoupled transaction
  (`docs/milestones/M9.md` §3.4), applied here to a construction-time
  risk instead of a request-time one. It is deliberately *not* solved by
  passing `check_dir=False` — that would trade a loud, immediately
  diagnosable failure for a silent one (requests to `/dashboard/static/*`
  would then 404 with no log line explaining why), which is a worse
  outcome, not a better one. The primary fix is still correct packaging
  (§4.4); this containment is the safety net behind it, preserving
  `architecture-mapping.md` §15's characterization of `app.py` as a
  side-effect-free factory — verified concretely by
  `tests/unit/api/test_app.py::test_create_app_wires_independent_instances`,
  which is not gated behind `@requires_postgres` and already proves
  `create_app()` succeeds with completely unreachable placeholder
  database URLs. A dashboard packaging defect must not be able to make
  that invariant false.
- **`dashboard.js`** — plain `fetch()` calls against the existing JSON
  endpoints (§2), rendering results into the DOM. No framework, no
  virtual DOM, no state-management library.
  - **Escaping — a blanket rule, no exception list.** *(Reversed by the
    hostile-review pass.)* Every string value taken from any API response
    and inserted into the DOM **must** go through safe, escaping
    insertion (`textContent`/equivalent), never raw `innerHTML`
    concatenation — unconditionally, not only for a named subset of
    fields. The first draft of this section named exactly three fields
    (`rationale`, `resolution_notes`, `reviewer`); that framing is
    corrected here because it is actively misleading, not merely
    incomplete — it invites an implementer to treat every other field as
    safe by omission. `System.name` is a concrete counter-example: it
    carries no character or length restriction beyond `min_length=1`
    (`schemas/system.py`), and is auto-provisioned directly from the
    **public**, unauthenticated ingestion endpoint's
    `system_id`/`source_system` fields
    (`SystemRepository.get_or_create_by_name`, established M1) — reachable
    by anyone who can call `POST /v1/ingestion/events/{adapter}`, a step
    below even the unauthenticated admin endpoints the original framing
    implicitly treated as the only source of risk. There is no closed,
    enumerable set of "the risky fields" in a platform where every write
    endpoint is unauthenticated (§6); the requirement has to cover every
    string the dashboard ever renders, present or future.
  - **Fetch-failure handling — an explicit requirement.** *(Added by the
    hostile-review pass; absent from the first draft entirely.)* Every
    view must handle a failed or non-2xx `fetch()` by rendering a
    visible, honest error state, never leaving the page blank or
    partially rendered with no explanation. This matters more here than
    for an ordinary admin tool because of a real coupling: the Overview
    page's metrics and readiness data are read from the same database
    `/readyz` reports the health of — the moment an operator most needs
    the dashboard to work (a real outage) is also the moment its own data
    source is most likely to be returning errors.
- **`api/app.py`** — gains one new router registration and one new
  `StaticFiles` mount, wrapped in the `try`/`except` described above —
  the same two-line addition pattern every prior milestone's new Admin
  API surface has already followed there, with one additional line of
  failure containment this milestone's own packaging risk requires.

### 4.4 Packaging: static assets must be real package data, not silently dropped

A real, concrete implementation risk worth naming now rather than
discovering after the fact (mirroring M7's own "found necessary while
implementing," not "designed in advance," discipline): `pyproject.toml`'s
`[tool.setuptools.packages.find]` currently discovers **Python** modules
under `src/`; non-`.py` files (the new `dashboard.js`/`.css`/`.html`) are
**not** automatically included in an installed package unless explicitly
declared (`package_data`/`include_package_data` plus a matching
`MANIFEST.in`, or an equivalent `setuptools` configuration). **Getting
this wrong does not mean the dashboard silently 404s** — that was the
first draft's claim, and the hostile-review pass found it understated the
real risk. Because `StaticFiles(check_dir=True)` (the default) raises
`RuntimeError` at construction time when its directory is missing, the
actual consequence, verified directly against a real, non-editable
install (`infra/docker/Dockerfile` runs `pip install --no-cache-dir .`,
exactly the path this risk lives on, and the exact path CI's
`docker-smoke` job exercises): `create_app()` never returns an
application object at all, and the entire platform — not just the
dashboard — fails to start. This must be verified directly against a
real, non-editable install (mirroring how M7's own connection-timeout
finding was "measured directly... not assumed"), not merely assumed to
work because local development testing never exercises a non-editable
install. §4.3's construction-failure containment requirement exists
precisely because packaging correctness alone was judged, on hostile
review, to be an insufficient single point of defense for a risk this
severe — defense in depth, not a substitute for getting the packaging
declaration right.

## 5. Database/API changes

**None.** This is a purely additive, presentation-only milestone:

- **No new migration.** No new table, no new column, no change to any
  existing table's schema or privileges.
- **No new JSON endpoint.** Every view in §4.2 is backed entirely by
  endpoints that already exist, unmodified (§2).
- **No change to any existing endpoint's request or response shape.**
  `GET /v1/admin/metrics`, `GET /v1/admin/population-findings`,
  `GET /v1/admin/verdict-reviews`, `GET /v1/admin/population-finding-reviews`,
  `GET /v1/admin/systems`, `GET /readyz`, `GET /healthz` are all consumed
  exactly as M6/M7/M9 left them.

Two additions were considered and **rejected** for this milestone
specifically, both directly on precedent already established by prior
milestones' own restraint:

- **A combined "dashboard summary" endpoint**, aggregating metrics +
  finding counts + review-queue counts into one round trip. Rejected on
  the identical "no premature abstraction without a demonstrated need"
  basis M8 used to decline a third statistical test and M9 used to
  decline a generic verdict-listing endpoint: three to four `fetch()`
  calls on a single page load, against a low-traffic internal admin tool,
  is not a real performance problem today. Revisit only if a concrete,
  measured need appears.
- **Pagination on the endpoints M10 depends on.** A real gap (§7), but
  fixing it means changing M6's/M9's own repository and API contracts —
  out of an additive, presentation-only milestone's own scope. See §8.3.

## 6. Production-readiness considerations

- **No authentication — the least defensible instance of this
  standing gap yet.** Named in every design document since M2, restated
  and sharpened at every milestone since (M5 "flagged loudly," M6
  "flagged more sharply," M8 "a concrete lever against the platform's own
  governance purpose," M9 "the first milestone where an unauthenticated
  caller can fabricate a specific, named person's professional judgment
  about a real bias finding"). M10 does not close it — still `M13` — but
  this is the first milestone whose *entire deliverable* is making
  governance-sensitive data (which systems have been flagged for bias,
  who claimed which review and what they concluded) directly, visually
  consumable by anyone who can reach the URL in a browser, with no login
  screen at all. The JSON was already exactly as exposed via the API;
  this milestone does not increase the *technical* exposure, but it does
  remove the last remaining friction (knowing the API shape, using
  `curl`) between "data is technically reachable" and "data is
  immediately, legibly visible to a casual visitor." Named as plainly as
  this document can name it, not solved here.
- **Stored-XSS discipline for every string the dashboard renders — no
  exception list.** *(Broadened by the hostile-review pass; the first
  draft named only three fields.)* `PopulationFinding.rationale`,
  `VerdictReview`/`PopulationFindingReview.resolution_notes`, the
  self-asserted `reviewer` string, `System.name`, and every other
  API-sourced string value the dashboard ever renders are all,
  unconditionally, in scope — some already free text writable by any
  unauthenticated caller today (M6/M9's own admin endpoints), others
  (`System.name`) writable via the *public* ingestion endpoint with no
  character restriction at all (`schemas/system.py`,
  `SystemRepository.get_or_create_by_name`), and all of them would, for
  the first time, be rendered as part of an HTML page rather than a JSON
  payload a script parses. `dashboard.js` must insert every one of them
  via safe DOM APIs (`textContent`, not `innerHTML` string-concatenation)
  — a hard requirement (§4.3) with no named subset of "the risky fields,"
  because that framing was found, on hostile review, to be actively
  misleading rather than merely incomplete: skipping it for even one
  unlisted field would let anyone who can reach that field's write path
  (unauthenticated everywhere in this platform, public in `System.name`'s
  case) plant a stored-XSS payload that executes in the browser of the
  next person who opens the dashboard.
- **A dashboard packaging failure must never take down the rest of the
  application.** *(Added by the hostile-review pass.)* `create_app()`'s
  new `StaticFiles` mount and dashboard router registration are
  construction-time operations that can fail (§4.3/§4.4) — specifically,
  a real, non-editable install missing package data for the dashboard's
  static assets raises `RuntimeError` at the moment `StaticFiles` is
  constructed. Wrapping that construction in its own `try`/`except`,
  logging loudly and simply omitting the dashboard's routes on failure,
  is what keeps this milestone's own additive, presentation-only scope
  from being able to regress `/healthz` liveness for the entire platform
  — the one guarantee no milestone since M0 has ever put at risk.
- **Client-side fetch failures must produce a visible, honest error
  state, never a silent blank page.** *(Added by the hostile-review
  pass; absent from the first draft entirely.)* This is not merely good
  practice — the Overview page's own metrics and readiness data are read
  from the same database `/readyz` is reporting the health of, so the
  moment an operator most needs the dashboard to explain what's wrong is
  also the moment its own data source is likeliest to be failing. A
  dashboard that goes silently blank during an outage is worse than
  useless at exactly the moment it matters most.
- **No CORS configuration needed, and none should be added.** The
  dashboard is served from the same FastAPI application, on the same
  origin, as every endpoint it calls (§4.3) — deliberately, to avoid
  needing any cross-origin allowance at all. Serving the dashboard from a
  separate deployment/origin was not seriously considered (§8.4 records
  why).
- **No new database load pattern.** Every request the dashboard makes is
  an existing, already-exercised read path (`GET /v1/admin/metrics` is
  already windowed and indexed per M7 §6; the review-queue and
  population-findings list endpoints are already indexed per M9 §5.2).
  A human manually reloading a browser tab is a categorically lighter,
  lower-frequency load pattern than the scripted-polling concern M7 §12
  already named and dismissed for its own endpoint.
- **No build step, no minification, no bundler, no source maps.** A
  deliberate scope boundary (§4.1), not an oversight — revisit only if
  the dashboard's own client-side complexity later grows enough to
  justify the tooling, mirroring this project's own "generalize only
  after a second, real, concrete need appears" discipline (M4, M8).
- **Static-asset packaging must be verified against a real,
  non-editable install** (§4.4), not merely assumed correct because
  local/editable development never exercises the failure mode.
- **Browser/JS correctness is not covered by this project's existing
  test suite**, and this document does not propose adding browser-
  automation infrastructure (Selenium/Playwright) to acquire that
  coverage — see §8.5 for the explicit scope call this raises.

## 8. Architectural ambiguities, each with a recommendation and justification

### 8.1 — Should the dashboard be read-only, or should it also let a human claim/release/resolve a review directly from the page? **(the second-highest-stakes call in this document, after §4.1)**

The architecture names this milestone "Compliance Dashboard," not "Human
Review Console" or "Review Workbench" — a naming choice that reads more
naturally as a *visibility/reporting* surface (what a compliance officer
looks at to understand the current state of governance) than an
*action-taking* one. M9 already built a complete, working REST API for
claim/release/resolve; nothing technically prevents wiring those same
calls into `dashboard.js` as buttons.

**Recommendation: read-only for this milestone.** Three reasons, not one:
first, the literal name supports it, and this document's own instructions
say not to invent functionality the architecture doesn't support — "view"
is supported directly by the name; "act on" is an inference. Second, the
security posture differs in a way worth taking seriously even though the
underlying exposure is technically identical either way (§6): a page with
visible "Claim" and "Resolve" buttons *invites* action from anyone who
opens it, in a way a bare JSON API — reachable only to someone who already
knows to look for it — does not; adding those buttons without
authentication (§6) is a materially different **invitation to act** than
the identical capability already sitting, unadvertised, behind a REST
endpoint. Third, this keeps M10 in the same "manages facts, never
computes, and now — never mutates either" category the rest of this
document argues for. **This is presented as a recommendation requiring
your explicit sign-off, not a foregone conclusion** — reasonable
compliance-dashboard products absolutely do combine viewing and acting,
and if that's the intended reading here, it changes §4.2's page list (the
Review Queue view would need claim/resolve forms, not just tables) and
sharpens §6's authentication gap from "uncomfortable" to "the dashboard
can now let an anonymous visitor resolve a real bias finding with one
click."

### 8.2 — Does `dashboard.js` need any framework-adjacent tooling at all (a tiny templating helper, a micro-library), or is genuinely plain `fetch()` + DOM manipulation sufficient?

Considered as a narrower version of §4.1's question: even having ruled
out a full SPA framework, is a small, dependency-free *helper* (e.g., a
minimal client-side templating function, hand-written in the same file)
warranted, or is directly building DOM nodes acceptable for three small
read-only tables? **Recommendation: no tooling, not even a small
hand-rolled helper, for this first cut.** Three tables and a status strip
do not need one; if the dashboard's own scope grows in a later milestone
(more views, more interactivity), that growth is the concrete second use
case this project's own discipline requires before reaching for an
abstraction (M4/M8's own precedent) — not something to build in
anticipation of now.

### 8.3 — Is the pagination gap on the endpoints M10 depends on this milestone's problem to fix, or a separate, dedicated follow-up?

M9 §9.5/§9.6 already established the precedent for exactly this
situation: a real, verified gap, found as a byproduct of a later
milestone's own design work, that belongs to an *earlier* milestone's
surface, not the one that happened to notice it. **Recommendation: not
M10's problem to fix.** `population-findings`/`verdict-reviews`/
`population-finding-reviews` list endpoints having no pagination is a
change to M6's/M9's own API contracts (a new query parameter, a new
response envelope shape, or both) — a different milestone's surface, by
this project's own established convention for exactly this kind of
discovery. M10's own first cut should render whatever these endpoints
return today, with no client-side pretense that the list is complete if
it turns out to be large, and this gap should be named (as done in §7)
as a verified, outstanding candidate for a small, dedicated, cross-cutting
follow-up — not silently absorbed into an unrelated milestone's scope,
and not silently ignored either. The consequence at real scale is more
severe than a first read suggests, and is stated plainly rather than
softened: with no virtualization or windowing on the client (§4.1/§8.2)
and no cap on the client, an operator's first look at a mature
deployment's `population_findings` table (a table that only ever grows,
until M11) is a plausible browser-tab freeze, not a mild inconvenience —
this does not change the recommendation above, only how honestly its
risk is described.

### 8.4 — Should the dashboard be served from the same application/origin as the API, or as an independently deployable frontend?

Two real shapes: **(a)** mounted directly in the existing `api/app.py`
composition root, same process, same origin, as this document proposes
throughout §4; **(b)** a fully separate static site (deployed to a CDN,
object storage, or a second container), calling the API cross-origin.
**Recommendation: (a).** Architecture §17 ("Deployment Architecture")
remains, unchanged since M1, "single container, single service" — a
second, independently-deployed frontend artifact would be the first
departure from that shape, requiring its own build/deploy pipeline and
CORS configuration (§6) this platform has never needed before, for no
benefit this milestone's own small, read-only scope demonstrates a need
for. Multi-plane deployment remains M13's explicit territory
(`docs/architecture-mapping.md` §17), not something M10 backs into as a
side effect of choosing where to put some HTML files.

### 8.5 — Does M10 need browser-automation test coverage (Selenium/Playwright), or is server-side "serves the right static bytes" testing sufficient?

This project has never once added a browser-driving test dependency in
ten milestones (M0–M9's entire test suite is `pytest` + `httpx`'s
`TestClient`, zero browser automation). **Recommendation: no new browser-
automation dependency for this milestone.** Testing scope is: does
`GET /dashboard`/`/dashboard/population-findings`/`/dashboard/reviews`
each return `200` with the expected static HTML; are the static JS/CSS
assets served correctly (right path, right content-type); does the
composition root wire the new router/mount without requiring a live
database at construction time (the same DB-free `create_app()` invariant
M3 established and every milestone since has preserved). The client-side
JavaScript's own correctness (does the fetched data render into the DOM
correctly) is **not** covered by this test suite under this
recommendation — verified manually against a running instance instead,
the same "verified directly, not assumed" discipline this document
applies to packaging (§4.4), but through manual rather than automated
means. Flagged explicitly as a real, accepted gap (§6), not hidden by
omission.

### 8.6 — Should a dashboard packaging/construction failure be allowed to prevent the whole application from starting? *(new — discovered during the hostile-review pass)*

`StaticFiles(check_dir=True)` (Starlette's own default) raises
`RuntimeError` at construction time if its directory is missing —
verified directly against Starlette's source, not assumed. Combined with
§4.4's packaging risk, mounting the dashboard's static assets the same
way every other router in `api/app.py` is currently registered (a bare
call inside `create_app()`, no failure isolation) would mean a packaging
mistake in a real, non-editable install prevents `create_app()` from
returning an application object at all — not a degraded dashboard, a
dead process, `/healthz` included.

**Recommendation: contain it.** Construct the dashboard's `StaticFiles`
mount and register `api/dashboard.py`'s router inside their own
`try`/`except` in `create_app()`; on failure, log an error loudly and
proceed without the dashboard's routes, leaving every other endpoint
fully functional. This is not a new pattern invented for M10 — it is the
exact "a failure in this non-essential subsystem must never take down
what matters more" precedent M9 already established for
`_queue_verdict_review`'s decoupled transaction (`docs/milestones/M9.md`
§3.4), applied here to a construction-time risk instead of a
request-time one. Explicitly rejected as insufficient on their own:
`check_dir=False` (trades a loud, diagnosable failure for a silent one —
worse, not better) and "just fix the packaging" alone (correct as the
primary fix, but a single point of failure for a risk this severe, given
packaging correctness in a non-editable install is exactly the kind of
thing this project's own local tests cannot exercise and therefore
cannot catch before it reaches production). This recommendation does not
require your sign-off the way §4.1/§8.1 do — it is a direct, mechanical
consequence of the "side-effect-free factory" invariant
`architecture-mapping.md` §15 already commits `app.py` to, verified
concretely by the existing, ungated
`test_create_app_wires_independent_instances` test.

### 8.7 — Should `api/dashboard.py`'s router use a shared path prefix and relative routes, or absolute paths like `health`/`readiness`? *(new — discovered during the hostile-review pass)*

`api/health.py`/`api/readiness.py` are each included with no `prefix=`
argument, since each owns exactly one absolute route. Every `admin_*`
router is instead included with `prefix="/v1/admin"` and uses relative
route decorators. The dashboard has three sub-paths sharing one prefix
(`/dashboard`, `/dashboard/population-findings`, `/dashboard/reviews`),
structurally closer to the `admin_*` shape than the single-route
`health`/`readiness` shape it was originally described as mirroring.

**Recommendation:** `app.include_router(dashboard.router,
prefix="/dashboard")`, with relative decorators (`@router.get("/")`,
`@router.get("/population-findings")`, `@router.get("/reviews")`) inside
`api/dashboard.py` — for internal consistency with the codebase's own
established convention for multi-route routers, not because the
alternative would be broken. A minor implementation-clarity point, not a
design flaw; does not require your sign-off.

### Implementation-time bug found and fixed

One real bug was found during verification, not during design — the kind
of thing this document's own discipline (§4.4, "verified directly... not
assumed") requires naming here rather than glossing over:

**`GET /dashboard` 307-redirected instead of returning 200 directly.**
§8.7's own recommendation — `app.include_router(dashboard.router,
prefix="/dashboard")` with a relative `@router.get("/")` decorator for the
index route — combines to register the exact path `/dashboard/` (trailing
slash), not `/dashboard`. Starlette's default `redirect_slashes=True`
then 307-redirects a bare `GET /dashboard` to `/dashboard/` rather than
matching it directly. This is not a cosmetic issue: it contradicts §4.2's
own plain listing of the route as `/dashboard`, and it silently broke the
literal command this milestone's own README documents
(`curl http://127.0.0.1:8000/dashboard`, no `-L`) — a plain `curl` without
`-L` does not follow redirects, so that documented command would have
printed nothing. It was not caught by the initial test suite because
`TestClient`'s default `follow_redirects=True` transparently follows the
redirect, masking the extra hop. Found by running the real app with
`uvicorn` and exercising the documented `curl` commands directly (the same
"verified directly against a real path, not merely assumed" discipline
§4.4 already required for packaging) — a plain `curl` (no `-L`) returned
`307` where `200` was expected.

**Fix:** `@router.get("/")` → `@router.get("")` (empty string) for the
index route only — `""` combined with `prefix="/dashboard"` registers the
exact path `/dashboard`, matching directly with no redirect, and is no
less "a relative decorator" than `"/"` was, so it does not depart from
§8.7's own recommendation in spirit. `/dashboard/population-findings` and
`/dashboard/reviews` were never affected (their own decorators
(`"/population-findings"`, `"/reviews"`) already produced exact-matching
paths with no ambiguity). Verified by direct `curl`/`uvicorn` re-test
(bare `GET /dashboard` now returns `200` with no redirect) and pinned down
by a new regression test,
`test_overview_route_matches_exactly_without_a_redirect`
(`tests/unit/api/test_dashboard.py`), which uses a `TestClient` constructed
with `follow_redirects=False` specifically so this class of bug cannot
recur silently behind the default client's redirect-following behavior.

This does not change §4/§8.7's architecture — the router still uses
`prefix="/dashboard"` with relative decorators, exactly as recommended;
only the index route's own decorator string changed, to actually produce
the exact path §4.2 already named.
