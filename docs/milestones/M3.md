# M3 — Plugin Architecture: Registry, Discovery, Lifecycle & Sandboxing

**Status:** Approved and frozen — 2026-07-26
**Basis:** `ARCH-GOV-002` (architecture, frozen) · `IMPL-GOV-001` (implementation plan, frozen) · M0, M1, M2 frozen and approved

## What Was Built

Everything in the approved design below, built exactly to the eight
decisions you confirmed, plus what implementing it against real code and a
real Postgres required beyond what the design review anticipated:

- **`plugins/registry.py`** — in-process `register_adapter`/`register_policy`
  decorators + lookup, no database. `plugins/bootstrap.py` explicitly
  imports every first-party plugin module so their decorators run.
- **`plugins/sandbox.py`** — `run_sandboxed`, a timeout + exception-isolation
  wrapper around every registry-dispatched plugin call, exactly as scoped
  in §13.1 (no process/container isolation).
- **`schemas/plugin_registration.py` + migration `0010`** —
  `PluginType`/`PluginLifecycleState`/`PluginRegistration`, the
  `plugin_registrations` table with a partial unique index enforcing at
  most one `PRODUCTION` version per plugin, and `shadow_findings`, kept
  structurally separate from `findings` so a shadow policy's output can
  never be mistaken for one that actually governed a decision.
- **`db/repositories/plugin_registration.py` and `shadow_finding.py`** —
  `promote` advances one lifecycle stage and demotes whatever it replaces
  to `SHADOW`; both `create` and `promote` translate a database race into
  a clean `ValueError` rather than a raw `IntegrityError` (a production-
  readiness fix, see below).
- **`api/admin/plugins.py`** — register/list/get/promote, rejecting any
  `plugin_id`/`version` this process's own code hasn't registered
  in-process (§13.5: never loads new code).
- **`plugins/seed_registry.py`** — the CLI that seeds the four first-party
  plugins to `PRODUCTION`, kept separate from `create_app()` specifically
  to preserve the DB-free-construction invariant M0 through M2 established.
- **`api/ingestion/routes.py` rewritten** — one real, independently-typed
  FastAPI route generated per registered adapter (§13.4), resolving its
  `PRODUCTION`/`SHADOW` policies from the database fresh on every request.
  Route *existence* stays a pure function of the in-process registry, so
  `create_app()` still needs no live database — see the production-
  readiness note below on why this took more care than the design review
  anticipated.
- **All four M2 plugins retrofitted** (§13.7) — `SyntheticAdapter`,
  `CreditScorecardAdapter`, `AlwaysAllowPolicy`, `DirectAttributeInInputsPolicy`
  now carry registry identity and are registered; `api/app.py`'s
  hand-wiring of them is gone entirely.

## Production-Readiness Review

Performed after implementation, before freeze.

**Finding (fixed): `create_app()`'s DB-free-construction invariant would
have broken if routes were generated from database lifecycle state.**
The original design's most literal reading — "generate routes from
whichever adapters are `PRODUCTION`" — would require a live database read
at app-construction time, breaking an invariant every milestone since M0
has relied on (dozens of unit tests construct an app against an
unreachable placeholder URL). Resolved by splitting the concern: route
*existence* is generated from the in-process registry (`plugins.bootstrap`'s
imports — no database, ever), while *which policy currently governs* a
request is resolved fresh from the database on every request, inside the
handler. This still satisfies "new adapters become available without
modifying the composition root" and "preserve FastAPI validation" exactly
as decided — it's a refinement of *how*, not a change to *what* was
approved.

**Finding (fixed): a database race in `create`/`promote` surfaced as a
raw 500.** Both methods do check-then-write; two concurrent callers
registering/promoting the identical identity could both pass the check
before either writes, and the database's own constraints (the correct,
real guarantee, per §13.6) would then reject the loser with a raw
`IntegrityError`. Fixed by catching it and re-raising a clean `ValueError`
(the same client-error category `ProtectedAttributeResolver`'s errors
already use, established in M2). `create()`'s version is tested directly
(calling it twice is the identical code path a race would hit).
`promote()`'s equivalent branch is annotated `# pragma: no cover` with a
detailed comment: a genuine two-thread test was attempted and found
unreliable, not because the race is untestable in principle, but because
low-contention timing produces a second, equally-correct outcome (both
promotions succeeding sequentially) that a test asserting one specific
interleaving would flag as failure. **Known, accepted, minor inconsistency
this fix introduces**: the Admin API's own pre-check still returns `409`
for the common (non-race) duplicate-registration case, while the rare
race that slips past it now returns `422` instead of `500` — two
different status codes for conceptually the same problem, depending on
timing. Not fixed further: unifying them would mean the route catching
and re-wrapping this specific `ValueError`, for a genuinely rare edge case.

**Reviewed, no issue found:**
- `unregister_adapter`/`unregister_policy` (the test-only registry escape
  hatch) are never called from any non-test code path — confirmed by
  search, not assumption.
- The sandbox's `executor.shutdown(wait=False)` genuinely doesn't block
  the caller on a still-running thread — proven by a test asserting
  wall-clock elapsed time, not just that the exception type is right.
- A raising `SHADOW` policy cannot affect real ingestion — proven by a
  dedicated test, not just reasoned about.
- No SQL injection surface in any new code — all access goes through the
  SQLAlchemy ORM/parameterized queries, consistent with every prior
  milestone.

## 1. What M3 is exactly responsible for

Every prior milestone named the same four things for M3, consistently,
going back to M0 (`M0.md` line 68, `M1.md` line 208,
`architecture-mapping.md` line 13, `adapters/__init__.py`,
`policy_engine/__init__.py`):

1. **Adapter/Policy registry** — a real catalog of which `Adapter` and
   `Policy` implementations exist, replacing M2's hardcoded pairs wired
   directly in `api/app.py`.
2. **Discovery** — new implementations become known to the platform
   without editing the composition root's Python code for each one.
3. **Sandboxing** — isolating plugin execution so a faulty (or, per
   `adapters/base.py`'s own docstring, third-party — "a plugin surface
   other teams will extend") implementation can't take down or corrupt
   the platform.
4. **The draft/shadow/production promotion lifecycle** — a plugin can
   exist in three states: registered but not run (`draft`), run against
   real traffic for comparison without affecting real decisions
   (`shadow`), or actually governing (`production`) — an operational
   promotion process, not a code deploy.

M2's own module docstrings additionally name the specific technical debt
M3 is meant to retire: `ingest_event`'s docstring says dispatching to
"whichever adapter a given `system_id` requires" is "M3 scope... introducing
it now, for one adapter, would be speculative generality with no second
case to validate it against" — and M2's own design doc (§11.1) explicitly
chose the two-hardcoded-routes shape *because* a real registry didn't
exist yet, not because that's the intended end state.

**What M3 is not responsible for**, per the same record: `GovernanceEngine`
taking more than one *contributing* `Policy` (policy plurality,
disagreement surfacing) is M4; "which policy applies to which
domain/jurisdiction" (Policy Bindings) is M5; the full four-state Verdict
model, escalation, and signing are M5; auth on any endpoint is M5+/M13.
Where M3 touches territory adjacent to these (see §13.3, §13.6), the
boundary matters and is flagged explicitly, not blurred.

## 2. How M3 builds on M2

M2 deliberately built the smallest thing that could prove two real
things worked: `Adapter[TPayload]`'s port generalizes to a second,
differently-shaped implementation, and `Policy`'s port supports a second,
judgment-bearing implementation with its own constructor dependency. It
did this by hardcoding both pairs directly into `api/app.py` and giving
each adapter its own ingestion route — and named this explicitly as a
stopgap in three places: the ingestion route's docstring, `api/app.py`'s
docstring, and M2's own design doc §11.1.

M3 is the generalization M2 pointed at but didn't build: instead of a
third adapter meaning a third hardcoded route and a third manually-wired
`GovernanceEngine`, a third adapter should mean one registration call.
Concretely, M3 must:

- Retrofit `SyntheticAdapter`, `CreditScorecardAdapter`, `AlwaysAllowPolicy`,
  and `DirectAttributeInInputsPolicy` into the new registry as its first
  four entries (see §13.7) — proving the registry against the two real
  cases M2 already built, the same way M2 proved `Adapter[TPayload]`
  against a second real case rather than a hypothetical one.
- Replace (or generalize) M2's two hardcoded ingestion routes with
  registry-driven dispatch (see §13.4).
- Leave `protected_attributes/classification.py`'s static ruleset alone
  — M2 explicitly deferred *whether* it becomes DB-backed config to "M3
  plugin config, or M5 Policy Bindings, whichever the real architecture
  doc specifies" (M2.md §11.5). This review's recommendation is **M5**,
  not M3 — see §13.8.
- Leave `Policy.evaluate(event) -> Finding` and `Adapter.translate` alone.
  M3 adds identity/lifecycle *around* plugins, not new parameters *into*
  their existing methods — the same discipline M2 applied when it chose
  a constructor dependency over widening `Policy.evaluate`'s signature.

## 3. Why each piece exists architecturally

**Registry + discovery.** Without one, every new adapter or policy is a
composition-root code change and a redeploy — fine for two cases (M2
said so explicitly), not fine for the plugin ecosystem §6 describes
("other teams will extend from M3 onward"). A registry decouples *what
implementations exist* from *what's currently wired into the running
app*, which is the precondition for discovery, promotion, and eventually
third-party contribution meaning anything at all.

**The promotion lifecycle.** A new policy is a governance-affecting
change — the platform's entire reason to exist is producing trustworthy,
audited verdicts. Shipping a new policy straight to "affects real
decisions" with no intermediate step is the operational equivalent of
deploying to production with no staging environment. `shadow` exists so
a new policy's real behavior against real traffic is observable and
comparable *before* it can flag or clear anything for real — the
governance-domain equivalent of a shadow deployment in ordinary software
delivery.

**Sandboxing.** Once a plugin can be someone else's code (even
same-organization, different-team code, let alone eventual third-party
contributions), the platform needs to survive that code being wrong —
an infinite loop, an unhandled exception, a memory leak — without an
adapter or policy bug becoming a platform outage. This is the "protect
the whole from one part" concern that M0's global exception handler and
M2's `ValueError`→422 handler already partially address at the API
boundary, extended to cover plugin *execution* specifically.

## 4. Proposed architecture (this review's recommendation)

This is one coherent proposal, not a menu — but every non-obvious choice
in it is also listed as its own numbered ambiguity in §13, with the
reasoning that led here repeated there so you can disagree with one part
without rejecting the whole shape.

**Identity.** `Adapter` gains `adapter_id: str` and `version: str` class
attributes, mirroring `Policy`'s existing `policy_id`/`version` — a small,
additive change to the ABC (identity metadata, not a signature change to
`translate`).

**Registration.** Adapter/Policy *implementations* register themselves
in an in-process registry at import time (a decorator or explicit call in
the composition root), the same way they're Python classes today — M3
does not mean dynamically loading arbitrary code from outside this
deployed codebase (see §13.2). What's new is that the registry also
carries a **lifecycle state** (`DRAFT` / `SHADOW` / `PRODUCTION`) per
`(plugin_type, plugin_id, version)`, persisted in Postgres and mutable
via the Admin API *without a redeploy* — this is the part that actually
needs a database: which of several already-deployed implementations is
currently trusted with real traffic is an operational fact, not a code
fact.

**Dispatch.** Recommended: one real FastAPI route **per registered,
`PRODUCTION`-state adapter**, generated from the registry at app-startup
time rather than hand-written per adapter in `routes.py` — not a single
universal endpoint doing manual runtime schema dispatch. See §13.4 for
the full trade-off; the short version is that a single endpoint can't
keep FastAPI's automatic per-adapter request validation and OpenAPI docs,
and this project has consistently treated "malformed input gets a real
schema-validation error" as a load-bearing quality bar, not a nice-to-have.

**Shadow execution.** A `SHADOW`-state policy runs against every real
event its adapter's route receives, in addition to the `PRODUCTION`
policy — but its `Finding` is persisted to its own side channel (see
§6) and never contributes to the `GovernanceVerdict` served to the
caller. This is deliberately *not* M4's "policy plurality": there is no
aggregation, no disagreement surfacing in the response, and exactly one
policy (the `PRODUCTION` one) still determines `GovernanceVerdict.status`.
`GovernanceEngine` gains an optional capability for this, not a widened
"one policy" constraint — see §9.

**Sandboxing, scoped down.** Recommended: timeout + exception isolation
around every plugin call (`Adapter.translate`, `Policy.evaluate`), not
process- or container-level isolation. See §13.1 — this is the biggest
scope call in this whole document and is argued at length there.

## 6. Database schema changes

One new migration, `0010_create_plugin_registrations.sql`:

```sql
CREATE TABLE plugin_registrations (
    id              TEXT PRIMARY KEY,
    plugin_type     TEXT NOT NULL,   -- 'ADAPTER' | 'POLICY'
    plugin_id       TEXT NOT NULL,   -- e.g. 'credit-scorecard', 'direct-attribute-in-inputs'
    version         TEXT NOT NULL,
    lifecycle_state TEXT NOT NULL,   -- 'DRAFT' | 'SHADOW' | 'PRODUCTION'
    registered_at   TIMESTAMPTZ NOT NULL,
    promoted_at     TIMESTAMPTZ,     -- last lifecycle-state transition, NULL if still DRAFT

    UNIQUE (plugin_type, plugin_id, version)
);

-- At most one PRODUCTION version per (plugin_type, plugin_id) at a time --
-- many DRAFT/SHADOW candidates may coexist, but exactly one implementation
-- may actually govern real decisions for a given plugin_id.
CREATE UNIQUE INDEX one_production_version_per_plugin
    ON plugin_registrations (plugin_type, plugin_id)
    WHERE lifecycle_state = 'PRODUCTION';
```

A second new table for shadow output, since shadow `Finding`s must never
land in the same `findings` table the real `Verdict` is built from
(mixing them would corrupt `VerdictRepository.get`'s join and, worse,
the evidence chain's payload):

```sql
CREATE TABLE shadow_findings (
    id                  TEXT PRIMARY KEY,
    decision_event_id   TEXT NOT NULL REFERENCES decision_events(id),
    plugin_registration_id TEXT NOT NULL REFERENCES plugin_registrations(id),
    outcome             TEXT NOT NULL,
    confidence          DOUBLE PRECISION NOT NULL,
    rationale           TEXT NOT NULL,
    metric_values       TEXT NOT NULL,
    evaluated_at        TIMESTAMPTZ NOT NULL
);
```

No changes to `findings`, `verdicts`, or `evidence_chain` — shadow output
is additive and fully separate, by design (see §13.3).

## 7. Public API changes

New Admin API surface, `api/admin/plugins.py`:

- `POST /v1/admin/plugins` — register a `(plugin_type, plugin_id, version)`
  as `DRAFT`. Registering a plugin *type/id/version* the process doesn't
  actually have Python code for should fail — see §13.5 on how discovery
  validates this without dynamic code loading.
- `GET /v1/admin/plugins` / `GET /v1/admin/plugins/{id}` — list/inspect
  registrations and their current lifecycle state.
- `POST /v1/admin/plugins/{id}/promote` — advance one lifecycle stage
  (`DRAFT`→`SHADOW`→`PRODUCTION`). Promoting to `PRODUCTION` demotes
  whatever previously held that slot for the same `(plugin_type, plugin_id)`
  — enforced by the DB constraint in §6, surfaced as a clear response
  (e.g. `previous_production_version` in the response body), not a silent
  side effect.
- No `DELETE` — demotion, not deletion, matches this platform's existing
  append-only-leaning posture (nothing else in this schema is hard-deleted
  either).

Ingestion API: routes become registry-generated (see §13.4) but the
per-route *contract* (`IngestionResponse`'s shape, status codes) is
unchanged — this is a dispatch-mechanism change, not a response-shape
change.

class PluginType(StrEnum):

## 9. Interfaces and abstractions

`Adapter` and `Policy` stay exactly as they are today (`translate`/
`evaluate` unchanged) plus the small `adapter_id`/`version` addition to
`Adapter` noted in §4/§5 — M3 does not add a third port. The registry
itself is a concrete service (`plugins/registry.py`), same reasoning M2
used for `ProtectedAttributeResolver`: there's exactly one registry
implementation, no second strategy to justify an abstraction.

`GovernanceEngine` gains an *optional* seam for shadow execution. Two
shapes are viable:

- **(Recommended) `GovernanceEngine(policy=..., shadow_policies=[...])`** —
  a second constructor list, defaulting to empty. `govern` still builds
  its returned `Verdict` from exactly `policy` alone; shadow policies are
  evaluated and their `Finding`s returned via a second return value or a
  side-effect callback for the caller (the ingestion route) to persist.
  Keeps `GovernanceEngine`'s core contract ("wraps one Policy's Finding
  into a Verdict") completely intact — shadow is additive, not a
  redefinition.
- **(Rejected)** Teaching `GovernanceEngine` to persist shadow findings
  itself. Rejected because `GovernanceEngine` has never touched
  persistence — that's `EvidenceStore`'s job — and giving it a database
  dependency now would blur a boundary M0 through M2 have all kept clean.

## 10. Testing strategy

Following the established pattern:

- `tests/unit/plugins/test_registry.py` — pure logic: register, look up,
  promote/demote, the "only one PRODUCTION at a time" invariant enforced
  in-process (before the DB constraint is even reached) if the registry
  layer itself enforces it, or a `tests/integration/` test if only the DB
  constraint does (see §13.6 for which — this is itself worth deciding).
- `tests/unit/plugins/test_sandbox.py` — a deliberately slow/deliberately
  raising fake plugin proves the timeout/exception wrapper does its job
  without needing any real adapter or policy.
- `tests/integration/test_plugin_registrations_postgres.py` — repository
  round trip + the one-production-per-plugin DB constraint, `@requires_postgres`.
- `tests/integration/test_admin_plugins_api.py` — register/list/promote
  over real HTTP, mirroring `test_admin_systems_api.py`'s shape.
- `tests/integration/test_shadow_execution_postgres.py` — a shadow-state
  policy alongside a production one, real Postgres: proves the shadow
  `Finding` lands in `shadow_findings` and the served `Verdict` is
  unaffected by what the shadow policy would have decided.
- `tests/integration/test_ingestion_api.py` — extended with a regression
  proof that registry-driven dispatch produces byte-identical behavior to
  M2's hardcoded routes for both existing adapters (the same "prove the
  old path still works" discipline M2 itself required of its own change).
- Coverage floor stays `--cov-fail-under=98`, verified against real
  Postgres locally, per the workflow M1's verification pass established.

## 11. Acceptance criteria (proposed)

1. `SyntheticAdapter`, `CreditScorecardAdapter`, `AlwaysAllowPolicy`, and
   `DirectAttributeInInputsPolicy` are registered as `PRODUCTION` and
   reachable exactly as they are today — a full regression proof, not an
   assumption.
2. A new adapter/policy can be registered as `DRAFT`, promoted to
   `SHADOW`, and promoted to `PRODUCTION` via the Admin API, with each
   transition reflected immediately (no redeploy) in what the ingestion
   routes actually dispatch to.
3. Promoting a plugin to `PRODUCTION` correctly demotes whatever
   previously held that slot; at most one `PRODUCTION` version exists per
   `(plugin_type, plugin_id)` at all times, DB-enforced.
4. A `SHADOW`-state policy's `Finding`s are persisted to `shadow_findings`
   for every real event its adapter handles, and provably never influence
   the served `GovernanceVerdict`.
5. A plugin that raises an exception or exceeds its execution time budget
   is isolated — the request fails cleanly (an appropriate error status,
   not a hung worker or a crashed process) and does not affect other
   concurrent requests.
6. `ruff`, `mypy --strict`, and the full suite pass at 100% coverage
   against real Postgres, migrations idempotent, matching M1/M2's
   established bar.
7. `docs/architecture-mapping.md`'s §6 row updated from "the two ports
   exist" to real registry/discovery/lifecycle, with sandboxing's actual
   (scoped-down) scope stated precisely.

## 12. Expected production-readiness review points

- **Timeout value(s) for the sandbox wrapper** — one global constant, or
  per-plugin-type, or admin-configurable? A hardcoded magic number here
  has the same "who approved this and when" governance smell M2's review
  flagged for policy thresholds.
- **What happens to an in-flight production request when its adapter/policy
  gets demoted mid-request** — a real race condition once promotion is a
  live API call rather than a deploy. Likely fine to accept (the request
  in flight finishes with whatever it already resolved), but worth stating
  explicitly rather than leaving implicit.
- **Shadow execution's cost.** Every shadow-state policy roughly doubles
  (or worse, multiplies) the work done per ingested event. Worth an
  explicit, documented understanding of what happens under load — probably
  "M3 doesn't optimize this, M6's async ingestion plane is where that's
  actually addressed" rather than solving it now.
- **Audit trail for promotions.** `promoted_at` records *when*, but not
  *who* promoted a plugin or *why* — real compliance requirements for a
  governance platform specifically will likely want this. Flagging as a
  likely near-term gap, not fixing preemptively (no auth exists yet at
  all, per M5+/M13 — attributing "who" without auth would be hollow).

## 13. Architectural ambiguities, with my recommendation for each

### 13.1 — How much does "sandboxing" actually mean? **(the biggest call in this document)**

Options, roughly in order of how much isolation they provide:

- **(a) OS-process isolation** — each plugin call runs in a subprocess,
  communicating via IPC/serialization. Real isolation (a crashed or
  hung plugin can't take the main process with it), but a large
  engineering lift: serialization of `DecisionEvent`/payloads across a
  process boundary, subprocess pool management, and a meaningful latency
  cost on every single ingested event.
- **(b) Container-per-plugin isolation** — matches this project's
  existing Docker deployment story conceptually, but running a container
  per request (or even per plugin-as-a-persistent-service) is a much
  bigger deployment-architecture shift than M3's card describes, and
  conflicts with M1's explicit note that "single container, single
  service... multi-plane topology... [is] M13."
- **(c) In-process language-level restriction** (e.g. restricted
  globals/builtins) — lighter, but well-documented as leaky in Python;
  claiming "sandboxed" while shipping something with known escape vectors
  would be a worse look than not claiming it at all.
- **(d) Recommended: timeout + exception isolation only.** Every
  registry-dispatched `Adapter.translate`/`Policy.evaluate` call runs
  under a bounded time budget (e.g. a thread with a timeout, since these
  calls are synchronous — matching the existing plain-`def`-handler
  reasoning already established in `api/ingestion/routes.py`) and any
  exception is caught and converted into a clean 4xx/5xx at the API
  boundary rather than propagating raw. This is **not** true security
  isolation — a sufficiently malicious plugin could still read process
  memory, make network calls, etc. — but there is no untrusted
  third-party plugin author yet (every `Adapter`/`Policy` in this
  repository is first-party code reviewed the same way any other module
  is), so building real sandboxing now would be solving a threat model
  that doesn't exist yet, the exact "speculative generality" this
  project has declined at every prior milestone. Real isolation belongs
  with whichever milestone first admits genuinely untrusted, externally-
  contributed code — not previously named in any milestone card, which
  itself suggests it's further out than M3.

**Recommendation: (d).** This needs your explicit sign-off more than any
other item in this document, because "sandboxing" sounds like it promises
(a) or (b) and this review is recommending something much narrower.

### 13.2 — Does "discovery" mean dynamic code loading from outside this codebase?

**Recommendation: no.** New adapters/policies are still Python classes
added to this repository and deployed the normal way; "discovery" means
the *registry* (a database-backed catalog) becomes aware of an already-
deployed class's existence and lifecycle state without the composition
root (`api/app.py`) needing a code change to wire it in. True external
plugin loading (arbitrary code from outside the deployed artifact) is a
much larger, security-sensitive feature with no milestone currently
named for it — flagging its absence rather than silently deciding it's
out of scope forever.

### 13.3 — Does shadow execution count as M4's "policy plurality"?

**Recommendation: no, and the distinction is load-bearing.** M4 owns
*multiple policies whose Findings all contribute to the Verdict*, with
aggregation and disagreement surfaced to whoever consumes the Verdict.
Shadow execution runs an *additional* policy against the same event, but
its Finding never reaches the Verdict, is never aggregated, and is never
surfaced to the ingestion caller at all — it exists purely for offline
comparison (an operator later queries `shadow_findings` against what
`findings` actually recorded). `GovernanceVerdict.status` is still
determined by exactly one policy throughout M3, same as M0-M2. If this
distinction doesn't hold up against the real architecture document,
that's the one finding in this review most likely to require redesign,
not just a parameter tweak.

### 13.4 — Single universal ingestion endpoint, or registry-generated per-adapter routes?

Already argued in §4: **recommend registry-generated per-adapter routes**,
not one endpoint doing manual runtime schema dispatch — preserves
FastAPI's automatic request validation and OpenAPI accuracy, which this
project has consistently treated as load-bearing (`test_malformed_payload_returns_422_not_500`
exists at every milestone that touches ingestion). The cost: "one
endpoint" language in prior docstrings turns out to mean "one *dispatch
mechanism*," not literally one URL path. Worth your explicit confirmation
since the prior phrasing was fairly literal.

### 13.5 — How does registering a plugin validate that the code actually exists?

If `POST /v1/admin/plugins` accepts an arbitrary `plugin_id`/`version`
string with no relationship to what's actually deployed, an admin could
register a phantom plugin that then fails at dispatch time. **Recommendation:**
registration only succeeds for `(plugin_type, plugin_id, version)`
combinations the in-process registry already knows about (i.e., the
Python class registered itself via the decorator at import time, before
the Admin API call ever arrives) — the Admin API call sets/changes
*lifecycle state* for something that self-registered at process startup,
it doesn't conjure a new implementation into existence. This mirrors
`SystemRepository.get_or_create_by_name`'s general shape (the DB records
facts about things the code already knows how to handle) rather than the
DB being a source of truth the code has to dynamically satisfy.

### 13.6 — Where does the "one PRODUCTION per plugin_id" invariant live?

**Recommendation: the database** (the partial unique index in §6), not
application-layer checking. This is the exact lesson M1's evidence-
immutability work already taught this project: a guarantee enforced only
in application code is one bug away from being silently violated; a
guarantee enforced by the database is structurally guaranteed. The
promotion endpoint should still *also* check first and return a clean
error (not rely on catching a constraint-violation exception as its
primary UX) — but the DB constraint is the actual guarantee, the
application check is just a nicer error message.

### 13.7 — Do M2's existing adapters/policies get retrofitted into the registry?

**Recommendation: yes, immediately, as part of M3 itself** — already
argued in §2. Leaving them permanently hardcoded while only new (M3+)
plugins go through the registry would leave two parallel, inconsistent
dispatch mechanisms coexisting indefinitely, which is a worse end state
than either "everything hardcoded" (M2's honest stopgap) or "everything
registry-driven" (M3's actual job). The retrofit is also the acceptance
criterion (§11.1) that proves the registry works against real cases
rather than only hypothetical future ones — the same standard M2 held
itself to with `CreditScorecardAdapter`.

### 13.8 — Does M3 finally make protected-attribute classification rules DB-backed?

**Recommendation: no — defer this specifically to M5,** not M3. M2's own
design doc left this genuinely open between "M3 plugin config" and "M5
Policy Bindings." Having now designed M3's actual scope, it's clear M3's
registry is about **which implementation is trusted to run** (identity +
lifecycle), not **how a given trusted implementation is internally
parameterized** (a policy's ruleset, thresholds, etc.) — those are
different axes. The latter is much closer to M5's explicitly-named
"which policy applies to which domain/jurisdiction" territory (Policy
Bindings), since a ruleset is itself a kind of binding between a policy
and a domain. Conflating them into M3 would widen this already-large
milestone further without a forcing case (no second domain exists yet
that would need a *different* ruleset, which is the same "no second case
to validate against" reasoning M2 used to defer generalizing the
ingestion endpoint).
