## What Was Built

Everything in the approved design below, built exactly as decided across
all fourteen approval-checklist items — no schema surprises beyond the
two purely additive migrations, no scope creep past architecture §12, and
no genuine architectural contradiction forced a deviation from the frozen
design.

- **`schemas/human_review.py`** — `VerdictReviewStatus`/
  `VerdictReviewResolution`/`VerdictReview`,
  `PopulationFindingReviewStatus`/`PopulationFindingReviewResolution`/
  `PopulationFindingReview` (two separate enum pairs, per §3.3), and
  `_REVIEWABLE_VERDICT_STATUSES = {ESCALATE_FOR_REVIEW, RECOMMEND_HOLD}`
  per §3.6/§9.1 — the one canonical definition, imported by both the live
  write path and the reconciliation tool, not duplicated.
- **`db/repositories/verdict_review.py`,
  `db/repositories/population_finding_review.py`** — idempotent-upsert
  `create` (`INSERT ... ON CONFLICT (verdict_id) WHERE status !=
  'RESOLVED' DO NOTHING`, matching the partial unique index exactly, per
  §3.4/§4.8) and conditional-`UPDATE` `claim`/`release`/`resolve` (checked
  by row count, never a read-then-write two-step, per §3.7). `resolve`
  requires `reviewer` to match who claimed it.
- **`VerdictRepository.get_many`** — the new batch-fetch method §5.1
  called for, avoiding an N+1 query pattern in the verdict-reviews list
  endpoint.
- **`api/admin/verdict_reviews.py`, `api/admin/population_finding_reviews.py`**
  — five endpoints each, per §3.7: `list`/`get`/`claim`/`release`/
  `resolve`, embedding the full `Verdict`/`PopulationFinding` in every
  response. The verdict-reviews list endpoint supports the `severity`
  filter (joins to the referenced `Verdict`'s own `status`); both list
  endpoints default to oldest-open-first ordering. `claim`/`release`/
  `resolve` translate a repository `ValueError` into a `409` via an
  explicit `try`/`except`, never the codebase's global `ValueError → 422`
  handler.
- **`human_review/backfill_reviews.py`** — the reconciliation tool
  (`reconcile_verdict_reviews`, `reconcile_population_finding_reviews`,
  `main`), using the identical idempotent-upsert semantics as the live
  path and scoped to the same `_REVIEWABLE_VERDICT_STATUSES` constant, per
  §3.5/§9.3. Per-record `Session` isolation, mirroring
  `run_policies.py`'s own per-binding isolation — one record's failure is
  logged and counted, never allowed to abort reconciling the rest.
- **Migrations `0023`–`0024`** — `verdict_reviews`, `population_finding_reviews`:
  purely additive `CREATE TABLE`, each with an explicit `ON DELETE
  RESTRICT` foreign key, a partial unique index scoped to non-`RESOLVED`
  rows (not a plain `UNIQUE` — §3.2), and a `status` index for the list
  endpoints' primary query, per §5.2.
- **`audit/evidence_store.py`** — `EvidenceStore.append` gains
  `_queue_verdict_review`, called after `append`'s own transaction commits,
  in a **separate** `Session`; `append`'s own transaction body is
  byte-for-byte unchanged, per §3.4.
- **`population_engine/run_policies.py`** — the identical decoupled,
  idempotent, failure-swallowing pattern for `PopulationFindingReview`,
  per §3.4.
- **`api/dependencies.py`, `api/app.py`** — three new repositories and two
  new Admin API routers wired into the composition root, per §5.1.
- **No new plugin port, no UI, no notification mechanism, no reviewer
  authentication beyond the identity-continuity check, no signing of the
  resolution itself** — §3.8/§8, as designed.

## Production-Readiness Review

Performed after implementation, before freeze — mirroring M0–M8's own
finalization passes, with one material difference from every prior
milestone's own review, disclosed here rather than glossed over: **this
sandbox has no working Docker daemon this session** (confirmed directly —
`docker ps` fails with "failed to connect to the docker API," not merely
"no container running"), so none of this milestone's Postgres-dependent
behavior could be exercised against a real database. Every prior
milestone's own finalization pass (M1 onward) explicitly notes this same
sandbox constraint for *local* runs and relies on CI's Postgres service
container for the real gate; M9 is the first milestone where that CI-only
reliance is total, because unlike M5–M8 (where at least some session in
this project's history had a local Postgres available to verify against
directly, per those documents' own "Verified against: Real Postgres 16
(local container)" lines), no session producing this document had one
available at all. This is named as loudly as this section can name it —
see "What Could Not Be Verified" below for exactly what that means and
what remains for CI (or a follow-up local run) to actually confirm.

**Finding (fixed): `sqlalchemy.dialects.postgresql.insert(...)`'s `Insert`
construct does not accept a mapped class's `__table__` attribute under
`mypy --strict`.** The first implementation pass built the idempotent
upsert as `pg_insert(VerdictReviewRow.__table__).values(...)`
`.on_conflict_do_nothing(index_elements=[VerdictReviewRow.__table__.c.verdict_id], ...)`.
`mypy --strict` rejected the `Insert` construct's first argument
(`FromClause` is not assignable to the stubbed parameter type). Fixed by
passing the ORM-mapped class directly (`pg_insert(VerdictReviewRow)`) and
referencing `index_elements`/`index_where`/`returning` via the class's own
instrumented attributes (`VerdictReviewRow.verdict_id`,
`VerdictReviewRow.status`, `VerdictReviewRow.id`) rather than
`__table__.c.*` — semantically identical SQL, a cleaner, more idiomatic
SQLAlchemy 2.0 ORM-DML construction, and the one `mypy`-accepted spelling.
Applied identically in `population_finding_review.py`.

**Finding (fixed): `Session.execute()`'s static return type
(`Result[Any]`) does not expose `.rowcount` under `mypy --strict`, even
though a Core `UPDATE` against a mapped class always returns a
`CursorResult` at runtime.** `claim`/`release`/`resolve` each depend on
`result.rowcount == 0` to detect a conditional `UPDATE` that matched no
row — the entire concurrency-safety mechanism this milestone's claim/
resolve design depends on (§3.7/§9.6). Fixed with an explicit
`assert isinstance(result, CursorResult)` immediately after
`session.execute(statement)`, in all six call sites (three transitions ×
two repositories) — narrows the type for `mypy`, and, since it reflects a
genuine runtime invariant for every Core DML statement this codebase
issues (no exotic `execution_options` are used anywhere that would change
this), never actually raises.

**Confirmed, not fixed — the two pre-existing defects named in the design
(§9.5/§9.6).** Re-confirmed during implementation by reading
`infra/migrations/0008_grant_evidence_chain_privileges.sql` and
`db/repositories/population_policy_binding.py`/`db/repositories/policy_binding.py`
directly, exactly as the design's own hostile-review pass had already
verified them: `verdicts`/`findings`/`decision_events`/`model_versions`/
`systems`/`verdict_findings` still have no `REVOKE UPDATE, DELETE`, and
`set_lifecycle_state` still has no conditional-update protection. Neither
touched — both remain M9's disclosed, out-of-scope findings, not
implementation-time fixes.

**Reviewed, no issue found:**
- **Every existing test file, run unmodified against the M9 codebase** —
  all 429 pre-M9 tests (220 passing locally, 209 requiring Postgres and
  skipping cleanly, exactly as before) continue to pass/skip identically;
  no existing API request/response shape, migration, or table was altered.
- **`EvidenceStore.append`'s own transaction body** — confirmed

  the only addition is one new call
  (`self._queue_verdict_review(verdict)`) between the existing

- **`run_policies.py`'s existing per-binding failure-isolation and

- **The claim/release/resolve conditional-`UPDATE` pattern's departure

**Named, not fixed — deliberate scope boundaries, not gaps found late:**

### What Could Not Be Verified

Named explicitly rather than silently assumed passing, per this
milestone's own discipline for everything else it documents:

- **The idempotent `ON CONFLICT ... WHERE ... DO NOTHING` upsert against

  by careful static reading against Postgres's own documented `ON

  but **never executed against a real Postgres** in this session.

  under genuine concurrent load — reasoned through carefully (§3.7/§9.6)
  and exercised by `test_the_claim_race_directly`/
  `test_the_backfill_and_live_traffic_race_never_raises_for_either_writer`,
  but those tests, like every other Postgres-dependent test this
  milestone adds, could not actually run.
- **All 70 new Postgres-dependent tests** (12 unit tests for
  `schemas/human_review.py` *did* run locally and pass; the remaining 70
  integration tests across six new/extended files are marked
  `@requires_postgres` and skipped cleanly, exactly as this codebase's own
  standing convention requires when `POSTGRES_URL` is unset — see
  Test Statistics).
- **The real HTTP round trip** for all ten new endpoints, including the
  `409`-vs-`422` distinction the design specifically calls for (§3.7/§7)
  and the reopening path exercised through the API
  (`test_resolving_then_reopening_makes_both_rows_visible_in_the_list`).

**Recommendation, stated as plainly as this section can state it:** treat
this milestone as *implemented and locally verified for everything that
does not touch Postgres* (lint, types, the 12 new/232 total non-Postgres

majority of its own logic, until the 70 new integration tests actually run
— in CI, or in a follow-up session with a working local Postgres. This is
a stronger caveat than any prior milestone's own review needed to state,
because M9's core mechanism (idempotent upsert against a partial index,

## Verdict

M9 is implemented exactly as the frozen design specifies, across all
fourteen approval-checklist items, with zero deviation forced by a genuine
implementation-time architectural contradiction. Two real issues were
found and fixed during this milestone's own post-implementation review —
both `mypy --strict` type-checking corrections that reflect getting the
underlying SQLAlchemy 2.0 API usage right (the ORM-class-vs-`__table__`
argument to `sqlalchemy.dialects.postgresql.insert`, and a
`CursorResult`-vs-`Result` narrowing for `.rowcount`), neither a change to
the design's own logic. The two pre-existing defects the design's own
hostile-review pass found and deliberately left unfixed (§9.5/§9.6) were
re-confirmed present, exactly as documented, and remain untouched.
`GovernanceEngine`, every per-event `Policy`/`Adapter`, both ingestion
routes, `evidence_chain`, `population_findings`, and every M7/M8 endpoint
remain completely untouched; the full pre-M9 test suite continues to
pass/skip unmodified against the M9 codebase.

**Unlike M5–M8, this milestone's own finalization pass could not verify
its Postgres-dependent behavior against a real database in this session**
— Docker was unavailable throughout, confirmed directly rather than
assumed. Everything checkable without a live database (lint, strict
types, and the 232 tests that don't touch Postgres) is clean. The 70 new
integration tests — including the two directly targeting this milestone's
most novel mechanism, the idempotent `ON CONFLICT` upsert against a
partial unique index racing under real concurrency — are written,
reviewed carefully against Postgres's and SQLAlchemy's own documented
semantics, and believed correct, but **not yet empirically proven**. This
milestone should not be considered fully verified, in the sense every
prior milestone's own "Verdict" used that word, until those 70 tests
actually run against a real Postgres — in CI, or in a follow-up session
with Docker available — and the result is folded back into this document.

### Revision note (hostile-review pass)

This document has been through a hostile-review pass (assume-it's-wrong-
until-proven-otherwise, the identical discipline M5–M8 each went through
before their own implementations began). Eleven findings came out of it.
Three were severe enough to change the proposed architecture rather than
just annotate it, and are folded in below, in place, rather than kept as a
separate errata section — mirroring exactly how M8 folded in its own two
hostile-review corrections:

1. **§3.4 reversed**: review-row creation moves out of
   `audit/evidence_store.py`'s `EvidenceStore.append` transaction (and out
   of `population_engine/run_policies.py`'s finding-persistence transaction)
   into a separate, immediately-following transaction whose failure never
   fails the underlying request/run. The original design's "same
   transaction, always" recommendation would have let a bug in this
   milestone's own new, non-essential workflow code silently prevent the
   recording of a real, already-made governance decision — this platform's
   single most important guarantee, put at risk by a feature that has
   nothing to do with evidence integrity.
2. **§3.2/§5.2 reversed**: the full `UNIQUE (verdict_id)` /
   `UNIQUE (population_finding_id)` constraints become partial unique
   indexes scoped to non-`RESOLVED` rows. The original design reproduced,
   in a brand-new table, the *exact* defect M8 spent an entire migration
   fixing in `population_policy_bindings` — a plain uniqueness constraint
   that permanently forecloses legitimate re-creation. Here that meant no
   escalation could ever be reopened once resolved.
3. **§3.3 reversed**: the workflow gains an explicit `IN_REVIEW → OPEN`
   release/unclaim transition. The original three-state, no-path-backward
   design had no way to recover an abandoned claim — an `IN_REVIEW` item
   with a reviewer who went silent was *permanently* hidden from anyone
   filtering the open queue, which is worse than the item never having
   been claimed at all.

Beyond these three, several findings are folded in as amendments — real
gaps that don't change the overall shape of the design but do change its
details: idempotent (`ON CONFLICT ... DO NOTHING`) semantics are now
required for review-row creation on both the live path and the backfill
script, since decoupling (correction 1) and concurrent backfill runs both
create a real race the original design never examined (§3.4/§3.5); the
backfill script is reframed from a one-time migration helper into a
standing, periodically-safe-to-rerun reconciliation tool (§3.5/§9.3); the
Admin API gains a `release` endpoint (correction 3), severity-aware
filtering for verdict reviews (§9.1's refinement), oldest-open-first
default ordering, and a cheap non-auth identity-continuity check requiring
`resolve` to restate the `reviewer` who claimed the item (§3.7/§7); the new
foreign keys specify `ON DELETE RESTRICT` explicitly rather than relying on
Postgres's implicit default (§5.2); and the implementation plan now
accounts for a new batch-fetch method `VerdictRepository` needs to avoid an
N+1 query pattern in the review-list endpoint (§5.1), which the original
plan omitted entirely.

Two more findings were confirmed as **real, pre-existing defects in code
this milestone did not write and is not responsible for fixing** — found
only as a byproduct of designing M9's own foreign keys and concurrency
model, exactly the way M8 §13.20 found `policy_bindings`' identical
recreate-after-deactivate defect as a byproduct of fixing
`population_policy_bindings`' copy of it. Both are documented at §9.5/§9.6
as verified, outstanding candidates for a dedicated follow-up — **not**
silently fixed inside M9, and not blocking this milestone's own
implementation:

- `verdicts`, `findings`, `decision_events`, `model_versions`, `systems`,
  and `verdict_findings` are not `REVOKE UPDATE, DELETE`-locked at the
  database-privilege level — only `evidence_chain` and `population_findings`
  ever received that lockdown. This has been true since M1/M5; no design
  document has ever said so until this one, because M9 is the first
  milestone to add a real foreign key pointing *at* `verdicts` (§9.5).
- `PopulationPolicyBindingRepository.set_lifecycle_state` (and
  `PolicyBindingRepository`'s identical twin) use a plain read-then-write
  with no conditional-update/row-count check — a genuine, previously
  undocumented race between two concurrent activate/deactivate calls,
  found only because M9's own `claim`/`resolve` needed a *stronger*
  pattern and this was the natural precedent to check first (§9.6).

Four findings were examined and confirmed **not** to require any change:
no FK from either review table to `plugin_registrations` means a
deregistered or demoted `PopulationPolicy` plugin has zero effect on an
existing finding or its review (§3.8); there is no delete pathway for
`systems` anywhere in this codebase's API surface, so system deletion is a
moot risk for the new foreign keys (§5.2); the two review queues staying
independent with no cross-linking, even when both population policies
flag overlapping evidence, is consistent with — not a violation of — M8's
own "no cross-policy aggregation" stance (§1); and `resolve`'s binary
`CONFIRMED`/`DISMISSED` outcome with mandatory non-empty notes needed no
change at all.

This section records that the design below is the **corrected** design —
every subsection that follows already reflects the reversals and
amendments above, the same convention M8 used ("this section records the
design exactly as approved before implementation began").

### Final approval and freeze

Following the hostile-review pass above, three genuine value/scope
judgments remained open (§9.1, §9.2, §9.3) — the hostile-review pass could
refine the reasoning behind each but, correctly, did not manufacture an
answer to any of them itself. All three have now been decided, explicitly,
and are recorded as final:

1. **Both `ESCALATE_FOR_REVIEW` and `RECOMMEND_HOLD` create review
   records** (§9.1) — the generous reading, not the narrower one the
   architecture's literal citation would have supported on its own.
2. **Review workflow state remains unsigned**; cryptographic signing of a
   review's resolution is deferred to a future milestone, not built here
   (§9.2).
3. **The reconciliation/backfill tool remains part of M9 itself**, as a
   versioned, idempotent application component that can be safely rerun —
   not separate ops-runbook tooling (§9.3).

Every section below already reflects these three decisions as settled
architecture, not as open recommendations. **This design is now frozen**
(see "Design frozen" at the end of this document) — implementation has not
begun, and should not begin from any reading of this document other than
the one recorded here.

## TL;DR

M9 builds `architecture-mapping.md` §12's "Human Review Workflow" — the one
deferred item named explicitly, by number, in every design document since
M5 (`docs/milestones/M5.md` §12/§15, M6 §12/§15, M7 §12/§15, M8 §12/§15)
and never once touched. The citation trail is unusually consistent across
four milestones: an `ESCALATE_FOR_REVIEW` (or `RECOMMEND_HOLD`)
`GovernanceVerdict` (M5) and a `FLAGGED` `PopulationFinding` from either
population policy (M6/M8) are both fully computed, persisted, signed
(population findings) or chained (verdicts), and — as of M7 — countable via
`GET /v1/admin/metrics`. Nothing anywhere converts either of those computed
facts into a queue a human can act on. `README.md`'s own "What remains
after M8" section states this plainly: M9 is what "finally gives ...
somewhere to go."

This is a materially different shape of milestone than M7 or M8. M7 was a
read-only window onto existing state; M8 was a generalization of an
existing port. M9 introduces the first genuinely new, **mutable**,
admin-managed workflow state this platform has ever needed for a
**computed governance output** — every existing mutable table
(`plugin_registrations`, `policy_bindings`, `population_policy_bindings`)
tracks the lifecycle of *configuration* (is this code trusted, does this
policy apply here), never the lifecycle of a *result*. `verdicts`,
`findings`, `population_findings`, and `evidence_chain` are all
insert-once, append-only, evidentiary records precisely because a computed
governance judgment must never be edited after the fact. A human review
workflow is the first feature this platform has ever needed that must
track changing state (open → claimed → resolved, and now — after the
hostile-review pass — reopenable) **about** one of those immutable
records, without ever mutating the record itself. That tension — real
workflow mutability sitting next to an evidentiary record that must stay
frozen — is the central architectural problem this document works through,
not a generic "add a queue" CRUD exercise.

Concretely, the (now hostile-review-corrected) design adds two new,
parallel, purely additive tables — `verdict_reviews` and
`population_finding_reviews` (§3) — each a thin, mutable workflow record
with a real foreign key to exactly one already-persisted `Verdict` or
`PopulationFinding`. **Corrected from the original design** (see the
revision note above): a review row is created in its own, separate
transaction, immediately after — not inside — the transaction that
persists its qualifying `Verdict`/`PopulationFinding`
(`audit/evidence_store.py`'s `EvidenceStore.append`, and
`population_engine/run_policies.py`'s per-binding write), using an
idempotent (`ON CONFLICT ... DO NOTHING`) insert, so neither a bug in this
new code nor a race with the reconciliation script (§3.5) can ever prevent
a real governance decision from being recorded as evidence. The workflow
is four-state (`OPEN → IN_REVIEW → RESOLVED`, plus `IN_REVIEW → OPEN` via
an explicit release), and the uniqueness constraint that used to make a
resolved review permanent now only enforces "at most one *active* review
per verdict at a time" — a resolved verdict can be reopened by a later
review, mirroring the exact partial-index fix M8 built for
`population_policy_bindings`.

No new plugin port. No change to `GovernanceEngine`, `Policy`, `Adapter`,
`PopulationPolicy`, `evidence_chain`, `population_findings`, or any M7
endpoint. No UI (`M10`, the Compliance Dashboard, is what would render this
data for a human — this platform has never built a UI in eight milestones
and does not start here). No notification/paging mechanism, no reviewer
authentication, no signing of the resolution itself — all named explicitly
and deferred, not silently skipped (§7/§8).

Two findings surfaced by this design's own two-pass hostile review are
severe enough to be load-bearing rather than footnotes. First:
**same-transaction auto-creation only ever covers records written from M9
onward** — every `ESCALATE_FOR_REVIEW`/`RECOMMEND_HOLD` `Verdict` and every
`FLAGGED` `PopulationFinding` already sitting in a real deployment's
database at the moment M9 ships needs an explicit backfill, the same
"a new feature over old data needs an explicit answer for the old data"
lesson M6 learned for `classification_snapshot` and M8 learned for
`parameters_used`, recurring a third time (§3.5). Second, found during the
*second* hostile-review pass specifically: **decoupling review-row
creation from the evidence-write transaction (fix #1 above) reopens a
narrow race between the live write path and the backfill/reconciliation
script** — both must use idempotent upsert semantics, or whichever writer
loses the race fails outright (§3.4/§3.5). The backfill script is
therefore reframed from a one-time migration helper into a standing,
periodically-safe-to-rerun reconciliation tool — closer in spirit to
`audit/verify_chain.py` (a permanent, reusable tool) than to
`infra/ci/setup_test_role.py` (genuinely one-shot, CI-only tooling).

## 1. Scope and architectural responsibilities

What M9 is exactly responsible for:

- A durable, queryable **review queue** for exactly two kinds of computed
  governance output that currently have no consumer: a per-event
  `GovernanceVerdict` whose `status` is `ESCALATE_FOR_REVIEW` or
  `RECOMMEND_HOLD` (M5), and a `PopulationFinding` whose `outcome` is
  `FLAGGED` (M6/M8), from either population policy.
- A minimal **workflow state machine** for each queued item: `OPEN` (newly
  queued, unclaimed) → `IN_REVIEW` (a named reviewer has claimed it) →
  `RESOLVED` (a recorded outcome and a mandatory human-written rationale),
  with an explicit `IN_REVIEW → OPEN` **release** transition for an
  abandoned claim, and — since a resolved item is no longer permanently
  terminal (§3.2/§3.3) — a path for a *new* review to open against a
  verdict/finding whose prior review already reached `RESOLVED`.
- **Reliable, idempotent queuing** at the moment a qualifying record is
  persisted, immune to both a bug in this new code blocking the underlying
  evidence write (§3.4) and a race between the live write path and the
  reconciliation tool (§3.4/§3.5) — not "exactly once by construction"
  (the original, now-corrected claim) but "eventually exactly once,
  self-healing under either failure mode, and never blocking the more
  important write it depends on."
- A **backfill/reconciliation tool** so records that already exist in a
  real deployment's database before M9 ships — or, rarely, a record whose
  live-path review-row creation failed — are not permanently excluded from
  the workflow (§3.5).
- A minimal **Admin API** to list/inspect the queue, claim an item,
  release it, and resolve it — the same "manages facts, computes nothing,
  loads no new code" boundary every other Admin API in this codebase
  draws, applied here to *workflow state about* a computed fact rather
  than to configuration.

What M9 is explicitly **not** responsible for, named here so it isn't
assumed by omission:

- Rendering any of this to a human visually — no UI, no dashboard. That is
  `architecture-mapping.md` §11, M10's job, and M10 needs M9's data to
  exist first, the same "compute, then expose, then visualize" layering
  M6 → M7 → M10 already establishes for population findings.
  (`README.md`'s own framing: "M9 is the Human Review Workflow that
  finally gives ... somewhere to go; M10 is the Compliance Dashboard that
  would actually render this data for a human.")
- Notifying, paging, or otherwise pushing a review item at anyone. The
  workflow is pull-only (an admin queries the queue); no email, webhook,
  or scheduled digest is built (§8). The one concession to this gap that
  *is* in scope, at essentially zero cost, is the list endpoint's default
  ordering (oldest-open-first, §3.7) — not a substitute for real
  notifications, just a cheap way to keep the oldest, most-overdue items
  from being invisible at the bottom of an unbounded, unpaginated list.
- Authenticating who is allowed to claim, release, or resolve an item.
  This platform has had no authentication in front of any endpoint since
  M2 first documented the gap; M9 does not close it, and — as argued in
  §7 — sharpens why it matters more here than anywhere it has been named
  before. The one in-scope mitigation is a **non-authentication** sanity
  check: `resolve` must restate the `reviewer` recorded at `claim` time,
  and a mismatch is rejected (§3.7) — this catches accidental cross-wiring
  (two tabs, a copy-pasted request against the wrong item), not a
  malicious actor, and does not change the fundamental gap named in §7.
- Blocking, delaying, or otherwise changing what any ingestion route
  returns to its caller. `RECOMMEND_HOLD` is, and remains, advisory —
  `api/ingestion/routes.py` already returns whatever `VerdictStatus` was
  computed with no branching on its value (confirmed by reading the
  route: the response body's `status` field is set unconditionally to
  `verdict.status`). M9 adds a place for a human to act on that
  recommendation *afterward*; it does not add a synchronous hold
  mechanism, which would be a fundamentally different, much larger
  feature this milestone does not attempt.
- A cross-policy or cross-verdict aggregation view ("show me everything
  flagged for system X across both Verdicts and PopulationFindings, ranked
  by severity"). Each of the two queues stays independent and parallel,
  mirroring every prior "structurally separate, never combined" call this
  project has made (`Policy`/`PopulationPolicy`, M6 §13.3;
  `policy_bindings`/`population_policy_bindings`, M6 §13.8; two population
  policies' findings, M8 §13.5) — confirmed correct on the second,
  hostile-review pass specifically for the case where both population
  policies flag overlapping evidence for the same system/window: two
  unlinked review items is an accepted, named limitation, not a defect.
- Building an actual "reopen" Admin API endpoint. The schema no longer
  *forecloses* a second review once the first is `RESOLVED` (§3.2/§3.3),
  but nothing in M9 exposes a code path that creates one — see §8.
- Fixing either of the two pre-existing defects the hostile-review pass
  found as a byproduct (§9.5/§9.6) — both real, both verified, neither
  introduced by M9, neither this milestone's to fix.

## 2. Relationship to previous milestones

M5 introduced the four-state `VerdictStatus` (`ALLOW` /
`ALLOW_WITH_FLAG` / `ESCALATE_FOR_REVIEW` / `RECOMMEND_HOLD`) and named,
in its own words, the gap this milestone closes: *"Escalation without
Human Review Workflow (M9) is a verdict that says 'review me' to nobody
yet"* (`docs/milestones/M5.md` §12) and *"architecture §12 (Human Review
Workflow) is explicitly M9's card, not folded into M5 by implication"*
(§13.14). M6 gave population-level analysis its own binary outcome
(`PopulationFindingOutcome.CLEAR` / `FLAGGED`) and repeated the same
deferral almost verbatim: *"A `PopulationFinding` has nowhere to escalate
to ... the identical gap M5 §12 already named for per-event verdicts, now
also true for population findings"* (`docs/milestones/M6.md` §12). M7 made
both kinds of output countable — `GET /v1/admin/metrics` reports
governance-health and population-binding-staleness signals — while
explicitly declining to add any consumer for either: *"Human Review
Workflow (architecture §12) — M9, still nothing consumes an
`ESCALATE_FOR_REVIEW` verdict or a `FLAGGED` `PopulationFinding` beyond
being queryable/countable"* (`docs/milestones/M7.md` §15). M8 added a
second population policy that can also produce `FLAGGED`, and repeated the
same line once more: *"a `FLAGGED` outcome from either population policy
still has no queue, notification, or escalation state to go to"*
(`docs/milestones/M8.md` §15).

So M9 is not a generalization of an existing port (M8's shape) and not a
new pipeline computing a new kind of governance judgment (M6's shape). It
is the first milestone whose entire job is to build **workflow
infrastructure around outputs every prior milestone already finished
computing** — nothing in `governance_engine/`, `population_engine/`,
`policy_engine/`, or any `Adapter` needs to change at all. This is closer
in shape to M7 (a new *consumer* of existing computed state) than to M6 or
M8 (new *producers* of governance judgments) — except M7's consumer was
read-only and stateless (a query), where M9's consumer is genuinely
stateful (a workflow with a lifecycle). No prior milestone in this
codebase has built a mutable table whose entire purpose is tracking a
process *about* an already-immutable evidentiary record — this is a new
relationship, not a repeat of an existing one, and §3 treats it as such.

M9's own hostile-review pass adds one more relationship worth naming: this
is the first milestone whose new write path is *deliberately decoupled*
from `EvidenceStore.append`'s single transaction, after M2 and M5 each
*added* a write inside it. Every addition to that transaction until now
made sense because the thing being added was part of what a governed
decision fundamentally *is* (a `Finding`, a `ProtectedAttributeResolution`,
a signature). A review row is not — it's a downstream consumer's
bookkeeping about an already-complete `Verdict` — and M9 is the first
milestone to draw that line explicitly rather than extend the transaction
further by default (§3.4).

M9 touches: `audit/evidence_store.py` (a new, separate transaction
immediately following `append`'s own, §3.4), one new step in
`run_policies.py`'s existing per-binding flow, two new schema files, two
new repositories, two new Admin API routers, and two new tables. M9 does
not touch `GovernanceEngine`, `Policy`, `Adapter`, `PopulationPolicy`,
`evidence_chain`, `verdicts`, `findings`, `population_findings`,
`plugin_registrations`, or any M7 endpoint — every existing computed
record's shape and meaning is completely unchanged.

## 3. Proposed architecture (this review's recommendation)

### 3.1 A new, parallel review-tracking layer — not new columns on immutable evidence tables

The most tempting wrong design is adding a `review_status` column directly
to `verdicts` and `population_findings`. Both tables are evidentiary
records at the core of this platform's audit story: `verdicts` is embedded,
verbatim, inside `evidence_chain.payload` (hash-chained, signed since M5);
`population_findings` is independently signed and append-only at the
database-privilege level (`REVOKE UPDATE, DELETE`, migration `0015`).
Adding a mutable column to either would either (a) require granting
`UPDATE` back on `population_findings`, undoing the exact privilege
lockdown M6 built specifically because "a `population_finding` is computed
governance output, evidentiary in the same sense a `Verdict` is" (migration
`0015`'s own comment), or (b) for `verdicts`, mutate a table whose row is
also frozen inside `evidence_chain`'s hashed payload, creating two
disagreeing views of "the verdict" (the chain's frozen copy vs. the
row's now-mutable one) for the first time in this platform's history.
**Recommendation: never.** Review state lives in a new, separate table with
a foreign key to the evidentiary record it's about, exactly the same
"structurally separate, not a shared column" discipline this codebase
already applies to `shadow_findings` (parallel to `findings`, never
combined) and `population_findings` (parallel to `findings`, never
combined). See §4.2 for the alternative this rejects explicitly.

Confirmed unchanged by both hostile-review passes.

### 3.2 Two parallel tables, each with a partial-unique, reopenable identity — not a polymorphic table, and not a permanently-terminal one

Two real per-subject-type shapes were considered for *which tables*:

**(a) One polymorphic `human_reviews` table**, with a `subject_type`
discriminator column (`VERDICT` / `POPULATION_FINDING`) and a
`subject_id` column referencing either `verdicts.id` or
`population_findings.id` depending on `subject_type`.

**(b) Two parallel tables**, `verdict_reviews` and
`population_finding_reviews`, sharing no table, only a common workflow
*shape* at the Python schema/API level.

**Recommendation: (b), unchanged from the original design.** A single
column cannot carry a real foreign-key constraint to two different parent
tables — option (a) would mean Postgres can never enforce that
`subject_id` actually names an existing row, silently reopening exactly
the kind of referential-integrity gap this codebase has never accepted
anywhere else (every existing table with a natural parent —
`decision_events.model_version_id`, `findings.decision_event_id`,
`population_policy_bindings.system_id`, `verdict_findings`'s composite key
— uses a real `FOREIGN KEY`, enforced at the database, not validated only
in application code). `Verdict` and `PopulationFinding` are different
shapes with different identity keys; a review of one is not
interchangeable with a review of the other, and this codebase already has
a working precedent for "two genuinely parallel entities get two
genuinely parallel tables, sharing schema shape, not storage" —
`policy_bindings`/`population_policy_bindings` themselves.

**Corrected by the hostile-review pass: the identity constraint on each
table.** The original design specified `verdict_id TEXT NOT NULL UNIQUE
REFERENCES verdicts(id)` — a full uniqueness constraint making "at most
one review, ever, ever again" a hard schema fact. That reproduces, in a
brand-new table, the exact mistake M8 spent migration `0022` fixing in
`population_policy_bindings`: a plain constraint that was fine at the
moment it shipped (nothing needed a second row yet) but permanently
forecloses a legitimate future need the moment one appears — here, a
regulator or auditor requesting re-examination of a previously-`DISMISSED`
escalation, or new evidence surfacing after the fact. **Corrected to a
partial unique index scoped to non-terminal status**:
`one_open_verdict_review_per_verdict`, `UNIQUE (verdict_id) WHERE status
!= 'RESOLVED'` (and the identical shape,
`one_open_population_finding_review_per_finding`, for the other table).
At most one *active* review per verdict at a time; once `RESOLVED`, a new
row (not a mutation of the old one) can open a second review, preserving
the first's history exactly as it was written. As with M8's own version
of this fix: relaxing the constraint alone does not build a "reopen"
capability (nothing yet creates that second row) — this schema-level fix
is deliberately made *now*, before any real data exists under the wrong
constraint, precisely so a future milestone that *does* build reopening
doesn't have to repeat M8's own two-step discovery (relax the constraint,
then separately discover the application code also needs to change).
Building the reopen endpoint itself remains out of scope for M9 (§8).

This also settles a related, smaller question the original design didn't
examine: whether each table needs its own surrogate `id` primary key, or
whether `verdict_id`/`population_finding_id` could serve as the natural
key directly (mirroring `verdict_findings`' composite-key precedent, which
has no surrogate `id` at all). Under the corrected, partial-index design,
multiple rows legitimately exist per `verdict_id` over time — a surrogate
`id` is therefore the right call, matching `population_policy_bindings`'
own shape (surrogate `id` **and** a partial unique index) exactly, not
`verdict_findings`' (composite key, no surrogate, because that join table
never needs more than one row per pair).

**Also corrected: `ON DELETE` behavior is now explicit.** The original
design left it to Postgres's implicit default (`NO ACTION`). Every other
constraint in this schema is accompanied by a comment explaining its
shape — an unstated default here was inconsistent with that convention.
Both foreign keys now specify `ON DELETE RESTRICT` explicitly, with a
comment noting that nothing in this codebase currently deletes a `Verdict`
or `PopulationFinding` (there is no delete pathway for either), so this
enforces an invariant rather than changing behavior — but states it,
rather than relying on an unstated default matching it by accident.

### 3.3 Review lifecycle: `OPEN` ⇄ `IN_REVIEW` → `RESOLVED`, with reopening via a new row

Four transitions, not three, after the hostile-review pass:

- **`OPEN`** — created (§3.4) when a qualifying `Verdict`/`PopulationFinding`
  is persisted, or by the reconciliation tool (§3.5) for one that already
  existed. Unclaimed.
- **`IN_REVIEW`** — a named reviewer has claimed it
  (`POST .../{id}/claim`, body `{"reviewer": "..."}`). Exactly one claimant
  at a time; claiming an already-claimed or already-resolved item is
  rejected (§3.7, §7).
- **`IN_REVIEW → OPEN` (release)** — **new, added by the hostile-review
  pass.** `POST .../{id}/release`, clearing `reviewer`/`claimed_at`,
  returning the item to `OPEN` so a different reviewer (or the same one,
  later) can claim it. The original design had no path back from
  `IN_REVIEW`; an abandoned claim (a reviewer reassigned, on leave, or who
  simply forgot) was **permanently** invisible to anyone filtering the
  queue by `status=OPEN` — worse than the item never having been claimed,
  since an unclaimed item is at least still visible. Given this platform
  has no authentication to even identify who claimed an item for
  follow-up, an unrecoverable claim was a realistic, not hypothetical,
  failure mode.
- **`RESOLVED`** — terminal *for this row*, not for the verdict/finding it
  references (§3.2). Set via `POST .../{id}/resolve`, body
  `{"reviewer": "...", "resolution": "CONFIRMED" | "DISMISSED", "notes":
  "..."}`. `notes` is `Field(..., min_length=1)` — mandatory, non-empty
  free text — mirroring the mandatory `rationale: str = Field(...,
  min_length=1)` this codebase already requires on every `Finding` and
  `PopulationFinding`. **`reviewer` is now required on `resolve`, not just
  `claim`, and must string-match the value recorded at claim time** — a
  cheap, pre-authentication integrity check added by the hostile-review
  pass (§7): it cannot stop a malicious actor (there is no real identity
  behind either string), but it does catch accidental cross-wiring (two
  browser tabs, a copy-pasted request against the wrong item) for free.

Resolution stays deliberately **binary** — `CONFIRMED`/`DISMISSED` — and
two separate enums (`VerdictReviewResolution` /
`PopulationFindingReviewResolution`) rather than one shared enum, exactly
as in the original design; both confirmed unchanged by the hostile-review
pass. `resolve` still requires `IN_REVIEW`, never directly from `OPEN` —
also unchanged (§4.4).

### 3.4 Review-row creation: a separate, idempotent transaction immediately following the qualifying write — not the same transaction

**This subsection is the headline correction from the hostile-review
pass.** The original design's recommendation was: *"synchronously, inside
the exact transaction that persists the qualifying `Verdict` or
`PopulationFinding`, never as a separate later step."* That recommendation
is reversed.

**What was wrong with it.** `audit/evidence_store.py`'s `EvidenceStore.append`
is the single most protected operation in this platform — it holds
`pg_advisory_xact_lock(913_411_007)`, a platform-wide serialization point
every ingestion request across every adapter passes through, and its
transaction exists to atomically persist `System`, `ModelVersion`,
`DecisionEvent`, every `Finding`, the `Verdict`, every protected-attribute
resolution, and the hash-chained `evidence_chain` row. Every one of those
writes is part of what makes a governed decision *complete* — a `Verdict`
without its `Finding`s is incomplete data. A `VerdictReview` is not: it is
a downstream consumer's bookkeeping about an already-complete `Verdict`.
Putting it inside the same transaction meant that if
`VerdictReviewRepository.create` ever raised — a bug, a transient lock
timeout, anything — the *entire* transaction would roll back, including
the hash-chained evidence record for a real, already-made decision. Unlike
`run_policies.py` (a batch job that already tolerates and gracefully
retries a per-binding failure on its next scheduled invocation, since a
rolled-back finding is simply recomputed cleanly next run), the ingestion
path has no such self-healing contract: a caller gets a `500` for a
decision that already happened in the real world, and whether it is ever
recorded as evidence depends entirely on whether the caller happens to
retry. For a platform whose entire purpose is "every governed decision
gets recorded," letting a brand-new, non-essential feature be capable of
silently defeating that guarantee was a real regression, not a
hypothetical one.

**The corrected design.** For `Verdict`: immediately after
`EvidenceStore.append`'s own `session.commit()` succeeds, a **second,
separate** `Session`/transaction inserts the `verdict_reviews` row (still
synchronous, still inside the same request — no new scheduling primitive,
no daemon, no poller; see §4.3 for why that remains rejected), guarded by
`if verdict.status in _REVIEWABLE_VERDICT_STATUSES`. If this second
transaction fails for any reason, the failure is logged and **does not
propagate** to the ingestion route's caller — the evidence record, which
already committed successfully in the first transaction, is unaffected,
and the gap this creates (a `Verdict` that qualifies for review but has no
review row yet) is exactly what the reconciliation tool (§3.5) exists to
close. For `PopulationFinding`: the identical pattern — a second,
separate transaction immediately after `population_finding_repository.create(...)`'s
own commit inside `run_policies.py`, guarded by `if finding.outcome is
PopulationFindingOutcome.FLAGGED`, applied for consistency even though
this path's existing per-binding retry tolerance already made the
original coupling comparatively low-risk.

**The new race this reopens, and its fix.** Decoupling widens the window
during which a qualifying record can exist with no review row yet — which
is precisely the window the reconciliation tool (§3.5) also operates in.
If the tool runs concurrently with live traffic (a realistic operational
scenario, not an edge case reserved for a maintenance window), it can
observe "no review row yet" for a verdict whose own live-path insert is
about to commit, and both writers can attempt to insert a row for the same
`verdict_id`. **Both the live path's insert and the reconciliation tool's
insert must therefore use idempotent upsert semantics** — `INSERT ...
ON CONFLICT (verdict_id) WHERE status != 'RESOLVED' DO NOTHING` (matching
the partial-index shape from §3.2), not a plain `INSERT` — so whichever
writer loses the race silently no-ops instead of raising. This requirement
applies identically to `population_finding_reviews`, and to two
concurrent invocations of the reconciliation tool itself (§3.5).

**What the original design got right and keeps.** A real foreign key with
a partial unique index still makes double-creation of an *active* review
for the same record impossible at the database level, not just by
application-level assumption — the database, not the application, remains
the final guarantee, matching this codebase's consistent preference for a
real constraint over an assumed invariant.

### 3.5 The backfill/reconciliation tool: covers historical gaps and the narrow live-path race alike

Same-transaction creation is gone (§3.4); a reconciliation mechanism was
already required for one reason (historical data) and is now required for
a second, related reason (the narrow, self-healing gap decoupling can
leave behind). Any real, non-trivial deployment reaching M9 already has
`Verdict`s with `status = ESCALATE_FOR_REVIEW`/`RECOMMEND_HOLD` and
`PopulationFinding`s with `outcome = FLAGGED` sitting in its database from
M5 through M8 — every one of them needs a review row created for it, or it
is permanently, silently excluded from this workflow. This is the same
shape of finding M6's own hostile-review pass found for
`classification_snapshot` and M8's found for `parameters_used`: **a new
feature over old data needs an explicit answer for the old data, never a
silent "starts now."**

**Recommendation, reframed from the original design's "one-time backfill
script" into a standing tool**: a small, dedicated, idempotent,
explicitly-invoked reconciliation tool (proposed:
`human_review/backfill_reviews.py`, `main(argv)` taking `--database-url`),
run once as a deployment step immediately after M9's migrations and code
ship, **and safe — and recommended — to re-run periodically thereafter**
(e.g. a nightly ops job, or manually after any incident), rather than
treated as a single migration-adjacent event. Concretely: `LEFT JOIN
verdicts v ... LEFT JOIN verdict_reviews vr ON vr.verdict_id = v.id WHERE
v.status IN ('ESCALATE_FOR_REVIEW', 'RECOMMEND_HOLD') AND vr.id IS NULL`,
using the same `ON CONFLICT ... DO NOTHING` insert (§3.4) — not a plain
`INSERT` — so a concurrent run of this same tool, or a concurrent live
write racing it, never raises. This is closer in spirit to
`audit/verify_chain.py` (a permanent, reusable verification tool this
platform re-runs whenever it wants assurance) than to
`infra/ci/setup_test_role.py` (genuinely one-shot, CI-only tooling) —
confirmed on the hostile-review pass as the more accurate frame, and
addressed as an open placement question at §9.3.

The tool is scoped, in code, to the identical `_REVIEWABLE_VERDICT_STATUSES`
constant the live write path uses (§5.1) — one definition, two consumers,
never a second, independently-maintained copy of "which statuses count"
that could silently drift out of sync with the live path over time. It
does not queue the legacy pre-M5 `VerdictStatus.FLAGGED` (§3.6).

### 3.6 Scope of "reviewable": both non-`ALLOW`/`ALLOW_WITH_FLAG` verdict statuses

`ESCALATE_FOR_REVIEW` (`PolicySeverity.MEDIUM`) and `RECOMMEND_HOLD`
(`PolicySeverity.HIGH`) both queue for review; `ALLOW` and
`ALLOW_WITH_FLAG` (`PolicySeverity.LOW`) never do. This reads the
architecture's literal `ESCALATE_FOR_REVIEW` citation generously rather
than narrowly — reasoned through in full at §9.1, reaffirmed by the
hostile-review pass, and **approved as final** (§9.1/§10): both statuses
create a review record.

The legacy `VerdictStatus.FLAGGED` member (pre-M5, historical-read-only —
`schemas/verdict.py`'s own docstring: "No M5+ code path ever *constructs*
a new `GovernanceVerdict` with `FLAGGED`") is excluded from
`_REVIEWABLE_VERDICT_STATUSES` and from the reconciliation tool's query
(§9.4) — confirmed unchanged by both hostile-review passes.

### 3.7 New Admin API surface

Two new routers — **now five endpoints each, ten total**, up from the
original design's four each/eight total, after the hostile-review pass
added `release` (§3.3) — mirroring every existing Admin API's shape
(plain `def` handlers, dependency-injected repositories, `HTTPException`
with a constructed string `detail`, action-verb sub-resource endpoints for
state transitions):

- `GET /v1/admin/verdict-reviews?status=&severity=` — list. **Corrected by
  the hostile-review pass in three ways**: (1) results default to
  **oldest-open-first** ordering (`created_at ASC`), not newest-first —
  with no pagination (unchanged from the original design, see §4.5) and no
  notification mechanism (§8), a newest-first default would actively bury
  the stalest, most-overdue items at the bottom of a response nobody
  scrolls to the end of; (2) an optional `severity` filter, resolved by
  joining to the referenced `Verdict`'s `status` at query time (no
  denormalized severity column needed on `verdict_reviews` itself, since
  `VerdictStatus` already encodes it via `governance_engine/engine.py`'s
  `_SEVERITY_TO_STATUS` mapping) — added because including both
  `ESCALATE_FOR_REVIEW` and `RECOMMEND_HOLD` in one undifferentiated queue
  (§3.6/§9.1) risks burying the more severe `RECOMMEND_HOLD` items among
  the more numerous `ESCALATE_FOR_REVIEW` ones without a way to prioritize
  them; (3) implemented via a new batch-fetch method on `VerdictRepository`
  (§5.1), not a per-row loop calling its existing `get()` — the naive,
  loop-based implementation an engineer following this codebase's existing
  repository patterns would reach for by default is an N+1 query pattern
  the original design's implementation plan never called out.
- `GET /v1/admin/verdict-reviews/{id}` — one item, same embedded shape
  (unchanged).
- `POST /v1/admin/verdict-reviews/{id}/claim` — body `{"reviewer": str}`.
  `409` if not currently `OPEN` (unchanged).
- `POST /v1/admin/verdict-reviews/{id}/release` — **new.** No body. `409`
  if not currently `IN_REVIEW`. Returns the item to `OPEN`, clearing
  `reviewer`/`claimed_at` (§3.3).
- `POST /v1/admin/verdict-reviews/{id}/resolve` — body `{"reviewer": str,
  "resolution": "CONFIRMED" | "DISMISSED", "notes": str}`. `409` if not
  currently `IN_REVIEW`, **or if `reviewer` does not match the value
  recorded at `claim` time** (new — §3.3/§7).
- The identical five endpoints under `/v1/admin/population-finding-reviews`,
  embedding `PopulationFindingRecord` instead of `GovernanceVerdict` (no
  `severity` filter — `PopulationFindingOutcome` is already binary, there
  is no severity tier to filter by).

Still no `PATCH`, no `DELETE`, no endpoint that mutates a resolved item in
place — a resolved row is only ever superseded by a *new* row (§3.2), never
edited.

### 3.8 No new plugin port; signing of the resolution record remains deferred, on refined grounds

A human review is not a computation a third party's code could ever
implement differently — no new `PluginType` member, no new registry entry,
no new lifecycle-promotion concept. Confirmed unchanged by both
hostile-review passes.

**Signing.** The original design deferred this as an open question (§9.2)
on the grounds that every existing signed table (`evidence_chain`,
`population_findings`) is insert-once, while a review reaches `RESOLVED`
only at the end of a genuinely mutable, multi-step process — making
"sign only once resolved" a new pattern this codebase has no working
precedent for. The hostile-review pass's own correction to §3.2
(reopening via a new row, never mutating a resolved one) **weakens, but
does not eliminate, that original objection**: under the corrected schema,
a `RESOLVED` row genuinely is never written to again — reopening creates
a new row, so "mutable while `OPEN`/`IN_REVIEW`, frozen forever once
`RESOLVED`" is actually closer to this codebase's existing signed-table
shape than the original design's own reasoning gave it credit for.
**Approved as final (§9.2/§10): still defer.** The underlying question —
whether a review resolution should become part of this platform's
tamper-evident evidence trail — was a genuine value judgment about what
counts as "evidence" here, not a mechanical consequence of the schema fix;
it has now been decided: review workflow state, including a resolved
review's outcome, remains unsigned, ordinary workflow state, with signing
deferred to a future milestone should a concrete need for it appear. One
thing the hostile-review pass explicitly rejects, unaffected by this
approval: preemptively adding unused,
always-`NULL` `signature`/`signing_key_id` columns to either table now,
"just in case" a future milestone wants them. Every existing signed table
in this codebase gained signing exactly when it was built to be signed
(`evidence_chain` at M5, `population_findings` at M6), never speculatively
ahead of a concrete, named need — adding unused columns now would be the
first instance of this project's own repeatedly-rejected pattern of
building for a hypothetical future requirement rather than a current one.

## 4. Design alternatives considered

Consolidated here as a single reference list; each was reasoned through in
place in §3 and is not re-argued in full below. Four of the original seven
stand exactly as before; three gain a clarifying note tying them to the
hostile-review corrections.

### 4.1 A single polymorphic `human_reviews` table (rejected — §3.2)

Rejected because a `subject_id` column cannot carry a real foreign key to
two different parent tables, reopening a referential-integrity gap this
codebase has never accepted anywhere else. Two small parallel tables cost
little; a fake shared identity column costs real correctness. Unchanged by
the hostile-review pass.

### 4.2 Review status as new mutable columns on `verdicts`/`population_findings` (rejected — §3.1)

Rejected because both tables are evidentiary records this platform has
gone out of its way to make immutable. Unchanged by the hostile-review
pass.

### 4.3 An ongoing, scheduled reconciliation poller in place of a write-time insert (rejected — §3.4)

A separate, periodically-invoked *daemon or scheduled job* that is the
**only** mechanism creating review rows (never inserting at write time at
all) was considered and remains **rejected**, on the same grounds as the
original design: it introduces a second scheduled-job mechanism into a
platform whose one existing batch job
(`population_engine/run_policies.py`) is a deliberate, considered,
manually-invoked design (`docs/milestones/M6.md` §13.4: no daemon, no
in-process scheduler); and it has an inherent staleness window between a
qualifying record being written and its review row appearing, which the
corrected §3.4 design still avoids almost entirely (the review-row insert
still happens synchronously, moments after the evidence write, inside the
same request — it is simply in its own transaction rather than the same
one). **This is a different, narrower thing than the corrected design's
own reconciliation tool (§3.5)**: the reconciliation tool is a periodic
*safety net* catching the rare case where the synchronous second insert
failed or a historical gap predates M9 — it is not the primary mechanism
by which review rows come to exist, and it is not a daemon (it remains an
explicitly-invoked script, run by an operator or a cron entry, never
started automatically by `create_app()`). The distinction matters: §4.3's
rejection of a poller-as-primary-mechanism stands; it is not contradicted
by the reconciliation tool's expanded, still-secondary role.

### 4.4 Allowing `resolve` directly from `OPEN`, skipping `claim` (rejected — §3.3)

Considered as a simpler model. **Rejected**: without a claim step, two
different reviewers could race to resolve the same item with different,
disagreeing outcomes, and neither the API nor the data would record who
was actually working on it in the interim. Unchanged by the hostile-review
pass — the new `release` transition (§3.3) adds a way *out* of
`IN_REVIEW`, it does not add a way to skip *into* `RESOLVED` without ever
passing through it.

### 4.5 A generic "list/get all Verdicts" (and "all Findings") Admin endpoint (rejected — §3.7)

Considered, since `VerdictRepository` has no `list_all` today. **Rejected
as out of scope for M9 specifically** (a plausible, small, separate future
improvement, §8): this milestone's own review-list endpoints already
return every `Verdict`/`PopulationFinding` a reviewer needs, embedded in
context. Unchanged by the hostile-review pass — the new batch-fetch method
`VerdictRepository` gains (§3.7/§5.1) is scoped specifically to "fetch the
verdicts referenced by a set of review rows," not a general-purpose
unscoped listing capability; it does not reopen this rejection.

### 4.6 Extending `/v1/admin/metrics` with review-queue-depth counts this milestone (rejected — §8)

Considered, and **rejected for M9 specifically**, on direct precedent: M8
added a second population policy — genuinely new countable governance
state — and explicitly declined to touch M7's metrics endpoint at all.
Unchanged by the hostile-review pass.

### 4.7 Signing or chaining the resolution record (deferred by approved decision — §9.2)

Unlike 4.1–4.6, this alternative was not confidently rejected by the
design review alone — it was a genuine value judgment, refined (without
being reversed) by the hostile-review pass at §3.8, and has now been
decided: deferred. Review workflow state stays unsigned; signing is a
candidate for a future milestone, not this one.

### 4.8 A plain `INSERT` for review-row creation, with no conflict handling (rejected — §3.4/§3.5, found during the hostile-review pass)

Not present in the original design at all — the original design's
same-transaction recommendation made this question briefly moot (no
concurrent writer could ever race the evidence-store transaction for the
same verdict). Decoupling (§3.4) reopens exactly this race between the
live path and the reconciliation tool (§3.5), and between two concurrent
reconciliation-tool runs. **Rejected**: a plain `INSERT` would let
whichever writer loses the race fail outright, including — in the worse
direction — a live ingestion request racing an ops-triggered reconciliation
run. **Recommendation: `INSERT ... ON CONFLICT (verdict_id) WHERE status
!= 'RESOLVED' DO NOTHING`** on both writers, so the loser silently no-ops.

### 5.2 Database schema changes

Two migrations, both **purely additive** (`CREATE TABLE` only — no
`ALTER` of any existing table, unlike M8's one necessary exception):

- **`0023_create_verdict_reviews.sql`** — **corrected by the
  hostile-review pass**: a partial unique index in place of a full
  `UNIQUE` column constraint (§3.2), and an explicit `ON DELETE RESTRICT`
  (§3.2):

  ```sql
  CREATE TABLE verdict_reviews (
      id                TEXT PRIMARY KEY,
      verdict_id        TEXT NOT NULL REFERENCES verdicts(id) ON DELETE RESTRICT,
      status            TEXT NOT NULL,   -- 'OPEN' | 'IN_REVIEW' | 'RESOLVED'
      reviewer          TEXT,
      resolution        TEXT,            -- 'CONFIRMED' | 'DISMISSED', set only at RESOLVED
      resolution_notes  TEXT,
      created_at        TIMESTAMPTZ NOT NULL,
      claimed_at        TIMESTAMPTZ,
      resolved_at       TIMESTAMPTZ
  );

  -- At most one *active* review per verdict at a time -- not "ever, full
  -- stop" (the corrected version of this milestone's own first draft,
  -- which reproduced the plain-UNIQUE mistake migration 0022 already
  -- fixed once for population_policy_bindings). A resolved review can be
  -- superseded by a new row; the old row is never mutated.
  CREATE UNIQUE INDEX one_open_verdict_review_per_verdict
      ON verdict_reviews (verdict_id)
      WHERE status != 'RESOLVED';

  -- Supports the review-list endpoint's primary filter.
  CREATE INDEX idx_verdict_reviews_status ON verdict_reviews (status);

  GRANT SELECT, INSERT, UPDATE, DELETE ON verdict_reviews TO gov_platform_app;
  ```

  Ordinary `GRANT` privileges, not `evidence_chain`'s/`population_findings`'
  lockdown — this is live, legitimate workflow state (is this review open,
  claimed, or resolved), not computed governance output itself (the
  `Verdict` it references remains exactly as immutable as before, and
  `ON DELETE RESTRICT` makes that explicit rather than relying on
  Postgres's implicit default).

- **`0024_create_population_finding_reviews.sql`** — identical shape,
  `population_finding_id TEXT NOT NULL REFERENCES population_findings(id)
  ON DELETE RESTRICT`, `one_open_population_finding_review_per_finding`
  partial unique index, `idx_population_finding_reviews_status`, same
  ordinary `GRANT`.

No changes to `verdicts`, `population_findings`, `evidence_chain`,
`policy_bindings`, `population_policy_bindings`, `plugin_registrations`, or
any M7 index. Both migrations remain plain `CREATE TABLE`/`CREATE INDEX`
statements (not `CONCURRENTLY` — neither table has any existing rows to
lock against, so the `db/migrate.py` single-transaction constraint M8
found for `population_policy_bindings` doesn't even apply here).

### 5.3 Public API changes

- Two new routers, **ten** new endpoints total (§3.7 — up from eight in
  the original design, after adding `release`) — all additive; no
  existing endpoint's request or response shape changes at all. No change
  to `/readyz`, `/v1/admin/metrics`, or any ingestion route.

### 5.4 New domain models

`VerdictReview`, `PopulationFindingReview` (plus their four small enums) —
genuinely new top-level schema types, unlike M8 (which only added fields to
existing ones). Each is a normal `BaseModel` with `model_config =
ConfigDict(frozen=True)` at the domain-schema layer, constructed fresh by
the repository on each read. Unchanged by the hostile-review pass.

### 5.5 Interfaces and abstractions

None. No new plugin port, no new abstract base class.
`_REVIEWABLE_VERDICT_STATUSES` is a plain module-level constant, not a
pluggable rule. The idempotent-upsert repository behavior added by the
hostile-review pass (§3.4/§4.8) is an implementation detail of `create`,
not a new abstraction or interface.

### 5.6 Sequencing / rollout order

1. Migrations `0023`/`0024` (additive; safe to apply to a running

2. New schemas, repositories, the decoupled `EvidenceStore`/`run_policies.py`

## 6. Testing strategy

### 6.1 Unit

- `schemas/human_review.py` — construction, `frozen=True` immutability,
  `notes`/`reviewer`'s `min_length=1` validation where applicable.
- `_REVIEWABLE_VERDICT_STATUSES` — a direct, explicit test that `ALLOW`
  and `ALLOW_WITH_FLAG` are excluded and `ESCALATE_FOR_REVIEW`/
  `RECOMMEND_HOLD` are included.

### 6.2 Integration (real Postgres, `@requires_postgres`)

- **Repository — claim/release/resolve state machine**: `claim()` on an
  `OPEN` row succeeds; `claim()` on an already-`IN_REVIEW`/`RESOLVED` row
  raises `ValueError`; **`release()` on an `IN_REVIEW` row returns it to
  `OPEN`, and it can be claimed again by a different reviewer (new)**;
  `release()` on an `OPEN`/`RESOLVED` row raises `ValueError` (new);
  `resolve()` on an `IN_REVIEW` row with the matching `reviewer` succeeds;
  **`resolve()` with a non-matching `reviewer` raises `ValueError` even
  though the row is genuinely `IN_REVIEW` (new — the identity-continuity
  check, §3.3/§7)**; `resolve()` on an `OPEN` row (never claimed) raises
  `ValueError`.
- **Repository — the claim race directly**: two concurrent `claim()` calls
  against the same `OPEN` row — exactly one succeeds, the other observes
  zero-rows-affected and raises.
- **Repository — reopening (new)**: resolve a review, then call `create()`
  again for the same `verdict_id` — a second, independent `OPEN` row is
  created, distinct from the first, resolved row; the first row's
  `resolution`/`resolution_notes` are unchanged; **attempting `create()`
  again while the newly-created row is still active (`OPEN`/`IN_REVIEW`)
  is the conflict case** — it returns `None` (or is a no-op), not a second
  active row, direct proof of the partial unique index (§3.2).
- **Repository — the backfill/live-traffic race directly (new)**: seed a
  verdict qualifying for review; concurrently run (a) the reconciliation
  tool's insert and (b) the live-path insert for the same verdict — assert
  exactly one `verdict_reviews` row results, and **neither writer raises**
  (the direct regression test for §3.4/§4.8's `ON CONFLICT ... DO NOTHING`
  requirement). A companion test runs two concurrent reconciliation-tool
  invocations against the same historical gap with the identical
  assertion.
- **`EvidenceStore.append` + the decoupled review-row insert, extending
  `tests/integration/test_evidence_store_postgres.py`**: appending a
  `Verdict` with `status=ESCALATE_FOR_REVIEW`/`RECOMMEND_HOLD`, followed by
  the new, separate review-row-creation step, produces exactly one `OPEN`
  `verdict_reviews` row; an `ALLOW`/`ALLOW_WITH_FLAG` verdict produces
  none. **New, and the direct regression test for the headline correction
  (§3.4)**: forcing the review-row-creation step to raise (e.g. a mocked
  repository failure) leaves the `evidence_chain`/`verdicts`/`findings`
  rows fully committed and unaffected — the ingestion request's own
  success is not contingent on this new, separate write succeeding.
- **`run_population_policy_binding` + the decoupled review-row insert,
  extending `tests/integration/test_population_run_policies_postgres.py`**:
  a `FLAGGED` finding, followed by the new separate insert step, produces
  exactly one `OPEN` `population_finding_reviews` row; a `CLEAR` finding
  produces none; the existing "duplicate window is a clean skip" test
  continues to pass unmodified.
- **`human_review/backfill_reviews.py`**: run against a database seeded
  with pre-existing `ESCALATE_FOR_REVIEW`/`RECOMMEND_HOLD` verdicts and
  `FLAGGED` findings that have no review row — every one gets exactly one
  `OPEN` row after a single run; running it again immediately afterward is
  a genuine no-op; **running it while concurrent live ingestion is
  simultaneously creating new qualifying verdicts (new) does not raise for
  either writer and does not create duplicate rows for any verdict.**

### 6.3 API

- `GET /v1/admin/verdict-reviews`/`...?status=&severity=` — list, filtered
  and unfiltered; **default ordering is oldest-open-first (new,
  regression-tested directly, not just asserted in prose)**; **the
  `severity` filter returns only reviews whose verdict has the requested
  `VerdictStatus` (new)**.
- `POST .../{id}/claim` then `.../release` then `.../claim` again by a
  different `reviewer` — the full new lifecycle path, end to end through
  the HTTP layer, not the repository directly.
- `POST .../{id}/claim` then `.../resolve` — the original happy path,
  still end to end through the HTTP layer.
- `POST .../{id}/claim` on an already-claimed item — `409`.
- `POST .../{id}/release` on an item that is not `IN_REVIEW` — `409`
  (new).
- `POST .../{id}/resolve` with a `reviewer` that does not match the one who
  claimed it — `409` (new — the identity-continuity check).
- `POST .../{id}/resolve` with an empty `notes` string — `422`.
- `POST .../{id}/resolve` before `.../claim` — `409`.
- **Resolving, then creating a new review for the same underlying verdict,
  then listing — both the resolved and the new `OPEN` row are visible,
  distinctly (new — the reopening path, exercised through the API, not
  just the repository).**
- The identical suite mirrored for `/v1/admin/population-finding-reviews`.

Coverage gate unchanged: 100% target, 98% minimum, exactly as M2–M8.

### 6.4 Acceptance criteria

1. Every `Verdict` persisted with `status` in `{ESCALATE_FOR_REVIEW,
   RECOMMEND_HOLD}` gets exactly one corresponding `OPEN` `verdict_reviews`
   row; every `ALLOW`/`ALLOW_WITH_FLAG` verdict gets none.
2. Every `PopulationFinding` persisted with `outcome=FLAGGED` gets exactly
   one corresponding `OPEN` `population_finding_reviews` row; every
   `CLEAR` finding gets none.
3. **(new)** A failure in review-row creation never fails the underlying
   ingestion request or `run_policies.py` invocation — the evidence/finding
   write's success is fully independent of the review-row write's
   success, demonstrated directly by forcing the latter to fail.
4. An admin can list open reviews (oldest-open-first by default, optionally
   filtered by status and — for verdict reviews — severity), claim one,
   optionally release it back to `OPEN`, and resolve it with a matching
   `reviewer` and a mandatory rationale, through the Admin API end to end
   — demonstrated for both `verdict_reviews` and `population_finding_reviews`.
5. Two concurrent claim attempts against the same review item never both
   succeed.
6. **(new)** Resolving an item that was never claimed, releasing an item
   that is not currently claimed, or resolving with a `reviewer` that does
   not match the claimant, are each rejected with a clear `409`, never a
   generic `500` or a silent overwrite.
7. **(new)** Resolving a review and then creating a new one for the same
   underlying `Verdict`/`PopulationFinding` succeeds, producing two
   distinct rows with the first's resolution unchanged; attempting to
   create a second *active* review while one is already `OPEN`/`IN_REVIEW`
   does not create a duplicate.
8. Running the reconciliation tool against a database containing pre-M9
   qualifying verdicts/findings creates exactly one `OPEN` row per
   qualifying record; running it again immediately afterward, or
   concurrently with live traffic creating new qualifying records, creates
   no duplicates and raises no error for any writer.
9. No existing table's schema, no existing API's request/response shape,
   and no existing test changes at all — `ruff`, `ruff format --check`,
   `mypy --strict`, and the full pytest suite are clean; coverage ≥ 98%,
   target 100%.

## 7. Production-readiness considerations

Anticipated hostile-review points, addressed in the design above rather
than deferred as "future work" where a same-milestone fix is reasonable:

- **The claim/release/resolve races are addressed structurally, not by
  assumption** (§3.7/§4.4/§6.2): every transition is a conditional
  `UPDATE ... WHERE status = '<expected>'` (and, for `resolve`, `AND
  reviewer = :reviewer`) statement whose affected-row count is checked,
  never "read current status, then write" two-step application logic.
  Worth naming explicitly: this is a **stronger** concurrency-safety
  pattern than `PopulationPolicyBindingRepository.set_lifecycle_state` (and
  its `PolicyBindingRepository` twin) actually use elsewhere in this exact
  codebase today — see §9.6 for the pre-existing race that comparison
  surfaced.
- **The review-row write is now decoupled from the evidence/finding write
  it depends on (§3.4), specifically so a failure in this milestone's new
  code cannot prevent a real governance decision from being recorded.**
  The residual risk this reopens — a narrow, rare gap where the decoupled
  insert fails or races the reconciliation tool — is closed by the same
  reconciliation tool (§3.5) using idempotent upsert semantics (§4.8), not
  left as an unmitigated risk.
- **No authentication on any of the ten new endpoints — the sharpest
  version of a gap this project has named in every design document since
  M5.** This is the first milestone where the unauthenticated actor is
  recording **a specific named person's professional judgment about a real
  bias finding** — the `reviewer` field is a free-text string with no
  binding to any real identity. The one in-scope mitigation is the
  identity-continuity check added by the hostile-review pass (`resolve`
  must restate and match the `reviewer` who claimed the item) — it catches
  accidental cross-wiring, not a malicious actor, and does not close this
  gap (§8).
- **Query performance and indexing.** Both new tables get an index on
  `status` (§5.2), matching the "index the column the new read pattern
  actually filters on" discipline M7 §6 already applied elsewhere. The
  review-list endpoint's embedded `Verdict`/`PopulationFinding` data is
  fetched via a new batch method, not a per-row loop (§3.7/§5.1) — an N+1
  query pattern the original design's implementation plan did not account
  for. Neither table has an unbounded-growth risk materially different
  from `population_policy_bindings`' own.
- **No notification means the queue is pull-only, forever, until some
  future milestone adds push** — an `OPEN` review with nobody watching the
  queue could sit unclaimed indefinitely. The oldest-open-first default
  ordering (§3.7) is a cheap, in-scope partial mitigation, not a
  substitute for real notifications, which stay deferred (§8).
- **The reconciliation tool's correctness is exactly as important as its
  existence**, and now doubly so since it also guards the live path's
  narrow decoupling gap (§3.4/§3.5): it is scoped, in code, to the
  identical `_REVIEWABLE_VERDICT_STATUSES` constant the live write path
  uses (§5.1), and both use identical idempotent-upsert semantics (§4.8) —
  one definition and one conflict-handling strategy, two consumers, never
  independently-maintained copies that could silently drift.
- **Resolution immutability is enforced only at the application layer, not
  the database-privilege level.** Unlike `evidence_chain`/
  `population_findings`, `verdict_reviews`/`population_finding_reviews`
  grant `UPDATE` unconditionally (§5.2) — a resolved row is *conventionally*
  terminal (no repository method mutates a `RESOLVED` row; reopening always
  creates a new row, §3.2), but nothing at the database level stops a
  direct `UPDATE` issued outside this application from altering a
  `RESOLVED` row after the fact. This gap is accepted (§9.2/§10): this is
  workflow metadata, not the evidentiary record itself, and stays
  unsigned, ordinary workflow state — a future milestone's problem to
  revisit if a concrete need for signed resolutions ever appears.
- **Two pre-existing defects, found as a byproduct of this milestone's own
  design and its hostile-review pass, are named here and documented in
  full at §9.5/§9.6 — neither is fixed inside M9.** `verdicts`/`findings`/
  `decision_events`/`model_versions`/`systems`/`verdict_findings` lack the
  `REVOKE UPDATE, DELETE` lockdown `evidence_chain`/`population_findings`
  have; and `set_lifecycle_state`'s read-then-write pattern (both
  `policy_binding.py` and `population_policy_binding.py`) has no
  conditional-update protection against concurrent lifecycle transitions.

## 9. Architectural decisions (approved) and disclosed pre-existing issues

Section 9.1–9.3 were, until this revision, open questions requiring your
explicit decision. **They are now approved, per your direction, and are
recorded below as decided architecture, not open questions.** 9.4 was
already settled by the original design; 9.5/9.6 are disclosures of
pre-existing defects, not decisions to make.

### 9.1 — Does "Human Review Workflow" cover only `ESCALATE_FOR_REVIEW`, or also `RECOMMEND_HOLD`? **(approved)**

`architecture-mapping.md` §12 and every prior milestone's own deferred-item
citation name `ESCALATE_FOR_REVIEW` specifically, by name, every time —
`RECOMMEND_HOLD` is never mentioned in any of those citations. Read
narrowly, M9 would queue only `ESCALATE_FOR_REVIEW` verdicts. **Decided:
read generously — both.** `RECOMMEND_HOLD` (`PolicySeverity.HIGH`) is
strictly *more* severe than `ESCALATE_FOR_REVIEW`
(`PolicySeverity.MEDIUM`); excluding the more severe of the two while
including the less severe one would have been a stranger reading than the
citations' silence suggested. **Both `ESCALATE_FOR_REVIEW` and
`RECOMMEND_HOLD` create a review record** — this is now the approved,
final architecture, not a recommendation. The hostile-review pass's
refinement stands alongside it: §3.7's `severity` filter on the
verdict-review list endpoint exists specifically so an operator can
prioritize the more urgent `RECOMMEND_HOLD` items rather than having them
buried among the more numerous `ESCALATE_FOR_REVIEW` ones in one
undifferentiated queue.

### 9.2 — Should a resolved review become part of this platform's signed, tamper-evident evidence trail? **(approved)**

Argued both ways in §3.8/§4.7/§7. **Decided: defer.** Review workflow
state — including a resolved review's outcome — remains ordinary,
unsigned workflow state; cryptographic signing is deferred to a future
milestone, should a concrete need for it appear. The reasoning that
supports this without weakening it: the hostile-review pass's §3.2
reopening fix means a `RESOLVED` row is genuinely never written to again
(reopening happens via a new row, not a mutation of the old one), so this
decision does not leave a `RESOLVED` row any less trustworthy than the
original design assumed — it simply does not (yet) carry this platform's
strongest, cryptographic guarantee. What stands unaffected by this
approval: no preemptive, unused `signature`/`signing_key_id` columns are
added to either table now "just in case" — every existing signed table in
this codebase gained signing exactly when it was built to be signed, never
speculatively ahead of a concrete need, and a future milestone that does
decide to sign resolutions gets its own migration then, exactly as
`evidence_chain` (M5) and `population_findings` (M6) each did.

### 9.3 — Is the reconciliation tool (§3.5) part of M9's own versioned deliverable, or ops-runbook tooling outside it? **(approved)**

`plugins/seed_registry.py` is versioned application code, invoked as a
documented deployment step; `infra/ci/setup_test_role.py` is explicitly
scoped as CI-only tooling. **Decided: it ships as part of M9**, as
versioned, idempotent application code
(`human_review/backfill_reviews.py`, §5.1) that can be safely re-run —
not ops-runbook tooling outside this milestone's own deliverable. The
hostile-review pass's reasoning stands behind this as-approved decision:
the tool needs genuine concurrency-safety logic (idempotent upsert
semantics, §3.4/§4.8) to avoid racing live traffic or a concurrent run of
itself — real logic that needs real tests and code review, the opposite
of what "ops runbook tooling" would imply — and is reframed from a
one-time migration helper into a standing tool this platform re-runs
periodically (closer to `audit/verify_chain.py`'s shape than to a
one-shot script).

### 9.4 — Does the pre-M5 legacy `VerdictStatus.FLAGGED` need any backfill accounting?

Reasoned through in §3.6: **recommendation is no** — no live code path can
ever produce this status after M5 shipped, and no `PolicySeverity` was
ever computed for verdicts written under the old two-state model.
Unchanged by either hostile-review pass.

### 9.5 — `verdicts`/`findings`/`decision_events`/`model_versions`/`systems`/`verdict_findings` are not `REVOKE UPDATE, DELETE`-locked at the database-privilege level. Is this M9's problem to fix? **(pre-existing defect, found as a byproduct of this milestone's own hostile-review pass)**

Migration `0008` grants `SELECT, INSERT, UPDATE, DELETE` on `systems,
model_versions, decision_events, findings, verdicts, verdict_findings` to
`gov_platform_app`, and only `evidence_chain` ever receives `REVOKE UPDATE,
DELETE` in that same migration. `population_findings` gets the identical
lockdown at M6 (migration `0015`). `verdicts` and `findings` — the
per-event evidentiary tables `evidence_chain`'s payload is built from —
never did, and no design document has ever said so until now. This was
found only because M9 is the first milestone to add a real foreign key
pointing *at* `verdicts` (`verdict_reviews.verdict_id`): that FK's
integrity is only as strong as `verdicts`' own immutability, and
`verdicts` is not actually immutability-locked at the database level —
only its embedded copy inside `evidence_chain.payload` is tamper-evident.
**Confirmed real, verified directly against migration `0008`'s actual
`GRANT` statement — and confirmed pre-existing, not introduced by M9.**
**Recommendation: do not fix inside M9.** This is a standing gap in a
different milestone's scope (M1/M5's own tables), unrelated to Human
Review Workflow's own job, and deserves its own dedicated review of
exactly which tables should gain the lockdown and what (if anything) ever
legitimately needs `UPDATE`/`DELETE` on them today. Documented here and at
§7/§8 as a verified, outstanding candidate for a small, separate
follow-up — the same treatment M8 §13.20 gave the `policy_bindings`
recreate-after-deactivate defect it found the same way.

### 9.6 — `set_lifecycle_state`'s read-then-write pattern has no conditional-update protection. Is this M9's problem to fix? **(pre-existing defect, found as a byproduct of this milestone's own hostile-review pass)**

`PopulationPolicyBindingRepository.set_lifecycle_state` (confirmed by
reading `db/repositories/population_policy_binding.py` directly) is a
plain `session.get(...)`, mutate the attribute, `session.flush()` — no
row-count check, no conditional `WHERE` clause guarding against a
concurrent transition. `PolicyBindingRepository`'s identical
activate/deactivate method shares the same shape. Two concurrent
activate/deactivate calls against the same binding can both "succeed,"
last-write-wins, with no conflict signal to either caller. This was found
only because M9's own `claim`/`release`/`resolve` needed a *stronger*
pattern (a conditional `UPDATE ... WHERE status = '<expected>'`, checked
by row count, §3.7/§9), and this was the natural existing precedent to
check first. **Confirmed real, verified directly against the repository's
actual code — and confirmed pre-existing, not introduced by M9.**
**Recommendation: do not fix inside M9.** The risk profile differs
materially from a review claim/resolve race (a lifecycle-activation race
requires two admins acting on the same binding within milliseconds of each
other — rare — versus a shared review queue several reviewers might
plausibly work from concurrently), and fixing two other milestones'
repository methods is out of scope for a Human Review Workflow milestone.
Documented here and at §7/§8 as a verified, outstanding candidate for a
small, separate follow-up.

## Design frozen

This design is **frozen** as of this revision. `architecture-mapping.md`
§12 ("Human Review Workflow") is scoped, for M9, exactly as described in
this document: two new tables (`verdict_reviews`,
`population_finding_reviews`), each with a partial-unique-index-backed,
reopenable four-state workflow (`OPEN → IN_REVIEW → RESOLVED`, plus
release); review-row creation decoupled from the evidence/finding write it
depends on, using idempotent upsert semantics; a versioned, rerunnable
reconciliation tool covering both historical and live-path gaps; both
`ESCALATE_FOR_REVIEW` and `RECOMMEND_HOLD` in scope; signing deferred; ten
new Admin API endpoints; no new plugin port; no UI; no authentication. Any
further architectural change from here — including during implementation,
if a real constraint is discovered that this design did not anticipate —
should go through the same hostile-review discipline this document itself
went through, not be made silently, mirroring M5–M8's own freeze
discipline.

Implementation is complete, per "What Was Built" above. §9.5/§9.6's two
pre-existing, verified defects (the `verdicts`/`findings`-family
database-privilege gap, and `set_lifecycle_state`'s unprotected race)
remained explicitly out of scope for M9 and were not fixed as a side
effect of implementing this design — confirmed still present during the
post-implementation review, and left as candidates for their own,
separate, dedicated follow-up.
