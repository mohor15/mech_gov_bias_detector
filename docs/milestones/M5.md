## What Was Built

Everything in the approved design below, built exactly as decided across
all fourteen ambiguities — no schema surprises, no scope creep, and no
architectural issue forced a deviation from the approved design.

- **`schemas/policy_binding.py`, `db/repositories/policy_binding.py`,
  `api/admin/policy_bindings.py`** — `PolicyBinding` (`adapter_id`-keyed,
  per §13.1), `PolicySeverity` (`LOW`/`MEDIUM`/`HIGH`), `ACTIVE`/`INACTIVE`
  lifecycle (per §13.2). Admin API mirrors the plugin registry's shape:
  `create`/`list`/`get`/`activate`/`deactivate`.
- **`schemas/protected_attribute_rule.py`, `db/repositories/protected_attribute_rule.py`,
  `api/admin/protected_attribute_rules.py`** — a separate table from
  `policy_bindings` (per §13.4), consumed only by `ProtectedAttributeResolver`'s
  new DB-backed mode.
- **`governance_engine/engine.py`** — `GoverningPolicy` (a `Policy` bundled
  with its binding's `PolicySeverity`, per §9); `GovernanceEngine`'s
  constructor takes `governing_policies: list[GoverningPolicy]`; `govern()`
  aggregates via highest-flagged-severity-wins into the real four-state
  `VerdictStatus`.
- **`schemas/verdict.py`** — `VerdictStatus` gains `ALLOW_WITH_FLAG`,
  `ESCALATE_FOR_REVIEW`, `RECOMMEND_HOLD`; `ALLOW`/`FLAGGED` kept
  permanently as historical-only members (per §13.10) — no data migration
  of M0–M4 verdicts, none was needed or attempted.
- **`adapters/base.py`** — `governing_policy_ids` removed outright (per
  §13.3); `plugins/seed_registry.py` seeds the equivalent bindings for both
  first-party adapters, reproducing M0–M4 behavior exactly at cutover.
- **`audit/signing.py`, `audit/evidence_store.py`, `audit/verify_chain.py`**
  — Ed25519 signing, single static key (env-configurable, ephemeral
  per-process fallback otherwise), per §13.8; `verify_chain`/its CLI gained
  an optional `--public-key`. No retroactive signing of M0–M4 records, per
  §13.10's evidence-immutability reasoning applied to signing too.
- **`protected_attributes/resolver.py`** — an optional `engine` constructor
  parameter switches `ProtectedAttributeResolver` to the DB-backed table;
  `EvidenceStore` uses it, `DirectAttributeInInputsPolicy` does not (per
  §13.9) — a deliberate, documented divergence, not an oversight.
- **`api/ingestion/routes.py`** — the per-request policy-resolution loop
  now queries `policy_bindings` instead of a class attribute; an adapter
  with zero active bindings fails the whole request with a 503, mirroring
  the "no partial governance" discipline M3/M4 already established for a
  missing production policy.

## Production-Readiness Review

Performed after implementation, before freeze.

**Finding (fixed): `protected_attributes/classification.py`'s module
docstring was stale.** It still described DB-backed, admin-configurable
protected-attribute rules as entirely future work, after this milestone
partially delivered them (for `EvidenceStore`'s resolution path
specifically). Updated to name the real, scoped-to-one-consumer state and
the deliberate divergence with `DirectAttributeInInputsPolicy`. The same
class of finding M4's own review caught in three other files.

**Reviewed, no issue found:**
- **Backward compatibility.** Every existing table kept its exact shape;
  the three new migrations (`0011`–`0013`) are two new tables and two
  nullable columns — no `ALTER` of any existing column, no data rewrite.
  Seeding reproduces M0–M4's effective policy-to-adapter and
  attribute-classification behavior exactly, verified by the full test
  suite passing unchanged for every pre-M5 scenario (e.g. the well-formed
  `credit-scorecard` payload still resolves to `ALLOW`).
- **The `policy_bindings`/`protected_attribute_rules` uniqueness-race
  window.** Both repositories' `create()` methods follow the exact
  established pattern (check-then-insert at the API layer for a clean
  `409`, a database `UNIQUE` constraint as the actual guarantee, an
  `IntegrityError`-to-`ValueError` translation as defense in depth) — the
  same accepted `409`-vs-`422` asymmetry M3's own review already named and
  accepted, not a new gap.
- **Signing key exposure.** `Settings.SIGNING_PRIVATE_KEY` is never read by
  any response-serializing code path; only `signature`/`signing_key_id`
  (public, non-secret identifiers) ever reach `EvidenceRecord` or any API
  response.
- **The ephemeral-key fallback's real limitation, tested directly.**
  `load_signer(None)` generates a fresh key per call — verified (rather
  than merely stated) that two `EvidenceStore` instances with no configured
  key produce mutually non-verifying signatures, and that the CLI's
  `--public-key` check correctly fails against a real mismatch, not just
  against a contrived unit-level record.
- **No genuine architectural issue requiring a stop-and-explain arose.**
  The implementation matched the approved design across all fourteen
  ambiguities; the one deviation from a literal reading of "Policy
  Bindings" (§13.1's `adapter_id` key, not domain/jurisdiction) was an
  explicit, pre-approved decision, not a discovered issue.

**Named, not fixed — deliberate scope boundaries, not gaps found late:**
- No authentication on the two new admin endpoints, consistent with every
  existing endpoint but flagged as a materially higher-stakes gap now that
  a Policy Binding write can silently stop a policy from governing real
  financial decisions (§13.11).
- `DirectAttributeInInputsPolicy` and `protected_attribute_rules` can
  diverge in judgment for the same event (§13.9) — named at design time,
  confirmed present exactly as scoped, not a surprise.

## TL;DR

**M5 owns**, per the frozen record's own citations, exactly five things:

1. **Policy Bindings** — dynamic, admin-managed, database-backed association
   of policies to adapters, replacing the static, code-defined
   `Adapter.governing_policy_ids` tuple M3/M4 built.
2. **The full four-state `VerdictStatus`** (`ALLOW` / `ALLOW_WITH_FLAG` /
   `ESCALATE_FOR_REVIEW` / `RECOMMEND_HOLD`), replacing the current two-state
   placeholder.
3. **Escalation rules** that decide which of the three non-`ALLOW` states a
   flagged verdict lands in.
4. **Cryptographic signing** of evidence records.
5. **DB-backed, admin-configurable protected-attribute classification
   rules**, replacing `protected_attributes/classification.py`'s static
   `_RULES_BY_DOMAIN` dict.

**Deferred**, explicitly, past M5: the Human Review Workflow that actually
*consumes* an `ESCALATE_FOR_REVIEW` verdict (M9); the Compliance Dashboard
(M10); encryption at rest and retention tiers (M11); async ingestion and
population-level policies (M6); authentication in front of any endpoint
(named `M5+/M13` in `README.md` — this review recommends **not** claiming it
for M5; see §13.11); real OS-level plugin sandboxing beyond timeout/exception
isolation (unassigned).

**Fourteen ambiguities** are identified below (§13), each with a
recommendation. Three are the highest-stakes calls in this document and are
flagged inline: §13.1 (binding granularity), §13.5 (where severity lives),
and §13.9 (how a DB-backed-rules policy gets database access at all, given
`Policy` has never needed it). Skip to §16 for a plain checklist of every
decision this review needs your sign-off on before implementation starts.

## 1. What M5 is exactly responsible for

Every prior milestone's docstrings name the same five things for M5,
consistently:

1. **Policy Bindings.** `adapters/base.py`: "*that richer 'which policy for
   which domain/jurisdiction' concept is explicitly M5's Policy Bindings,
   not this [`governing_policy_ids`]*." `api/admin/__init__.py`: "*Dynamic,
   admin-managed binding of policies to domains/jurisdictions is M5's Policy
   Bindings, not this.*"
2. **The full four-state verdict model.** `schemas/verdict.py`: "*the full
   four-state model (ALLOW / ALLOW_WITH_FLAG / ESCALATE_FOR_REVIEW /
   RECOMMEND_HOLD)... only means something once Policy Bindings, escalation
   rules, and signing exist to drive it — that is M5's job.*"
3. **Escalation rules.** `governance_engine/engine.py`: "*the full four-state
   model remains M5's job*" — named alongside signing and bindings as the
   three things that give the four-state model meaning.
4. **Cryptographic signing.** `governance_engine/__init__.py`: "*Policy
   Bindings, escalation rules, and cryptographic signing remain M5.*"
5. **DB-backed protected-attribute rules.** `protected_attributes/
   classification.py`: "*DB-backed, per-tenant rule configuration... belongs
   to a later milestone (M3's plugin config, or M5's Policy Bindings...),
   not this one.*" `README.md`'s milestone summary confirms this same
   attribution independently: "*DB-backed/admin-configurable
   protected-attribute classification rules (M5)*."

**What M5 explicitly is not**, per the same record: the Human Review
Workflow itself (§12 of the architecture, a UI/queue for a human to act on
an `ESCALATE_FOR_REVIEW` verdict) is M9 — M5 produces the correct four-state
*data*, M9 builds what a human does with it. Async ingestion and
population-level policies are M6/M8. Getting the M5/M9 boundary right is
this document's third-highest-stakes call — see §13.7.

## 2. How M5 builds on M4

M4 gave `GovernanceEngine` real plurality — N policies, aggregated via
any-`FLAGGED`-wins into a two-state `VerdictStatus`. M5 is not a new
mechanism layered on top of that; it is the direct generalization of two
things M4 deliberately left static and binary:

- **From static to dynamic policy association.** M3 gave `Adapter` a single
  `governing_policy_id`; M4 widened it to a tuple, `governing_policy_ids`
  — but both remained a fixed, code-defined class attribute, requiring a
  code deploy to change. M5 moves that association into the database,
  admin-managed, exactly the way M3 already moved plugin *lifecycle* out of
  code and into `plugin_registrations`. Policy Bindings are to
  `governing_policy_ids` what `plugin_registrations` was to "the adapter
  registry didn't exist yet, adapters were hardcoded in `api/app.py`."
- **From binary to four-state aggregation.** M4's `any(FLAGGED) ->
  VerdictStatus.FLAGGED` was explicitly scoped as a placeholder — "*this
  needs no new `VerdictStatus` values (still the two-state ALLOW/FLAGGED
  placeholder; the full four-state model remains M5's job)*"
  (`governance_engine/engine.py`). M5 is the milestone that makes that
  widening make sense, because only once a policy's binding carries a
  *severity* is there any information to decide which of three non-`ALLOW`
  states applies.

**No schema changes were needed for the enum column itself.**
`infra/migrations/0005_create_verdicts.sql`'s own comment predicted this
exactly: `status` is `TEXT NOT NULL`, "*not a SQL ENUM — enum values
changing at M5 would otherwise require an ALTER TYPE migration for no
behavioral benefit today.*" M5 is the milestone that comment was written
for; widening `VerdictStatus` needs zero migration to the `verdicts` table.

## 3. Why each piece exists architecturally

**Policy Bindings.** A code-defined `governing_policy_ids` tuple means every
change to which policy governs which adapter is a deploy — fine for two
first-party adapters and three first-party policies, but the platform's own
stated purpose (a domain-agnostic layer other teams register adapters and
policies against) breaks down once a compliance team needs to change a
binding faster than a release cycle allows. This is the same argument M3
already made for plugin *lifecycle* (draft/shadow/production shouldn't need
a redeploy either) — M5 applies it one layer up, to *which* policies apply,
not just *whether* a given implementation is trusted to run at all.

**Four-state verdict + escalation.** A binary ALLOW/FLAGGED verdict treats
"a low-confidence advisory flag" and "a hard compliance violation" as the
same outcome — throwing away exactly the graduated-response information a
real governance platform exists to preserve (the same P4/P9
reproducibility/evidentiary-integrity principle M4's design doc already
invoked for *why* findings must be plural, applied here to *why* the verdict
state must be graduated). `ALLOW_WITH_FLAG` / `ESCALATE_FOR_REVIEW` /
`RECOMMEND_HOLD` map a real regulatory posture: log-and-continue, hold-for-
human-review, and stop, respectively.

**Cryptographic signing.** The hash chain (M1) proves *internal*
consistency — that a record hasn't been altered after being chained. It
proves nothing about *who* produced a given record; anyone with database
access under the current architecture could in principle read the chain but
could never forge a *new*, differently-signed link without the signing key
if one existed. Signing adds *authenticity* — a third party with the public
key can verify a record was produced by this specific deployment, not just
that the chain is self-consistent. These are genuinely different guarantees
architecture §13 asks for, and the evidence chain has had neither before now.

**DB-backed protected-attribute rules.** `classification.py`'s own docstring
already names the gap: a compliance team changing which attributes count as
protected characteristics for a domain (e.g., adding a new proxy attribute
after a disparate-impact finding) currently requires a code change and
redeploy — the same class of problem Policy Bindings solves for policy
association, applied to the attribute-classification ruleset instead.

## 4. Proposed architecture (this review's recommendation)

### 4.1 Policy Bindings

**Keyed by `adapter_id`, not by `System.domain`/jurisdiction — deferred
generalization, not the literal architecture phrase.** See §13.1 for the
full reasoning; the short version: the architecture's own phrase ("which
policy applies to which domain/jurisdiction") describes a richer binding
than M5 should build with only one real domain (`FINANCE`) and zero real
jurisdictions to validate a domain/jurisdiction-keyed design against. A
`PolicyBinding` row is `(adapter_id, policy_id, severity, lifecycle_state)`
— the direct, dynamic replacement for one entry in today's
`governing_policy_ids` tuple, administered without a redeploy. This is the
real, load-bearing part of "Policy Bindings" (dynamic, admin-managed,
no-redeploy) without also committing to a domain/jurisdiction key this
milestone has no second case to validate.

**Lifecycle: `ACTIVE`/`INACTIVE`, not `DRAFT`/`SHADOW`/`PRODUCTION`.** A
binding's job is "does this already-`PRODUCTION`-trusted policy currently
apply to this adapter" — an orthogonal question to "is this policy's code
trusted to run at all," which `plugin_registrations` already answers
completely. Reusing the three-stage plugin lifecycle at the binding layer
would create two independent shadow/production axes answering overlapping
questions. See §13.2.

**`Adapter.governing_policy_ids` is removed, not deprecated-in-place.**
Consistent with every prior milestone's own retrofit discipline (M3 deleted
hand-wired routes outright; M4 renamed the singular attribute to a tuple
with no compatibility shim) — the class attribute is deleted from the
`Adapter` ABC entirely. Existing behavior is preserved by seeding equivalent
`PolicyBinding` rows for both adapters at bootstrap, the same idempotent
pattern `plugins/seed_registry.py` already uses for plugin lifecycle. See
§13.3.

### 4.2 Four-state Verdict & escalation

**Severity lives on the `PolicyBinding`, not on `Policy`.** A `Policy` class
declares *what it checks*; how serious a violation is *in the context of a
specific adapter* is an administrative judgment, not a property of the
policy's code — the same reasoning that moved `governing_policy_ids` off
`Adapter` and into the database applies here too. See §13.5 (this review's
second-highest-stakes call).

**Aggregation: highest-severity-flagged-wins, statically mapped, no rule
engine.** `LOW -> ALLOW_WITH_FLAG`, `MEDIUM -> ESCALATE_FOR_REVIEW`, `HIGH ->
RECOMMEND_HOLD`, taking the maximum severity among all flagged findings in
one verdict (an `ALLOW`-only verdict needs no severity at all). This is the
same "most restrictive wins" principle M4 already used for its binary OR,
extended to three tiers instead of two — and, per the same "no abstraction
without a second case" discipline M4 §13.3 already applied to aggregation,
this review recommends against a configurable rule DSL (weighted scoring,
multi-policy combination rules) with no second aggregation strategy yet to
justify one. See §13.6.

**`GovernanceEngine`'s constructor changes again**, from `list[Policy]` to
`list[GoverningPolicy]` (`policy` + `severity` bundled) — see §9 for the
concrete proposed shape.

### 4.3 Cryptographic signing

**Sign the evidence-chain record's `record_hash`, with a single Ed25519
keypair loaded from configuration — not a KMS/HSM integration, not
per-record keys, not key rotation.** Ed25519 over RSA for smaller, faster
signatures and because there is no legacy interoperability constraint
forcing RSA. The private key is read the same way every other secret in
this codebase is (`Settings`, env-driven) — `infra/ci/setup_test_role.py`'s
pattern for CI-only secrets, not a new secret-management mechanism. Building
real key custody (HSM-backed, rotatable, multi-signer) is real
infrastructure scope beyond what one milestone should absorb without a
second deployment environment to design it against — the same
"no-second-case" discipline applied to infrastructure instead of code. See
§13.8.

**Signing applies going forward only — no retroactive signing of M0–M4
evidence.** A signature asserts "this deployment, holding this key,
produced this record" — retroactively computing one over data that predates
the key's existence would assert something false. See §13.10.

**A standalone verification CLI**, mirroring `audit/verify_chain.py`'s
existing shape (`python -m gov_platform.audit.verify_chain
--database-url ...`) — either extending that module or a sibling
`verify_signatures.py`, TBD at implementation time, not an architectural
question this review needs to settle now.

### 4.4 DB-backed protected-attribute rules

**A `protected_attribute_rules` table, separate from `policy_bindings`** —
keyed by `(domain, attribute_name)`, shaped like today's
`DomainProtectedAttributeRules` (`direct_attributes` become rows with
`classification = 'DIRECT'`; `proxy_attributes` become rows with
`classification = 'PROXY'` and a `proxy_of` column). Grouping this with
Policy Bindings into one table just because both are "M5, DB-backed
config" would conflate two unrelated keys and shapes for no reason — see
§13.4.

**Consumed by `ProtectedAttributeResolver` (already has a natural DB
touchpoint via `EvidenceStore`), *not* by `DirectAttributeInInputsPolicy`'s
own copy — a deliberately scoped, named divergence.** This is the review's
third-highest-stakes call; see §13.9 for the full reasoning on why giving a
zero-argument-constructed `Policy` database access is a bigger architectural
question than this milestone should fold in silently alongside four other
changes.

## 6. Database schema changes (proposed)

```sql
-- policy_bindings: dynamic, admin-managed replacement for the static
-- Adapter.governing_policy_ids tuple M3/M4 built.
CREATE TABLE policy_bindings (
    id              TEXT PRIMARY KEY,
    adapter_id      TEXT NOT NULL,
    policy_id       TEXT NOT NULL,
    severity        TEXT NOT NULL,   -- 'LOW' | 'MEDIUM' | 'HIGH'
    lifecycle_state TEXT NOT NULL,   -- 'ACTIVE' | 'INACTIVE'
    created_at      TIMESTAMPTZ NOT NULL,

    UNIQUE (adapter_id, policy_id)
);

-- protected_attribute_rules: dynamic, admin-managed replacement for
-- classification.py's static _RULES_BY_DOMAIN dict.
CREATE TABLE protected_attribute_rules (
    id             TEXT PRIMARY KEY,
    domain         TEXT NOT NULL,
    attribute_name TEXT NOT NULL,
    classification TEXT NOT NULL,   -- 'DIRECT' | 'PROXY'
    proxy_of       TEXT,            -- set iff classification = 'PROXY'
    created_at     TIMESTAMPTZ NOT NULL,

    UNIQUE (domain, attribute_name)
);

-- Evidence signing: additive columns, not a new table -- one signature per
-- evidence_chain row, 1:1, written at insert time alongside record_hash.
ALTER TABLE evidence_chain ADD COLUMN signature TEXT;
ALTER TABLE evidence_chain ADD COLUMN signing_key_id TEXT;
```

`policy_bindings` and `protected_attribute_rules` get the same
`GRANT SELECT, INSERT, UPDATE, DELETE ... TO gov_platform_app` treatment as
`plugin_registrations`/`protected_attribute_resolutions` — ordinary,
admin-mutable operational tables, not append-only ledgers. The
`evidence_chain` columns inherit that table's *existing* `REVOKE
UPDATE, DELETE` privilege restriction automatically (migration `0008`
applies at the table level) — a signature can only ever be set at `INSERT`
time, never altered afterward, consistent with the rest of that table's
append-only guarantee. `signing_key_id` (not the raw key) is stored per
record so a future key-rotation milestone can tell which key verifies which
historical record without guessing.

**Two open schema questions flagged for your input, not decided
unilaterally:** whether `policy_bindings.severity` needs a `CHECK` constraint
(`IN ('LOW','MEDIUM','HIGH')`) the way lifecycle states don't currently get
one anywhere in this schema (validation lives in the Pydantic layer
throughout this codebase so far) — recommend staying consistent and *not*
adding one, but flagging since this table introduces a value with real
behavioral weight (it drives `VerdictStatus`) unlike, say,
`plugin_registrations.plugin_type`.

## 7. Public API changes (proposed)

**New Admin API surface:**

```
POST   /v1/admin/policy-bindings                     {adapter_id, policy_id, severity}
GET    /v1/admin/policy-bindings
GET    /v1/admin/policy-bindings/{id}
POST   /v1/admin/policy-bindings/{id}/deactivate      (ACTIVE -> INACTIVE)
POST   /v1/admin/policy-bindings/{id}/activate        (INACTIVE -> ACTIVE)

POST   /v1/admin/protected-attribute-rules            {domain, attribute_name, classification, proxy_of?}
GET    /v1/admin/protected-attribute-rules
GET    /v1/admin/protected-attribute-rules/{id}
```

Mirrors the existing `/v1/admin/plugins` and `/v1/admin/systems` REST shape
for consistency — `POST` to create, `GET` to list/read, a dedicated
state-change endpoint rather than a general `PATCH` (the same design M3's
`promote` endpoint already established, for the same reason: an explicit,
named action is more auditable than an implicit field update).

**Ingestion response shape is unchanged** (`IngestionResponse`'s fields stay
the same) — the only externally-visible difference is that `status` can now
be one of four values instead of two. This *is* a real behavioral/contract
change for any existing API consumer that pattern-matches on
`"ALLOW"`/`"FLAGGED"` specifically (the Docker smoke test's own assertion,
`grep -q '"status":"ALLOW"'`, still matches unchanged — but a consumer
checking `status != "ALLOW"` to mean "flagged" would now also need to
handle three flagged variants, not one). Flagged as a real compatibility
consideration, not just a schema footnote — see §13.14.

## 9. Interfaces and abstractions (proposed)

```python
@dataclass(frozen=True)
class GoverningPolicy:
    """One Policy bundled with the severity its binding assigns it --
    the unit GovernanceEngine actually needs per policy, now that severity
    determines the verdict's state, not just whether it flags at all."""
    policy: Policy
    severity: PolicySeverity


_SEVERITY_TO_STATUS: dict[PolicySeverity, VerdictStatus] = {
    PolicySeverity.LOW: VerdictStatus.ALLOW_WITH_FLAG,
    PolicySeverity.MEDIUM: VerdictStatus.ESCALATE_FOR_REVIEW,
    PolicySeverity.HIGH: VerdictStatus.RECOMMEND_HOLD,
}
_SEVERITY_RANK: dict[PolicySeverity, int] = {
    PolicySeverity.LOW: 0, PolicySeverity.MEDIUM: 1, PolicySeverity.HIGH: 2,
}


class GovernanceEngine:
    def __init__(self, governing_policies: list[GoverningPolicy]) -> None:
        if not governing_policies:
            raise ValueError("GovernanceEngine requires at least one GoverningPolicy")
        self._governing_policies = governing_policies

    def govern(self, event: DecisionEvent) -> GovernanceVerdict:
        findings = [gp.policy.evaluate(event) for gp in self._governing_policies]
        flagged_severities = [
            gp.severity
            for gp, finding in zip(self._governing_policies, findings, strict=True)
            if finding.outcome is FindingOutcome.FLAGGED
        ]
        status = (
            _SEVERITY_TO_STATUS[max(flagged_severities, key=_SEVERITY_RANK.__getitem__)]
            if flagged_severities
            else VerdictStatus.ALLOW
        )
        return GovernanceVerdict(..., status=status, findings=findings, ...)
```

No new port. `Policy` and `Adapter` remain the only two plugin surfaces;
`GoverningPolicy` is a plain data-carrier, not an abstraction with more than
one implementation to justify a base class — same discipline as every prior
milestone's concrete-class-over-new-port calls.

**This constructor signature is this review's proposal, not yet
implemented** — flagged explicitly in §16 as a decision needing your
sign-off, the same way M4's §13.2 flagged `GovernanceEngine`'s prior
signature change before building it.

## 11. Acceptance criteria (proposed)

1. A `PolicyBinding` (not `Adapter.governing_policy_ids`, which no longer
   exists) determines which policies govern an adapter's events; changing a
   binding via the Admin API takes effect on the next request, no redeploy.
2. `GovernanceEngine` produces one of four `VerdictStatus` values based on
   the highest severity among flagged findings; an all-`CLEAR` verdict is
   always `ALLOW`.
3. Every evidence record persisted from M5 onward carries a signature that
   independently verifies against the platform's public key; a tampered
   `record_hash` or payload fails verification.
4. Protected-attribute classification rules for `FINANCE` are read from
   `protected_attribute_rules`, administrable without a redeploy, with
   existing M0–M4 behavior preserved exactly at cutover (verified by seeding
   the current static ruleset as the initial DB rows).
5. `ruff`, `mypy --strict`, and the full suite pass at 100% coverage against
   real Postgres.
6. `docs/architecture-mapping.md` updated to reflect real Policy Bindings,
   real four-state verdicts, real signing, and real DB-backed classification
   rules — with each row explicitly reconfirming what's still deferred past
   M5 (Human Review Workflow, dashboard, retention, auth).

## 12. Expected production-readiness review points

- **Severity is a hardcoded admin judgment with no audit trail of who set
  it or why** — same governance smell M2 flagged for its fairness
  threshold and M4 flagged for its debt-ratio constant. The realistic fix
  at M5's scope is documenting the gap precisely, not building a
  change-approval workflow (that's arguably M9-adjacent).
- **Escalation without Human Review Workflow (M9) is a verdict that says
  "review me" to nobody yet.** Worth stating explicitly as an intentional,
  named gap — an `ESCALATE_FOR_REVIEW` verdict is fully computed and
  persisted correctly by M5, but nothing currently *acts* on it beyond
  being queryable. Not a regression to fix; M9's actual reason to exist.
- **Signing key loaded from `Settings` (env-driven) has no rotation story
  and a single point of failure if leaked** — explicitly scoped out per
  §4.3/§13.8; flagged here as the real production caveat that scoping
  implies, not silently absorbed.
- **`protected_attribute_rules` and `DirectAttributeInInputsPolicy`'s own
  static copy can diverge** — a deliberately named, scoped divergence (see
  §13.9), directly analogous to M2's own already-accepted
  auto-provisioned-system divergence.
- **`VerdictStatus.FLAGGED`/`ALLOW` staying valid enum members forever**
  means new code must never *write* them while old rows can still *read*
  as them — a discipline enforced by code review, not a type-system
  guarantee. Worth a lint/test assertion that no M5+ code path constructs
  a `GovernanceVerdict` with the legacy values.

## 13. Architectural ambiguities, with my recommendation for each

### 13.1 — Policy Binding granularity: keyed by `adapter_id`, or by `System.domain`/jurisdiction? **(the highest-stakes call in this document)**

The architecture's own phrase is "which policy applies to which
domain/jurisdiction" — a richer key than `adapter_id`. Options: **(a)**
keyed by `adapter_id` (recommended) — the direct, dynamic replacement for
today's `governing_policy_ids` tuple, no pipeline change needed (the
ingestion route already knows `adapter_id` before `translate()` even runs).
**(b)** keyed by `System.domain` — matches the literal architecture phrase,
lets one binding govern every adapter/system sharing a domain without
duplication, but requires resolving a `DecisionEvent`'s `System.domain`
*before* `GovernanceEngine` can be constructed — today, `System`
auto-provisioning/lookup happens inside `EvidenceStore.append`, *after*
governance already ran (see `api/ingestion/routes.py`: policies are
resolved and run, *then* `evidence_store.append` is called, which is where
`System.domain` first gets looked up). Adopting **(b)** means moving System
resolution earlier in the request pipeline — a real, non-trivial reordering,
not just a new table. **(c)** keyed by `System.domain` *and* a new
`jurisdiction` field — doesn't exist anywhere in the schema today
(`System` has `domain`/`risk_tier`/`owner`, no jurisdiction), and this
platform has exactly one domain (`FINANCE`) and zero real jurisdictions to
validate a jurisdiction-keyed design against.

**Recommendation: (a).** This is the same "no speculative generalization"
discipline every milestone so far has applied (M2 declined multi-domain
generalization with only one domain; M4 declined dynamic binding with only
one binding pattern to prove). `adapter_id`-keyed bindings deliver the real,
load-bearing part of "Policy Bindings" — dynamic, admin-managed, no-redeploy
— without inventing a pipeline reorder and a jurisdiction concept neither
has a second real case to validate against yet. If this reading is wrong
against the real architecture document, it is the one finding in this
review most likely to require a materially different design, not a
parameter tweak — flagging exactly as prominently as M4's §13.1 did for its
own highest-stakes call.

### 13.2 — Binding lifecycle: reuse `DRAFT`/`SHADOW`/`PRODUCTION`, or a simpler `ACTIVE`/`INACTIVE`?

**Recommendation: `ACTIVE`/`INACTIVE`.** A binding answers "does this
already-trusted policy apply here," not "is this code trusted to run" —
`plugin_registrations` already fully owns the latter question. Reusing
three lifecycle stages at the binding layer would mean two independent
shadow/production axes (is the *policy* SHADOW-trusted; is the *binding*
SHADOW-active) answering overlapping questions with no clear precedence
rule between them — genuine confusion, not genuine flexibility.

### 13.3 — Does `Adapter.governing_policy_ids` get deleted outright, or kept as a bootstrap-time default?

**Recommendation: deleted outright**, per §4.1 — no compatibility shim, per
this project's standing practice (M2's `Policy.evaluate` never grew a
legacy path; M3 deleted hand-wired routes rather than leaving them dead; M4
renamed rather than dual-tracked). Existing behavior for the two first-party
adapters is preserved by seeding equivalent `PolicyBinding` rows in
`plugins/seed_registry.py`, the same idempotent mechanism that already seeds
plugin lifecycle state.

### 13.4 — One combined table for bindings and protected-attribute rules, or two separate tables?

**Recommendation: two.** They're keyed differently (`adapter_id`/`policy_id`
vs. `domain`/`attribute_name`) and shaped differently (severity+lifecycle vs.
classification+proxy). The only thing they share is "M5, DB-backed,
admin-configurable" — not a reason to conflate schema, per the same
"no abstraction without shared structure" discipline used everywhere else
in this codebase (e.g., `shadow_findings` staying structurally separate from
`findings` per M3 §13.3, for an analogous reason).

### 13.5 — Where does severity live: on `Policy`, or on `PolicyBinding`? **(second-highest-stakes call)**

Options: **(a)** a `severity` class attribute on `Policy` itself, alongside
`policy_id`/`version` — static, code-defined, uniform across every adapter
the policy governs. **(b)** on `PolicyBinding` (recommended) — the same
policy can carry different severity for different adapters (e.g., a fairness
policy might be `HIGH` severity bound to a lending adapter and `MEDIUM`
bound to a lower-stakes advisory adapter).

**Recommendation: (b).** Severity is inherently a judgment about
*consequence in context*, not a property of what the policy's code checks —
the same separation-of-concerns argument that already moved
`governing_policy_ids` off `Adapter` and into the database. A `Policy`
class staying purely about *what* it evaluates, with *how serious a
violation is here* living in the (admin-configurable, no-redeploy) binding,
is the more consistent architecture and the one that actually needs Policy
Bindings to exist at all — if severity lived on `Policy` instead, this
entire concern could have shipped as an M4-scale change to `Policy` itself,
without any new table.

### 13.6 — Escalation rule complexity: static severity-to-status mapping, or a configurable rule engine?

**Recommendation: static mapping** (§4.2/§9's `_SEVERITY_TO_STATUS` dict),
highest-flagged-severity-wins. No second aggregation strategy exists yet to
justify a configurable DSL — identical reasoning to M4 §13.3's rejection of
weighted/confidence-based aggregation in favor of plain OR.

### 13.7 — Where exactly is the M5/M9 boundary — does M5 need to notify anyone or create a review queue?

**Recommendation: no.** M5's job ends at correctly computing and persisting
a four-state `VerdictStatus`; it does not create a queue, send a
notification, or expose a "pending review" query endpoint. `GET`-ing
verdicts by status (to build such a queue) isn't itself blocked by anything
M5 does or doesn't build — a query API doesn't exist yet for *any* status,
including today's `FLAGGED` — so this isn't a new gap M5 introduces, just
one M5 doesn't have to close. Architecture §12 (Human Review Workflow) is
explicitly M9's card, not folded into M5 by implication.

### 13.8 — Signing algorithm and key custody: Ed25519 with an env-loaded key, or something more robust?

**Recommendation: Ed25519, single static keypair, loaded via `Settings`.**
Already argued in §4.3. A KMS/HSM-backed, rotatable, multi-signer system is
real infrastructure scope this platform has no second deployment
environment to design correctly against yet — building it now would be
guessing at requirements a real production rollout would actually dictate.
Flagged in §12 as a named, real production caveat, not silently absorbed.

### 13.9 — How does a Policy that needs DB-backed rules get database access, given `Policy` has always been constructed with zero arguments? **(third-highest-stakes call)**

`ProtectedAttributeResolver` is documented as "pure and DB-free" today,
deliberately. `DirectAttributeInInputsPolicy` holds one as a constructor
collaborator specifically *because* it has no other way to get resolution
logic without giving `Policy.evaluate` a database-carrying signature. Making
`classification.py`'s rules DB-backed means `ProtectedAttributeResolver`
needs a live `Engine`/`Session` somewhere — but the ingestion route
instantiates every production policy uniformly and with zero arguments
(`production_policy_cls()`); there's no existing hook to hand a
DB-backed policy an `Engine` at construction time. Options: **(a)** give
`Policy` a new construction protocol (e.g. a classmethod hook) so a policy
can opt into receiving an `Engine` — a real `Policy` port change, on top of
four other changes this milestone already makes. **(b)** cache DB rules
in-process, refreshed periodically, so `ProtectedAttributeResolver` stays
zero-argument-constructible — rule changes have a staleness window, unlike
every other M5 admin change, which is live on the next request. **(c)**
(recommended) — DB-back the rules *only* for `EvidenceStore`'s own
resolution path (which already holds a live `Session` every request and
already constructs its own `ProtectedAttributeResolver`) and leave
`DirectAttributeInInputsPolicy`'s copy on the current static, in-code
ruleset, unchanged, for now.

**Recommendation: (c).** This keeps the `Policy` port completely untouched
— already the busiest interface across M2–M4 — and avoids inventing a new
policy-construction protocol inside a milestone that's already changing
`GovernanceEngine`'s constructor, `Adapter`'s attributes, and `VerdictStatus`
simultaneously. The cost is an explicitly named divergence: an admin editing
`protected_attribute_rules` changes what `EvidenceStore` *persists* as
resolved, but not what `DirectAttributeInInputsPolicy` *judges* as a
`FLAGGED` direct-attribute leak, until a later milestone unifies the two
consumers. This is structurally the same kind of gap M2's own
production-readiness review already accepted for auto-provisioned systems
(`docs/architecture-mapping.md`'s M2-specific notes) — named honestly rather
than solved prematurely. If you'd rather solve both consumers in the same
milestone, that's option (a), and it should be called out as a `Policy`
port change requiring the same explicit approval `GovernanceEngine`'s
constructor changes have gotten at every prior milestone.

### 13.10 — Do historical `ALLOW`/`FLAGGED` verdicts get migrated to four-state values, or does the enum keep them permanently?

**Recommendation: keep them permanently, migrate nothing.** A `Verdict`'s
`status` is embedded in the hash-chained `evidence_chain.payload` JSON blob,
computed and hashed at write time — `evidence_chain` has `UPDATE`/`DELETE`
revoked at the database-privilege level (migration `0008`), so that
immutable record can never legitimately change regardless. Rewriting the
*separate*, mutable `verdicts.status` operational column for historical rows
would make the queryable view disagree with the immutable evidence-of-record
for the same event — a real integrity problem, not a cosmetic one. `ALLOW`
and `FLAGGED` become permanent, read-only-for-history members of
`VerdictStatus`; no M5+ code path ever constructs a new `GovernanceVerdict`
with either value (see §12's flagged test/lint gap).

### 13.11 — Does M5 add authentication in front of the new (more governance-critical) admin endpoints?

**Recommendation: no.** `README.md` already names this "M5+/M13" —
deliberately non-committal about which milestone actually closes it, and no
endpoint anywhere in this platform has authentication today (plugin
promotion, system registration — all open). Adding auth to *only* the two
new M5 endpoints while every existing admin endpoint stays open would be
inconsistent scoping, not a security improvement. Flagged explicitly,
though, because Policy Bindings materially raise the stakes of that gap: an
unauthenticated `POST /v1/admin/policy-bindings/{id}/deactivate` can now
silently stop a policy from governing real financial decisions, a more
consequential write than anything the plugin registry's admin surface
exposes today. This review recommends *naming* that increased risk loudly
in the M5 production-readiness review rather than solving it piecemeal here
— but this is a real judgment call your instincts as the platform owner
might weigh differently than a pure architecture-continuity read does.

### 13.12 — Does `FindingOutcome` need a third value (e.g. a severity-carrying outcome), instead of severity living entirely on the binding?

**Recommendation: no — `FindingOutcome` stays binary `CLEAR`/`FLAGGED`.**
A `Policy` still only ever says "does this decision violate what I check,"
full stop; *how much that matters* is the binding's job (§13.5). Adding
severity to `Finding` itself would duplicate information already available
via the binding that produced the `GoverningPolicy`, the same
denormalization M4 §13.4 already declined for disagreement-surfacing.

### 13.13 — Does `plugins/seed_registry.py` also need to seed a default `protected_attribute_rules` dataset, or is that left to a manual admin step?

**Recommendation: seed it**, mirroring exactly how plugin lifecycle is
seeded today — the current `FINANCE` ruleset (`race`, `gender`, `age`,
`marital_status` direct; `zip_code`, `first_name` proxies) becomes the
initial DB rows, so M0–M4 behavior is preserved exactly at cutover with no
manual step required before existing tests/demos keep working.

### 13.14 — Does the ingestion response need a new field surfacing *why* a verdict escalated (e.g. which policy/severity drove it), given `status` alone doesn't say?

**Recommendation: no change to `IngestionResponse` — `status` plus
`GET`-ing the persisted `Verdict`'s `findings` (already possible via direct
DB access, same as M4) is sufficient**, consistent with M4 §13.4's decision
not to extend the synchronous response with derivable information. Flagged
here, explicitly, as the closest thing to a product decision in this
document rather than a purely architectural one: a caller integrating
against this API synchronously might reasonably want "why" inline rather
than via a follow-up lookup. Recommending the conservative default, not
asserting it's the only defensible one.

## 14. What M5 owns

1. **Policy Bindings** — a new `policy_bindings` table, `adapter_id`-keyed,
   `ACTIVE`/`INACTIVE` lifecycle, admin-managed via a new Admin API surface,
   replacing `Adapter.governing_policy_ids` entirely.
2. **The full four-state `VerdictStatus`** — `ALLOW`, `ALLOW_WITH_FLAG`,
   `ESCALATE_FOR_REVIEW`, `RECOMMEND_HOLD` — computed by `GovernanceEngine`
   from the highest severity among flagged findings.
3. **Escalation rules** — a static, three-tier severity-to-status mapping,
   with severity declared per `PolicyBinding`.
4. **Cryptographic signing** of every evidence record from M5 onward
   (Ed25519, single static key, standalone verification tooling).
5. **DB-backed, admin-configurable protected-attribute classification
   rules** for `EvidenceStore`'s resolution path, via a new
   `protected_attribute_rules` table and Admin API surface.

## 15. What remains deferred past M5

- **Human Review Workflow** (the actual UI/queue/action a human takes on an
  `ESCALATE_FOR_REVIEW` verdict) — M9.
- **Compliance Dashboard** — M10.
- **Encryption at rest and retention tiers** for the evidence store and
  `protected_attribute_resolutions` — M11.
- **Async ingestion and population-level policies** — M6/M8.
- **Authentication in front of any endpoint**, including the new M5 admin
  surface — named `M5+/M13`; this review recommends M5 does not claim it
  (§13.11).
- **Real OS-level plugin sandboxing** beyond timeout/exception isolation —
  no milestone named yet.
- **Domain/jurisdiction-keyed Policy Bindings** (as opposed to
  `adapter_id`-keyed) — deferred until a second real domain or a real
  jurisdiction concept exists to design against (§13.1).
- **Unifying `DirectAttributeInInputsPolicy`'s own protected-attribute
  judgment with the new DB-backed rules** — deferred; it keeps reading the
  static, in-code ruleset until a later milestone gives `Policy` a real
  database-access construction protocol (§13.9).
- **Signing key rotation and KMS/HSM-backed custody** — deferred past a
  single static, env-loaded keypair (§13.8).
