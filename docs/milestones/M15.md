## Revision note (hostile-review pass)

This document was drafted, then re-read as though written by someone
else, assuming it wrong until proven otherwise — the identical discipline
M6–M14 were each built under. Items 1–7 are from this document's own
first-pass, self-directed hostile review. Item 8 is from a second,
completely independent pass performed separately — re-reading
`docs/architecture-mapping.md`, M0–M14, and the current codebase cold,
not trusting the first pass's own conclusions, per the same "don't assume
the first review was correct" discipline M11's own third hostile-review
pass was run under (§4.4 there). All eight findings are folded into the
text below rather than presented as a separate errata list, matching
M9–M14's own convention.

1. **First candidate considered and reversed: extending pagination to
   every list endpoint in the Admin API** (`systems`, `plugins`,
   `policy-bindings`, `protected-attribute-rules`,
   `population-policy-bindings`, in addition to the three named by the
   citation trail). Reversed on rereading the actual citations: M10 §8.3
   and M12 §12.15 both name exactly three endpoints, and both name the
   *reason* precisely — `population_findings`/`verdict_reviews`/
   `population_finding_reviews` are, in current practice, read from tables
   with no code path that ever removes a row, and whose row count tracks
   decision/ingestion volume rather than admin registration activity (see
   Revision note item 8 for the precise, corrected version of this claim —
   an earlier draft overstated it as a database-enforced guarantee for all
   three, which is only true of `population_findings`). The five other
   list endpoints read from genuinely bounded, admin-configuration-scale
   tables (row count bounded by real adapter/policy/rule registration
   activity, not by request or decision volume) — the identical "bounded
   vs. unbounded" distinction this document draws on a *growth-driver*
   axis (registration activity vs. decision volume), not the *database-
   privilege* axis `docs/milestones/M11.md` §5.3 uses for its own,
   different purpose (see item 8: that axis actually groups
   `verdict_reviews`/`population_finding_reviews` together with
   `population_policy_bindings`, not against it). Extending pagination to
   the five bounded endpoints would have no citation supporting it and
   would repeat the exact "audit every table for this defect shape" scope
   creep `docs/milestones/M14.md` §3 explicitly declined for its own,
   narrower defect class.
2. **Second candidate considered and reversed: a shared `Page[T]`
   pagination framework/response envelope.** Considered on the reasoning
   that three call sites is "already reuse." Reversed: this project's own
   standing discipline (`docs/milestones/M9.md`'s and every subsequent
   milestone's repeated invocation of "three similar lines beat a
   premature abstraction") applies to a *generic* type before a second,
   differently-shaped need exists to prove it generalizes — and, more
   concretely, the four underlying repository methods (not three —
   `PopulationFindingRepository` alone contributes two, corrected by this
   document's own second hostile-review pass, Revision note item 8)
   already have genuinely different `WHERE`-clause shapes
   (`PopulationFindingRepository.list_all`'s no filter at all;
   `list_for_system`'s `system_id` filter; `VerdictReviewRepository.list_all`'s
   `status` *and* `severity`-via-join filters;
   `PopulationFindingReviewRepository.list_all`'s `status`-only filter) —
   there is no single query shape to genericize over yet, only a shared
   *concept* (limit/offset). §5 below applies that concept across all
   four, directly, not through a shared abstraction.
3. **Third candidate considered and reversed: a response envelope
   (`{"items": [...], "total_count": N}`) instead of a bare list.**
   Reversed after checking FastAPI's own constraint directly: a route's
   `response_model` is one fixed shape, so an envelope would apply
   *unconditionally*, including to the overwhelming majority of calls that
   never pass `limit`/`offset` at all — breaking every existing consumer's
   response-parsing code (concretely, `docs/milestones/M10.md`'s own
   `dashboard.js`, which calls `response.json()` and iterates the result
   directly as an array) for a milestone whose own citation trail never
   asked for a backward-compatibility break. See §5.3/§12.1 for the
   full reasoning and the option this rules out.
4. **A genuine correctness gap found while designing the mechanism, not
   before**: all three repository methods order by a single timestamp
   column alone (`evaluated_at` or `created_at`), with no tiebreaker.
   `OFFSET`-based pagination over a non-uniquely-ordered result set can
   silently duplicate or skip a row across two page requests whenever two
   rows share a timestamp — a real, live possibility for
   `population_findings` (multiple findings from one `run_policies`
   invocation can share an `evaluated_at`) and for `verdict_reviews`/
   `population_finding_reviews` (multiple reviews auto-queued from the
   same batch write, or from `human_review/backfill_reviews.py`, can
   share a `created_at` at low clock resolution). This is the identical
   defect class `docs/milestones/M4.md` §13.7 already found and fixed
   once in this exact codebase, for the identical reason ("two policies
   evaluated in the same request could in principle share a timestamp at
   low clock resolution"), by adding `policy_id` as a secondary sort key.
   §5.2 now requires the same fix here — each table's own primary key
   (`id`) as the tiebreaker — not left as an implementation detail for
   whoever builds this to discover independently.
5. **A related, pre-existing observation, named but not adopted as part
   of this milestone's own scope**: `PopulationFindingRepository.list_for_system`'s
   `WHERE system_id = :system_id ORDER BY evaluated_at` has no supporting
   index — the one composite index on this table
   (`idx_population_findings_policy_system_evaluated_at`, migration
   `0019`) leads with `population_policy_id`, a column this query never
   filters on, so Postgres cannot use it for this exact access pattern.
   This is a real, pre-existing query-planning gap, verified directly
   against migration `0019`'s own `CREATE INDEX` statement — but it
   predates this milestone, is not made worse by adding `limit`/`offset`
   (the unpaginated query already scans the same rows today), and this
   platform's own real data volume remains too small for this to be a
   measured problem rather than a theoretical one, the identical
   "no measured need yet" reasoning `docs/milestones/M7.md` §12 and
   `docs/milestones/M12.md` §12.15 already apply to comparable index

   own migration (§8: none).

## TL;DR

M15 closes a small, concrete, three-times-independently-disclosed gap in
this platform's Admin API: `GET /v1/admin/population-findings`,
`GET /v1/admin/verdict-reviews`, and
`GET /v1/admin/population-finding-reviews` each return every matching row
in one response, with no limit, from tables with no code path that ever
removes a row. `population_findings` is the strongest case: permanently
`REVOKE UPDATE, DELETE`-locked at the database-privilege level since M6,
hardened by M11's own privilege lockdown (§5.3) — no application code,
today or in the future, can delete a row from it without a schema/
privilege change. `verdict_reviews`/`population_finding_reviews` are
unbounded in current practice for a related but weaker reason, corrected
by this document's own second, independent hostile-review pass (Revision
note item 8): M11's own retention-scope reasoning (§5.2, "Scope: exactly
two tables") never discusses either table at all, and M11's own
Production-Readiness Review (§5.3, itself corrected during M11's third
hostile-review pass) explicitly classifies both — together with
`population_policy_bindings`, the very table this document's own §4.2
treats as bounded and out of scope — as "genuinely admin-mutable
operational config" retaining the full `DELETE` grant given at each
table's own originating migration. No code path exercises that grant
against either table today (M11 §12.16), and each table's row count
tracks decision/ingestion volume, not admin registration activity — a
real, different growth driver from `population_policy_bindings`'s own
human-paced growth, and the actual basis this document relies on — but
this is a fact about the current absence of a deleting code path, not a
database-enforced guarantee the way `population_findings`'s own lockdown
is. Named by M10 (§7/§8.3, "a well-known browser-tab-freezing failure
mode, not a mild rough edge"), reaffirmed by M12 (§12.15), and reaffirmed
again by M14 (§4.6/§12.3) — each milestone independently confirming the
gap is real and correctly out of *that* milestone's own scope, never that
it had stopped existing.

**The fix is additive, optional `limit`/`offset` query parameters on all
three endpoints, mirroring the identical "optional query parameter, safe
default preserves today's exact behavior" shape `GET /v1/admin/metrics?since=`
(M7) already established** — not a new pagination framework, not a
response-envelope redesign, not a cursor/keyset mechanism. Omitting both
parameters (the overwhelming majority of calls today, including the M10
dashboard's own, unmodified `fetch()` calls) returns exactly what these
endpoints already return — no response shape change, no behavior change,
byte-for-byte. A caller that *does* pass `limit`/`offset` gets a
same-shaped, shorter list, sliced server-side.

**One genuine correctness gap was found while designing this, not
before**: none of the three repository methods behind these endpoints
orders by more than a single, non-unique timestamp column — the exact
defect class `docs/milestones/M4.md` §13.7 already found and fixed once
in this codebase (secondary sort key: `policy_id`), recurring here in
three more places. §5.2 fixes all three the identical way (`id` as the
tiebreaker), closing a `OFFSET`-pagination correctness hazard (a silently
duplicated or skipped row across two page requests) that would otherwise
ship alongside the pagination mechanism this document exists to add.

**One genuine value judgment is held for your explicit approval (§12.1)**,
the same way M11–M14 each held their own single highest-stakes call:
should `limit` stay unbounded when omitted (this document's own
recommendation — fully backward-compatible, but does not by itself
protect a caller that never opts in, including today's dashboard), or
should a sane default cap apply even when a caller passes neither
parameter (closes the tab-freeze risk for every caller unconditionally,
at the cost of a real, disclosed behavioral break for the one known
existing consumer). Everything else in this document is this review's
own confident recommendation.

## 1. Scope

**In scope** — exactly three existing endpoints, no others:

1. `GET /v1/admin/population-findings` and its `list_for_system`/`list_all`
   repository methods (`api/admin/population_findings.py`,
   `db/repositories/population_finding.py`).
2. `GET /v1/admin/verdict-reviews` and its `list_all` repository method
   (`api/admin/verdict_reviews.py`, `db/repositories/verdict_review.py`).
3. `GET /v1/admin/population-finding-reviews` and its `list_all`
   repository method (`api/admin/population_finding_reviews.py`,
   `db/repositories/population_finding_review.py`).

Each gains two new, optional query parameters (`limit`, `offset`) and a
secondary sort key (`id`) added to its existing `ORDER BY`. No other
change to any of these six files — the same `status`/`severity`/
`system_id` filters, the same response models, the same role gates M13
already wired on, all untouched.

**Out of scope**, argued in full at §4:

- Every other list endpoint in this codebase (`systems`, `plugins`,
  `policy-bindings`, `protected-attribute-rules`,
  `population-policy-bindings`) — bounded, admin-configuration-scale
  tables with no citation naming them and no forcing case (§4.2,
  Revision note item 1).
- A shared pagination framework, helper, or response envelope type —
  three call sites with three different filter shapes, no second
  differently-shaped need to justify an abstraction (§4.3, Revision note
  item 2).
- Cursor/keyset-based pagination — a real, "more correct at scale"
  alternative, declined for this milestone for lack of a forcing case
  (§12.2).
- Updating `api/dashboard_static/dashboard.js` (M10) to actually request
  paged results, or to add any pager/"load more" UI control — a real,
  separate follow-up this document names but does not build (§12.3,
  §11).
- Any change to `PopulationFindingResponse`/`VerdictReviewResponse`/
  `PopulationFindingReviewResponse`'s field shape, to any existing filter
  parameter's behavior, to any role gate M13 wired on these three
  endpoints, or to any other table in this schema.
- Any new migration, new index, new table, or new column (§6/§8).
- Authentication, retention, encryption, or any other cross-cutting
  platform concern — untouched.

## 2. Relationship to previous milestones

M15 closes a gap that is, by this project's own record, exactly as old as
the tables it concerns:

- **M6** built `population_findings` — permanently append-only from the
  start (migration `0015`'s `REVOKE UPDATE, DELETE`), with no retention
  mechanism ever proposed for it, and its own read endpoint
  (`api/admin/population_findings.py`) shipped with no `limit`/`offset`
  from day one, since M6's own citation trail never named pagination as
  part of its job.
- **M9** built `verdict_reviews`/`population_finding_reviews` the same
  way — `VerdictReviewRepository.list_all`'s own docstring, unchanged
  since M9, already states "with no pagination... a newest-first default
  would bury the stalest, most-overdue items" as a known, accepted
  characteristic at the time, not a defect M9 was responsible for fixing.
- **M10**, building the Compliance Dashboard as the first consumer that
  actually *renders* these lists (rather than a script parsing JSON),
  found the consequence these three endpoints' unbounded shape actually
  has at real scale — a browser-tab freeze — and explicitly declined to
  fix it, naming the reason precisely: "fixing pagination is M6's/M9's
  own API surface to own... not something M10's own additive scope
  stretches to cover" (M10 §8.3). This document is that fix, five
  milestones later.
- **M11**, classifying every table in this schema by evidentiary/
  retention status, is the reason `population_findings` is *provably*
  unbounded rather than merely currently large: permanently
  `REVOKE UPDATE, DELETE`-locked (§5.3 there), with no retention mechanism
  ever proposed for it (§5.2's own retention scope is exactly
  `shadow_findings`/`protected_attribute_resolutions`). `verdict_reviews`/
  `population_finding_reviews` are a related but weaker case, corrected by
  this document's own second hostile-review pass (Revision note item 8):
  M11 never discusses either table in its retention-scope reasoning at
  all, and its own Production-Readiness Review (§5.3) explicitly groups
  both with `population_policy_bindings` as ordinary, admin-mutable
  operational config retaining full `DELETE` grant — not database-locked
  the way `population_findings` is. What M11 does establish for these two
  is narrower but still real: no code path exercises that grant today
  (§12.16), and unlike `population_policy_bindings`, their row count
  tracks decision volume, not admin registration activity. Without M11's
  own classification, M15's own citation would be an unchecked assumption
  for all three tables; with it, it is a checked fact for
  `population_findings` and a checked, narrower fact (no current deleting
  code path, decision-volume-driven growth) for the other two.
- **M12**, building a periodic reporting CLI that reads from the same
  underlying tables (`verdicts`, `findings`, `population_findings`,
  `verdict_reviews`, `population_finding_reviews`), independently
  re-confirmed the pagination gap (§12.15) while correctly noting its own
  reporting queries are `GROUP BY` aggregates, not row-by-row fetches,
  and are therefore unaffected by it — direct confirmation that M12's own
  scope is untouched by this document (§2/§9 below).
- **M13** added `require_role` gates to all three endpoints
  (`require_role(*PrincipalRole)` for `list`/`get` on both review
  routers; the same gate, applied at the router level, for
  `population-findings`) — unchanged by this document. Pagination is
  additive to the request's query string, not a change to who may call
  these endpoints.
- **M14**, the most recent milestone, explicitly considered and declined
  this exact gap a third time (§4.6/§12.3 there), for scope-discipline
  reasons specific to *that* milestone (a different, narrower defect in
  two unrelated repositories) — not because the gap had been resolved.
  M15 is not a continuation of M14's own defect (policy-binding
  lifecycle transitions); it is the next item in this project's own,
  independently-maintained list of "real, verified, repeatedly-named,
  never-picked-up" gaps, selected by the identical methodology M14 itself
  established (§4 below repeats that methodology against the current,
  post-M14 record).

No prior milestone's approved architectural decision is revised,
weakened, or reopened by this document. `PopulationFindingResponse`/
`VerdictReviewResponse`/`PopulationFindingReviewResponse`'s field shapes,
every existing filter parameter, M9's `status`/`severity` semantics, and
every M13 role gate are all unchanged — see §10 for the precise, narrow
behavioral guarantee this milestone makes.

## 3. Explicit non-goals

- **Not a general "add pagination everywhere" initiative.** §1/§4.2 name
  exactly three endpoints, each backed by a specific citation naming it
  by name. A future milestone that adds a new, similarly-unbounded table
  is responsible for pagination from that table's own first migration —
  the same "use the now-established pattern from the start" discipline
  `docs/milestones/M14.md` §3 already states for its own defect class.
- **Not a change to what these three endpoints return when called exactly
  as they are called today.** Every existing caller — the M10 dashboard,
  any external consumer, every existing test — continues to receive the
  identical, complete, unbounded list it receives today, unless it
  explicitly opts into a page.
- **Not a fix for `PopulationFindingRepository.list_for_system`'s missing
  index** (Revision note item 5) — a real, pre-existing, unmeasured query-
  planning gap, named in §9, not built here for lack of a demonstrated
  performance need at this platform's real, current data volume.
- **Not an update to `dashboard.js`.** Whether and how the Compliance
  Dashboard should adopt pagination (a "load more" control, an infinite
  scroll, a page-number picker) is a real, undecided UI question this
  document does not answer — see §11/§12.3. `dashboard.js` continues to
  request everything, exactly as M10 built it, and continues to work
  unmodified.
- **Not a retention or archival mechanism.** `limit`/`offset` change how
  much of a table's *current* content one response returns; they do not
  delete, age out, or reduce what a table holds. M11's own retention
  scope (`shadow_findings`/`protected_attribute_resolutions` only) is
  unaffected and unrevisited.
- **Not a change to any existing filter's semantics.** `system_id`
  (population findings), `status`/`severity` (verdict reviews), `status`
  (population finding reviews) all continue to mean exactly what M6/M9
  already defined; `limit`/`offset` apply *after* filtering, the same
  ordering every SQL `LIMIT`/`OFFSET` clause already implies.

## 4. Architectural analysis

### 4.1 The selection methodology, restated and reapplied

`docs/milestones/M14.md` §4.1 established a two-test methodology for
selecting a milestone's scope when no numbered architecture citation
exists to inherit: **(a)** does this platform's own record show a
concrete, current forcing case for building it now — not a hypothetical
future one; and **(b)** is this actually one coherent concern, or does it
bundle several unrelated ones. Unlike M14, M15 *does* have a citation
trail (§ Sourcing note) — but the same two tests still apply, since a
citation existing is not the same as a citation being ready to build
against without checking it.

**Test (a):** the forcing case is not speculative, though its strength
differs across the three tables — corrected here after this document's
own second, independent hostile-review pass found the original version
of this paragraph overstated it uniformly (Revision note item 8).
`population_findings` is permanently locked against deletion at the
database-privilege level (M6/M11 §5.3) — a present, structural guarantee
already built and shipped, that this specific response shape has no upper
bound, full stop. `verdict_reviews`/`population_finding_reviews` are not
database-locked the same way (M11 §5.3 explicitly retains full `DELETE`
grant on both, grouping them with `population_policy_bindings`) — their
forcing case rests on a narrower, still-real pair of facts: no code path
in this codebase exercises that grant today (M11 §12.16), and each
table's row count is driven by decision/ingestion volume rather than
admin registration activity, unlike every one of the five bounded
endpoints §4.2 declines to touch. This is still a materially different
situation from every "no forcing case" rejection this project's own
record contains (multi-tenancy: zero tenants exist; rate limiting: no
concrete algorithm has ever been named; KMS: no second deployment
environment exists) — those are all absent future requirements, where
this is a present, observable growth pattern with no code anywhere in
this repository that reverses it — but it is a claim about current
behavior for two of the three tables, not an architectural guarantee
against future behavior the way it is for the third.

**Test (b):** one coherent concern — "these three endpoints have no
pagination" — not three unrelated things sharing a citation the way
architecture §17 or the historical use of "M13" did. All three are the
identical fix (optional `limit`/`offset`, a secondary sort key) applied
to the identical underlying problem (an unbounded table with no response
cap), not three different features that happen to be adjacent.

### 4.2 Why not extend to every list endpoint (Revision note item 1)

`docs/milestones/M14.md` §3 draws the line this document reuses
verbatim: "not a general 'audit every repository for this defect shape'
initiative." The five other Admin API list endpoints —
`GET /v1/admin/systems`, `GET /v1/admin/plugins`,
`GET /v1/admin/policy-bindings`, `GET /v1/admin/protected-attribute-rules`,
`GET /v1/admin/population-policy-bindings` — read from tables whose row
count is bounded by real-world *registration* activity (how many
adapters, policies, bindings, and rules a compliance team actually
configures), not by request or decision *volume*. `docs/milestones/M11.md`
§4.2 already drew exactly this distinction for a different purpose
(retention eligibility: "the only tables in this schema that are
simultaneously non-evidentiary and not locked against deletion") — the
same underlying fact (bounded, admin-mutable, human-paced growth) that
made those tables *not* need retention is also why they do not need
pagination. No citation anywhere in this project's record names any of
the five, and this platform's own real registration activity (two
adapters, a handful of policies and bindings, confirmed by every prior
milestone's own "at this platform's actual observed scale" framing) gives
no reason to expect any of the five to ever need a cap.

### 4.3 Why not a response envelope or a pagination framework (Revision note items 2–3)

Considered directly, not dismissed by reflex: a `{"items": [...],
"total_count": N}` envelope is the more conventional REST pagination
shape, and would give a caller certainty about how many results exist
without an extra round trip. Rejected for two concrete reasons, not a
stylistic preference. First, FastAPI's `response_model` fixes a route's
response shape unconditionally — an envelope would apply even to the
overwhelming majority of calls that never request a page at all, breaking
every existing caller's response-parsing code (concretely, M10's own
`dashboard.js`, confirmed by reading it directly: every fetch call treats
the response as a bare array). Second, no prior milestone has ever
introduced a response envelope anywhere in this codebase — every list
endpoint since M1 returns a bare `list[X]` — making an envelope here the
first new response-shape convention in fifteen milestones for a milestone
whose own citation trail never asked for one. A pagination *framework*
(a shared `Page[T]`/`paginate()` abstraction) is rejected on the
identical "no second differently-shaped case yet" discipline this project
has applied everywhere else (M2's resolver, M4's aggregation rule, M6's
one population policy, M7's fixed metric set, M8's declined
metrics-registration framework, M12's declined report-type plugin
surface) — three call sites with three genuinely different filter shapes
is not evidence of a shared shape to extract, only a shared *concept*
(limit/offset) this document applies three times directly.

### 4.4 What actually survives both tests

Optional `limit`/`offset` query parameters on exactly three endpoints,
mirroring `GET /v1/admin/metrics?since=`'s own already-proven shape
(M7: an optional query parameter with a safe, behavior-preserving
default), plus a secondary sort key fixing a real, newly-found
correctness gap in all three repository methods (Revision note item 4,
mirroring `docs/milestones/M4.md` §13.7's own already-shipped fix for the
identical defect class). This is the scope §5 proposes.

## 5. Proposed architecture (this review's recommendation)

### 5.1 Query parameters: `limit`/`offset`, optional, unbounded by default

Each of the three endpoints gains:

```python
limit: int | None = Query(default=None, gt=0, le=1000)
offset: int | None = Query(default=None, ge=0)
```

`gt=0, le=1000` bounds `limit` to a sane range the moment it's supplied
at all — a caller cannot request a zero/negative page size, and a
`FastAPI`/Pydantic `422` (not a `500`, not a silently-clamped value)
results from an out-of-range request, the same "reject at the boundary,
loudly" discipline `api/admin/population_policy_bindings.py`'s own
`_reject_non_finite_parameters` (M8) and `schemas/decision_event.py`'s
own timezone-aware-timestamp validator already established for this
codebase. `1000` is a conservative, generous ceiling — larger than any
plausible page size a human-facing view would ever request, small enough
that even a maximally-sized page cannot itself cause the "unbounded"
problem this document exists to close; not cited to any external
standard, the same "a defensible, documented default, not a discovered
regulatory figure" framing this codebase already uses for its own
non-regulatory constants (e.g. `MAX_REQUEST_BODY_BYTES`, M0). `offset`
has no upper bound — a caller paging deep into a large result set is a
real, disclosed cost (§9), not a validation error.

**When both are omitted (`None`), behavior is byte-for-byte identical to
today**: every matching row, in the existing sort order, no truncation —
this is the backward-compatibility guarantee §10 formalizes.

**`limit` and `offset` are independent, not a paired all-or-nothing
option** — a caller may supply either alone. `offset=100` with no `limit`
is valid, ordinary SQL (skip the first 100 matching rows, return every
remaining one, unbounded) and is deliberately not rejected — a caller
that already knows how many rows to skip but wants everything after that
point is a real, coherent use, not a malformed request. `limit=50` with no
`offset` is the common first-page case, equivalent to `offset=0`. Found
missing from an explicit statement during this document's own second
hostile-review pass (Revision note item 8) — the mechanism already
supports both independently (§5.2's conditional application of each
clause), only the prose previously left it implicit.

### 5.2 A secondary sort key, closing a real correctness gap

Each affected repository method's `ORDER BY` gains the table's own
primary key as a tiebreaker, mirroring `docs/milestones/M4.md` §13.7's
own already-shipped fix exactly:

```python
# db/repositories/population_finding.py — list_all and list_for_system
.order_by(PopulationFindingRow.evaluated_at, PopulationFindingRow.id)

# db/repositories/verdict_review.py — list_all
.order_by(VerdictReviewRow.created_at, VerdictReviewRow.id)

# db/repositories/population_finding_review.py — list_all
.order_by(PopulationFindingReviewRow.created_at, PopulationFindingReviewRow.id)
```

`.limit(limit).offset(offset)` is applied to the same statement,
conditionally (only when the caller supplied a value — an unconditional
`.limit(None)` is a SQLAlchemy no-op, but the conditional form is written
explicitly rather than relied upon implicitly, matching this codebase's
own preference for explicit conditionals over relying on a library's
incidental no-op behavior elsewhere — e.g. `population_policy_bindings.py`'s
`parameters is None` checks). Existing filter clauses (`system_id`,
`status`, the `severity`-via-`VerdictRow`-join) are applied exactly as
today, unconditionally *before* `LIMIT`/`OFFSET`, in the same statement —
pagination slices the *filtered* result set, the same relationship every
SQL `LIMIT`/`OFFSET` clause already implies and no design decision this
document makes.

### 5.3 Response shape: unchanged, bare list, no envelope, no new header

`PopulationFindingResponse`/`VerdictReviewResponse`/
`PopulationFindingReviewResponse` and each endpoint's `response_model`
are completely unchanged. A caller supplying `limit`/`offset` receives
the identical response *type* — a shorter `list[X]` — not a different
shape. A caller determines whether more results exist the standard,
metadata-free way this document recommends over inventing a header or
envelope convention with zero precedent in this codebase (§12.1's sibling
question, §4.3): request `limit=N`; a response shorter than `N` means
this is the last page; a response of exactly length `N` means there may
be more, fetched by incrementing `offset` by `N`. No `X-Total-Count`
header, no `has_more` field, no `total_count` field — all three
considered and declined for the identical "no precedent, no citation
asking for this" reasoning §4.3 already applies to the full envelope
option, at a smaller scale.

## 6. Database/schema changes

**None.** No new table, no new column, no new migration. `id` already
exists as the primary key on all three tables (`population_findings`,
`verdict_reviews`, `population_finding_reviews`) — §5.2's secondary sort
key is a pure `ORDER BY` clause change, requiring no schema change of any
kind. `LIMIT`/`OFFSET` are plain SQL clauses, needing no new index to
function correctly (only, potentially, to perform well at a scale this
platform does not yet have — see §9's disclosed, unmeasured caveat,
Revision note item 5).

## 7. Public API changes

Two new, optional query parameters on three existing `GET` endpoints:

```
GET /v1/admin/population-findings[?system_id=][&limit=][&offset=]
GET /v1/admin/verdict-reviews[?status=][&severity=][&limit=][&offset=]
GET /v1/admin/population-finding-reviews[?status=][&limit=][&offset=]
```

No new endpoint, no new router, no change to any existing request or
response field, no change to any role gate (`require_role(*PrincipalRole)`
on all three, unchanged since M13). `limit`/`offset` outside their
declared bounds (`limit` not in `(0, 1000]`; `offset` negative) produce a
`422`, matching every other query-parameter validation failure this
codebase already returns (e.g. a naive `since` on `GET /v1/admin/metrics`,
M7). Omitting both parameters is not an error and is not deprecated —
it is the expected, common case for the foreseeable future, and remains
fully supported.

## 8. Migration strategy

**None required.** No migration file is added by this document. Nothing
about §5's repository-layer or API-layer changes depends on any database
state that isn't already present in every already-migrated deployment
since the table in question was first created (M6 for `population_findings`,
M9 for both review tables).

## 9. Production-readiness implications

**What this closes.** The specific, three-times-disclosed risk — an
operator's or a script's first request against a mature deployment's
`population_findings`/`verdict_reviews`/`population_finding_reviews`
returning an unbounded, ever-growing response — now has a real, working
mitigation available to any caller that chooses to use it. This does
**not**, by itself, close the risk for a caller that does not opt in
(§10/§12.1) — named plainly, not overstated.

**A real, disclosed limitation of `OFFSET`-based pagination, not fixed by
this document.** `OFFSET` pagination's well-known cost profile — a query
requesting `offset=N` still has to scan and discard the first `N` rows
server-side — means very deep pagination (a caller repeatedly paging
through tens of thousands of rows) gets linearly more expensive per page,
not constant-time. Cursor/keyset pagination (ordering by, and filtering
past, the last-seen row's own sort key rather than counting from zero
every time) avoids this at real scale — considered and declined for this
milestone at §12.2, for the identical "no second, current forcing case to
design the more complex mechanism against" reasoning this project applies
everywhere: at this platform's actual, current data volume (confirmed by
every prior milestone's own "handful of" framing for exactly these
tables), `OFFSET`'s cost profile is not yet a measured problem.

**A related, pre-existing, unmeasured index gap, named not fixed
(Revision note item 5).** `PopulationFindingRepository.list_for_system`'s
`WHERE system_id = :system_id` has no supporting index (the one
composite index on this table leads with `population_policy_id`, unused
by this query) — true before this milestone, unchanged by it, and not
worsened by adding `LIMIT`/`OFFSET` to a query that already scans the
same rows today. Worth a real `EXPLAIN ANALYZE` check against a
realistically-sized dataset before this becomes a real operational
concern, not before.

**No security implication.** No `require_role` dependency changes; no
new data becomes reachable that a caller could not already reach by
omitting the new parameters and receiving everything, as before.

**No coverage regression expected.** New tests are additive: `limit`/
`offset` combined with each endpoint's existing filters; `limit` and
`offset` supplied independently of each other (§5.1); the boundary
validation (`limit=0`, `limit=1001`, negative `offset`, each expecting
`422`); and — directly mirroring `docs/milestones/M4.md` §13.7's own
"formalize a determinism guarantee cheaply" test shape — a stable-
pagination regression test: seed two rows sharing an identical
`evaluated_at`/`created_at`, page through with `limit=1`, and assert no
row is returned twice or omitted, proving §5.2's secondary sort key
actually closes the correctness gap it exists to close, not merely
asserting it by inspection.

## 10. Backward compatibility

- **Every existing call to all three endpoints, made exactly as it is
  made today (no `limit`/`offset`), returns the identical response —
  same status code, same shape, same content, same order** (secondary
  sort key aside — see below). This is the central guarantee this
  document makes, verified directly against the one known first-party
  consumer: `api/dashboard_static/dashboard.js` (M10) calls all three
  endpoints with no `limit`/`offset` anywhere in its own source, and
  continues to receive everything, unmodified, exactly as it does today.
- **§5.2's secondary sort key is a narrow, disclosed exception to
  "byte-for-byte identical."** Two rows that previously happened to tie
  on the primary sort column, and whose relative order in a response was
  therefore whatever Postgres happened to return (unspecified, not
  guaranteed, by SQL's own semantics for an unordered tie), may now
  appear in a different relative order than before, because the tie is
  now broken deterministically by `id`. No caller in this codebase
  depends on any particular tie-break order today (confirmed: no test
  asserts a specific order between two same-timestamp rows) — this is a
  correctness fix closing an unspecified behavior, not a change to a
  contract anything actually relied on, the identical framing
  `docs/milestones/M4.md` §13.7 already used for its own, structurally
  identical fix.
- **`limit`/`offset` outside their declared bounds are a new source of
  `422` responses** that did not exist before (since the parameters
  themselves did not exist before) — not a behavior change to any
  existing, valid request, only a new failure mode for a request no
  caller has ever made until this milestone makes the parameter exist at
  all.
- **No change to any existing filter parameter's behavior, to any
  response field, or to any role gate.**
- **This document does not, by itself, reduce the tab-freeze risk for the
  M10 dashboard**, since `dashboard.js` is not updated to request pages
  (§3/§11) — named explicitly as the honest limit of choosing the fully
  backward-compatible option, not glossed over.

## 11. Deferred items

- **Extending pagination to any other list endpoint** — no citation names
  one, no forcing case exists for a bounded, admin-configuration-scale
  table (§4.2). A future milestone that introduces a new unbounded table
  should build pagination for it from that table's own first migration.
- **A shared pagination framework/response envelope** — three call sites,
  three different filter shapes, no second differently-shaped need yet
  (§4.3).
- **Cursor/keyset pagination** — the more scalable mechanism at real
  volume, declined for this milestone for lack of a current forcing case
  (§9/§12.2); revisit if `OFFSET`'s cost profile ever becomes a measured
  problem at this platform's real, current scale.
- **`dashboard.js` adopting pagination** (a "load more" control, infinite
  scroll, or a page picker) — a real, undecided UI question, explicitly
  not answered here (§3/§12.3). The dashboard continues to request
  everything, unmodified.
- **`PopulationFindingRepository.list_for_system`'s missing supporting
  index** — a real, pre-existing, unmeasured gap, named (§9, Revision
  note item 5), not fixed, absent a demonstrated performance need.
- **A default page-size cap applied even when a caller omits `limit`
  entirely** — the one genuine value judgment held for your explicit
  decision, not resolved by this document (§12.1).
- **Authentication, retention, encryption, or any other cross-cutting
  concern** — untouched, unaffected.

## 12. Architectural ambiguities, each with a recommendation and justification

### 12.1 — Should `limit` default to unbounded when omitted, or should a sane cap apply even to a caller that never opts in? **(this document's own highest-stakes call — held for your explicit approval)**

**Option (a) (recommended): unbounded by default.** `limit`/`offset` are
purely additive — a caller that never supplies either receives exactly
what it receives today, with no behavior change of any kind. This is the
fully backward-compatible choice §10 documents, mirroring `GET
/v1/admin/metrics`'s own `?since=` parameter shape (M7: an optional query
parameter, a safe default that preserves prior behavior for a caller that
doesn't ask). The cost, stated plainly: this does not, by itself, close
the tab-freeze risk this document's own sourcing note names — a caller
(including the M10 dashboard) that never opts in continues to receive an
unbounded response, exactly as it does today, forever, unless a future,
separate change updates that caller to actually request pages.

**Option (b): a default page size (e.g. 100) applied even when `limit`
is omitted**, with an explicit, larger `limit` (up to the `1000` ceiling)
required to see more per page, and an explicit way to request "everything,
unpaginated" if that's still needed (e.g. a documented `limit=0`/`all=true`
escape hatch). This *does* close the risk unconditionally — no caller,
including a script nobody remembers to update, can trigger the unbounded
response this milestone exists to prevent. The cost is real and
disclosed, not hypothetical: this is a genuine, breaking change to these
three endpoints' current contract (M10's own `dashboard.js` would, from
the moment this ships, silently start receiving only the first 100
results of what may be a much larger table, with no error and no visible
sign anything changed, unless `dashboard.js` is updated in the same
change to either request a larger `limit` or add a pager) — the same
class of "genuine, disclosed contract break, coordinated with the one
known affected consumer" this project has made exactly once before
(`docs/milestones/M13.md`'s own `AUTH_ENABLED=True` default, which
required updating `docker-smoke`'s CI job and `tests/conftest.py`'s
fixtures in the same milestone as a condition of shipping the default at
all).

**Recommendation: (a).** M13's own breaking change was justified by a
security property with no adequate substitute (an unauthenticated caller
being able to fabricate evidence or silently deactivate real governance).
This milestone's own forcing case — three tables that grow forever, at a
platform whose own real, current data volume is still small enough that
every prior milestone describes it as "a handful of" records — does not
carry the same urgency, and this platform has no citation or disclosed
incident describing an *actual* tab freeze having happened, only the
correctly-named *risk* of one at real scale. Shipping a default cap now,
with no coordinated `dashboard.js` update in the same change (out of this
document's own declared scope, §3), would silently change what an
operator sees on a page they already use today with no visible signal
anything is incomplete — a worse failure mode than the unbounded response
it replaces, unless the dashboard update ships in lockstep. Option (a)
lets this capability exist and be adopted deliberately, by a caller that
chooses to, the moment a real need appears — the identical "the mechanism
exists; a future milestone can adopt it" relationship
`docs/milestones/M9.md` already has to
`docs/milestones/M10.md` (M9 built the review-workflow data; M10, a later
milestone, built the view that actually renders it).

**This is not a unilateral call this document makes for you.** Unlike
every other decision in this document, a real, working platform
component (the dashboard) would need explicit, coordinated follow-up work
if option (b) is chosen, and no citation in this project's record settles
which of "fully backward compatible" or "safe by default, breaking" is
correct for this specific case. Approve (a) or (b) explicitly before
implementation begins — see §13, item 1.

### 12.2 — Offset/limit pagination, or cursor/keyset-based pagination?

Already argued in §9. **Recommendation: offset/limit**, the simpler
mechanism, sufficient at this platform's real, current data volume, and
requiring no new index or new sort-key-based filter clause beyond §5.2's
own tiebreaker. Keyset pagination (`WHERE (evaluated_at, id) >
(:last_evaluated_at, :last_id) ORDER BY evaluated_at, id LIMIT :n`) is the
more scalable, "textbook correct" mechanism at real volume — declined for
this milestone for the identical "no second, current case to design the
more complex mechanism against" reasoning `docs/milestones/M6.md` §13.2
already applied to a dedicated analytical store and `docs/milestones/M7.md`
§13.1 applied to a real metrics stack. If `OFFSET`'s cost profile ever
becomes a measured problem, that is the concrete forcing case this
document's own methodology (§4.1) requires before building the more
complex mechanism — not anticipated speculatively here.

### 12.3 — Should M15 also update `dashboard.js` to consume pagination?

**Recommendation: no**, mirroring `docs/milestones/M14.md` §12.3's
identical reasoning for a different pair of routers: "a real, verified
gap... found as a byproduct of a later milestone's own design work, that
belongs to an earlier milestone's surface, not the one that happened to
notice it" — restated here in the opposite direction: this milestone
*is* the one fixing the API surface M10 originally deferred, but
updating M10's own dashboard code to actually *use* the fix is a UI
question (does "load more" mean a button, infinite scroll, or a page
picker; does the Overview page's own read pattern need to change at all)
this document has no basis to decide unilaterally, the same category of
judgment call `docs/milestones/M10.md` §8.1 already declined to make
unilaterally for its own read-only-vs-interactive question. `dashboard.js`
continues to work, unmodified, requesting everything, exactly as it does
today (§10) — a real, plausible, small follow-up, not silently absorbed
into this milestone and not silently ignored either (§11).

### 12.4 — Does `list_all`'s existing `status`/`severity`/`system_id` filtering logic need to change to support pagination correctly?

**Recommendation: no.** `LIMIT`/`OFFSET` compose with an existing `WHERE`
clause in standard SQL exactly the way this document's own §5.2 pseudocode
shows — applied to the already-filtered result set, in the same
statement, no reordering of clauses, no second query. Verified directly
against SQLAlchemy's own `Select` builder semantics (`.where(...).order_by(...).limit(...).offset(...)`
chains in exactly the order the resulting SQL clauses appear), not
assumed.

   /v1/admin/metrics?since=`'s own already-proven optional-parameter
   shape. Out-of-bounds values produce a `422`, the same discipline every
   other query-parameter validation in this codebase already uses.
4. **§5.2/§9 — (a real correctness fix, not just a feature addition)**
   All three repository methods' `ORDER BY` gains the table's own
   primary key (`id`) as a secondary sort key, closing an `OFFSET`-
   pagination correctness hazard (a silently duplicated or skipped row
   across two pages when two rows share a timestamp) — the identical
   defect class, and the identical fix, `docs/milestones/M4.md` §13.7
   already shipped once in this codebase.
5. **§5.3/§4.3** — No response envelope, no new header, no pagination
   framework. Every response stays a bare `list[X]`, the exact type it
   is today; a caller determines whether more results exist by page-size
   comparison, not a new metadata field.
6. **§6/§8** — No new migration, no new table, no new column, no new
   index required for correctness (a related, pre-existing, unmeasured
   index gap is named at §9/Revision note item 5, not fixed here).
7. **§10** — Every existing call made with no `limit`/`offset` receives a
   byte-for-byte identical response to today's, with one narrow, disclosed
   exception: the relative order of two rows that previously tied on the
   primary sort column is now deterministic (§5.2) rather than
   unspecified — a correctness fix, not a change to any contract a caller
   actually depended on.
8. **§9** — No security implication (no role-gate change); no coverage
   regression expected; `OFFSET`'s well-known deep-pagination cost
   profile is named as a disclosed, not-yet-measured limitation, not
   fixed by keyset pagination this milestone (§12.2).
9. **§12.3** — `dashboard.js` is not updated to consume pagination —
   named, not silently absorbed, the identical treatment M10's own
   pagination gap received from M14 in the opposite direction.
