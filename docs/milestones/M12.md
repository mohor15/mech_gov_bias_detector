    `PopulationFindingCounts`/`ReviewOutcomeCounts`/`ComplianceReport`

    own literal text in two small, purely syntactic ways** — a qualified
    `de.id` instead of a bare, ambiguous `id`, and `CAST(:system_id AS
    text) IS NULL` instead of a bare `:system_id IS NULL` — both real bugs

    `bootstrap_plugins()` call, no `Settings` fields read, `--database-url`

    determinism goal (§2's `canonical_json` citation) implied it without
    spelling out the CSV case explicitly).

## Production-Readiness Review

Performed after implementation, before freeze — mirroring M5–M11's own
finalization passes, with the same "assume it's wrong until proven
otherwise" discipline applied to the *implementation* this time, not the
design. **This section was written twice.** The first pass (static
verification only — lint, strict mypy, and a local pytest run with no
Postgres available) concluded no implementation-time bug existed. That
conclusion was wrong, and is preserved below as a documented lesson rather
than silently rewritten: a later session obtained a real Postgres instance
and found two genuine bugs neither `ruff`, `mypy`, nor a Postgres-less
`pytest` run could ever have caught, because both are errors a real SQL
engine raises only when the query actually executes.

**Two real implementation-time bugs, found only once this milestone's SQL
was actually executed against a real Postgres database:**

1. **Ambiguous column reference.** All three queries that filter by
   `--system-id` through a `decision_events`/`model_versions` join
   (`_VERDICT_COUNTS_SQL`, `_FINDING_COUNTS_SQL`, `_REVIEW_OUTCOME_SQL`)
   contained `SELECT id FROM decision_events de JOIN model_versions mv ON
   mv.id = de.model_version_id WHERE mv.system_id = :system_id` — a bare
   `id` in the outer `SELECT`, when *both* joined tables have their own
   `id` primary key column. Postgres rejected this outright:
   `psycopg.errors.AmbiguousColumn: column reference "id" is ambiguous`.
   This SQL was copied verbatim from the frozen design (§5.1) — the design
   document itself carried this defect; it was never caught during design
   review because a design review reads SQL, it doesn't execute it.
   **Fixed:** qualified as `de.id`, the specific column the subquery
   actually means (it wants decision-event ids, never model-version ids).
2. **Untyped parameter in an `IS NULL`-only context.** Every query's
   `--system-id` filter follows the shape `CAST(:system_id AS text) IS
   NULL OR ... = :system_id` (see fix below) — but the *first* draft, per
   §5.1's own literal text, was `:system_id IS NULL OR ... = :system_id`
   with no cast. Postgres's extended query protocol (used by `psycopg`'s
   server-side parameter binding) failed to infer a concrete type for the
   parameter occurrence that appears *only* in an `IS NULL` comparison
   (which accepts any type, giving the planner nothing to infer from):
   `psycopg.errors.AmbiguousParameter: could not determine data type of
   parameter $3`. Reproduced in isolation with a two-line
   `text("SELECT :x IS NULL OR :x = 'a'")` probe before touching the real
   queries, to confirm the root cause precisely rather than guessing.
   **Fixed:** `CAST(:system_id AS text) IS NULL OR ...` — the cast gives
   that one occurrence an explicit type without touching the other
   occurrence, whose type is already inferred from the column it's
   compared against. Applied to all five queries (all five have this
   shape; the bug is not exclusive to the three queries above).

Both fixes are pure SQL corrections — no join, filter, table, or semantic
change; `--system-id` scoping behaves exactly as §5.1 specifies once the
query is actually valid SQL. Neither is a design contradiction or a scope
change; both are documented in the Design Review section below exactly as
originally approved (unedited, per this project's own convention of
preserving the frozen record) — the corrected SQL lives only in
`reporting/compliance_report.py` and in this section.

**Two further bugs, in test code rather than implementation code**, also
surfaced only once run against real Postgres:
`tests/integration/test_generate_report_postgres.py`'s two JSON-output
assertions assumed a flatter shape than `ComplianceReport.model_dump()`
actually produces (`report["verdicts"]["ALLOW"]` instead of the real
`report["verdicts"]["by_status"]["ALLOW"]` — nested Pydantic models
serialize as nested dicts, correctly; the test's assumption was wrong, not
the implementation). Fixed in the tests; no production code changed for
this one.

**How this was found:** Docker Desktop (present but not running in the
original session) was started, and an existing, previously-used
`gov-platform-pg` Postgres container from an earlier session was resumed
and brought current with `db.migrate` (idempotent — applied only the five
migrations it was missing, `0023`–`0027`). Running the full M12 suite
against it surfaced both SQL bugs immediately, plus a set of *other*
failures that traced back to this Claude session's own earlier, improperly
terminated `pytest` invocations still running as orphaned background
processes and concurrently writing to the shared `evidence_chain` table —
not a code defect, an artifact of this session's own process management,
resolved by killing the stray processes (confirmed via `pg_stat_activity`
and Windows process listing before and after). To rule out any further
contamination from that container's multi-day accumulated history, a
second, completely fresh `postgres:16` container was started on a separate
port, migrated from zero (all 27 migrations, confirming none of them —
including this milestone's own `0027` — has any bind-parameter or syntax
defect), and the full suite run against it. That fresh-database run is the
one this document reports below; the throwaway container was removed
afterward.

**Two remaining failures in that fresh-database run are confirmed
pre-existing and unrelated to M12**, not fixed here:
`test_metrics_postgres.py::test_verdict_counts_reflect_a_real_ingested_event`
and
`test_verify_population_findings_postgres.py::test_verify_from_database_reads_real_rows_and_reports_a_checked_count`.
Neither test imports from, or exercises, anything in `reporting/`; both
pass cleanly when run in isolation (confirmed directly); both fail only as
part of the full ordered suite, the signature of a pre-existing,
order-dependent shared-state sensitivity in those tests' own
`since`-window-based isolation strategy (documented as a known risk
pattern in `test_metrics_postgres.py`'s own docstring) — not something
introduced by, or in scope for, this milestone. Left unfixed, and named
here rather than silently ignored.

No design contradiction surfaced. `observability/metrics.py`,
`api/dashboard.py`, every Admin API router, both ingestion routes, and
every table this milestone reads remain byte-for-byte untouched — verified
directly (no import of, or change to, any of them from `reporting/`), not
assumed.

## Verdict

M12 is implemented exactly as the frozen design specifies, across every
item in the approval checklist (§13, items 1–17), with zero deviation
forced by a genuine implementation-time architectural contradiction. Two
real bugs were found in this milestone's own SQL — both present in the
frozen design's own literal text, both invisible to every static check
this project runs (lint, strict mypy, a Postgres-less pytest run), both
found only once the SQL was actually executed against a real database, and
both fixed with a pure syntax correction that changes no join, filter, or
semantic behavior. This milestone's own first-pass production-readiness
review claimed "no implementation-time bug was found"; that claim was
false, and is preserved above, not deleted, specifically so this
document's own record stays honest about what static verification can and
cannot prove. **All 43 new M12 tests (28 unit, 15 integration) pass against
a real, freshly-migrated Postgres 16 instance.** Two pre-existing,
unrelated test failures remain in the wider suite (see above) — named,
diagnosed, and explicitly out of this milestone's scope, not silently
carried forward. `observability/metrics.py`, `population_engine/window.py`,
every Admin API router, and both ingestion routes remain completely
untouched.

**Unlike this document's own first-pass finalization, this milestone's
Postgres-dependent behavior has now actually been verified against a real
database, not merely believed correct from documented semantics.** This
closes the exact caveat M9's and M11's own finalization passes had to
leave open in their own equivalent sessions.

## Revision note (hostile-review pass)

This document has been through the identical hostile-review discipline
M6–M11 were each built under before implementation began. Two findings
were severe enough to reverse part of the first draft's proposed
architecture; two more were folded in as amendments — all four recorded
in place below, not as a separate errata section, matching the convention
M6/M8/M9/M11 each established for their own passes. A second, independent
hostile-review pass — treating this document as though written by someone
else, assuming it wrong until proven otherwise — later found five further
issues: none severe enough to reverse anything in the already-corrected
architecture, but real enough to fold in the same way, matching M11's own
precedent of a second pass folding more findings into an already-corrected
document. All nine corrections are recorded in place below, in the order
each was found:

1. **§5.2/§12.3 reversed — M12 does not reuse
   `observability/metrics.py::get_governance_health_metrics`.** The first
   draft assumed the fastest path to governance-health numbers for a
   report was to call M7's own existing function. Traced directly against
   that function's actual signature: `get_governance_health_metrics(engine,
   *, since: datetime)` computes `[since, now())` — an **open-ended**
   window whose upper bound is always the moment the function runs, never
   a caller-supplied end. A monthly compliance report needs a **closed**
   historical window (`[window_start, window_end)`, both ends fixed and in
   the past) — "last calendar month," not "since the start of last month,
   through right now." These are genuinely different windowing shapes, not
   a small parameter gap: M7's own function was never designed to answer
   "what did this look like as of a specific past moment," and retrofitting
   a second, optional upper bound onto it would mean reopening a module
   this project's own standing discipline (M8 §13.14, M9 §9.1, M11 §4.3)
   has repeatedly declined to reopen for a different milestone's unrelated
   need. See the corrected §5.2/§12.3 below: M12 owns its own,
   self-contained bounded-window query functions, structurally parallel to
   M7's but never touching it.
2. **§5.1/§12.2 reversed — the report excludes shadow-disagreement and
   population-binding-staleness content entirely, not merely "when
   convenient."** The first draft's report content list included
   `shadow_findings`-derived disagreement rates, mirroring M7's own
   `GovernanceHealthMetrics` shape wholesale. Traced against M11's own,
   already-frozen design: `shadow_findings` is one of exactly two tables
   M11 makes retention-eligible (`docs/milestones/M11.md` §5.2). A report
   depending on it would silently inherit the identical undisclosed-drift
   risk M11's own hostile-review pass found and disclosed for M7's
   `?since` parameter (`docs/milestones/M11.md` §4.3): regenerating "the
   same" historical report after an operator has configured retention and
   purged old `shadow_findings` rows would silently under-report, with
   nothing in the regenerated report distinguishing "no disagreement
   occurred" from "the evidence for it no longer exists." Corrected: the
   report's content is scoped to exactly the tables no code path in this
   platform ever deletes from (`verdicts`, `findings`, `population_findings`,
   `verdict_reviews`, `population_finding_reviews`) — a report for a given
   historical window is therefore guaranteed byte-reproducible on
   regeneration, with no retention-interaction caveat needed at all, not
   because the interaction was solved, but because this document's own
   scoping choice never creates it in the first place. See §5.1/§12.2.
3. **§5.4/§12.8 amended — report generation needs no elevated database
   credential.** The first draft, reasoning by analogy to M11's retention
   tool (which needs a separately-credentialed, elevated connection because
   the app's own role has no `DELETE` privilege on the tables it purges),
   assumed report generation would need something similar. Checked
   directly against what the report's own queries actually require: every
   one of them is a read-only `SELECT`/`GROUP BY`, and `gov_platform_app`
   already holds `SELECT` on every table this milestone reads (including
   the append-only-locked ones, which have always permitted `SELECT` —
   only `UPDATE`/`DELETE` are revoked). Corrected: report generation runs
   under the app's own ordinary runtime connection, the same one every
   other read-only CLI/endpoint in this codebase already uses — no new
   credential tier, unlike retention's genuinely necessary one.
4. **§5.1/§9 amended — the report is not cryptographically signed.** The
   first draft considered extending `audit/signing.py` to the report the
   same way M6 extended it to `population_findings`, reasoning "signing
   is cheap and this project already has the machinery." Reconsidered:
   `population_findings` needed signing because it is itself a **new
   piece of evidence** — a genuinely new governance judgment nothing else
   in the platform had ever computed before. A compliance report is the
   opposite: a **derived rendering** of judgments the platform already
   computed, signed, and (for `verdicts`/`findings`) chained at their own
   point of origin. Signing a rendering of already-signed data adds a
   second, redundant authenticity claim with no concrete forcing case
   (no cited requirement that a report recipient must cryptographically
   verify the report file itself, as opposed to trusting the delivery
   channel the same way any other exported document is trusted) and real,
   non-trivial questions this document has no reason to answer
   speculatively (what payload gets hashed — the exact CSV/JSON bytes? —
   and whether two byte-identical regenerations must produce the same
   signature). Named as a real, disclosed, deliberately deferred capability
   (§11), not built now. See §5.1/§12.7.

5. **§5.4/§12.8 amended — corrected an internal miscount: three
   `DELETE`-locked evidentiary tables among this milestone's five, not
   four.** Traced directly against migration `0025` (`REVOKE UPDATE,
   DELETE` on `systems`, `model_versions`, `decision_events`, `findings`,
   `verdicts`, `verdict_findings`) and migration `0015`
   (`population_findings`): of the five tables this milestone actually
   reads, only three — `verdicts`, `findings`, `population_findings` — are
   `DELETE`-locked; `verdict_reviews`/`population_finding_reviews` retain
   `GRANT SELECT, INSERT, UPDATE, DELETE` in full (migrations `0023`/`0024`),
   exactly as §4.3 already states elsewhere in this same document. The
   first draft's §5.4/§12.8 miscounted these as "four," contradicting its
   own §4.3. The underlying conclusion — no elevated credential needed — is
   unaffected, since `SELECT` is unrevoked on all five tables regardless of
   the count; only the count itself is corrected. See §4.3 (unchanged),
   §5.4, §12.8.
6. **§5.1/§5.5/§12.10 amended — CSV export produces five files, not four;
   review-outcome content is split into two of them.** The first draft's
   CSV plan named four files (`-verdicts`, `-findings`,
   `-population-findings`, `-reviews`) for what it described as "four
   differently-shaped tables," but `ReviewOutcomeCounts` (§5.1) actually
   holds two independently-keyed dicts —
   `verdict_reviews_by_resolution` and
   `population_finding_reviews_by_resolution` — with no shared key space.
   Cramming both into one `-reviews.csv` file would need either an
   undocumented discriminator column or the "ad hoc
   multi-section-in-one-file convention" this same section already rejects,
   for exactly this reason, when comparing multiple files against a single
   file. Corrected: CSV export produces five files —
   `<prefix>-verdicts.csv`, `<prefix>-findings.csv`,
   `<prefix>-population-findings.csv`, `<prefix>-verdict-reviews.csv`,
   `<prefix>-population-finding-reviews.csv` — each mapping to exactly one
   flat dict, so the "one genuinely flat table per file, no ad hoc
   convention" rule the first draft already committed to is actually
   applied to its own model, not just stated. See §5.1/§5.5/§12.10.
7. **§5.3 amended — `reporting/generate_report.py` must construct its
   database engine via `db.session.create_db_engine`, not a bare
   `create_engine`.** The first draft's §5.3 described `--database-url` as
   following "the same explicit-argument convention every CLI in this
   codebase already uses," citing `db/migrate.py` and the
   `create_db_engine`-based CLIs in the same sentence, without
   distinguishing that these two groups use different engine constructors.
   `db/session.py`'s own module docstring records a real CI failure from
   this milestone cycle (`ModuleNotFoundError: No module named 'psycopg2'`)
   caused by a bare `postgresql://` URL reaching `create_engine`
   unnormalized; the fix (`with_psycopg_driver`) now lives inside
   `create_db_engine`, which every CLI except `db/migrate.py` already calls
   for exactly this reason (`retention/purge_expired_records.py`,
   `population_engine/run_policies.py`, `audit/verify_chain.py`,
   `plugins/seed_registry.py`, `human_review/backfill_reviews.py` —
   verified directly). Leaving §5.3 ambiguous about which constructor this
   milestone's own CLI uses risked an implementer reaching for the wrong
   one and silently reintroducing the identical bug this project just spent
   a CI cycle diagnosing and fixing. Corrected: §5.3 now states explicitly
   that `reporting/generate_report.py` uses `create_db_engine`. See §2,
   §5.3.
8. **§5.1/§9 amended — narrowed the CSV-injection claim.** The first draft
   claimed "every field is either a fixed enum-value key or an integer
   count." `VerdictStatus`/`FindingOutcome`/review `resolution` values are
   genuinely fixed enums, but `policy_id`/`population_policy_id` (the dict
   keys in `FindingCounts.by_policy`/`PopulationFindingCounts.by_policy`)
   and the CLI's own `--system-id` value are free-form strings set at
   plugin-registration/system-creation time (`schemas/finding.py`,
   `schemas/policy_binding.py`, `schemas/population_finding.py` all declare
   these as open `str` fields, not a closed enum) — not attacker-reachable
   via the unauthenticated ingestion surface, unlike `resolution_notes` (the
   field M9's own review named as reachable that way), but not "fixed enum
   values" either. Corrected: §5.1/§9 now distinguish the two categories
   explicitly rather than claiming a blanket "fixed enum-value keys only."
   This is a wording correction, not a reason to add escaping logic or new
   infrastructure — the practical CSV-injection risk from an
   operator-configured identifier remains low and is named, not newly
   mitigated by code.
9. **§6 — added, not amended: a documentation note verifying, rather than
   assuming, index support for the `--system-id` scoping subquery; no
   schema change follows from it.** §6 already verified index support for
   each table's own time-range filter directly against each index's column
   order, but the `--system-id` scoping subquery (`decision_events JOIN
   model_versions WHERE system_id = :system_id`, reused by three of the
   five queries) was never checked the same way.
   `decision_events (model_version_id, occurred_at)` (migration `0016`)
   supports the `decision_events` side; `model_versions` has no index on
   `system_id`, but `model_versions` is bounded by the number of (system,
   version) pairs this platform has ever registered — small at any
   realistic scale — so a sequential scan there is a non-issue, the same
   conclusion this document already reaches for other small tables. Named
   explicitly now, for the same "verified directly, not assumed"
   discipline this section already holds itself to elsewhere. No new
   index, no schema change.

This section records that the design below is the **corrected** design —
every subsection that follows already reflects all nine changes (four from
this document's own first hostile-review pass, five more from a second,
independent hostile-review pass), the same two-pass convention M11 itself
used when a second review folded four more findings into its own
already-corrected document.

## TL;DR

M12 completes architecture §14 ("Reporting") — the one deferred item every
milestone since M7 has pointed at by the same one-word citation and never
built. Per M10 §3.4's own, most load-bearing articulation, M12 is
**periodic and document-shaped**: a scheduled job produces a static,
downloadable artifact for an audience that may never touch the live
system at all — the deliberate opposite of M10's own on-demand, interactive
dashboard. Like M7 and M10 before it, **M12 computes no new governance
judgment of its own** — it is a new *export* pattern over data M0–M11
already compute, aggregate, and persist, not a fourth plugin port and not
a new analytical computation.

Two findings, found by tracing what the first draft's proposal actually
implied rather than accepting it at face value, are severe enough to
shape this document's entire recommendation:

1. **M7's own governance-health query function cannot be reused as-is,
   and must not be modified to fit.** It computes an open-ended
   `[since, now())` window; a historical report needs a closed
   `[window_start, window_end)` window with both ends fixed in the past.
   M12 ships its own, small, self-contained bounded-window queries rather
   than reopening a module this project's own standing discipline has
   repeatedly declined to reopen for an unrelated milestone's need
   (§5.2/§12.3).
2. **The report's content is deliberately scoped to exclude
   `shadow_findings`-derived signals, and this scoping decision is what
   makes the report immune to M11's retention purge — not an accident, a
   design choice with a concrete, checkable payoff.** Every table the
   report actually reads from (`verdicts`, `findings`, `population_findings`,
   `verdict_reviews`, `population_finding_reviews`) is one no code path in
   this platform ever deletes from. A report for a given historical window
   is therefore always byte-reproducible on regeneration, with no
   undisclosed-drift caveat needed — the same class of interaction M11's
   own hostile-review pass found and could only *disclose* for M7's
   `?since` parameter, avoided here entirely by scope (§5.1/§12.2).

No new plugin port, no new external dependency, no new database
credential tier, and (per §12.1, this document's own highest-stakes call)
no PDF-rendering library — the `csv`/`json` standard-library modules this
platform already relies on for every other JSON/CSV-shaped surface are
sufficient for "document-shaped," the same zero-new-dependency discipline
M0 (stdlib logging), M6 (no dedicated analytical store), M7 (no
Prometheus/OpenTelemetry), M8 (stdlib `statistics.NormalDist`), M10 (no
SPA framework), and M11 (`cryptography`, already a dependency since M5)
have each already applied to their own milestone's temptation to reach
for infrastructure.

A second, independent hostile-review pass (Revision note above) found five
further corrections — a self-contradicted table count, an unresolved CSV
file-shape ambiguity, a hidden assumption about which database-engine
constructor the CLI uses, an overstated CSV-injection claim, and a missing
index-verification note. None changes this recommendation's substance;
all five are folded into the sections below.

## 1. Scope

**M12 owns:**

- **A single, fixed "compliance summary" report type** — governance
  outcomes (verdict/finding counts by status/policy/outcome, population
  finding counts by policy/outcome) and Human Review Workflow resolution
  outcomes (how many reviews were resolved, and how, within the window),
  for a bounded, closed historical time window, optionally scoped to one
  `System` — assembled from data M1–M9 already compute and persist, no
  new domain computation (§4, §5.1).
- **Two export formats, both already-available standard-library
  capabilities**: JSON (the complete, structured format) and CSV (a
  flattened, per-section export) — no new dependency (§5.1, §12.1).
- **An explicitly-invoked CLI**, `python -m gov_platform.reporting.generate_report`,
  mirroring `population_engine/run_policies.py`'s and
  `retention/purge_expired_records.py`'s existing shape exactly: no
  daemon, no in-process scheduler, real scheduling (cron, a Kubernetes
  `CronJob`) remains deployment-topology scope, architecture §17/M13,
  unchanged (§5.3, §12.9).
- **Two new indexes** on `verdict_reviews`/`population_finding_reviews`
  (`(status, resolved_at)`, composite) supporting the one genuinely new
  query pattern this milestone introduces — "which reviews were resolved
  within this window" (§6, §12.16).

**M12 explicitly does not own** — each backed by a finding in §4/§5, not a
judgment call made unilaterally:

- **A PDF renderer, or any new rendering/templating dependency.** The one
  illustrative example in this platform's entire citation trail ("e.g. a
  monthly compliance PDF") is read as an example of "periodic,
  document-shaped, non-interactive," not a literal format commitment —
  see §12.1, this document's own highest-stakes call.
- **A new `reports` database table, a new Admin API surface, or any
  persistence of generated reports inside this platform at all.** The CLI
  produces a file (or writes to stdout); tracking which reports were
  generated, when, is left to whatever the operator's own scheduling/
  storage tooling already does — see §5.4/§12.4.
- **A fourth plugin port** for "report types." One fixed report type ships;
  a second, genuinely different report type is a real, plausible future
  need with zero real cases today to design the right extension point
  against — see §12.5.
- **Delivery or distribution of a generated report** (email, upload to a
  compliance portal, a shared drive) — a real deployment/operational
  concern this milestone's own citation never asks it to solve, the
  identical "real scheduling is deployment topology, not this milestone's
  job" boundary M6 §13.4 and M11 §5.2 already drew for their own batch
  tools (§9, §11).
- **Signing of the generated report.** A report is a derived rendering of
  already-signed/already-chained source data, not new evidentiary output —
  see §5.1's revision-note correction and §12.7.
- **Verifying the evidence chain's own integrity as part of report
  generation.** `audit/verify_chain.py` remains the one dedicated tool for
  that job; folding a whole-chain verification into a recurring reporting
  job would impose an unbounded, ever-growing cost on a job this
  milestone's own citation never asked to also be an audit-integrity
  check — see §12.11.
- **Encryption or retention changes of any kind.** M11 is frozen; this
  milestone reads through the exact same repository/query boundary every
  other consumer already does, and (per §5.1's own scoping) never touches
  either of M11's two retention-eligible or four encrypted columns at all
  — see §4.3's verification of this claim, not merely an assumption of it.
- **Authentication of any kind.** Still `M13` — the tenth consecutive
  milestone naming this exact gap, M11 having named itself the ninth
  (§9).

## 2. Relationship to previous milestones

M7 built the first, and until now only, aggregate read pattern over
governance data — `GovernanceHealthMetrics`, computed live, always ending
at "now," served as JSON with no persistence of its own. M10 built the
first UI, an on-demand, interactive rendering of that same data (plus
M6's and M9's) for a human at a browser. M12 is the third consumer of
this same underlying data, for a genuinely different audience and
cadence than either: not "an operator polling a live endpoint" (M7), not
"a human opening a browser to see current state" (M10), but "a
document, generated on a schedule, for whoever needs to file or review
it, whether or not they ever touch this platform directly" — M10 §3.4's
own framing, quoted in full above, is the load-bearing distinction this
entire document is built around.

Concretely, M12 depends on, and changes nothing about, the following
prior-milestone artifacts:

- **`schemas/verdict.py`/`schemas/finding.py`** (M0/M4/M5) — `VerdictStatus`'s
  four real values and `FindingOutcome`'s two are read, never written to,
  by this milestone's own count queries.
- **`schemas/population_finding.py`** (M6/M8) — `PopulationFindingOutcome`
  and the `(population_policy_id, outcome)` shape M7 already established
  as the right grouping for this data are reused verbatim for the
  report's own population-finding section.
- **`schemas/human_review.py`**, **`db/models.VerdictReviewRow`/`PopulationFindingReviewRow`**
  (M9) — `status`/`resolution`/`resolved_at` are read directly via new,
  bounded `text()` queries (§5.2), the same "plain query functions, no
  repository round trip" style M7's own `observability/metrics.py`
  already established for aggregate-shaped reads, not the row-by-row
  repository methods M9 built for the Admin API's own CRUD needs.
- **`observability/metrics.py`** (M7) — read, not modified. `GovernanceHealthMetrics`'s
  own field shapes (`verdict_counts_by_status`,
  `finding_counts_by_policy`, `population_finding_counts_by_policy`) are
  the direct template this milestone's own `ComplianceReport` model
  reuses for internal consistency across the platform's two aggregate
  surfaces — same field names, same nesting shape, different (bounded,
  not open-ended) underlying query. See §5.2's own note on exactly what
  is and is not shared between the two.
- **`population_engine/run_policies.py`**, **`retention/purge_expired_records.py`**
  (M6/M11) — the direct structural template for this milestone's own CLI:
  an explicitly-invoked batch tool, a fixed/calendar-aligned default
  window (M6's own "yesterday's full UTC day" convention, scaled here to
  "last full calendar month"), `--window-start`/`--window-end` as an
  override taken together or not at all (mirroring `run_policies.py`'s
  own argument-pairing validation exactly).
- **`docs/milestones/M11.md` §5.2/§5.3** — the specific, load-bearing fact
  this document's own §5.1 scoping decision depends on: `shadow_findings`
  and `protected_attribute_resolutions` are the *only* two tables M11
  makes retention-eligible; every other table this milestone reads from
  is either hash-chained/signed-and-locked (`verdicts`, `findings`,
  `population_findings`, all locked against `DELETE` since M1/M6/M11) or,
  for `verdict_reviews`/`population_finding_reviews`, ordinarily
  `DELETE`-capable but never actually deleted by any code path this

  `db/repositories/verdict_review.py`/`population_finding_review.py` —
  neither exposes a delete method, and M11's own privilege-classification
  review already verified this for the identical reason it left these two
  tables' `DELETE` grant untouched).
- **`audit/hash_chain.canonical_json`** (M0/M1) — reused for the report's
  own JSON serialization, so a report regenerated for the same window
  twice produces byte-identical output (deterministic key ordering), the
  same discipline this function already provides for hash-chain payloads.
- **`db/session.py::create_db_engine`** (M1/M11) — the shared
  database-engine constructor every CLI in this codebase except
  `db/migrate.py` already uses for its own `--database-url` argument
  (`retention/purge_expired_records.py`, `population_engine/run_policies.py`,
  `audit/verify_chain.py`, `plugins/seed_registry.py`,
  `human_review/backfill_reviews.py`). This is not a stylistic preference:
  `create_db_engine` carries the `with_psycopg_driver` normalization added
  during M11's own implementation, after a real CI failure
  (`ModuleNotFoundError: No module named 'psycopg2'`) traced to a bare
  `postgresql://` URL reaching a bare `create_engine` unnormalized —
  `db/session.py`'s own module docstring records the incident in full.
  `reporting/generate_report.py` (§5.3) uses `create_db_engine` for
  exactly this reason, not the bare `create_engine` `db/migrate.py` uses
  for its own, different, documented reason (no `connect_timeout`).

M12 is not a new pipeline stage and computes nothing — like M7 and unlike
every milestone that shipped a new plugin port (M3's registry, M6's
`PopulationPolicy`), it adds no new domain computation at all, and unlike
M6/M9/M11 it also adds almost no new persisted state (two new indexes,
no new table, no new column). Its job is entirely about **presenting
already-computed, already-persisted governance facts in a periodic,
exportable, document shape** — the third and final of the three
non-computational "read pattern over existing data" milestones this
platform's own architecture named (§9 Monitoring/M7, §11 Dashboard/M10,
§14 Reporting/M12), completing that trio.

## 4. Architectural analysis

### 4.1 Why "Reporting" cannot mean "reuse M7's metrics endpoint with a nicer file extension"

The naïve reading — wrap `GET /v1/admin/metrics`'s existing JSON response
in a file and call it a report — fails for a reason specific to what that
endpoint was actually built to answer. `observability/metrics.py::get_governance_health_metrics`
takes exactly one temporal parameter, `since: datetime`, and its own
implementation computes `window_end = datetime.now(UTC)` unconditionally
(confirmed directly against the function body) — every call answers "what
does governance activity look like from `since` through this exact
instant," never "what did it look like during some specific, already-closed
past period." A monthly compliance report is definitionally the second
kind of question: "January's numbers," queried in February or in
December, must return the same answer either time. Retrofitting a second,
optional upper-bound parameter onto `get_governance_health_metrics` would
work mechanically, but it means reopening a module this project's own
standing discipline has explicitly declined to reopen for an unrelated
milestone's need at every opportunity so far (M8 §13.14 declined to add
review-queue-depth counts to it; M9 §9.1 restated the same boundary; M11
§4.3 disclosed, rather than fixed, a real interaction with it rather than
touch its frozen shape) — this document holds itself to the identical
line, applied to its own, different need this time (§12.3).

This is not a reason to duplicate M7's actual SQL blindly — it is a
reason to build a small, self-contained, bounded-window equivalent that
happens to produce data shaped consistently with `GovernanceHealthMetrics`
(same field names, same nesting), so an operator who already understands
M7's live endpoint's response shape recognizes the report's own shape
immediately, without this milestone ever importing from, or modifying,
`observability/metrics.py` itself.

### 4.2 Why a report is not "the dashboard, but a file"

M10 §3.4 already drew this line explicitly and this document does not
re-litigate it, only confirms it holds under this milestone's own design:
the Compliance Dashboard renders **current, live state** for a human
actively looking at a browser right now; a report renders a **specific,
closed, already-past window**, generated once and then static regardless
of what happens on the platform afterward. These produce genuinely
different artifacts even when the underlying numbers happen to overlap —
a dashboard view of "this month so far" necessarily changes if you reload
it tomorrow; a report for "last month" must not, no matter when it is
regenerated or re-opened. M10 built no export/download capability from
its own live views specifically to keep this boundary intact
(`docs/milestones/M10.md` §3.4: *"M10 does not add any export/download/
scheduled-generation capability that would blur this line"*) — this
document is the fulfillment of that deferral, not a discovery that M10
left something out.

### 4.3 Why the report's content is scoped to exactly five tables, verified directly against M11's own retention scope

`docs/milestones/M11.md` §5.2 names `shadow_findings` and
`protected_attribute_resolutions` as the *only* two tables this schema
treats as retention-eligible — the only two simultaneously
non-evidentiary and not locked against deletion at the database-privilege
level. Every other table in this schema is either permanently append-only
(the eight evidentiary tables §5.3 locks down: `systems`, `model_versions`,
`decision_events`, `findings`, `verdicts`, `verdict_findings`,
`evidence_chain`, `population_findings`) or, for `verdict_reviews`/
`population_finding_reviews` specifically, ordinarily `DELETE`-capable at
the privilege level but never actually deleted by any code this platform
has shipped — confirmed directly by reading both repositories
(`db/repositories/verdict_review.py`, `db/repositories/population_finding_review.py`):
neither exposes a delete method, and every write path (`create`, `claim`,
`release`, `resolve`) is an `INSERT` or a conditional `UPDATE`, never a
`DELETE`.

This document's own report content — verdict counts, finding counts,
population finding counts, and review-resolution counts — reads
exclusively from `verdicts`, `findings`, `population_findings`,
`verdict_reviews`, and `population_finding_reviews`. **None of these five
tables is retention-eligible, and none is ever deleted from in practice.**
A report generated for a historical window today and regenerated for the
identical window a year from now — after any amount of M11 retention
activity against `shadow_findings`/`protected_attribute_resolutions` — is
therefore guaranteed to read the identical underlying rows both times.
This is a load-bearing, checked property of this design, not an
incidental one: the first draft's inclusion of shadow-disagreement content
(read from `shadow_findings`) would have broken exactly this guarantee,
and is why §5.1 excludes it (§12.2).

### 4.4 Why report generation needs no new plugin port

A `PopulationPolicy` (M6) was justified as a new port because
`Policy.evaluate`'s single-event, one-`Finding` contract is *structurally*
incapable of expressing an aggregate result — a genuinely different kind
of question, not a variation on an existing one (`docs/milestones/M6.md`
§9). No equivalent structural incompatibility exists here: "assemble
already-computed counts into a document" is one well-defined operation
with one shape of input (a time window, an optional system filter) and
one shape of output (a `ComplianceReport`). A second, differently-shaped
report (e.g., "an audit-trail export" or "a per-reviewer workload report")
is a plausible future need, but "plausible future need" with zero real
cases today is exactly the condition this project's own discipline
(M2's resolver staying concrete, M4's aggregation staying a plain
function, M7's fixed metric set, M8's declined metrics-registration
framework) has consistently declined to build ahead of — see §12.5.

## 5. Proposed architecture (this review's recommendation)

### 5.1 Report content: five tables, one fixed shape, no free text

**A new, small, top-level package, `reporting/`** — mirroring the exact
"a new top-level package only when nothing existing is a natural home"
bar `human_review/` (M9) and `retention/` (M11) each had to clear:
compliance reporting spans data from `governance_engine`-adjacent tables
and `human_review`-adjacent tables alike, with no existing package that
naturally owns both.

**`reporting/compliance_report.py`** defines the report's own Pydantic
model, deliberately **not** placed in `schemas/`:

```python
class VerdictCounts(BaseModel):
    model_config = ConfigDict(frozen=True)
    by_status: dict[str, int]  # VerdictStatus value -> count


class FindingCounts(BaseModel):
    model_config = ConfigDict(frozen=True)
    by_policy: dict[str, dict[str, int]]  # policy_id -> outcome -> count


class PopulationFindingCounts(BaseModel):
    model_config = ConfigDict(frozen=True)
    by_policy: dict[str, dict[str, int]]  # population_policy_id -> outcome -> count


class ReviewOutcomeCounts(BaseModel):
    """Reviews *resolved* within the window -- not reviews *created*
    within it (a review created in one window and resolved in a later
    one is counted in the window it was actually resolved, matching what
    a compliance audience actually wants to know: what got decided during
    this period, not merely what was queued). The two fields below are
    two independently-keyed dicts, not one -- a verdict-review resolution
    and a population-finding-review resolution are different key spaces
    with no shared row shape, and are exported as two separate CSV files,
    not one (see §5.5)."""
    model_config = ConfigDict(frozen=True)
    verdict_reviews_by_resolution: dict[str, int]     # 'CONFIRMED' | 'DISMISSED' -> count
    population_finding_reviews_by_resolution: dict[str, int]


class ComplianceReport(BaseModel):
    """A read-time view with no backing row -- the identical relationship
    MetricsResponse (M7) has to a live query, applied to a closed,
    historical window instead of an open-ended one. Deliberately not
    persisted anywhere in this platform (see §5.4/§12.4)."""
    model_config = ConfigDict(frozen=True)

    window_start: datetime
    window_end: datetime
    system_id: str | None  # None means "platform-wide, all systems"
    verdicts: VerdictCounts
    findings: FindingCounts
    population_findings: PopulationFindingCounts
    reviews: ReviewOutcomeCounts
    generated_at: datetime
```

**No free text anywhere in this model** — no `rationale`, no
`resolution_notes`, no `reviewer`. This is a deliberate scoping choice,
not an oversight: the report is a *counts-and-outcomes* summary, the same
level of abstraction `GovernanceHealthMetrics` (M7) already established
for its own aggregate view. This has two concrete, checked benefits
beyond consistency with M7's own precedent: it means encryption (M11)
is a complete non-issue for this milestone (§9 verifies this directly,
not by assumption), and it substantially narrows the CSV export format's
(§5.5) exposure to CSV-injection.

**Corrected by this document's own second hostile-review pass:** the
model's fields are not uniformly "fixed enum-value keys or integer
counts." `VerdictCounts.by_status`, and the outcome/resolution values
inside `FindingCounts`/`PopulationFindingCounts`/`ReviewOutcomeCounts`,
are genuine fixed enums (`VerdictStatus`, `FindingOutcome`, review
`resolution`). But `FindingCounts.by_policy`/`PopulationFindingCounts.by_policy`'s
own outer keys — `policy_id`/`population_policy_id` — and the CLI's own
`--system-id` value are free-form strings set at
plugin-registration/system-creation time (`schemas/finding.py`,
`schemas/policy_binding.py`, `schemas/population_finding.py` each declare
these as open `str` fields, not a closed enum), not values from a fixed
set. They are, however, **not** attacker-reachable via the unauthenticated
ingestion surface the way `resolution_notes` is — M9's own review named
`resolution_notes` specifically as reachable that way; `policy_id`/
`population_policy_id`/`system_id` are set only by whoever registers a
plugin or provisions a system, an operator-trust boundary this platform
has never treated as adversarial. The residual CSV-injection exposure from
an operator-configured identifier is real but low, and is named here
rather than mitigated with new escaping logic or infrastructure this
milestone has no concrete forcing case to build (see §9).

**Bounded-window query functions**, self-contained inside
`reporting/compliance_report.py`, structurally parallel to but
independent of `observability/metrics.py`'s own (§4.1/§12.3):

```python
_VERDICT_COUNTS_SQL = text(
    """
    SELECT status, COUNT(*) AS count
    FROM verdicts
    WHERE created_at >= :window_start AND created_at < :window_end
      AND (:system_id IS NULL OR decision_event_id IN (
          SELECT id FROM decision_events de
          JOIN model_versions mv ON mv.id = de.model_version_id
          WHERE mv.system_id = :system_id
      ))
    GROUP BY status
    """
)
# _FINDING_COUNTS_SQL, _POPULATION_FINDING_COUNTS_SQL: the identical
# closed-window shape, one bound added to each of M7's own query patterns.

_REVIEW_OUTCOME_SQL = text(
    """
    SELECT vr.resolution, COUNT(*) AS count
    FROM verdict_reviews vr
    JOIN verdicts v ON v.id = vr.verdict_id
    WHERE vr.status = 'RESOLVED'
      AND vr.resolved_at >= :window_start AND vr.resolved_at < :window_end
      AND (:system_id IS NULL OR v.decision_event_id IN (
          SELECT id FROM decision_events de
          JOIN model_versions mv ON mv.id = de.model_version_id
          WHERE mv.system_id = :system_id
      ))
    GROUP BY vr.resolution
    """
)
# _POPULATION_FINDING_REVIEW_OUTCOME_SQL: same shape, one join shallower --
# population_finding_reviews.population_finding_id -> population_findings.id,
# which already carries system_id directly (M6), no decision_events/
# model_versions join needed for this one.
```

**A real join-path detail worth naming here rather than left to be
discovered at implementation time** — the identical discipline M7 §4.2
already applied to its own shadow-disagreement query: `verdict_reviews`
has no `system_id` of its own (nor does `verdicts`, directly —
`system_id` is a foreign-key column on `model_versions`, reached only via
`decision_events.model_version_id -> model_versions.system_id`; no query
here needs to actually join the `systems` table itself, since nothing is
read *from* it). Every one of this milestone's five queries must
therefore respect `--system-id` identically, or a report scoped to one
system would silently include another system's review outcomes while
correctly excluding its verdicts/findings — an internal inconsistency
within a single report, not merely an omission. `_REVIEW_OUTCOME_SQL`'s
own join chain (`verdict_reviews -> verdicts -> decision_events ->
model_versions`) is one hop deeper than `_VERDICT_COUNTS_SQL`'s own
(`verdicts -> decision_events -> model_versions`) for exactly this reason
— named explicitly so the extra join isn't mistaken for redundancy at
implementation time.

The `system_id` filter for verdicts/findings/verdict-reviews joins through
`decision_events`/`model_versions` (the same join path
`population_engine/window.py` already established for its own
system-scoped reads); `population_findings` (and, through it,
`population_finding_reviews`) already carries `system_id` directly (M6),
needing no join at all.

`get_compliance_report(engine, *, window_start, window_end, system_id=None) -> ComplianceReport`
runs all five queries inside one `REPEATABLE READ` transaction — the
identical concurrency reasoning `population_engine/window.py` already
established (M6 §13.13) for a multi-statement read over tables that can
change between statements: nothing here is as sensitive as a
computed-and-signed finding, but a report whose own five counts were read
under five different, silently-inconsistent snapshots (a verdict included
in one count but its matching review resolution missed by a
narrower/later snapshot) would be a real, avoidable correctness gap for a
document whose entire purpose is being trusted at face value by an
audience with no way to cross-check it against the live system.

### 5.2 Reuse of shape, not reuse of code, from `observability/metrics.py`

`VerdictCounts.by_status`, `FindingCounts.by_policy`, and
`PopulationFindingCounts.by_policy` intentionally mirror
`GovernanceHealthMetrics.verdict_counts_by_status`/`finding_counts_by_policy`/
`population_finding_counts_by_policy`'s exact field names and nesting —
an operator who already understands M7's live endpoint's response
recognizes the report's shape immediately. What is **not** shared:
`observability/metrics.py` is not imported by `reporting/`, and no
function in it is modified, extended, or given a new optional parameter.
This is a deliberate, small amount of query duplication (five SQL
statements, each a close cousin of one already in `observability/metrics.py`)
traded for zero risk of an M12 change altering M7's own already-frozen,
already-approved behavior — the same "three similar lines beat a
premature shared abstraction" reasoning this project applied when M8's
`_shared.py` extraction waited for a second real caller *within the same
milestone*, not a shared module reused *across* milestone boundaries with
different windowing semantics.

### 5.3 The CLI: `reporting/generate_report.py`

Mirrors `population_engine/run_policies.py`'s and
`retention/purge_expired_records.py`'s existing shape exactly: no daemon,
no in-process scheduler. Real scheduling remains deployment-topology
scope, architecture §17/M13, unchanged.

```
python -m gov_platform.reporting.generate_report \
    --database-url "$GOV_PLATFORM_DATABASE_URL" \
    [--window-start <ISO 8601> --window-end <ISO 8601>] \
    [--system-id <id>] \
    [--format json|csv] \
    [--output <path>]
```

- **Default window: last full calendar month (UTC)** — the direct scaling
  of `run_policies.py`'s own `default_window()` ("yesterday's full UTC
  day") to a monthly cadence, matching the one concrete cadence this
  platform's entire citation trail actually names ("a *monthly* compliance
  PDF," M10 §3.4). `--window-start`/`--window-end` override this, taken
  together or not at all — the identical argument-pairing validation
  `run_policies.py`'s own `main()` already enforces for its window
  arguments.
- **`--system-id` is optional**; omitted means platform-wide (every
  system), mirroring `GET /v1/admin/population-findings?system_id=`'s
  own optional-filter precedent (M6).
- **`--format` defaults to `json`** (the complete, structured format);
  `csv` is opt-in (§5.5).
- **`--output`**, if given, is a file path (for `json`) or a path prefix
  (for `csv`, per §5.5); omitted means write to stdout (`json` only —
  `csv`'s multi-file shape has no meaningful stdout equivalent, and
  `main()` rejects `--format csv` with no `--output` with a clear error
  rather than attempting to interleave multiple files on one stream).
- **No call to `bootstrap_plugins()`** — unlike `run_policies.py`, this
  tool touches no `Adapter`/`Policy`/`PopulationPolicy` at all; it reads
  five already-persisted tables directly. Including a plugin-bootstrap
  call this tool has no use for would be a copy-paste artifact, not a
  real dependency.
- **No `Settings` fields read at all** — `--database-url` is the same
  explicit-argument convention every CLI in this codebase already uses;
  unlike retention (which reads `RETENTION_DAYS_*` from `Settings`), report
  generation needs no environment-configured value beyond the connection
  string itself. This milestone adds **zero new `Settings` fields**.
- **Corrected by this document's own second hostile-review pass: the
  connection built from `--database-url` must use
  `db.session.create_db_engine`, not a bare `create_engine`.** Every CLI
  in this codebase that takes a `--database-url` argument falls into one
  of exactly two groups, not one uniform convention: `db/migrate.py`
  calls `create_engine` directly, deliberately, for its own documented
  reason (no bounded `connect_timeout` — see that module's own docstring);
  every other one (`retention/purge_expired_records.py`,
  `population_engine/run_policies.py`, `audit/verify_chain.py`,
  `plugins/seed_registry.py`, `human_review/backfill_reviews.py`) calls
  `create_db_engine`, which carries the `with_psycopg_driver`
  normalization M11 added after a real CI failure
  (`ModuleNotFoundError: No module named 'psycopg2'`, from a bare
  `postgresql://` URL reaching `create_engine` unnormalized — see §2).
  `reporting/generate_report.py` belongs to the second group:
  `create_db_engine`, not `create_engine`. Stated explicitly here so an
  implementer has no ambiguity to resolve by guessing which of the two
  existing patterns to follow.

### 5.4 No persistence, no new Admin API surface, no new database credential

The CLI's output *is* the artifact — a file (or stdout), not a database
row. No `reports` table records that a report was generated, when, or by
whom; no `GET /v1/admin/reports` endpoint lists or serves one. This is the
direct architectural sibling of retention's own CLI-only shape (M11 §5.2)
and population-policy evaluation's own (M6 §13.4): an explicitly-invoked
tool whose output is consumed by whoever ran it, not a new queryable
platform resource. See §12.4 for the real alternative (a persisted
`reports` table + minimal read API) this document considered and declined,
for lack of a concrete forcing case — the identical "no infrastructure
without a real, current need" reasoning every prior milestone's own
declined-alternative section has applied.

**No elevated database credential.** Every query in §5.1 is a `SELECT`;
`gov_platform_app` already holds `SELECT` on all five tables this
milestone reads (including the three evidentiary, `DELETE`-locked ones —
`verdicts`, `findings`, `population_findings`, per §4.3 — which have
always permitted `SELECT`, only `UPDATE`/`DELETE` are revoked;
`verdict_reviews`/`population_finding_reviews` are not `DELETE`-locked at
all, retaining their full `GRANT SELECT, INSERT, UPDATE, DELETE`, per
migrations `0023`/`0024`). `--database-url` is expected to be the same
`GOV_PLATFORM_DATABASE_URL` the running application already uses, never
a migration-owner or retention-tool-style elevated connection — corrected
from this document's own first draft, which assumed by analogy to M11's
retention tool that an elevated credential would be needed here too
(§12.8). (This document's own second hostile-review pass separately
corrected a miscount here — three `DELETE`-locked tables, not four — see
the Revision note's item 5.)

### 5.5 Export formats: JSON (primary) and CSV (flattened), no PDF

**JSON**: `canonical_json(report.model_dump(mode="json"))` — reusing
`audit/hash_chain.canonical_json` (sorted keys, deterministic) so
regenerating the identical report for the identical window twice
produces byte-identical output, not merely equivalent-but-differently-
ordered JSON.

**CSV**: one file per logical section, sharing a common `--output`
path-prefix, using the stdlib `csv` module, no new dependency. **Five
files, not four** — corrected by this document's own second
hostile-review pass, which found that the first draft's four-file plan
(`-verdicts`, `-findings`, `-population-findings`, `-reviews`) didn't
actually match its own model: `ReviewOutcomeCounts` (§5.1) holds two
independently-keyed dicts, `verdict_reviews_by_resolution` and
`population_finding_reviews_by_resolution`, with no shared key space —
cramming both into one `-reviews.csv` file would need either an
undocumented discriminator column or the ad hoc
multi-section-in-one-file convention this section already rejects for a
single-file CSV in general. The corrected, final file list — each one
mapping to exactly one flat dict in the model, with no exceptions:

- `<prefix>-verdicts.csv` — `VerdictCounts.by_status`
  (`status, count`).
- `<prefix>-findings.csv` — `FindingCounts.by_policy`
  (`policy_id, outcome, count`).
- `<prefix>-population-findings.csv` — `PopulationFindingCounts.by_policy`
  (`population_policy_id, outcome, count`).
- `<prefix>-verdict-reviews.csv` — `ReviewOutcomeCounts.verdict_reviews_by_resolution`
  (`resolution, count`).
- `<prefix>-population-finding-reviews.csv` — `ReviewOutcomeCounts.population_finding_reviews_by_resolution`
  (`resolution, count`).

A single flat CSV cannot naturally represent five differently-shaped
tables without an awkward, ad hoc multi-section-in-one-file convention
this project has no existing precedent for; five small, clearly-named
files, each a genuinely flat table with no internal sections of its own,
is the more honest fit for CSV's own actual shape, and the one that
actually matches the model as specified rather than an earlier,
uncorrected count of it — see §12.10 for the alternative considered and
declined.

**No PDF.** See §12.1, this document's highest-stakes call.

## 6. Database schema changes

**No new table.** One new migration, adding exactly the index this
milestone's own new query pattern needs and nothing else:

```sql
-- 0027_add_review_resolution_indexes.sql
-- Supports "which reviews were resolved within a given window" (M12,
-- architecture §14) -- neither review table has an index shaped for this
-- today (migrations 0023/0024 index status alone, for the Admin API's
-- own status-filtered list endpoint). status leads the composite here,
-- unlike M7's own created_at-leading indexes (0017-0019): M7's queries
-- have no separate equality filter (status there is a GROUP BY output,
-- not a WHERE clause), while this query's WHERE clause always starts
-- with the highly selective `status = 'RESOLVED'` before ranging over
-- resolved_at -- the textbook-correct column order for an
-- equality-then-range composite index, named explicitly here so the
-- deliberate difference from M7's own convention doesn't read as an
-- inconsistency.
CREATE INDEX idx_verdict_reviews_status_resolved_at
    ON verdict_reviews (status, resolved_at);
CREATE INDEX idx_population_finding_reviews_status_resolved_at
    ON population_finding_reviews (status, resolved_at);
```

No `ALTER` of any existing column, no new column, no data rewrite —
matching the smallest-footprint migrations this platform has shipped
(M4's "none," M7's three pure indexes, M11's two pure privilege/index
migrations). `verdicts`, `findings`, and `population_findings` already
have index support for a bounded time-range scan
(`idx_verdicts_created_at_status`, `idx_findings_evaluated_at_policy_id_outcome`,
`idx_population_findings_policy_system_evaluated_at`, all M7) — a
`BTree` range scan with both a lower *and* upper bound uses the identical
leading-column index a lower-bound-only scan already does, so no new
index is needed for those three tables at all; verified directly against
each index's own column order, not assumed.

**Added by this document's own second hostile-review pass, for the same
"verified directly, not assumed" discipline applied above:** the
`--system-id` scoping subquery (`decision_events JOIN model_versions
WHERE system_id = :system_id`, reused by three of the five queries in
§5.1) was not checked the same way in the first draft.
`decision_events (model_version_id, occurred_at)` (migration `0016`)
already supports the `decision_events` half of that join.
`model_versions` itself has no index on `system_id` — but `model_versions`
is bounded by the number of `(system, version)` pairs this platform has
ever registered, small at any realistic scale, so a sequential scan there
is a non-issue rather than an overlooked requirement. **No new index is
recommended for `model_versions.system_id`**; this is a documentation
completion, not a schema change.

## 7. Public API changes

**None.** No new endpoint of any kind. Every existing Admin API response
shape, `/healthz`, `/readyz`, and both ingestion routes are byte-for-byte
unchanged — this milestone's only surface is a new CLI and a new
top-level package with no HTTP presence at all, mirroring
`population_engine/run_policies.py`'s and `human_review/backfill_reviews.py`'s
own "explicitly-invoked CLI, no HTTP trigger" precedent (§5.4, §12.4).

## 8. Migration strategy

One purely additive migration (§6), applied via the same numbered,
idempotent-runner sequence every migration since M1 has used
(`db/migrate.py`). `CREATE INDEX` on two ordinarily low-write-volume
operational tables (`verdict_reviews`, `population_finding_reviews`) —
the identical low-risk profile M11's own migration `0026` already
established for its own two low-write-volume tables, needing no
maintenance window (unlike M11's `0025`, which touched this platform's
actual highest-throughput tables). Verified directly against
`db/migrate.py`'s own single-transaction-per-migration constraint (M8
§4.4 already established this cannot use `CREATE INDEX CONCURRENTLY`) —
a plain `CREATE INDEX` briefly locks writes (not reads) to two tables
with real-world write volume bounded by human review-queue activity, not
per-decision ingestion traffic; a non-event in practice, the same
judgment call M8's own migration `0022` already made for a comparably
low-volume table.

No backfill, no data migration of any kind — this milestone reads
existing rows exactly as they already are; nothing about a historical
`verdict`/`finding`/`population_finding`/review row needs to change for
a report to correctly summarize it.

## 9. Production-readiness implications

- **Report generation is opt-in and produces nothing until an operator
  explicitly invokes the CLI** — a fresh deployment generates zero
  reports on its own, mirroring `retention/purge_expired_records.py`'s
  identical "nothing happens until explicitly configured/invoked" shape.
- **No delivery mechanism** — the CLI produces a file; getting it to "an
  audience that may never touch the live system at all" (M10's own
  citation) is a real, disclosed deployment-operational gap this
  milestone does not close, the same class of gap M6/M11 both accepted
  for real scheduling.
- **No tracking of whether report generation is actually happening on
  schedule** — the identical blind spot M7 §13.12 built a real fix for
  (population-binding staleness) and M11's own retention tool simply
  accepted without a fix. This document follows M11's precedent, not
  M7's: adding a staleness signal here would mean either a new persisted
  marker (real, unrequested scope) or reopening M7's own
  `SystemHealthMetrics` shape (declined, per §4.1) — named as a real,
  disclosed, not-solved gap, consistent with the identical judgment call
  M11 already made for its own recurring CLI job.
- **Encryption (M11) is a verified non-issue for this milestone, not an
  untested assumption.** The report's own content (§5.1) never reads
  `resolution_notes` (the one M11-encrypted column on either review
  table) — confirmed directly against `_REVIEW_OUTCOME_SQL`'s own column
  list, which reads only `status`/`resolution`/`resolved_at`, none of
  which M11 ever encrypts (`resolution_notes` is the sole encrypted
  column on either review table; `reviewer`/`resolution`/`status` are all
  explicitly excluded from M11's encrypted-field list — see
  `docs/milestones/M11.md` §4.1/§5.1). Report generation therefore needs
  no `FIELD_ENCRYPTION_KEY` at all, regardless of whether the deployment
  it runs against has encryption enabled.
- **Retention (M11) is a verified non-issue for this milestone, not an
  untested assumption** — see §4.3's direct verification that every table
  the report reads from is either never retention-eligible or never
  actually deleted from in practice. If a future milestone ever extends
  the report to include `shadow_findings`-derived content, that
  milestone must re-examine this interaction explicitly — it will not be
  free anymore.
- **CSV-injection risk is substantially narrowed by content scope, not
  eliminated by escaping logic this milestone had to build — corrected by
  this document's own second hostile-review pass, which found the first
  draft's "every field is either a fixed enum-value key or an integer
  count" claim overstated.** A cell beginning with `=`/`+`/`-`/`@` can be
  interpreted as a formula by spreadsheet software opening a CSV — a real
  risk for any export containing attacker-influenceable free text. This
  report contains no free text (`rationale`/`resolution_notes`/`reviewer`
  are all excluded, §5.1), and no field it does contain is reachable via
  the unauthenticated ingestion surface (unlike `resolution_notes`, the
  field M9's own review named as reachable that way). But `policy_id`/
  `population_policy_id` (dict keys) and `--system-id` are
  operator-configured `str` identifiers (`schemas/finding.py`,
  `schemas/policy_binding.py`, `schemas/population_finding.py`), not
  values from a fixed enum the way `VerdictStatus`/`FindingOutcome`/review
  `resolution` genuinely are — a residual, low-probability, low-severity
  exposure this document names rather than silently claims away. Not
  mitigated with new escaping logic here, for lack of a concrete forcing
  case at this trust level; named explicitly so a future milestone that
  ever adds genuine free text to this report (e.g., per-review notes)
  knows to apply the standard mitigation (prefix-escaping a leading
  formula-trigger character) at that time, rather than assuming today's
  narrower exposure persists automatically or was ever fully zero.
- **No pagination for a very large window.** All five queries are
  `GROUP BY` aggregates, not row-by-row fetches, so memory use scales
  with the number of distinct `(policy_id, outcome)`/`(status)`
  combinations, not the number of underlying rows — bounded and small at
  this platform's real scale regardless of window size. Still, `EvidenceStore.all()`'s
  own "no pagination anywhere yet" gap (named since M0, never built) is a
  standing, disclosed platform characteristic this milestone does not
  change or newly introduce.
- **No authentication anywhere** — unaffected by this milestone, still
  `M13`, now a tenth-consecutive-milestone gap. The CLI's own implicit
  trust boundary (whoever has filesystem/credential access to invoke it)
  is the identical boundary `db/migrate.py`/`population_engine/run_policies.py`/
  `retention/purge_expired_records.py` already operate under, not a new
  or different one.

## 12. Architectural ambiguities, each with a recommendation and justification

### 12.1 — Does "document-shaped" mean a literal PDF, or is CSV/JSON sufficient? **(the highest-stakes call in this document)**

Options: **(a)** Build a real PDF renderer — the literal reading of M10
§3.4's own "e.g. a monthly compliance PDF" example. Every viable Python
PDF library (`reportlab`, `weasyprint`, `fpdf2`) is a genuinely new
dependency this platform has never needed before, and several
(`weasyprint`, in particular) pull in a non-trivial native-library
dependency chain (Cairo/Pango) well beyond anything `pyproject.toml`
currently lists. **(b)** (recommended) JSON and CSV only, using the
stdlib `json`/`csv` modules already relied on elsewhere in this codebase
— no new dependency at all. **(c)** HTML, reusing M10's own static-shell/
vanilla-JS precedent, rendered to a standalone file rather than served
live — closer to (b) in dependency cost (zero new dependencies) but a
worse fit for "a document a compliance team **files**," per M7 §13.14's
own phrasing, than a structured JSON/CSV export a downstream tool (a
spreadsheet, a compliance system's own importer) can actually ingest.

**Recommendation: (b).** M10's own citation names a PDF as an *example* of
"periodic, document-shaped, non-interactive" — not as a requirement in
its own right, and no other citation anywhere in this platform's record
ever repeats "PDF" specifically. This platform's own, seven-milestone-
consistent discipline (M0's stdlib logging, M6's no-analytical-store,
M7's no-Prometheus, M8's stdlib `NormalDist`, M10's no-SPA-framework, M11's
reuse of an existing dependency) treats "introduce this platform's first
genuinely new rendering/formatting dependency" as exactly the kind of
call that needs a concrete, current forcing case, not an illustrative
example in someone else's design doc three milestones prior. **This
requires your explicit sign-off** — if a real `ARCH-GOV-002` document (or
your own judgment as platform owner) specifies that a literal PDF is a
hard requirement for this platform's actual compliance audience, this is
the one finding in this document most likely to require a materially
different design (a new dependency, real template/layout work), not a
parameter tweak.

### 12.2 — Does the report include shadow-disagreement/system-health-shaped signals, or only governance-outcome content? **(reversed by this document's own hostile-review pass)**

Already argued in full in §4.3 and the revision note. **Recommendation:
governance-outcome content only** — verdict/finding/population-finding
counts and review-resolution outcomes, excluding shadow-disagreement and
population-binding-staleness entirely. This is not merely "less to build
this milestone" — it is the specific scoping choice that makes every
report this milestone generates immune to M11's retention purge, with no
undisclosed-drift caveat needed at all, unlike the identical class of
interaction M11's own hostile-review pass could only *disclose*, not
avoid, for M7's `?since` parameter. If a future milestone wants
shadow-disagreement content in a report, that milestone inherits the
obligation to design around (or explicitly accept) the interaction this
document sidesteps by scope.

### 12.3 — Bounded historical windows: new, self-contained M12 code, or an extension to M7's `observability/metrics.py`? **(reversed by this document's own hostile-review pass)**

Already argued in full in §4.1/§5.2. **Recommendation: new,
self-contained query functions inside `reporting/compliance_report.py`,**
never importing from or modifying `observability/metrics.py`. The
alternative (adding an optional `until: datetime | None = None` parameter
to `get_governance_health_metrics`, defaulting to `now()` to preserve
M7's exact current behavior) is a real, mechanically small change — but
it reopens a module this project's own standing discipline (M8 §13.14,
M9 §9.1, M11 §4.3) has repeatedly declined to reopen for a different
milestone's need, and the resulting shared function would need to serve
two callers with genuinely different windowing semantics (M7's own
endpoint always wants "through now"; M12 never does) forever after. A
small amount of duplicated SQL, fully owned by this milestone, is the
more conservative trade.

### 12.4 — Persisted `reports` table + minimal read API, or CLI-only file output?

Options: **(a)** A new `reports` table (id, window bounds, `system_id`,
`generated_at`, format, and either a file path or the report's own
content) plus a minimal `GET /v1/admin/reports[/{id}]`, mirroring M6
§13.12's own "avoid shipping infrastructure with zero callers" reasoning
for `population_findings`. **(b)** (recommended) CLI-only: the tool
writes a file (or stdout); nothing about which reports were generated is
tracked inside this platform at all.

**Recommendation: (b).** M6 §13.12's own reasoning for adding a
population-findings read API doesn't transfer here: that decision was
driven by "nothing in this codebase ever reads a `PopulationFinding`
except a human deciding what to do with one" — i.e., the *only* path to
the data was this platform's own future API, so declining to build one
risked the entire milestone being unreachable. A report's own output
*is* the file the CLI produces, handed directly to whoever ran it (or
written to wherever their own tooling expects it) — the "caller" already
has the artifact the moment generation finishes, with no platform-side
retrieval step needed at all. Building a `reports` table here would be
new, unrequested persistence and a new Admin API surface for a capability
this milestone's own citation trail never asks for — the identical
"no infrastructure without a real, current forcing case" reasoning this
project has applied everywhere else. Revisit only if an operator's own
file-based tracking demonstrably proves insufficient in practice.

### 12.5 — One fixed report type, or a report-type plugin surface?

**Recommendation: one fixed type** (the "compliance summary" in §5.1),
the same "no abstraction without a second real case" discipline M2's
resolver, M4's aggregation rule, M6's one concrete population policy, M7's
fixed metric set, and M8's declined metrics-registration framework have
each already applied to their own milestone's one new capability. A
second, genuinely different report shape (e.g., a raw per-decision
audit-trail export, closer in spirit to a data dump than a summary) is a
plausible, real future need — with no second case today to design the
right report-type port against. Building a `ReportType` plugin surface
now, for exactly one implementation, would repeat the identical
"speculative generality" mistake this project has declined at every
milestone since M0.

### 12.6 — Per-system scoping: required, optional, or platform-wide only?

**Recommendation: optional `--system-id` filter, defaulting to
platform-wide** (all systems combined) when omitted — mirroring
`GET /v1/admin/population-findings?system_id=`'s own optional-filter
shape (M6). A real compliance audience plausibly wants both views (one
system's own compliance officer wants that system's numbers only; a
platform-wide operator wants everything) — an optional filter serves
both without inventing two separate CLI entry points or a report-scope
enum with only two members.

### 12.7 — Does the generated report get cryptographically signed? **(amended by this document's own hostile-review pass)**

Already argued in full in the revision note. **Recommendation: no, not
this milestone.** A report is a derived rendering of already-signed
source data (`verdicts`/`findings` embedded and hash-chained since M1/M5;
`population_findings` signed since M6), not itself new evidentiary
output — unlike `population_findings` at M6, there is no concrete
forcing case here (no cited requirement that a report recipient verify
the report file's own authenticity cryptographically, as opposed to
trusting the delivery channel the way any other exported business
document already is). Revisit if a future milestone's real audience
specifically requires report-level, not just underlying-data-level,
tamper evidence.

### 12.8 — Does report generation need its own elevated database credential, like retention's? **(amended by this document's own hostile-review pass)**

Already argued in full in the revision note and §5.4. **Recommendation:
no.** Every query this milestone issues is a `SELECT`; `gov_platform_app`
already holds `SELECT` on all five tables involved, including the three
`DELETE`-locked evidentiary ones (`verdicts`, `findings`,
`population_findings` — which have always permitted `SELECT`; the
remaining two, `verdict_reviews`/`population_finding_reviews`, are not
`DELETE`-locked at all, per §4.3). Unlike retention (M11), which
genuinely needs `DELETE` privilege the ordinary role does not have,
report generation needs nothing beyond what the application's own
existing runtime connection already grants. (Corrected from an earlier
miscount of "four" `DELETE`-locked tables here — see the Revision note's
item 5.)

### 12.9 — What triggers report generation: an in-process scheduler/daemon, or an explicitly-invoked CLI?

**Recommendation: CLI**, mirroring `population_engine/run_policies.py`'s
and `retention/purge_expired_records.py`'s existing shape exactly. This
platform has zero always-running background processes anywhere — M6
§13.4 and M11 §5.2 have each already declined to introduce the first one
for their own batch/recurring needs; this milestone applies the identical
reasoning to a third recurring job. Real scheduling (cron, a Kubernetes
`CronJob`) remains deployment-topology scope, architecture §17/M13,
unchanged.

### 12.10 — CSV output shape: multiple files sharing a prefix, or one file with an ad hoc multi-section convention? **(resolved by this document's own second hostile-review pass — five files, not four)**

Options: **(a)** (recommended) Multiple, clearly-named CSV files sharing
a common `--output` path prefix, each a genuinely flat table. **(b)** One
CSV file, with section headers (e.g., a blank row and a new header line)
separating the report's differently-shaped tables within it.

**Recommendation: (a), five files exactly, per §5.5's corrected list** —
`<prefix>-verdicts.csv`, `<prefix>-findings.csv`,
`<prefix>-population-findings.csv`, `<prefix>-verdict-reviews.csv`,
`<prefix>-population-finding-reviews.csv`. The first draft of this
section recommended (a) but under-specified it as "four" files, treating
`ReviewOutcomeCounts`'s two independently-keyed dicts
(`verdict_reviews_by_resolution`/`population_finding_reviews_by_resolution`)
as one file's worth of content — an ambiguity this document's own second
hostile-review pass found unresolved (would `-reviews.csv` need a
discriminator column, or become two files after all?) and has now
settled: two files, one per dict, keeping every file a genuinely flat
table with zero internal sections, the same property every other file in
the list already has. CSV's own format has no native concept of "multiple
tables in one file" — any single-file convention is an ad hoc one this
project would be inventing from scratch, with no existing precedent
anywhere in this codebase to draw on. Five small, clearly-named files,
each parseable by a spreadsheet application or a `csv.reader` with zero
special-casing, is the more honest fit for what CSV actually is, at the
minor cost of `--output` meaning "a path" for JSON but "a path prefix"
for CSV — named explicitly here so that isn't a surprise at
implementation time.

### 12.11 — Does report generation verify the evidence chain's own integrity as part of producing a report?

**Recommendation: no.** `audit/verify_chain.py` already exists as the one
dedicated tool for this job, verifying the *entire* chain from genesis
(`EvidenceStore.all()`, unbounded, no windowing concept at all). Folding
a whole-chain verification into a recurring, windowed reporting job would
impose an ever-growing cost with no relationship to the report's own
window size — the identical "the readiness check must stay cheap" (M7
§12) and "don't reach for a full-table operation inside a job that has a
narrower real need" (M7 §13.16's `COUNT(*)` warning) disciplines already
established elsewhere in this platform, applied here to a different
operation with the same shape of risk. An operator wanting both a report
and a chain-integrity check runs both tools, independently, exactly as
they already can today.

### 12.12 — Does the report's own read pattern finally trigger the long-deferred raw-vs-normalized `DecisionEvent` pipeline-stage question?

**Recommendation: no — still declined, named explicitly rather than
silently dropped, the identical treatment M6 §13.11 already gave this
same standing question.** This milestone's own queries never touch
`decision_events` directly for anything beyond an `id`/`system_id` join
key (§5.1's `system_id` filter) — no raw payload, no per-event content,
nothing resembling a new pipeline stage. The trigger condition M0's
original deferral named ("a second entry point," already met by M2, and
declined again by M2 itself) remains unmet by anything this document
proposes.

### 12.13 — Does M12 need a new Admin API endpoint to trigger report generation on demand?

**Recommendation: no**, mirroring `population_engine/run_policies.py`'s/
`retention/purge_expired_records.py`'s own precedent exactly (§5.4/§7):
both are explicitly-invoked CLI tools with no HTTP trigger, and this
project has never added an Admin endpoint whose only purpose is to kick
off an existing CLI's own logic a second way.

### 12.14 — Does this milestone add authentication to anything?

**Recommendation: no**, restating every prior milestone's identical
reasoning (M5 §13.11 through M11 §9): consistent with every existing
endpoint (still none authenticated), and this milestone adds no new
*endpoint* at all to be inconsistent about — the CLI's own trust boundary
(filesystem/credential access) is the same one three other CLIs in this
codebase already operate under.

### 12.15 — Does the report generator need pagination/streaming for a very large window?

**Recommendation: no, not now — named as a standing, inherited
limitation, not newly introduced.** Every query in §5.1 is a `GROUP BY`
aggregate; result-set size scales with the number of distinct
`(policy_id, outcome)`/`status` combinations, not the number of
underlying rows, so this milestone's own memory footprint stays small
regardless of window length at any volume this platform has real reason
to expect soon. The broader "no pagination anywhere in this platform"
gap (named since M0, never built) is unaffected either way.

### 12.16 — Do `verdict_reviews`/`population_finding_reviews` need new indexes for this milestone's own query pattern?

**Recommendation: yes** — a composite `(status, resolved_at)` index on
each table, per §6. Neither table has an index shaped for "resolved
within this window" today (migrations `0023`/`0024` index `status`
alone, for the Admin API's own status-filtered list endpoint). `status`
leads the composite, not `resolved_at`, because this query's `WHERE`
clause always includes the highly selective equality filter
`status = 'RESOLVED'` before ranging over `resolved_at` — the
textbook-correct column order for an equality-then-range composite index,
and a deliberately different order from M7's own `created_at`-leading
indexes (whose queries have no equality filter at all, `status` there
being a `GROUP BY` output column, not a `WHERE` clause) — named
explicitly so the difference reads as a reasoned choice, not an
inconsistency with M7's own established convention.
