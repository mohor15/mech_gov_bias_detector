## Production-Readiness Review

Performed after implementation, before freeze — mirroring M0's and M1's
finalization passes.

**Finding (fixed): an unrecognized protected attribute produced a raw
500, not a 422.** `ProtectedAttributeResolver.resolve` raises `ValueError`
for a protected attribute a known domain's ruleset doesn't recognize (a
deliberate hard failure — see §8/§10 below). That exception originates
deep inside `Policy.evaluate` → `GovernanceEngine.govern`, with nothing in
the ingestion route translating it — it fell through to `api/app.py`'s
generic `Exception` handler and returned `500`, for what is structurally
valid but semantically rejected *input*, not a server fault. This is the
same category M0's own finalization review already drew a line around
("malformed input is rejected with a schema validation error, not a
500"). Fixed with a dedicated `@app.exception_handler(ValueError)`
returning `422`, registered alongside the existing generic handler — not
a new error-handling framework, just recognizing the built-in `ValueError`
as the same "client-correctable input" category Pydantic's own validation
errors already are. Verified with
`test_credit_scorecard_unrecognized_protected_attribute_returns_422_not_500`.

**Finding (verified, no change needed): mid-transaction resolution
failure rolls back cleanly.** If `ProtectedAttributeResolver` raises
partway through `EvidenceStore.append`'s transaction, does it leave an
orphaned `DecisionEvent`/`Finding`/`Verdict` with no matching evidence
row? Verified it does not —
`test_append_rolls_back_entirely_when_resolution_rejects_the_event`
confirms `Session`'s context-manager rollback-on-exception behavior
applies here exactly as it already does for M1's duplicate-`event_id`
case.

**Finding (documented, not fixed): the policy's fixed domain and
`EvidenceStore`'s live `System.domain` lookup can diverge.**
`DirectAttributeInInputsPolicy` always evaluates against the `FINANCE`
ruleset (fixed at construction — it has no database access). `EvidenceStore`
resolves against whatever domain the ingesting `System` is *actually*
registered with, which is `None` for an auto-provisioned (never
pre-registered) system. Practical effect: an unregistered
`credit-scorecard` system still gets correctly governed (`CLEAR`/`FLAGGED`
is unaffected — the policy's domain doesn't come from the System row) but
persists **zero** `protected_attribute_resolutions` rows, since
`EvidenceStore` found no ruleset for that system's real (`None`) domain.
For the persisted resolutions to reflect what the policy actually
evaluated, the system must be pre-registered via
`POST /v1/admin/systems` with `domain="FINANCE"` first. This is a
consequence of M1's own "auto-provisioning, not enforcement" design
(unchanged, not newly introduced) — documented explicitly in
`docs/architecture-mapping.md`'s M2 notes and exercised by both
`test_append_persists_protected_attribute_resolutions_for_a_known_domain`
(pre-registered) and `test_append_persists_nothing_for_a_system_with_no_known_domain`
(auto-provisioned) so the boundary is proven, not just described.

**Finding (documented, not fixed): domain matching is case-sensitive and
exact.** `System.domain="finance"` (lowercase) matches nothing —
`rules_for_domain` does no normalization. Not fixed: normalizing domain
names would be speculative without a second real domain's naming
convention to learn the right rule from. Documented in
`classification.py`'s docstring.

**Reviewed, no issue found:**
- Double resolution per credit-scorecard ingestion (once inside the
  policy, once for persistence) is safe because `ProtectedAttributeResolver`
  is pure and its ruleset is static in-process data — no risk of the two
  calls disagreeing within one request.
- `protected_attribute_resolutions` inherits the Evidence Store's
  "synthetic data only" caveat (no encryption at rest until M11) — the
  README's existing caveat already covers "the Evidence Store," and this
  table is populated by the same `append` call, so no separate caveat
  needed, just confirmed it applies.
- `MaxBodySizeMiddleware` applies to the new route automatically (it's
  global app middleware, not per-route) — no gap.

## 1. Exact goals of M2

Three things, consistently named across every prior milestone doc's
deferred-items table (`M0.md` line 67, `M1.md` line 207,
`architecture-mapping.md` line 12, `README.md` line 189):

1. **Formalize the Protected Attribute Resolution Service** (architecture
   §4.3) — classify each protected attribute a `DecisionEvent` carries as
   **direct**, **proxied**, or **withheld**, replacing the current
   pass-through (`DecisionEvent.protected_attribute_refs` holds whatever
   raw value an adapter supplied, unexamined).
2. **Ship the first real, non-synthetic adapter** — a second `Adapter`
   implementation, a realistic classical-ML credit-scorecard wire format,
   proving the port generalizes beyond the one reference case
   (`SyntheticAdapter`) it was built and tested against so far.
3. **Ship the first genuinely judgment-bearing `Policy`** — a fairness
   hard gate that flags a decision when a `DIRECT`-classified protected
   attribute appears in the model's own `input_features`, replacing
   `AlwaysAllowPolicy`, which by design never produces `FLAGGED`.

Decided: the new adapter and the new policy are in the **same fairness
thread** — resolution has a real consumer this milestone, not
infrastructure-with-no-caller. See §11 for the reasoning that led here.

Everything else stays exactly where M0/M1 left it: `FindingOutcome` stays
binary, `VerdictStatus` stays two-state (M5), `GovernanceEngine` still
takes exactly one `Policy` (M4), no plugin registry/discovery (M3), no
auth (M5+/M13), no DB-backed policy configuration (M3/M5).

## 2. Why each feature exists architecturally

**Protected Attribute Resolution (§4.3).** The architecture separates
"observe a decision" (§4.1 Adapter) from "understand what it means for
fairness" (§4.3) as two distinct pipeline stages, not because they're
unrelated but because resolution requires context normalization alone
doesn't have: whether `zip_code` is a proxy for race is a policy-domain
fact, not a structural one, and conflating the two stages would force
`NormalizationService` — which today is a pure, context-free structural
pass (whitespace/timezone/precision) — to start knowing about fairness
law. Keeping them separate is what let M0/M1 ship `NormalizationService`
without this milestone's complexity at all.

**A second adapter.** `Adapter[TPayload]`'s generic port was "tightened
during the M0 finalization review" specifically so a second, differently
shaped payload type could be added without touching the port itself
(`adapters/base.py`'s docstring: "costs nothing extra for M3's future
adapters"). M2 is the first opportunity to prove that promise — one
adapter is a design, two is evidence the design works. It's also the
trigger condition M0 explicitly named for revisiting the raw/normalized
`DecisionEvent` type question (`M0.md` line 73) — resolved in §11.4
without needing new pipeline-stage types at all.

**A judgment-bearing, fairness-consuming policy.** `AlwaysAllowPolicy`
proves the `Policy` contract's plumbing but nothing about its *content*
— it can't produce `FLAGGED` because it never evaluates anything.
Wiring the new policy directly to `ProtectedAttributeResolver`'s output
(rather than a domain-unrelated numeric gate) means M2 ships two features
that justify each other: resolution has an immediate reason to exist
beyond "the architecture doc says so eventually," and the policy proves
the full governance chain (`GovernanceVerdict.status`, the Evidence
Store's `FLAGGED` path) with a real fairness signal, not a synthetic
placeholder — the same "walking skeleton → real behavior" progression
M0→M1 followed for persistence, now applied to governance logic itself.

## 4. Database schema changes

One new migration, `0009_create_protected_attribute_resolutions.sql`:

```sql
CREATE TABLE protected_attribute_resolutions (
    id TEXT PRIMARY KEY,
    decision_event_id TEXT NOT NULL REFERENCES decision_events(id),
    attribute_name TEXT NOT NULL,
    classification TEXT NOT NULL,   -- 'DIRECT' | 'PROXIED' | 'WITHHELD'
    proxy_basis TEXT,               -- which direct attribute this proxies, if PROXIED; NULL otherwise
    resolved_at TIMESTAMPTZ NOT NULL
);
```

One row per (decision event, attribute) pair, including `WITHHELD` rows
for attributes a domain expects but the event didn't supply (§11.7) — a
`DecisionEvent` that's missing an expected attribute still produces a row
recording that fact, which is the entire point of resolving `WITHHELD` as
an absence rather than silently having nothing to say about it.

No `UPDATE`/`DELETE` privilege lockdown (decided in §11.6): this table is
derived, reconstructable data — re-running the resolver over the same
`DecisionEvent` reproduces it — not part of the hash-chained ledger, so it
doesn't need `evidence_chain`'s tamper-evidence guarantee. Written once at
ingestion time, in the same transaction as everything else, but ordinary
application-level discipline (no code path calls `UPDATE`/`DELETE` on it)
is sufficient here, unlike `evidence_chain` where that would have been an
application-layer stopgap.

No changes to any existing table. `systems.domain` (already a free-text
column since M1) is what keys the static classification ruleset in
`protected_attributes/classification.py` — read, not written to, by this
milestone.

## 5. Public API changes

- **New route:** `POST /v1/ingestion/events/credit-scorecard`, alongside
  the existing, unchanged `POST /v1/ingestion/events` (decided in §11.1
  — a separate route per adapter, not a generalized dispatch mechanism;
  that generalization is M3's job once a real registry exists). Request
  body is `CreditScorecardPayload`; response body is the same
  `IngestionResponse` shape both routes already share.
- **No changes** to `IngestionResponse`'s shape. Protected-attribute
  resolutions are a side effect of ingestion (persisted, queryable later
  via the database directly or a future read endpoint), not something
  the synchronous response surfaces. A read endpoint
  (`GET /v1/admin/decision-events/{id}/protected-attributes` or similar)
  is a reasonable follow-up but is **not scoped to M2** — flagging so it
  isn't mistaken for an oversight later.
- No new Admin API surface: classification rules are static code (§11.5),
  not admin-configurable data, so there is nothing to expose via API this
  milestone.

## 6. New domain models

```python
class ProtectedAttributeClassification(StrEnum):
    DIRECT = "DIRECT"
    PROXIED = "PROXIED"
    WITHHELD = "WITHHELD"

class ResolvedProtectedAttribute(BaseModel):
    model_config = ConfigDict(frozen=True)

    decision_event_id: str
    attribute_name: str
    classification: ProtectedAttributeClassification
    proxy_basis: str | None = None   # e.g. "race" if this attribute proxies race
    resolved_at: datetime
```

`WITHHELD` means **absence** (decided in §11.7): the domain's
classification ruleset also names which attributes it *expects*
(e.g. `FINANCE` expects `race`, `gender`, `age` to be resolvable), and
`ProtectedAttributeResolver` emits a `WITHHELD` row for any expected
attribute a given `DecisionEvent` doesn't actually carry. This means
`protected_attributes/classification.py` holds two things per domain, not
one: the direct/proxy mapping, and the expected-attribute list it's
checked against.

## 7. Interfaces and abstractions

**Decided: `ProtectedAttributeResolver` is a concrete class, not a new
`ABC`/port**, matching `NormalizationService`'s shape rather than
`Adapter`/`Policy`'s. `architecture-mapping.md`'s §6 row enumerates
exactly two ports today; introducing a third here without a second
resolution strategy to justify polymorphism would repeat the exact
"speculative generality" mistake M0/M1 have consistently avoided
elsewhere. If a future milestone needs domain-specific resolver
*strategies* (plural), that's the moment to extract a port — not before.

**A consequence worth your explicit attention, surfaced only once the
fairness-focused policy was decided (§1):** the new policy needs
`ResolvedProtectedAttribute` data, not just the `DecisionEvent` that
`Policy.evaluate(event: DecisionEvent) -> Finding` currently receives.
Two ways to give it that:

- **(Recommended) The policy owns its own resolver as a constructor
  collaborator** — `DirectAttributeInInputsPolicy(resolver=
  ProtectedAttributeResolver(...))` calls the resolver itself inside
  `evaluate`, exactly the pattern `VerdictRepository` already uses for
  `FindingRepository` (`VerdictRepository.__init__(self,
  finding_repository: FindingRepository | None = None)`). The `Policy`
  ABC's signature (`evaluate(event) -> Finding`) is **untouched**;
  `AlwaysAllowPolicy` needs no changes; `GovernanceEngine.govern` needs no
  changes. This does mean resolution runs twice per ingestion — once
  inside the policy (to decide `FLAGGED`), once in the ingestion route
  (to persist to `protected_attribute_resolutions`) — pure/idempotent
  computation, so this is a minor duplication cost, not a correctness
  risk, and avoids widening a stable port for one caller's need before a
  second policy shows whether that generalizes.
- **(Rejected for now) Widen `Policy.evaluate`'s signature** to
  `evaluate(event: DecisionEvent, resolved_attributes:
  list[ResolvedProtectedAttribute]) -> Finding`. This is the more
  "architecturally honest" long-term shape if most future policies end up
  needing resolved-attribute data — but changing an existing port's
  signature ahead of a second real case needing it is exactly the kind of
  premature generalization this project has consistently declined
  elsewhere (`GovernanceEngine` takes one `Policy`, not a list, for the
  identical reason). Revisit this once a second policy's needs are known
  (plausibly M4, when policy plurality arrives anyway).

This wasn't one of the four questions already asked — please confirm the
recommended (constructor-collaborator) shape before implementation, since
it's the one piece of this design invented after your answers rather than
directly requested.

## 10. Expected production-readiness review points

Based on the pattern of what M0's and M1's finalization reviews actually
found (2 High + ~10 Medium at M0; 4 real issues only surfaced by M1's
actual Postgres execution), M2's review should specifically probe:

- **The "matches neither direct nor proxy rule" default.** Silently
  treating an unrecognized attribute as safe-to-ignore is exactly the
  kind of "no method exists for it" application-layer stopgap M1's
  evidence-immutability work explicitly rejected in favor of an enforced
  guarantee. This needs an explicit answer (fail loudly? default
  classification? logged-and-skipped?), not an implicit one.
- **Double resolution's cost and consistency.** §7's recommended design
  calls the resolver twice per ingestion (once inside the policy, once
  for persistence). Since the resolver is pure, this is safe today — but
  the review should confirm no future version of `classification.py`
  introduces non-determinism (e.g., a DB-backed rule that could change
  between the two calls within one request) that would break that
  assumption.
- **`Policy` gaining a constructor dependency is a new pattern for this
  ABC.** `AlwaysAllowPolicy` has no collaborators; the new policy does.
  Confirm the composition root (`api/app.py`) wires this the same
  explicit way it wires everything else, and that this doesn't quietly
  become a precedent for policies reaching into arbitrary infrastructure
  without the same scrutiny `EvidenceStore`'s dependencies get.
- **PII in `protected_attribute_resolutions`.** `attribute_name` and
  `proxy_basis` are fairness-sensitive metadata (a persistent record that
  a given decision's zip code was flagged as a race proxy). No
  encryption-at-rest exists yet (M11) — `README.md`'s "synthetic data
  only" caveat for the Evidence Store should be extended explicitly to
  cover this new table.
- **Regression safety on the ingestion path**, per §8/§9 — the exact
  category of issue (a test not updated to match a codebase-wide pattern)
  M1's own verification pass actually found.

## 11. Decisions made, and how each was reached

**11.1 — Ingestion dispatch: separate route per adapter.** `ingest_event`'s
request body was hardcoded to `SyntheticSourcePayload`, with no dispatch
mechanism at all — by design, since "there is exactly one adapter, so
there is nothing to route between yet" stopped being true the moment a
second adapter shipped. Decided: `POST /v1/ingestion/events/credit-scorecard`,
a second thin route, rather than a generalized dispatch mechanism (which
would risk being mistaken for M3's real registry) or shipping the adapter
without any live endpoint at all (which would mean "the first real
adapter" isn't reachable end-to-end this milestone).

**11.2/11.3 — Domain and fairness focus.** The new adapter targets a
realistic classical-ML credit-scorecard wire format; the new policy flags
when a `DIRECT`-classified protected attribute leaks into the model's own
`input_features`. This gives Protected Attribute Resolution an immediate
consumer this milestone (avoiding the "infrastructure with zero callers"
tension against this project's consistent build-only-what's-needed
philosophy) and matches the platform's actual purpose.

**11.4 — No new pipeline-stage types.** Resolution's output
(`list[ResolvedProtectedAttribute]`) is a separate object, keyed by
`decision_event_id`, threaded alongside `DecisionEvent` rather than a new
field on it. `DecisionEvent` itself never needs to know it's been
resolved, which sidesteps the raw/normalized/resolved type-proliferation
question entirely rather than resolving it in favor of new types.

**11.5 — Static code for classification rules.** A small module
(`protected_attributes/classification.py`) keyed by `System.domain`, not
a new DB table/Admin API. Matches `AlwaysAllowPolicy`'s and M0/M1's
general minimalism; DB-backed, admin-configurable rules remain a named
future item (M3 plugin config, or M5 Policy Bindings — whichever the real
architecture doc specifies), not built now.

**11.6 — No privilege lockdown on the new table.** Unlike `evidence_chain`,
`protected_attribute_resolutions` is derived, reconstructable data, not
part of the tamper-evident hash chain — ordinary write-once application
discipline is the right amount of enforcement here, not a copy of
migration `0008`'s `REVOKE UPDATE, DELETE`.

**11.7 — `WITHHELD` means absence.** The classification ruleset also
declares which attributes a domain expects; `ProtectedAttributeResolver`
emits `WITHHELD` for any expected attribute a `DecisionEvent` doesn't
actually carry. (Not: a platform-side redaction of an attribute it did
receive — that's a different feature, not built here.)
