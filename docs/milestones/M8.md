## Production-Readiness Review

Performed after implementation, before freeze — mirroring M0–M7's own
finalization passes.

**Finding (fixed): `disparity_significance_test.py`'s expected-cell-count
guard needed to live in eligibility filtering, not as a separate pairwise
check, to also correctly subsume the degenerate-variance guard.** The
original implementation sketch checked degenerate variance
(`pooled_p <= 0 or pooled_p >= 1`) as an independent guard inside
`_two_proportion_z`, computed *after* eligibility filtering. Tracing
through the math during implementation: once every eligible group is
required to individually clear `favorable_outcome_count >= 5` and
`total_count - favorable_outcome_count >= 5` (the expected-cell-count
check), each eligible group's own rate is already guaranteed strictly
between `0` and `1` — which in turn guarantees any *pooled* proportion of
two eligible groups is too. Fixed by folding the expected-cell-count
check into the same per-group eligibility filter `minimum_group_size`
already uses, making the degenerate-variance guard inside
`_two_proportion_z` genuinely unreachable through `evaluate()` (confirmed
by test — see Test Statistics) rather than a check that could plausibly
still fire in normal operation. Kept as explicit defense in depth, not
removed, and marked `# pragma: no cover` only for the one sub-branch
(`standard_error == 0`) that is mathematically unreachable once
`pooled_p` is known to be strictly between `0` and `1` — verified this
is the only such line, not a blanket exclusion.

**Finding (fixed): a genuinely new problem class this codebase had never
had to solve before — adding a field to an already-signed,
already-populated model — required empirical verification, not just
careful reasoning, that the fix actually works.** Implemented the
design's own prescribed fix (`parameters_used` nullable and un-backfilled,
`exclude_none=True` on the hash) and then verified it directly: built a
`PopulationFinding` with no `parameters_used` key constructed at all
(reproducing a genuine pre-M8 record, not one with the field explicitly
set to `None` by M8-era code with the same intent), signed it, and
confirmed `population_finding_hash`/`verify_signature` still validates it
after this milestone's code is in place — see
`tests/unit/audit/test_verify_population_findings.py::test_a_pre_m8_finding_with_no_parameters_used_field_still_verifies`,
the one test in this suite that would fail against the *original*
(pre-hostile-review) design and passes against the corrected one. Also
verified the DB-level round trip directly: a `NULL` `parameters_used`
column reads back as Python `None`, never `{}` — the exact distinction
the fix depends on.

**Finding (fixed): the Admin API's conflict check needed
`get_active_by_identity`, and the fix had to be proven through the HTTP
layer itself, not just the repository.** Implemented exactly as
specified (§4.4/§13.19) and verified with a test that goes through
`create_population_policy_binding` end to end
(`test_recreating_a_binding_after_deactivation_succeeds_through_the_api`)
— deliberately not a repository-only test, since a repository-only test
would have passed even against the *original*, broken draft (the bug
lived entirely in the endpoint's own conflict check, never in
`PopulationPolicyBindingRepository` itself). A companion test
(`test_recreating_a_still_active_binding_is_still_409`) confirms the
conflict check did not become permissive across the board — only across
`lifecycle_state`.

**Finding (fixed, post-freeze addendum): the Admin API accepted a
non-finite (`NaN`/`Infinity`) `parameters` override at binding-creation
time with no rejection.** Originally raised in this review as "confirmed
real, deliberately not fixed" — re-evaluated on request and corrected.
The re-evaluation: §4.7/§13.2's design choice was specifically about
*per-metric semantic* validation (`threshold` must be in `(0, 1]`,
`z_critical` must be `> 0`) staying out of the API layer, so the API
never needs to know which policy a binding is for. "Is this value a
finite number at all" is not a per-metric judgment — `NaN`/`Infinity` are
never valid for *any* population-policy parameter, for *any* policy — so
rejecting them at the API boundary requires no per-metric knowledge and
does not contradict, widen, or reopen the design's own stated boundary.
Fixed with an explicit check in `create_population_policy_binding`'s
body (`_reject_non_finite_parameters`), not a Pydantic `field_validator`
— the latter was tried first and found to have a real, empirically-
confirmed problem of its own: raising `ValueError` from a validator still
lets Pydantic/FastAPI's own request-validation machinery build a
structured error response that echoes the raw invalid value back, and
Starlette's `JSONResponse` (`allow_nan=False`) then raises trying to
serialize that echoed `NaN` while building the very error response meant
to reject it — surfacing a confusing, generic `"Out of range float
values are not JSON compliant"` message instead of a clear one. An
explicit `HTTPException` with a plain string `detail` built by this
codebase's own code never echoes the raw float back, sidestepping the
problem entirely — and matches every other validation check already in
this file (unknown system, unknown `population_policy_id`, conflict),
none of which use a Pydantic validator either. Verified directly: `NaN`,
`Infinity`, and `-Infinity` all now return a `422` with a clear message
naming the offending parameter, nothing is persisted, and an ordinary
valid override still works unchanged.

**Confirmed, not fixed — the pre-existing `policy_bindings` (M5)
defect named in the design (§13.20).** Re-confirmed during
implementation by reading `api/admin/policy_bindings.py` and
`db/repositories/policy_binding.py` directly: the identical
lifecycle-blind `get_by_identity`-based conflict check, and the identical
plain, non-partial `UNIQUE (adapter_id, policy_id)` constraint (migration
`0011`). Left unfixed, as decided — this is M5's scope, not M8's.

**Reviewed, no issue found:**
- **The reference-group tie-breaking rule in `DisparitySignificanceTestPolicy`.**
  When two eligible groups for an attribute are tied at the same
  highest favorable-outcome rate, `max(eligible, key=...)` deterministically
  picks the first one in `attribute_value`-sorted order — unlike

  order-dependent in a way that could vary run to run — reproducibility
  is preserved, even though "which tied group is reference" is an
  arbitrary, if consistent, choice.

- **The full pre-M8 test suite** (`AdverseImpactRatioPolicy`,

**Named, not fixed — deliberate scope boundaries, not gaps found late:**

## Design Review (as approved before implementation)

This document has been through a hostile-review pass (assume-it's-
wrong-until-proven-otherwise, the same discipline applied to M5/M6/M7).
Two findings from that pass were severe enough to change the proposed
architecture rather than just annotate it — both are folded in below,
in place, rather than kept as a separate errata section: **(1)** the
original §4.5 design (a `NOT NULL DEFAULT '{}'` backfilled
`parameters_used` column, hashed via the existing unmodified
`population_finding_hash`) would have silently invalidated the signature
of every `PopulationFinding` signed before M8 the first time
`verify_population_findings` ran afterward — corrected to a nullable,
un-backfilled column plus a small, explicit change to the hash function
(§4.5). **(2)** the original §4.4 fix (relaxing the database constraint)
does not, by itself, make a binding's parameters actually changeable —
`api/admin/population_policy_bindings.py`'s own conflict check ignores
`lifecycle_state` and would still reject recreating a deactivated
binding even after the schema migration ships — corrected by adding a
lifecycle-scoped lookup the API uses instead (§4.4). This section records
the design exactly as approved before implementation began; see "What
Was Built" and "Production-Readiness Review" above for what happened
during implementation itself.

## TL;DR

M8 builds `architecture-mapping.md` §10's "Evaluation Framework" — the
one deferred item every milestone since M4 has pointed at by name and
never touched. The citation trail is unusually unambiguous: the
architecture-mapping table itself ties §10 directly to
`population_engine/policies/adverse_impact_ratio.py` and calls it
"partially real as of M6 — one hardcoded population-level metric, not a
general, pluggable statistical-evaluation framework," naming exactly two
things as missing: **multiple statistical tests** and **admin-defined
thresholds**. M7 §13.14 drew the same line from the other side: "M8 is
about *computing new statistical judgments* — M7 exposes counts *of*
judgments already computed by M0–M6."

So M8 is a generalization milestone, not a new pipeline — the same shape
M4 was to M0–M3 (second concrete `Policy`, proving `GovernanceEngine`
aggregates heterogeneous judgments) and M5 was to M4 (moving a judgment
call, severity, out of code and onto an admin-configurable binding).
Concretely, M8 does two things to `population_engine` (M6, unchanged
port):

1. Ships a **second concrete `PopulationPolicy`** — a statistical-
   significance test, genuinely different in kind from adverse impact
   ratio's practical-significance ratio threshold (the same "different
   kind of judgment, not a fairness-check variant" discipline M4 §13.10
   used for `HighDebtRatioGatePolicy`) — proving the port already
   generalizes across more than one metric, exactly as M4 proved for
   `Policy`.
2. Makes **thresholds admin-configurable per binding**, mirroring M5's
   own "severity is a judgment about context, not a property of the
   policy's code" reasoning (M5 §13.5) applied to a population policy's
   threshold instead of a per-event policy's severity.

Neither requires a new plugin port, a new persisted-output table, or a
rewrite of `population_engine/window.py`'s Event Lake read pattern — all
three stay exactly as M6 built them. What M8 does require, found by
tracing what "admin-configurable" actually touches: `PopulationWindow`
gains one new field (`parameters`), `PopulationFinding` gains one new
field (`parameters_used`, the same `classification_snapshot`-style
reproducibility fix M6's own hostile-review pass already established a
precedent for), `population_policy_bindings` gains one new column
(`parameters`) — and, the one non-purely-additive change this milestone
needs, its existing plain `UNIQUE (system_id, population_policy_id)`
constraint has to become a partial unique index scoped to `ACTIVE` rows,
mirroring `plugin_registrations`' own precedent, because the plain
constraint (found during this design's own review, not previously
documented anywhere) makes a binding's identity permanent — an admin who
wants to change a system's threshold has no way to do so today, not even
by deactivating and recreating.

No new external dependency: the second policy's math is a closed-form
two-proportion comparison computable entirely with the stdlib
`statistics.NormalDist` (available since Python 3.8) — no scipy, no
numpy. No aggregation mechanism across population policies (each stays
an independent, parallel finding, exactly as M6 already built it — M8
just proves that holds with two policies instead of one). No new Admin
API endpoint — one additive field on the existing
`POST /v1/admin/population-policy-bindings` body. No dashboard, no human
review workflow, no per-event `Policy` configurability, no auto-scheduled
recompute — all remain exactly where M6/M7/M9/M10 already put them.

Two corrections from this document's own hostile-review pass, both
real, both found by tracing what the original proposal actually implied
rather than accepting it at face value: `parameters_used` must be
nullable and excluded from the hash when absent, not backfilled with a
fabricated default, or every pre-M8 `PopulationFinding`'s signature
silently stops verifying the moment M8 ships (§4.5/§13.18); and the
constraint relaxation alone does not make a binding's parameters
changeable — the Admin API's own conflict check has to stop treating a
deactivated binding as still occupying its key, a fix at the application
layer, not only the schema (§4.4/§13.19). A related, pre-existing defect
was found in the process: `policy_bindings` (M5) has the identical
lifecycle-blind conflict check and the identical plain (non-partial)
uniqueness constraint, meaning `PolicyBinding.severity` has likely never
actually been changeable via deactivate-and-recreate in this platform's
history either — named here as a real, verified finding, deliberately
left unfixed by M8 (M5's scope, not this milestone's), and flagged for a
dedicated follow-up (§13.20).

## 1. What M8 is exactly responsible for

- A second concrete `PopulationPolicy` implementation — a statistical-
  significance test for disparity between two groups' favorable-outcome
  rates, grounded in the same real, citable standard adverse impact
  ratio uses (§4.2 below).
- Admin-configurable parameters (thresholds, minimum sample sizes) for
  population policies, set per `population_policy_binding` at creation
  time, with a documented fallback to each policy's own built-in default
  when none is given.
- The one schema fix required to make "configurable, and actually
  changeable" true: relaxing `population_policy_bindings`' uniqueness so
  a system's binding to a given population policy can be deactivated and
  re-created with different parameters.
- Point-in-time reproducibility for the new configurability, the same
  guarantee M6 already built for `protected_attribute_rules`: every
  `PopulationFinding` records the exact effective parameter values it was
  computed against, immune to a later change to the binding.
- Everything needed to prove all of the above generalizes: `run_policies.py`
  running two independent population policies against the same system in
  one invocation, without any change to its per-binding failure isolation
  or idempotency guarantees.

## 2. How M8 builds on M6/M7

M6 built the port (`PopulationPolicy`), the read path (`build_population_window`,
the Event Lake), the persisted output (`population_findings`), the binding
(`population_policy_bindings`), and one concrete policy
(`AdverseImpactRatioPolicy`) — explicitly declining, three separate times
in its own document (§4.4, §13.9, §15), to build "a general population-
metrics framework," naming that as M8's job. M7 built a read-only window
onto what M0–M6 already compute — explicitly declining to compute any new
governance judgment itself, naming that too as M8's job (§13.14).

M8 does not touch M7's endpoints, `evidence_chain`, `GovernanceEngine`,
`Policy`, `Adapter`, or the ingestion path at all. It touches exactly the
three M6 modules M6's own document flagged as intentionally incomplete
(`population_engine/base.py`, `population_engine/policies/`,
`population_policy_bindings`), the same targeted-generalization shape M5
had relative to M4 (M5 touched `PolicyBinding`/`plugin_registrations`,
not `GovernanceEngine` or `Policy` itself).

## 3. Why each piece exists architecturally

- **A second concrete `PopulationPolicy`, not a rewritten port**: the
  existing port (`evaluate(self, window: PopulationWindow) ->
  PopulationFinding`) already says nothing about *how many* concrete
  metrics can implement it — the only reason M6 shipped one was "no
  second case yet to justify more," the same discipline M0–M3 applied to
  `Policy` before M4. A second implementation is exactly what proves or
  disproves the port's generality; if it fit cleanly, the port was
  already right, and no port change is needed. It does fit cleanly (§4.2).
- **Configurable parameters via `PopulationWindow`, not a widened
  `evaluate()` signature or a policy constructor convention**: `PopulationWindow`
  is already the one object M6 designed specifically to carry everything
  `evaluate()` needs beyond the port's own two arguments —
  `classification_snapshot` already proved this pattern for one kind of
  "context beyond raw counts." Widening it a second time for parameters
  is the same pattern applied to a second kind of context, not a new one
  (§4.3).
- **`parameters_used` on `PopulationFinding`**: the exact reproducibility
  problem M6's hostile-review pass found for `protected_attribute_rules`
  (live, admin-mutable, unversioned data feeding into a computed,
  append-only finding) applies identically to a binding's `parameters`
  once they can be admin-set — a finding must never depend on a mutable
  table still agreeing with it later (§4.5).
- **Relaxing the binding uniqueness constraint**: found during this
  design's own review, not previously documented — `population_policy_bindings`'
  plain `UNIQUE (system_id, population_policy_id)` (migration `0014`) has
  no `WHERE lifecycle_state = 'ACTIVE'` scoping, unlike `plugin_registrations`'
  own partial index for exactly this reason (`one_production_version_per_plugin`).
  Today, once a binding for a given `(system_id, population_policy_id)`
  pair exists, it can be deactivated but never truly replaced — an admin
  who wants to change a system's threshold is permanently stuck. This was
  harmless at M6 (bindings carried no configurable data at all), and
  becomes a real operational trap the moment M8 adds one (§13.3).

## 4. Proposed architecture (this review's recommendation)

### 4.1 Generalize the existing `PopulationPolicy` port with a second concrete implementation — no new port, no port signature change

`PopulationPolicy.evaluate(self, window: PopulationWindow) -> PopulationFinding`
stays exactly as M6 defined it. The second concrete policy (§4.2)
implements it with zero deviation from the existing contract — same
input type, same output type, same registration mechanism
(`@register_population_policy`, `plugins/registry.py`, unchanged since M6),
same lifecycle (`plugin_registrations`, `PluginType.POPULATION_POLICY`,
unchanged since M6), same sandboxing (`run_sandboxed`, unchanged since M6).
This is the M4-shaped move: prove plurality by shipping a second concrete
implementation of an already-general-enough port, not by re-designing the
port.

### 4.2 A second concrete population policy: a statistical-significance test, not a second ratio-threshold variant

`AdverseImpactRatioPolicy` answers "is the practical size of the
disparity concerning" (a ratio against a fixed, EEOC-cited threshold).
The genuinely different question — the one that makes this a real second
case, not a disguised copy — is "is the observed disparity plausibly just
sampling noise, or is it statistically significant." Real EEOC/OFCCP
disparate-impact analysis pairs exactly these two tests in practice: the
four-fifths rule for *practical* significance, and a standard-deviations/
statistical-significance test for whether the gap could plausibly be
chance. *Castaneda v. Partida*, 430 U.S. 482 (1977), is the commonly
cited legal precedent for treating a disparity of two or more standard
deviations from the expected value as evidence warranting scrutiny — the
same kind of real, citable, external grounding `_RATIO_THRESHOLD` and
`HighDebtRatioGatePolicy`'s `0.43` already have.

Concretely: `DisparitySignificanceTestPolicy`
(`population_policy_id = "disparity-significance-test"`, `version =
"0.1.0"`) computes, for each `DIRECT`-classified attribute with at least
two eligible values, a two-proportion z-test between each value's
favorable-outcome rate and the reference (highest-rate) value's rate —
the same reference-group shape `AdverseImpactRatioPolicy` already uses,
for consistency, not because the math requires it. `FLAGGED` if any
comparison's `|z|` meets or exceeds a configurable `z_critical`
(default `2.0`, the Castaneda convention), `CLEAR` otherwise, `CLEAR` with
an "insufficient data" rationale if fewer than two values in an attribute
meet the (also configurable, §4.3) minimum-group-size floor — the exact
same three-way outcome shape `AdverseImpactRatioPolicy` already
established, deliberately not reinvented.

The z-statistic is closed-form (pooled-proportion two-proportion z-test);
converting it to significance only needs the standard normal CDF, which
`statistics.NormalDist().cdf(...)` (stdlib, Python ≥3.8) already provides.
No new dependency. `metric_values` records each comparison's `z`
statistic (not a p-value — `z_critical` is the parameter an admin
actually sets, matching how the legal convention itself is phrased in
standard deviations, not p-values), keyed the same way
`AdverseImpactRatioPolicy` keys its ratios
(`f"{attribute_name}:{attribute_value}"`).

### 4.3 Admin-configurable parameters, threaded through `PopulationWindow`, resolved at evaluate() time — not a widened port signature, not a policy-constructor convention

`PopulationWindow` gains one new field:

```python
class PopulationWindow(BaseModel):
    ...
    parameters: dict[str, float] = Field(default_factory=dict)
```

`population_engine/window.py`'s `build_population_window` is unchanged —
it stays exactly what M6 built it to be, a generic "read this system's
Event Lake for this window" function with no knowledge of which policy
will consume its output, or of any binding at all. `run_policies.py`
attaches the binding's own parameters immediately before calling
`evaluate()`:

```python
window = build_population_window(engine, system_id=..., window_start=..., window_end=...)
window = window.model_copy(update={"parameters": binding.parameters})
finding = run_sandboxed(lambda: population_policy.evaluate(window))
```

Each concrete policy resolves its own parameters with a documented
fallback to its own hardcoded default, e.g.:

```python
threshold = window.parameters.get("threshold", _RATIO_THRESHOLD)
minimum_group_size = int(window.parameters.get("minimum_group_size", _MINIMUM_GROUP_SIZE))
```

and records the *effective* values actually used — not merely whatever
was or wasn't in `window.parameters` — into the new `PopulationFinding.parameters_used`
field (§4.5), so a finding is reproducible even if you don't know what
that policy's built-in defaults were at the time.

This was considered against two alternatives and rejected: widening
`evaluate()`'s signature to `evaluate(self, window, *, parameters: dict[str, float])`
would touch the port itself for data that is already conceptually part of
"everything this evaluation needs to know about its window," which is
exactly what `PopulationWindow` exists to carry (`classification_snapshot`
already set this precedent for a different kind of context). A
constructor-injection convention (`population_policy_cls(threshold=...)`,
mirroring `DirectAttributeInInputsPolicy`'s resolver collaborator) was
rejected because it requires every concrete policy to agree on a uniform
constructor contract for parameters whose names and shapes are
inherently metric-specific (`threshold`/`minimum_group_size` for one
policy, `z_critical`/`minimum_group_size` for another) — a generic,
per-binding JSON blob threaded through the object `evaluate()` already
receives is the more honest fit, with no uniform-contract fiction to
maintain across future third and fourth policies.

### 4.4 Relaxing `population_policy_bindings`' uniqueness to a partial index scoped to `ACTIVE` — and fixing the Admin API's own conflict check to match

```sql
ALTER TABLE population_policy_bindings
    DROP CONSTRAINT population_policy_bindings_system_id_population_policy_id_key;

CREATE UNIQUE INDEX one_active_population_policy_binding_per_system
    ON population_policy_bindings (system_id, population_policy_id)
    WHERE lifecycle_state = 'ACTIVE';
```

This *shape* is the same one `plugin_registrations`' own
`one_production_version_per_plugin` partial index uses (M3) — at most
one currently-meaningful row per key, with historical, superseded rows
free to coexist deactivated — but it is not the identical *situation*:
`plugin_registrations`' partial index was part of its original migration
(`0010`); it never had a plain constraint to retrofit away from, and no
row has ever existed under a stricter rule than the one it ships with.
`population_policy_bindings` (migration `0014`) already has a plain,
unscoped `UNIQUE (system_id, population_policy_id)`, already enforced
against real rows since M6/M7 — this is genuinely dropping and replacing
a live constraint, not extending an original design, and the two are
worth distinguishing rather than waving at "the identical shape" as if
that made the change equally low-risk. It remains safe for existing
data specifically because the new partial index is strictly *less*
restrictive than the old plain one — any row set that satisfied the old
constraint (at most one row per key, full stop) trivially satisfies the
new one (at most one *`ACTIVE`* row per key) — but that equivalence is
worth stating explicitly rather than assumed.

**Migration-runner constraint, verified, not assumed:** `db/migrate.py`'s
`apply_migrations` wraps every migration file in one
`with engine.begin() as connection:` transaction. `CREATE UNIQUE INDEX
CONCURRENTLY` is illegal inside a transaction block — Postgres raises an
error and the migration fails outright — so this migration cannot use
`CONCURRENTLY` under this project's existing runner without also
changing the runner itself (out of scope; no other migration needs it).
A plain `CREATE UNIQUE INDEX` briefly holds a lock that blocks writes
(not reads) to `population_policy_bindings` for the build's duration.
**Recommendation: accept the plain, blocking form**, justified narrowly:
this table is bounded admin configuration (one row per real
`(system, population policy)` pair — tens or hundreds of rows even at
real scale, not `decision_events`' volume), with no request-path or
per-decision write throughput, so a brief write-lock is a non-event in
practice — but this
is a deliberate, stated judgment call for *this table specifically*, not
a general license to skip `CONCURRENTLY` on future migrations against
tables with real write volume. Operationally: apply this migration
during a low-admin-activity window as a documented precaution, the same
courtesy any constraint change deserves regardless of how small the
practical risk is.

**The schema change alone does not fix the problem it exists to fix.**
Traced empirically (`api/admin/population_policy_bindings.py`,
`db/repositories/population_policy_binding.py`, read in full during this
hostile-review pass): `create_population_policy_binding`'s own
conflict-check —

```python
existing = population_policy_binding_repository.get_by_identity(
    session, system_id=payload.system_id, population_policy_id=payload.population_policy_id
)
if existing is not None:
    raise HTTPException(status_code=409, ...)
```

— calls `get_by_identity`, which matches on `(system_id,
population_policy_id)` alone, **with no `lifecycle_state` filter at
all**. This means that even after migration `0022` relaxes the database
constraint, the API endpoint itself still returns `409 Conflict` for a
second binding whose predecessor is merely deactivated — the exact
scenario this whole fix exists to enable. The schema change is necessary
but not sufficient; without the code change below, `parameters` would
remain just as permanently write-once as it is today, only now for a
subtler, less visible reason (an API-layer check nobody thought to
revisit, rather than an honest 409 that immediately points at the real
constraint).

**Fix: add `get_active_by_identity`** (a new method on
`PopulationPolicyBindingRepository`, filtering additionally on
`lifecycle_state == ACTIVE`) **and switch the endpoint's conflict check
to use it**, rather than changing `get_by_identity`'s own existing
semantics — `get_by_identity` (lifecycle-blind) is depended on elsewhere
with that exact meaning (`plugins/seed_registry.py`'s idempotent-seed
check, and the equivalent method on `PolicyBindingRepository`,
`PluginRegistrationRepository`, and `ProtectedAttributeRuleRepository`,
none of which this milestone touches) and changing it would be a silent,
unrelated behavior change to every one of those call sites. Both this
code change and the migration must ship together — the migration
without the code change is a no-op fix; the code change without the
migration turns a clean `409` into an unhandled `IntegrityError` the
moment an admin tries the recreate flow (the insert would still hit the
still-plain database constraint). See §13.19.

### 4.5 `parameters_used` on `PopulationFinding` — the same reproducibility fix M6 already established a precedent for, corrected to not break every historical signature

**This section's original version was wrong, and would have shipped a
severe regression.** It claimed `population_finding_hash` needed no
change because it already hashes the whole model — true — and concluded
that adding `parameters_used` was therefore "confirmed... no change
needed" — false, and backwards: exactly *because* the hash covers the
whole model, adding any new field to it changes the hash for every
record, including every record signed before the field existed. Traced
through concretely:

`population_finding_hash(finding)` computes
`sha256(canonical_json(finding.model_dump(mode="json")))`.
`canonical_json` is `json.dumps(payload, sort_keys=True)` — deterministic
over whatever keys are present. Every `PopulationFinding` signed before
M8 was hashed over a dict with no `parameters_used` key at all. The
instant `PopulationFinding` gains that field (as a normal, always-present
field, the way the original draft specified it), `as_population_finding()`
(`db/repositories/population_finding.py`) will construct one for *every*
row — including rows created years before M8 — and `model_dump()` will
now include the key for all of them. `canonical_json`'s output changes,
the recomputed hash changes, and `verify_signature(new_hash, old_signature,
public_key)` fails for every single pre-M8 record. **The original
draft's own migration (`ADD COLUMN ... NOT NULL DEFAULT '{}'`) guarantees
this happens for every existing row, unconditionally, the first time
`verify_population_findings` (`audit/verify_population_findings.py`, an
already-shipped, real operational verification tool) runs after M8 is
deployed.** For a platform whose entire value proposition rests on
"these records are provably untampered," silently breaking that proof
for every pre-existing record as a side effect of an unrelated feature is
about as severe a regression as this codebase can produce — worse than
building the feature wrong, because it corrupts trust in work that was
already correct. See §13.18.

**Corrected design:**

```python
class PopulationFinding(BaseModel):
    ...
    parameters_used: dict[str, float] | None = None  # None means "not tracked" (pre-M8 record)
```

```python
def population_finding_hash(finding: PopulationFinding) -> str:
    return hashlib.sha256(
        canonical_json(finding.model_dump(mode="json", exclude_none=True)).encode()
    ).hexdigest()
```

`exclude_none=True` is the one, deliberate code change to
`audit/verify_population_findings.py` this milestone actually needs
(reversing this document's original claim that none was required). For
every other existing field on `PopulationFinding`, nothing changes —
none of them are `Optional`/`None`-valued today, so `exclude_none=True`
has no effect on any hash this codebase has ever computed for a
pre-M8 record. For a pre-M8 record, `parameters_used` is `None`
(migration `0021` adds the column **nullable, with no `DEFAULT` and no
backfill** — see §6), `exclude_none=True` drops the key entirely, and
`model_dump()` reproduces *exactly* the same dict shape, and therefore
exactly the same hash, that was originally signed — old signatures keep
verifying, unchanged. For a finding computed from M8 onward,
`parameters_used` is always a real (possibly empty, but non-`None`) dict
— each concrete policy is required to populate it with its effective
resolved values, never leave it `None` — so the field is present,
hashed, and signed for every new record, giving it the same tamper-
evidence guarantee `classification_snapshot` already has. This is not a
weaker guarantee than the original design's for new data — it is the
same guarantee, made honestly compatible with data that predates the
field's existence, the first time this codebase has had to solve that
problem at all (M2–M7's own schema changes to signed models — e.g.
`classification_snapshot` itself — always landed before any record had
been signed under the older shape, so this exact conflict never
previously arose).

### 4.6 Statistical validity guards `DisparitySignificanceTestPolicy` needs beyond a flat sample-size floor

Two production failure modes found by scrutinizing the z-test math
itself, not just its plumbing:

**Degenerate variance.** A two-proportion z-test's standard error is
`sqrt(p * (1 - p) * (1/n1 + 1/n2))` for pooled proportion `p`. If every
eligible group's favorable-outcome rate is identical (most acutely, if
`p` is exactly `0` or `1` — nobody, or everybody, in any group got a
favorable outcome), the standard error is `0` and the z-statistic is an
undefined `0/0` or a division by zero. `AdverseImpactRatioPolicy` already
has the equivalent guard (`if reference_rate == 0: ... insufficient
data`) — `DisparitySignificanceTestPolicy` needs the identical guard
before dividing, reporting `CLEAR`/"insufficient data" rather than
raising, exactly mirroring the existing policy's own established shape.

**Expected-cell-count validity, not just raw sample size.** A flat
`minimum_group_size` floor (reused verbatim from
`AdverseImpactRatioPolicy`, per §4.3) is not sufficient for a
two-proportion z-test specifically: the normal approximation the test
relies on additionally requires each group's *expected* favorable and
unfavorable counts to be large enough (the standard rule of thumb: `n *
p >= 5` and `n * (1 - p) >= 5` for each group being compared) — a
requirement about the *rate*, not just the *count*. A group with 40
decisions at a 3% approval rate passes a `minimum_group_size = 30` floor
but has an expected favorable count of `1.2`, far below the threshold the
normal approximation needs to be trustworthy — the test would still
compute a number, and that number would still look like a legitimate
z-statistic, while being statistically invalid. **Recommendation:**
`DisparitySignificanceTestPolicy` applies its own additional
expected-cell-count check (`n * p >= 5` and `n * (1 - p) >= 5` for both
groups in a comparison) alongside, not instead of, the shared
`minimum_group_size` floor; a comparison that fails this check is
excluded the same way an under-sized group already is, contributing to
the same "insufficient data" rationale path, not to a false-confidence
`FLAGGED`/`CLEAR` verdict. This is specific to this policy (the ratio
policy has no equivalent concept) and therefore lives in
`disparity_significance_test.py`, not `_shared.py` (§4.7/§13.8 unchanged).

### 4.7 Bounding admin-submitted parameter values

`parameters: dict[str, float]` accepts arbitrary admin input with no
validation in the original draft — a fat-fingered (there being no
authentication on this endpoint at all, `§13.15`, possibly not even an
authenticated admin) `threshold = -5` or `z_critical = -1e300` would
silently make every window `FLAGGED`, or a `threshold` above `1.0` or a
`z_critical` of `0` would silently make every window `CLEAR` — a
platform whose purpose is detecting bias would be trivially defeated (or
trivially spammed with false positives) by one bad or malicious API
call, with no error, no rejection, and no signal that anything was
misconfigured until someone manually audits the parameter values.
**Recommendation:** each concrete policy validates its own resolved
parameters against a documented, sane range before evaluating —
`threshold ∈ (0, 1]` for `AdverseImpactRatioPolicy`, `z_critical > 0` for
`DisparitySignificanceTestPolicy`, `minimum_group_size >= 1` for both
(further floored per §13.16) — and falls back to the built-in default,
recording that fallback in `rationale`, rather than silently proceeding
with a nonsensical value or raising an opaque exception mid-evaluation.
Validating in each policy (not centrally, and not at binding-creation
time in the API) keeps the API layer ignorant of per-metric parameter
semantics, consistent with §13.2's rejection of a uniform parameter
contract — the same reasoning, applied to validation instead of shape.

**Post-freeze addendum**: this section's own boundary ("not at
binding-creation time in the API") was about *per-metric semantic* range
validation specifically, not about rejecting values that are never valid
for *any* policy's *any* parameter. `NaN`/`Infinity` fall in the latter
category — the API now rejects them directly (`_reject_non_finite_parameters`,
`api/admin/population_policy_bindings.py`), which does not reopen or
contradict this section's recommendation. See the Production-Readiness
Review's addendum, above, for the full reasoning and a real framework
interaction found while implementing the fix.

## 6. Database schema changes (proposed)

Three migrations, each single-purpose (the same one-migration-one-change
convention M6/M7 used):

- **`0020_add_population_policy_binding_parameters.sql`** — `ALTER TABLE
  population_policy_bindings ADD COLUMN parameters TEXT;` (nullable —
  `NULL`/absent means "use this policy's built-in defaults," matching
  every existing binding created before M8; JSON-encoded, matching every
  other JSON-shaped column in this schema's own convention).
- **`0021_add_population_finding_parameters_used.sql`** — `ALTER TABLE
  population_findings ADD COLUMN parameters_used TEXT;` — **nullable, no
  `DEFAULT`, no backfill.** This document's original draft specified
  `NOT NULL DEFAULT '{}'`; that was wrong and would have silently
  invalidated every pre-M8 finding's signature (§4.5/§13.18). `NULL` for
  every existing row means, honestly, "not tracked — this finding
  predates parameter tracking," not a fabricated claim that no parameters
  were used. Every finding computed from M8 onward always has a real
  (non-`NULL`) value, enforced in application code (§4.7), not by a
  database-level `NOT NULL`, because the column must legitimately hold
  `NULL` for the append-only, never-rewritten historical rows that
  predate this milestone.
- **`0022_relax_population_policy_binding_uniqueness.sql`** — drops the
  plain `UNIQUE (system_id, population_policy_id)` constraint and
  replaces it with the partial unique index from §4.4. The one
  non-purely-additive schema change this milestone makes (§13.3/§13.12).
  **Must ship together with the `get_active_by_identity` application-code
  change (§4.4)** — neither is a complete fix alone. Uses a plain (not
  `CONCURRENTLY`) `CREATE UNIQUE INDEX`, since `db/migrate.py` runs every
  migration inside one transaction and `CONCURRENTLY` cannot run inside
  one — verified against the runner's actual code, not assumed (§4.4).

No changes to `decision_events`, `verdicts`, `findings`, `evidence_chain`,
`plugin_registrations`, or any M7 index.

## 10. Testing strategy (proposed)

- **Unit — `DisparitySignificanceTestPolicy` math**: verify the
  two-proportion z-statistic against hand-computed reference values (not
  just "runs without error") for known inputs; verify `FLAGGED`/`CLEAR`
  boundary behavior exactly at `z_critical`; verify the "insufficient
  data" path when fewer than two eligible values exist, mirroring
  `AdverseImpactRatioPolicy`'s own existing test shape for the identical
  case; verify the degenerate-variance guard (all-0%/all-100% rates
  don't raise `ZeroDivisionError`) and the expected-cell-count guard
  (a large-`n`, extreme-rate group is excluded even though it clears
  `minimum_group_size`) — both found during this hostile-review pass
  (§4.6), neither present in the original draft's testing strategy.
- **Unit — parameter resolution and validation**: both policies, with no
  `parameters` (empty dict) → identical behavior/output to their pre-M8
  hardcoded constants (a regression test, not just a new-feature test);
  with an explicit, in-range override → the override is what's actually
  used, and appears verbatim in `parameters_used`; with an
  out-of-range/nonsensical override (e.g. `threshold = -1`,
  `z_critical = 0`) → falls back to the built-in default with the
  fallback recorded in `rationale`, does not silently proceed or raise
  (§4.7).
- **Unit — `_shared.py`**: the grouping helper in isolation.
- **Repository**: `PopulationPolicyBindingRepository.create()` persists
  and reads back `parameters` (including the `None`/absent case);
  `PopulationFindingRepository.create()` persists and reads back
  `parameters_used`, specifically confirming a `NULL` column value round-
  trips as Python `None`, not `{}` (§4.5 — the exact distinction the
  hash-compatibility fix depends on); **`get_active_by_identity`** only
  returns a binding whose `lifecycle_state` is `ACTIVE`, returns `None`
  for a deactivated one even though `get_by_identity` still finds it
  (§4.4) — a direct test of the two methods' now-different behavior.
- **Integration — constraint relaxation, end to end through the API, not
  just the repository**: `POST` a binding, `POST .../deactivate`, `POST`
  a second binding for the same `(system_id, population_policy_id)` with
  different `parameters` — succeeds post-M8. Critically, this test must
  go through `create_population_policy_binding` (the HTTP layer), not
  call `PopulationPolicyBindingRepository.create()` directly — a
  repository-only test would have passed even in the original, broken
  draft, since the repository itself was never the layer blocking the
  recreate flow; the bug was entirely in the endpoint's own conflict
  check (§4.4).
- **Integration/unit — signature backward compatibility (the headline
  fix, §4.5/§13.18)**: sign a `PopulationFinding` built exactly as M6/M7
  code would have built it (**no `parameters_used` field constructed at
  all**, reproducing a genuinely pre-M8 record, not one with
  `parameters_used=None` freshly added by M8-era code with the same
  intent) and confirm `population_finding_hash`/`verify_signature` still
  validates it after M8's code ships. This is the one test in this
  document that must fail if run against the *original* (pre-hostile-
  review) design and pass against the corrected one — the direct
  regression proof for the most severe finding in this pass. A
  same-shape test also confirms a **new**, M8-era finding with a non-
  `None` `parameters_used` signs and verifies correctly, so both branches
  of `exclude_none=True` are exercised, not just the compatibility path.
- **Integration — `run_policies.py`**: two active bindings for the same
  system, one per population policy, evaluated in one CLI invocation;
  each produces its own independent, correctly-parameterized finding; a
  failure in one policy's evaluation still doesn't abort the other
  (regression test for M6's existing per-binding isolation guarantee,
  now exercised with genuinely different policy code on each side, not
  two copies of the same one).
- **API**: `POST /v1/admin/population-policy-bindings` with and without
  `parameters` in the request body; response shape includes the new
  field; no existing test for this endpoint's pre-M8 request/response
  shape should need to change (backward compatibility); a recreate
  attempt against a still-`ACTIVE` binding still correctly `409`s (the
  conflict check must not become permissive across the board, only
  across `lifecycle_state`).

Coverage gate unchanged: 100% target, 98% minimum, exactly as M2–M7.

## 11. Acceptance criteria (proposed)

1. `DisparitySignificanceTestPolicy` is registered, seeded to
   `PRODUCTION`, and computes a correct two-proportion z-statistic per
   `DIRECT`-classified attribute value pair, verified against
   hand-computed reference values, not merely "produces a number."
2. Every existing `AdverseImpactRatioPolicy` test continues to pass
   unmodified against a binding with no `parameters` set — byte-identical
   behavior to pre-M8, proving the parameters mechanism is genuinely
   additive.
3. An admin can create a `population_policy_binding` with explicit
   `parameters`, and the resulting `PopulationFinding`'s `metric_values`
   reflect those parameters, not the policy's built-in defaults.
4. Every `PopulationFinding` computed from M8 onward, regardless of
   whether its binding specified overrides, carries a complete
   `parameters_used` reflecting the *effective* values used to compute
   it; every `PopulationFinding` computed before M8 correctly shows
   `parameters_used = None` ("not tracked"), never a fabricated value.
5. A binding can be deactivated and a new one created for the same
   `(system_id, population_policy_id)` pair with different `parameters`,
   **through the Admin API endpoint itself, not only at the repository
   layer** — demonstrated to fail against the pre-M8 code/schema and
   succeed after both the migration and the `get_active_by_identity`
   conflict-check change ship together (§4.4).
6. `run_policies.py` evaluates two independently-registered population
   policies against the same system in one invocation, producing two
   independent, correctly-signed `PopulationFinding` rows.
7. Every `PopulationFinding` signed before M8 continues to verify
   correctly against its original signature after M8's code and
   migrations are deployed — demonstrated with a record built exactly as
   pre-M8 code would have built it (no `parameters_used` field
   constructed), not merely one with the field set to `None`.
   `population_finding_hash` requires exactly the one documented
   `exclude_none=True` change (§4.5); this criterion replaces the
   original draft's incorrect "zero code changes needed" claim.
8. Out-of-range or nonsensical parameter overrides (e.g. a negative
   `threshold`, a zero or negative `z_critical`) are rejected in favor of
   each policy's built-in default, with the fallback recorded in
   `rationale` — never silently applied, never an unhandled exception
   (§4.7).
9. `ruff`, `ruff format --check`, `mypy --strict`, and the full pytest
   suite are clean; coverage ≥ 98%, target 100%.
10. No existing API request/response shape is broken; no existing
    migration, table, or column is altered beyond the one named
    constraint change (§4.4), and that change ships in the same
    deployment as its matching application-code fix, never one without
    the other.

## 13. Architectural ambiguities, with my recommendation for each

### 13.1 — Does M8 need a new plugin port, or does it generalize the existing `PopulationPolicy` with a second concrete implementation? **(the highest-stakes call in this document)**

`PopulationPolicy.evaluate(window) -> PopulationFinding` was designed at
M6 with exactly one concrete implementation, the standard risk that a
port shaped around its only user quietly encodes that user's specific
needs rather than the real contract. **Recommendation: no new port, no
signature change.** A second concrete implementation
(`DisparitySignificanceTestPolicy`, §4.2) fits the existing signature
with zero strain — it consumes the same `PopulationWindow.group_counts`
shape, produces the same `PopulationFinding` shape, needs nothing the
port doesn't already provide once `parameters` is added (§13.2). This is
the direct, one-milestone-later analogue of M4 proving `Policy`
generalized by shipping `HighDebtRatioGatePolicy`, not by redesigning
`Policy` first and hoping the redesign was right.

### 13.2 — How does a `PopulationPolicy` receive admin-configurable parameters, given `evaluate()` currently takes only `window`? **(second-highest-stakes call)**

Three real options, reasoned through in §4.3: **(a)** widen `evaluate()`'s
own signature to accept a second argument; **(b)** a uniform
constructor-injection convention across every concrete policy; **(c)**
add a `parameters` field to `PopulationWindow` itself, resolved by
`run_policies.py` from the binding before calling `evaluate()`.
**Recommendation: (c).** `PopulationWindow` already exists specifically
to carry "everything this evaluation needs beyond the window's raw
data" (`classification_snapshot` already set this precedent for a
different kind of context at M6) — this is the same pattern, not a new
one, and it requires zero change to the abstract method's signature,
meaning no concrete `PopulationPolicy` subclass anywhere (including any
future third or fourth one) needs to change its method signature to stay
compilable. Option (b) was rejected because parameter names/shapes are
inherently metric-specific — a uniform constructor contract would have
to either force every policy into the same parameter vocabulary or
degrade into an untyped `**kwargs` convention with no real uniformity
benefit over just reading a dict off the window.

### 13.3 — Does `population_policy_bindings`' existing `UNIQUE (system_id, population_policy_id)` constraint need to change? **(found during this design's own review — previously undocumented)**

Traced directly from "parameters are admin-configurable" to "can an
admin actually change them" — the answer today is no. The existing plain
`UNIQUE` constraint (migration `0014`) has no `WHERE lifecycle_state =
'ACTIVE'` scoping, so once any binding exists for a given `(system_id,
population_policy_id)` pair, deactivating it does not free that key for
reuse — a second binding for the same pair can never be created, with
different parameters or otherwise. This was invisible at M6 (bindings
carried no configurable data, so nobody would ever have wanted to
"change" one), and becomes a real operational dead-end the moment M8
ships. **Recommendation: relax to a partial unique index scoped to
`ACTIVE`** (§4.4), the identical shape `plugin_registrations`' own
`one_production_version_per_plugin` index already uses for exactly this
reason. Rejected alternative: leave the constraint as-is and treat
"changing a system's threshold" as permanently unsupported — this
contradicts the citation's own explicit "admin-defined thresholds"
framing and would make the whole configurability feature a one-time,
write-only setting with no real operational value.

### 13.4 — Does `PopulationFinding` need a `parameters_used` field for point-in-time reproducibility?

The instant `population_policy_bindings.parameters` becomes admin-set
(and, per §13.3, admin-*changeable* over time via deactivate+recreate),
this is the identical reproducibility problem M6's own hostile-review
pass found for `protected_attribute_rules` — live, mutable, unversioned
configuration feeding a computed, signed, append-only finding.
**Recommendation: yes, add `parameters_used: dict[str, float] | None`**
(§4.5), populated with the policy's *effective* resolved values (defaults
included, not just overrides), the same discipline
`classification_snapshot` already established — but nullable, un-backfilled,
and excluded from the hash when absent, specifically *because*
`audit/verify_population_findings.py` hashes the entire model: adding a
field that's always present would change the hash for every historical
record too. See §13.18 for the full finding — this section's earlier
claim that no code change was needed here was wrong.

### 13.5 — Do population policies need a cross-policy aggregation mechanism, or do they stay independent forever?

M4 §13.6's own hedge ("revisit only if the real architecture document
specifies population-level or weighted aggregation, which would more
likely be M6/M8 territory") is the one place in this codebase's history
that raised aggregation as a hypothetical M8 concern. Three subsequent
milestones' worth of citations (M5, M6, M7) settled on "multiple tests +
configurable thresholds" as M8's concrete scope without ever repeating
the word "aggregation," and `architecture-mapping.md` §8's own frozen
statement ("`GovernanceEngine`/`GovernanceVerdict` remain per-event;
population-level results never flow through them") already forecloses
routing population findings through any per-event aggregator. M7's own
`shadow_disagreement_rate_by_policy`/`population_finding_counts_by_policy`
metrics already assume and report on multiple, *independent*,
per-policy population findings. **Recommendation: no aggregation
mechanism.** Each `PopulationPolicy`'s finding for a given
`(system_id, window)` stays its own independent, parallel row — the same
"structurally separate, never combined" relationship `shadow_findings`
already has to `findings` (M3). Building a "PopulationGovernanceEngine"
now, with exactly two policies and no concrete requirement to combine
their outputs, would be the same premature generalization this project
has declined at every prior opportunity (M4 §13.6, M6 §13.9).

### 13.6 — What is the second concrete population policy, and why this one?

**Recommendation: a two-proportion statistical-significance test**
(`DisparitySignificanceTestPolicy`, §4.2), not a second ratio-threshold
variant. Mirrors M4 §13.10's own discipline exactly ("deliberately not
another fairness/protected-attribute-check variant" — M4 picked a
genuinely different *kind* of judgment, `HighDebtRatioGatePolicy`, to
prove `GovernanceEngine` aggregates heterogeneous policies, not just
similar-shaped ones). A statistical-significance test answers a
genuinely different question from a ratio threshold ("is this disparity
plausibly noise" vs. "is this disparity practically large"), and both
are real, commonly-paired techniques in actual EEOC/OFCCP disparate-
impact practice, giving the second policy the same real-world grounding
discipline `_RATIO_THRESHOLD` (EEOC 4/5ths) and `HighDebtRatioGatePolicy`
(CFPB 0.43 ATR/QM) already have — the `Castaneda v. Partida` standard-
deviations convention.

### 13.7 — Does making `AdverseImpactRatioPolicy`'s threshold configurable require a version bump, or is in-place enhancement acceptable?

This project has an established alternative precedent for "does a
behavior change need a new version" — a genuine behavior change (the
credit-scorecard `0.1.0` → `0.2.0` case) got a version bump, not a
runtime knob. **Recommendation: in-place enhancement, no version bump,**
because *default* behavior is unchanged byte-for-byte (§4.3's fallback
means a binding with no `parameters` produces identical output to before
M8) — this is additive capability, not a behavior change to existing
callers, the same distinction M5 drew when it added an optional `engine`
parameter to `protected_attributes/resolver.py` (a frozen M2 module)
without bumping anything, because existing zero-argument callers kept
their exact existing behavior. A version bump would be warranted only if
the *default* threshold itself changed — it doesn't.

### 13.8 — Should there be a shared helper module between the two policies, and how much should it share?

With only one concrete policy (M6), extracting a shared "grouping"
helper had no second caller to justify it — pure speculation. With a
second, genuinely different policy (M8) needing the identical
`defaultdict`-by-`attribute_name` grouping step, this is now the exact
"real duplication with a second proven case" moment this project's own
discipline waits for before extracting anything. **Recommendation:
extract exactly the grouping step** (`population_engine/policies/_shared.py`),
and nothing else — eligibility filtering (the minimum-group-size floor)
and the metric computation itself (ratio vs. z-statistic) stay in each
policy, because those genuinely differ and forcing them into a shared
shape would be exactly the kind of premature, wrong-shaped abstraction
this project has consistently declined.

### 13.9 — Does M8 need a new Admin API endpoint, or an additive field on the existing one?

**Recommendation: an additive field**, `parameters: dict[str, float] |
None`, on the existing `POST /v1/admin/population-policy-bindings`
request body (§7) — no new endpoint, no new resource class. The binding
already is the right place to attach per-system, per-policy
configuration; nothing about "configurable thresholds" implies a
separate configuration resource distinct from the binding that already
exists to answer "does this policy apply to this system."

### 13.10 — Can a binding's parameters be updated in place, or only set at creation?

`PolicyBinding.severity` (M5) was intended to answer this question for
the structurally identical case — no update-in-place endpoint exists;
changing severity is supposed to mean deactivating and creating a new
binding. (This pass found that the recreate half of that pattern has
likely never actually worked for `PolicyBinding` either — §13.20 — but
the *design intent* is still the right one to reuse, per §13.21's
reasoning.) **Recommendation: the identical discipline for
population-policy-binding parameters** — no `PATCH` endpoint, deactivate
and recreate to change parameters, now actually functional end-to-end
post-§4.4/§13.19 (schema *and* application-code fix together), where it
wasn't before M8 at all, and arguably still isn't for `PolicyBinding`
itself. Avoids introducing a mutation-endpoint class this platform has
never needed anywhere else, and keeps binding history inspectable via
deactivated rows rather than silently overwritten.

### 13.11 — Does the second concrete policy need a new external statistical dependency (scipy/numpy), or is stdlib sufficient?

**Recommendation: stdlib only.** A two-proportion z-test is closed-form
arithmetic; converting a z-statistic to a significance judgment against
`z_critical` needs no CDF/p-value computation at all if `z_critical` is
itself the configured parameter (§4.2) — and even if a p-value framing
were wanted later, `statistics.NormalDist().cdf(...)` (stdlib since
Python 3.8) already provides it. Adding scipy or numpy for one closed-
form formula would be exactly the "infrastructure without a concrete
need" this project's own discipline declines.

### 13.12 — Is M8 still a purely additive milestone, or does it deliberately make one exception?

Every migration M2–M7 either created a new table or added a new column/
index to an existing one — none altered an existing constraint. M8's
§4.4 constraint relaxation is the first exception. **Recommendation: name
it explicitly rather than characterize the whole milestone as "purely
additive."** The change is narrowly scoped (one constraint, on one
table, replaced by a strictly less restrictive partial version — no
existing row can violate the new index if it satisfied the old one), and
justified by a concrete, previously-undocumented operational trap
(§13.3), not speculative future-proofing — consistent with "additive
wherever possible," not "additive no matter what," the same qualifier
this document's own instructions used.

### 13.13 — Does `run_policies.py`'s CLI need a manual parameters-override flag?

`--window-start`/`--window-end` exist for backfill/re-run scenarios where
a human needs to override the CLI's normal automatic windowing.
Parameters are different: they belong to the binding (an admin-owned,
persisted, auditable configuration), not to one CLI invocation.
**Recommendation: no CLI flag.** Adding one would create a second,
parallel, non-persisted way to set parameters that bypasses the binding
entirely — undermining the exact reproducibility (`parameters_used`)
this milestone is building. If an operator wants different parameters for
a run, the binding is the correct, auditable place to change them.

### 13.14 — Does the M8/M9/M10/M12 boundary need restating for this document, or does M7 §13.14 already cover it?

M7 §13.14 already drew this line precisely and remains accurate: M8
computes new statistical judgments; M9 (Human Review Workflow) is what
happens to an escalated judgment once one exists (still not built — M8
adds a second thing that can produce a `FLAGGED` outcome, but no queue,
notification, or escalation state for either policy, mirroring M6
§13.10's "purely informational" call, now with two policies instead of
one, unchanged); M10 (Compliance Dashboard) is UI, still not built; M12
(Reporting) is periodic document-shaped output, a different cadence and
audience than an on-demand finding. **Recommendation: reuse M7 §13.14
unchanged rather than re-litigate it** — nothing about shipping a second
population policy or configurable parameters shifts any of these
boundaries.

### 13.15 — Does M8 add authentication to the one endpoint it modifies?

**Recommendation: no**, unchanged from M5/M6/M7's identical answer.
`POST /v1/admin/population-policy-bindings`' request-body change is the
only endpoint surface M8 touches, and it inherits the platform-wide
"still `M5+/M13`" gap, now five consecutive milestones running.
Named here with the same explicitness M6/M7 used, not silently repeated.

### 13.16 — Should the minimum-group-size floor itself be admin-configurable, or is there a hard, non-overridable minimum beneath any configured value?

A genuinely new question raised by making `minimum_group_size` itself
overridable per binding (§4.3): an admin could configure
`minimum_group_size=1`, defeating the entire purpose the M6 hostile-
review pass added this floor for in the first place (excluding
statistically meaningless small-sample ratios/comparisons from producing
a `FLAGGED` verdict). **Recommendation: keep `minimum_group_size`
configurable, but enforce a hard floor in code beneath which no override
is honored** — e.g., `max(configured_value, 2)` for the "at least two
comparable values" structural requirement, and document (not enforce in
code, since "statistically meaningless" is a judgment call, not a hard
invariant) that overriding below the built-in default (`30`) is an
explicit, deliberate admin choice to accept noisier findings, the same
kind of judgment-in-context reasoning M5 §13.5 already established for
severity. This is a smaller, adjacent decision to §4.3/§13.2, worth its
own explicit answer rather than assuming "configurable" silently means
"unbounded."

### 13.17 — How do we know the new statistical test's implementation is actually correct?

**(a genuine production-readiness concern, not just a testing-strategy
checkbox)** A ratio computation (`AdverseImpactRatioPolicy`) is simple
enough that "the test asserts the expected ratio" is sufficient
verification. A z-statistic is easy to get subtly wrong (pooled vs.
unpooled variance, a sign error, an off-by-one in which proportion is
subtracted from which) in a way that still "looks plausible" without
being correct — exactly the kind of bug that would silently produce
wrong governance judgments. **Recommendation: unit tests must assert
against independently hand-computed (or textbook/reference-table)
values for at least three known cases — not just internal consistency
with the implementation's own formula** — named explicitly here so the
implementation phase doesn't treat "the code agrees with itself" as
sufficient proof of correctness for a governance-bearing calculation.

### 13.18 — Does adding `parameters_used` to a signed model invalidate every historical signature? **(the most severe finding of this hostile-review pass)**

Found by tracing, not assuming: `population_finding_hash` hashes
`finding.model_dump(mode="json")` — the whole model. The original
draft's `parameters_used: dict[str, float] = Field(default_factory=dict)`
plus a `NOT NULL DEFAULT '{}'` migration guarantees every historical
record, once re-hashed by post-M8 code, produces a hash that differs from
the one actually signed at creation time (which never had this key at
all) — `verify_population_findings` would report every pre-M8 finding as
invalid the first time it runs after deployment. **Recommendation:
`parameters_used: dict[str, float] | None = None`, an un-backfilled
nullable column, and `exclude_none=True` on the hash's `model_dump()`**
(§4.5) — historical records hash identically to their original signed
payload (the key is simply absent, exactly as it always was), new
records get the field signed as real tamper-evidence going forward. This
is the first time this codebase has had to add a field to an
*already-populated* signed model — every prior signed-schema change
(`classification_snapshot` included) landed before any record existed
under the older shape, so this exact class of problem never previously
arose and had no established precedent to reuse.

### 13.19 — Does the constraint relaxation alone make a binding's parameters changeable? **(found by reading the actual endpoint code, not by inspecting the schema)**

No. `create_population_policy_binding`'s conflict pre-check calls
`get_by_identity(system_id=..., population_policy_id=...)`, which has no
`lifecycle_state` filter — a deactivated binding still counts as
"existing" and the endpoint still returns `409` regardless of what the
database constraint allows. **Recommendation: add
`get_active_by_identity`** (a new, additional repository method,
filtering on `lifecycle_state == ACTIVE`) **and point the endpoint's
conflict check at it**, rather than changing `get_by_identity`'s
existing, lifecycle-blind semantics — which `plugins/seed_registry.py`
and this codebase's other three `get_by_identity` implementations
(`PolicyBindingRepository`, `PluginRegistrationRepository`,
`ProtectedAttributeRuleRepository`) all share and depend on unchanged.
Both this code change and migration `0022` must ship together — either
one alone leaves the feature either inert (schema without code) or
broken in a worse way than today (code without schema: a clean `409`
becomes an unhandled `IntegrityError`).

### 13.20 — The identical defect already exists in `policy_bindings` (M5) — is this M8's problem to fix? **(a genuinely pre-existing, previously-undiscovered defect, found as a side effect of this review)**

`policy_bindings` (migration `0011`) has the identical plain,
non-partial `UNIQUE (adapter_id, policy_id)` constraint, and
`create_policy_binding`'s conflict check (`api/admin/policy_bindings.py`)
calls the identical lifecycle-blind `get_by_identity`. This means
`PolicyBinding.severity` — which M5's own design explicitly declared
changeable via "deactivate and create a new binding" — has, as far as
this review can determine, **never actually been changeable that way in
this platform's history**: the recreate attempt would 409 in exactly the
way §13.19 found for its population-policy-binding twin. This was not
found by anyone at M5, M6, or M7's own hostile-review passes, and this
document's own earlier draft cited the (apparently non-functional)
pattern as an established, working precedent without verifying it.
**Recommendation: do not fix `policy_bindings` inside M8** — this is
M5's scope (per-event policy severity), not the Evaluation Framework,
and "implement only M8 scope" applies here as much as anywhere else in
this document. Instead: **name it explicitly, here, as a real, verified,
outstanding defect**, and raise it to you directly as a candidate for a
small, dedicated, out-of-band fix (mirroring `get_active_by_identity`'s
shape exactly) whenever convenient — not silently absorbed into M8's
scope, and not silently left undocumented either.

### 13.21 — Given both tables already `GRANT ... UPDATE`, was in-place parameter update reconsidered instead of the constraint relaxation?

Yes, explicitly, during this pass — worth recording the reasoning rather
than leaving it as an unexamined assumption. Both `policy_bindings` and
`population_policy_bindings` grant `UPDATE` at the database-privilege
level (unlike `population_findings`' locked-down grants), meaning an
in-place `PATCH` that updates `parameters` on the existing row would
technically work and would avoid the entire constraint-relaxation
exercise. **Recommendation: still reject in-place update, deactivate-
and-recreate remains correct** — not because it's the established
pattern (§13.20 shows that pattern has apparently never actually
functioned), but because it is the right design independent of
precedent: an in-place update would silently destroy the record of what
a system's threshold used to be and when it changed, information with
real audit value for a governance platform, in exchange for avoiding a
narrowly-scoped, well-understood, low-risk schema change. The `UPDATE`
grant existing at the database-privilege level was a deliberate M5/M6
choice to allow *lifecycle_state* transitions (`activate`/`deactivate`),
not an invitation to mutate a binding's substantive configuration in
place.

## 14. What M8 owns

- A second concrete `PopulationPolicy` (`DisparitySignificanceTestPolicy`),
  proving the M6 port generalizes across genuinely different kinds of
  population-level judgment.
- Admin-configurable parameters for population policies, set per binding
  at creation time, with documented fallback to built-in defaults.
- The `population_policy_bindings` constraint relaxation *and* the
  matching `get_active_by_identity` application-code fix that together
  make changing a system's configuration actually possible end-to-end
  through the Admin API (previously impossible via deactivate+recreate,
  and would have remained impossible with only the schema half of the
  fix — §4.4).
- Point-in-time-reproducible findings under configurable parameters
  (`parameters_used`), the same guarantee M6 already gave
  `classification_snapshot` — delivered without invalidating any
  historical `PopulationFinding`'s signature (§4.5).
- Statistical validity guards for the new policy (degenerate variance,
  expected-cell-count) and sane-range validation for admin-submitted
  parameter values (§4.6/§4.7) — both found necessary during this
  milestone's own hostile-review pass, not deferred as "future work."
- Proof, via `run_policies.py` running two independent policies per
  system in one invocation, that population-policy plurality holds with
  zero change to the existing per-binding failure-isolation or
  idempotency guarantees.
- A verified, documented (not fixed) record of the identical,
  pre-existing defect in `policy_bindings` (M5) — found as a byproduct of
  this milestone's own review, explicitly left to a separate follow-up
  (§13.20).

## 15. What remains deferred past M8

- **Cross-policy aggregation** of population findings into one combined
  system-level verdict — deliberately declined (§13.5); each policy's
  finding stays independent, unless a future milestone names a concrete,
  specific need for combining them.
- **Human Review Workflow** (M9) — a `FLAGGED` outcome from either
  population policy still has no queue, notification, or escalation
  state to go to.
- **Compliance Dashboard / UI** (M10) — no visualization of population
  findings, parameters, or the new policy.
- **Per-event `Policy` configurability** — this milestone's parameters
  mechanism is scoped to `PopulationPolicy` only; whether per-event
  policies (`Policy`) should gain similar admin-configurable thresholds
  is an unopened question, out of scope here.
- **Additional statistical tests beyond two** — this milestone
  deliberately stops at proving plurality with a second, genuinely
  different metric; a third, fourth, or a genuinely pluggable "bring your
  own statistical test" surface remains unscheduled until a concrete need
  for one actually appears.
- **A "what-if, recompute under different parameters" capability** —
  changing a binding's parameters only affects future windows;
  `population_findings`' own unique constraint (`population_policy_id`,
  `system_id`, `window_start`, `window_end`, unchanged since M6) already
  prevents recomputing a past window under new parameters, consistent
  with M6 §13.16's own explicit "no silent recompute" stance.
- **Authentication** — still `M5+/M13`, now a five-consecutive-milestone
  gap (M5, M6, M7, M8), sharpened by this pass's finding that the lack of
  auth on parameter-accepting endpoints is a concrete lever against the
  platform's own governance purpose, not just a generic gap (§4.7/§12).
- **Real scheduling of `run_policies.py`** — still a manually-invoked
  batch job, deployment/M13-adjacent, unchanged since M6.
- **The pre-existing `policy_bindings` (M5) recreate-after-deactivate
  defect** (§13.20) — verified real and left for a dedicated, small,
  out-of-band follow-up, not folded into M8 and not silently left
  undocumented.

## 16. Decisions requiring your approval before implementation

1. §13.1 — No new plugin port; a second concrete `PopulationPolicy`
   implementation generalizes the existing one.
2. §13.2 — Configurable parameters flow through a new `PopulationWindow.parameters`
   field, resolved by `run_policies.py` from the binding, not through a
   widened `evaluate()` signature or a policy-constructor convention.
3. §13.3/§4.4 — `population_policy_bindings`' `UNIQUE (system_id,
   population_policy_id)` constraint is relaxed to a partial unique index
   scoped to `ACTIVE`, the one non-purely-additive schema change this
   milestone makes.
4. §13.4/§4.5/§13.18 — `PopulationFinding` gains `parameters_used` for
   point-in-time reproducibility, as a nullable, un-backfilled field
   excluded from the hash when absent (`exclude_none=True`) — the one
   deliberate change to `audit/verify_population_findings.py` this
   milestone needs, specifically so no historical finding's signature is
   invalidated.
5. §13.5 — No cross-policy aggregation mechanism; population findings
   stay independent and parallel.
6. §13.6/§4.2 — The second concrete policy is a two-proportion
   statistical-significance test (`disparity-significance-test`,
   Castaneda-convention `z_critical`), not a second ratio-threshold
   variant.
7. §13.7 — `AdverseImpactRatioPolicy`'s parameter fallback is an
   in-place, additive enhancement; no version bump.
8. §13.8 — Exactly one small shared helper (`_shared.py`, the grouping
   step) is extracted between the two policies; nothing else.
9. §13.9/§13.10 — One additive field on the existing binding-creation
   endpoint; no new endpoint; no update-in-place endpoint (deactivate and
   recreate to change parameters).
10. §13.11 — No new external dependency; stdlib `statistics.NormalDist`
    is sufficient.
11. §13.16 — `minimum_group_size` is configurable but subject to a hard,
    code-enforced structural floor beneath any override.
12. §13.17 — The new statistical test's unit tests must assert against
    independently hand-computed reference values, not just internal
    self-consistency.
13. §13.18 — **(hostile-review finding, highest priority)**
    `parameters_used` is nullable, un-backfilled, and excluded from the
    hash when absent (`exclude_none=True`), so no historical
    `PopulationFinding`'s signature is invalidated by this milestone.
14. §13.19 — **(hostile-review finding)** The constraint relaxation ships
    together with a new `get_active_by_identity` repository method and a
    matching change to `create_population_policy_binding`'s conflict
    check — the schema change alone does not make parameters changeable.
15. §13.20 — **(hostile-review finding, pre-existing, not M8's to fix)**

16. §13.21 — In-place `UPDATE` for binding parameters was considered
    (both tables already grant it) and rejected in favor of

17. §4.6/§4.7 — `DisparitySignificanceTestPolicy` includes
