Everything in the approved design below, built exactly as specified —
this milestone needed no deviation from the design doc at all, and no
schema changes, confirming §6's prediction:

  list[Policy])`, raising `ValueError` for an empty list. `govern()` runs

  policy, a plain `debt_to_income` threshold gate (CFPB ATR/QM's 0.43,
  cited for concrete provenance) — deliberately not another fairness
  check, proving aggregation combines genuinely different kinds of
  judgment.
- **`CreditScorecardAdapter` retrofitted to `0.2.0`**, declaring
  `governing_policy_ids = ("direct-attribute-in-inputs",
  "high-debt-ratio-gate")` — registered and promoted through the existing
  plugin lifecycle (§13.11), not a silent change to what `0.1.0` meant
  while it was `PRODUCTION`. Verified live: promoting `0.2.0` correctly
  auto-demoted `0.1.0` to `SHADOW` via the same database-enforced
  mechanism M3 built, with zero runtime effect from the demoted version
  (its code no longer exists in this process).
- **`api/ingestion/routes.py`** — the per-request policy-resolution loop
  now runs once per declared governing policy family, collecting every
  `PRODUCTION` policy into one `GovernanceEngine` and failing the whole
  request if any family lacks one. `SHADOW` execution is per-family,
  entirely unaffected by how many families an adapter declares.
- **`db/repositories/verdict.py`** — `policy_id` added as a secondary
  sort key, closing the (rare, low-clock-resolution) tie-break gap
  §13.7 identified.
- **`SyntheticAdapter`** — mechanical `str` → `tuple[str, ...]` update,
  no version bump, no behavior change, exactly as scoped.

## 1. What M4 is exactly responsible for

Every prior milestone names the same two things for M4, consistently,
going back to M0:

1. **Policy plurality** — `GovernanceEngine` runs more than one `Policy`
   against a single `DecisionEvent`. Its constructor "changes in M4,
   deliberately, when there is a second policy and real aggregation
   logic to justify it" (`governance_engine/engine.py`'s own docstring).
2. **Disagreement surfacing** — when policies don't all agree, that fact
   is not lost. `GovernanceVerdict.findings` has been `list[Finding]`
   since M0 specifically so this milestone would have somewhere to put
   more than one ("`findings` is plural because that is what a Verdict
   *is* per the architecture" — `schemas/verdict.py`).

**What M4 explicitly is not**, per the same record: `VerdictStatus` stays
the two-value `ALLOW`/`FLAGGED` placeholder — the full four-state model
is M5's job, gated on Policy Bindings and escalation rules that don't
exist yet. Policy Bindings themselves — "which policy applies to which
domain/jurisdiction" — are also M5, not M4 (`governance_engine/engine.py`).
Getting this boundary right is the single most consequential judgment
call in this document — see §13.1.

## 2. How M4 builds on M3

M3 gave every `Adapter` a single, fixed `governing_policy_id` naming
which *one* policy family governs its events, and gave the ingestion
route a per-request database lookup that resolves that family's current
`PRODUCTION` (and any `SHADOW`) versions. M4 is the direct generalization
of that mechanism from one policy family to several — not a new
mechanism. Concretely:

- `Adapter.governing_policy_id: str` becomes `governing_policy_ids:
  tuple[str, ...]` — still static, code-defined identity, exactly like
  M3's singular version (see §13.1 on why this must **not** become
  dynamic/admin-configurable in M4).
- The ingestion route's per-request policy resolution loop (currently:
  look up one family, run its `PRODUCTION` version, run its `SHADOW`
  versions) runs once per declared family instead of once per adapter.
  `SHADOW` execution is completely unaffected — it was already scoped
  per policy family, not per adapter, so plurality doesn't touch it.
- `GovernanceEngine(policy: Policy)` becomes `GovernanceEngine(policies:
  list[Policy])`, and `govern()` aggregates N findings into one
  `GovernanceVerdict` instead of wrapping exactly one.
- **No schema changes are needed.** `verdict_findings` (migration `0006`)
  and `VerdictRepository`/`EvidenceStore` have looped over
  `verdict.findings`/persisted N rows since M1 — "exactly one finding
  exists per verdict until M4, not this table['s design]" is that
  migration's own comment. M4 is the milestone that finally exercises
  data-model foresight M0/M1 already built, not one that requires new
  tables.

## 3. Why each piece exists architecturally

**Plurality.** A single policy's judgment is a single opinion. Real
governance — the platform's whole reason to exist — means checking a
decision against every rule that applies to it, not just the first one
someone happened to register. `AlwaysAllowPolicy` and
`DirectAttributeInInputsPolicy` each prove the `Policy` contract in
isolation; M4 is what proves the contract composes, the same way M2's
second adapter proved `Adapter[TPayload]` generalizes and M3's retrofit
proved the registry works against real cases, not hypothetical ones.

**Disagreement surfacing.** If policy A clears an event and policy B
flags it, silently picking one answer (or silently OR-ing them with no
record of the disagreement) throws away exactly the information a
governance platform exists to preserve — architecture P4/P9's
reproducibility and evidentiary-integrity principles, already invoked
throughout this codebase, apply as much to *why* a verdict landed where
it did as to the verdict itself. `findings: list[Finding]` already
carries every contributing opinion; M4's job is making sure that list is
actually populated with more than one entry when more than one policy
ran, not inventing a new place to put the information.

## 4. Proposed architecture (this review's recommendation)

**Aggregation rule: any `FLAGGED` finding makes the verdict `FLAGGED`.**
A logical OR across all findings' outcomes — "most restrictive wins."
This requires no new `VerdictStatus` values (stays two-state, correctly
scoped to M5's job) and matches the plain compliance reading of
"multiple rules apply; if any one objects, the decision is flagged."
Aggregation logic lives inline in `GovernanceEngine.govern()`, not a new
pluggable strategy/port — there is exactly one aggregation rule and no
second one to justify an abstraction, the identical reasoning M2 used
for `ProtectedAttributeResolver` and M3 used for the plugin registry
itself.

**Failure semantics: one failing `PRODUCTION` policy fails the whole
request.** If any of the N production policies raises or times out
(under M3's sandbox), the entire ingestion request fails cleanly (the
same 500/504 semantics M3 already established for the single-policy
case) rather than aggregating from a partial, incomplete set of
findings. A governance decision made on deliberately incomplete
information is worse than a clear, temporary failure.

**Ordering: findings are aggregated in the declared order of
`governing_policy_ids`.** Deterministic and human-legible (an auditor
reading a Verdict's findings sees them in the same order every time for
the same adapter), and free — sequential evaluation already produces
this order naturally, no sorting step needed. `VerdictRepository.get`'s
existing `ORDER BY evaluated_at` should gain `policy_id` as a secondary
sort key (a small, cheap robustness fix — see §13.7) so a read is
guaranteed to reproduce write order even if two evaluations land in the
same timestamp.

**Disagreement is derived, not stored.** No new field on
`GovernanceVerdict` or `IngestionResponse`. Whether policies disagreed is
fully reconstructable from `findings` (`len({f.outcome for f in
findings}) > 1`) — see §13.4 for the full reasoning and the real
tradeoff this makes.

## 9. Interfaces and abstractions

`GovernanceEngine`'s constructor is the only interface that changes:

```python
class GovernanceEngine:
    def __init__(self, policies: list[Policy]) -> None:
        if not policies:
            raise ValueError("GovernanceEngine requires at least one Policy")
        self._policies = policies

    def govern(self, event: DecisionEvent) -> GovernanceVerdict:
        findings = [policy.evaluate(event) for policy in self._policies]
        status = (
            VerdictStatus.FLAGGED
            if any(f.outcome is FindingOutcome.FLAGGED for f in findings)
            else VerdictStatus.ALLOW
        )
        return GovernanceVerdict(
            verdict_id=str(uuid4()),
            decision_event_id=event.event_id,
            status=status,
            findings=findings,
            created_at=datetime.now(UTC),
        )
```

No new port. `Policy` and `Adapter` remain the only two plugin surfaces;
aggregation is a concrete algorithm inside a concrete class, the same
"no abstraction without a second strategy" discipline M2's
`ProtectedAttributeResolver` and M3's registry both already followed.

## 11. Acceptance criteria (proposed)

1. `GovernanceEngine` runs every policy passed to it and aggregates via
   OR-of-`FLAGGED`; raises `ValueError` for an empty policy list.
2. `CreditScorecardAdapter` events are governed by both
   `direct-attribute-in-inputs` and `high-debt-ratio-gate`; a payload
   that only one of the two would flag is genuinely `FLAGGED` end to end
   — the first real proof of disagreement-driven aggregation, not just
   plumbing.
3. Every contributing `Finding` is persisted and retrievable via
   `VerdictRepository.get`/`EvidenceStore`, in deterministic order.
4. A `PRODUCTION` policy failure (exception or timeout) fails the whole
   ingestion request cleanly; it never produces a Verdict built from a
   partial finding set.
5. Shadow execution is provably unaffected by plurality — a `SHADOW`
   candidate for one policy family has zero effect on aggregation
   involving the *other* family.
6. `ruff`, `mypy --strict`, and the full suite pass at 100% coverage
   against real Postgres, migrations idempotent (there are none new to
   apply, which is itself worth confirming, not assuming).
7. `docs/architecture-mapping.md` updated to reflect real plurality while
   explicitly reconfirming `VerdictStatus` and Policy Bindings remain M5.

## 12. Expected production-readiness review points

- **The debt-ratio threshold is a hardcoded constant.** Same governance
  smell M2's review flagged for its own policy: "who approved this
  number and when." Building admin-configurable policy parameters is
  M5-adjacent scope creep; the realistic fix at M4's scope is precise
  documentation of the threshold's provenance (illustrative vs. a real
  regulatory figure), not a configuration system.
- **OR-aggregation's false-positive rate.** Every additional governing
  policy strictly increases how often an event gets `FLAGGED` (OR only
  ever adds flags, never removes them). Worth stating explicitly as an
  expected, correct consequence of adding a second policy — not a
  regression to investigate if `FLAGGED` events become more common after
  M4 ships.
- **`GovernanceEngine.govern()`'s cost now scales with policy count.**
  N policies means N sequential sandboxed calls per request. Not
  addressed now (matches M3's own "not solved now, M6's async ingestion
  plane is where throughput is actually addressed" precedent) — flagged
  for awareness, not fixed.
- **Adapter-version discipline for `governing_policy_ids` changes.**
  Confirm the retrofit of `credit-scorecard` actually goes through a new
  registered version promoted via the existing lifecycle (§13.11), not a
  silent behavior change to the already-`PRODUCTION` `0.1.0` — this is
  exactly the kind of "which version is Y currently trusted with" gap
  M3's registry exists to prevent, and M4 is its first real test.

## 13. Architectural ambiguities, with my recommendation for each

### 13.1 — Is "policy plurality" (M4) the same thing as "Policy Bindings" (M5)? **(the highest-stakes call in this document)**

**Recommendation: no, and the boundary is exactly where the codebase's
own docstrings already draw it.** `governance_engine/engine.py`
distinguishes them explicitly: multi-policy aggregation is M4;
"Policy Bindings (which policy applies to which domain/jurisdiction)...
require concepts — bindings, an approval workflow..." is M5.
Read together with `api/admin/__init__.py`'s "Policy/binding
administration... arrives with the milestones that give it something to
administer (M4/M5)," the coherent reading is: **M4 answers "given a
statically-known, code-defined set of policies for an adapter, run them
all and aggregate" — the same static-identity pattern M3's single
`governing_policy_id` already established, just widened to plural. M5
answers "make *which* policies apply *dynamically* configurable per
domain/jurisdiction, without a code deploy."** `governing_policy_ids`
stays a fixed tuple on the `Adapter` class in M4, exactly like `version`
and `adapter_id` — not a new database table, not a new Admin API.
Conflating these would mean M4 quietly absorbing M5's actual job
(dynamic, admin-managed binding) years ahead of the milestone that's
supposed to justify that complexity — precisely the "no second case yet"
mistake this project has avoided at every prior milestone. If this
reading is wrong against the real architecture document, it's the one
finding in this review most likely to require redesign, not a parameter
tweak.

### 13.2 — What should `GovernanceEngine`'s new constructor signature actually be?

**Recommendation: `__init__(self, policies: list[Policy])`, full stop —
no backward-compatible single-`policy` parameter kept alongside it.**
This project's own standing practice is "avoid backwards-compatibility
shims... just change the code" (every prior milestone's retrofit — M2's
`Policy.evaluate` never grew a legacy path, M3 deleted `api/app.py`'s
old hand-wiring outright rather than leaving it dead). `GovernanceEngine`
has exactly two call sites (the two generated ingestion routes), both of
which this milestone updates anyway.

### 13.3 — OR-of-`FLAGGED`, or a more sophisticated aggregation rule?

Options: **(a)** OR — any `FLAGGED` finding makes the verdict `FLAGGED`
(recommended, see §4). **(b)** Majority vote among findings. **(c)**
Confidence-weighted voting, using `Finding.confidence`. **(b)** and
**(c)** both require answering questions the architecture doesn't
currently have machinery for (how are ties broken; what does "a 0.6-
confidence `CLEAR` outweighing a 0.9-confidence `FLAGGED`" even mean for
a two-state, non-numeric `VerdictStatus`) — and `Finding.confidence` has
never been read by anything in this codebase before, only ever written.
**(a)** needs none of that, matches plain compliance intuition ("if any
applicable rule objects, the decision is flagged"), and is a one-line
`any(...)`. Recommend **(a)**; revisit only if the real architecture
document specifies population-level or weighted aggregation, which would
more likely be M6/M8 territory (population-level policies) than M4's.

### 13.4 — Does "disagreement surfacing" mean a new explicit field, or is the existing `findings` list sufficient?

This is the second-highest-stakes call after §13.1, because "surfacing"
is a word that implies *visibility*, and a list a caller has to inspect
and diff themselves is a weaker form of visibility than a dedicated
signal. Options: **(a)** Nothing new — `findings` (already populated
with every contributing opinion) is the surfacing; a consumer computes
`len({f.outcome for f in findings}) > 1` if they care. **(b)** A new
computed field, e.g. `GovernanceVerdict.has_disagreement: bool` or
`dissenting_policy_ids: list[str]`, stored or computed at construction
time. **(c)** Expose per-policy outcomes in `IngestionResponse` itself
(the synchronous API response), not just the persisted `Verdict`.
**Recommendation: (a) for the persisted domain model, explicitly
declining (c).** `findings` already carries full information — adding a
redundant derived field to `GovernanceVerdict` is exactly the kind of
denormalization this project has avoided elsewhere (no cached/derived
columns anywhere in the schema so far). Extending the synchronous
`IngestionResponse` **(c)** is a real product decision (does a caller
need to know about disagreement *immediately*, or is after-the-fact
audit/query access sufficient?) that this review is deliberately not
making unilaterally — flagging as the one sub-question in this section
still worth your explicit input, since "not exposing it synchronously"
is a defensible default but not obviously the only correct one.

### 13.5 — What happens when a `PRODUCTION` policy fails mid-aggregation?

**Recommendation: fail the entire request.** Already argued in §4 — the
alternative (aggregate from whichever policies succeeded, note the gap
somehow) requires answering "is a Verdict built from 2 of 3 required
policies' opinions a valid Verdict at all," which this milestone's
two-state, undocumented-gaps `VerdictStatus` has no way to express
honestly. A clean failure is more honest than a silently-incomplete
success.

### 13.6 — Does M4 need to prove plurality against a real second policy, or is the aggregation mechanism enough on its own?

**Recommendation: yes, a real second policy, on `credit-scorecard`
specifically** — already argued in §5/§12. This project has never shipped
an abstraction without immediately exercising it against a genuine
second case (M2's second adapter, M3's registry retrofit); building
`GovernanceEngine`'s N-policy machinery and never actually registering a
second policy anywhere would leave M4 architecturally unverified in
exactly the way M1's original sandbox constraint left migrations
unverified until real execution happened. See §13.10 for which policy.

### 13.7 — Does finding order need a formal determinism guarantee, or is "evaluated sequentially" good enough?

**Recommendation: yes, formalize it cheaply.** `VerdictRepository.get`
already does `ORDER BY evaluated_at`; two policies evaluated in the same
request could in principle share a timestamp at low clock resolution,
making read-order not strictly guaranteed to match write-order in a rare
case. Adding `policy_id` as a secondary sort key costs one line and
removes the ambiguity entirely — recommended as a small, cheap fix bundled
into this milestone (it's a natural consequence of plurality actually
mattering for the first time), not deferred.

### 13.8 — Does `Adapter.governing_policy_id` get renamed to plural, or does a new attribute get added alongside it?

**Recommendation: rename (`governing_policy_ids: tuple[str, ...]`),
don't keep both.** Same reasoning as §13.2 — this project doesn't carry
compatibility shims for its own internal contracts, and both existing
adapters are updated by this same milestone regardless.

### 13.9 — Does M4 need any new Admin API surface?

**Recommendation: no.** `api/admin/plugins.py`'s existing
register/list/get/promote already handles per-policy lifecycle
regardless of how many *different* policy families exist — M4 just means
more `plugin_id`s get registered through the same endpoints, and the
ingestion route consults more of them per request. The grouped "M4/M5"
phrasing in `api/admin/__init__.py` most plausibly refers to M5's actual
new need (admin-managed *bindings*, per §13.1), not M4's.

### 13.10 — What should the second real policy actually check?

**Recommendation: a plain numeric threshold on `debt_to_income`** (already
present in `CreditScorecardPayload.feature_vector` since M2), reviving
the spirit of `legacy_v1`'s DTI check — explicitly named in this
codebase's own history as the "dead-code" check M2's fairness policy was
built to eventually replace, but never actually rebuilt as real logic.
This is deliberately **not** another fairness/protected-attribute check
— the point of M4's proof case is combining two genuinely *different
kinds* of judgment (a fairness gate and a risk gate), not two variations
on the same theme. The specific threshold value is a placeholder pending
your input (or the real architecture document's) — flagging this
explicitly rather than picking an arbitrary number and presenting it as
considered, per §12's production-readiness note on policy thresholds as
a governance-sensitive constant.

### 13.11 — Does retrofitting `CreditScorecardAdapter` with a second governing policy require a new registered adapter version?

**Recommendation: yes — register `credit-scorecard` `0.2.0` through the
existing draft → shadow → production lifecycle, rather than mutating
what `0.1.0` means while it's already `PRODUCTION`.** This is exactly
what M3's registry exists to prevent (silently changing what a
`PRODUCTION`-trusted identity does). One real wrinkle worth flagging: M3
deliberately left adapter-level `SHADOW` behaviorally identical to
`PRODUCTION` (both fully process and persist), so promoting `0.2.0`
through `SHADOW` doesn't yet provide the same safe "compare before
committing" value it does for policies — you'd be choosing between (a)
promoting `0.2.0` straight through both stages as a controlled admin
action anyway (fine, since it's still one deliberate step, not a code
deploy), or (b) treating this as the forcing case that finally gives
adapter-level `SHADOW` real meaning (a scope addition beyond what M4's
card names). Recommend **(a)** — accept the lifecycle as a controlled
promotion mechanism without the full shadow-comparison value for
adapters, and leave "adapter shadow" as the still-open item M3's own
production-readiness review already named, not something M4 quietly
expands to cover.
