## What Was Built

Everything in the approved design below, built exactly as decided across
the frozen design's own scope (§1) and approval checklist (§13) — no schema
surprises beyond the two purely additive migrations, no scope creep past
architecture §13, and no genuine architectural contradiction forced a
deviation from the frozen design. Two real implementation-time findings did
surface and are documented below, distinct from design contradictions.

- **`audit/encryption.py`** — `FernetFieldEncryptor`/`NoOpFieldEncryptor`
  (both satisfying a `FieldEncryptor` protocol), `FieldDecryptionError`,
  `UNREADABLE_PLACEHOLDER`, `is_encrypted`/`decrypt_field` (the single
  place every read path in this codebase checks the `"gpenc1:"` marker
  before consulting any encryptor — §5.1's own "marker detection is
  unconditional" invariant, centralized rather than duplicated per call
  site), and `load_encryptor`. No ephemeral fallback, per §5.1/§12.4.
- **`Settings.FIELD_ENCRYPTION_KEY: str | None`** and
  **`Settings.RETENTION_DAYS_SHADOW_FINDINGS`/`RETENTION_DAYS_PROTECTED_ATTRIBUTE_RESOLUTIONS: int | None`**
  — all three default to `None` (opt-in, per §5.1/§5.2); no numeric
  default for either retention setting, per §5.2's own corrected reasoning.
- **`audit/evidence_store.py`** — `EvidenceStore` gains an optional
  `encryptor` collaborator, threaded into `append` (hash-then-encrypt,
  §5.1) and `_to_model` (now an instance method, decrypts first, falls
  through to plaintext for an unmarked/pre-M11 row, raises
  `FieldDecryptionError` — never a placeholder — on a decrypt failure,
  since `payload` is evidentiary content, per §5.1/§12.15) and into the
  default-constructed `ProtectedAttributeResolutionRepository`/
  `VerdictReviewRepository`, per §5.1's minimal-plumbing item 1.
- **`db/repositories/verdict_review.py`,
  `db/repositories/population_finding_review.py`,
  `db/repositories/protected_attribute_resolution.py`** — each gains an
  optional `encryptor` collaborator; `resolve()`/`create()` encrypts
  `resolution_notes`/`proxy_basis` before writing; `_to_model` (now an
  instance method on all three) decrypts on read with per-record
  containment (logged, substituted with `UNREADABLE_PLACEHOLDER` for that
  one row, mirroring `human_review/backfill_reviews.py`'s own "one
  record's failure never aborts the rest" discipline), per §5.1/§12.15.
  `reviewer`/`attribute_name` are untouched, per §4.1/§5.1.
- **`audit/verify_chain.py`** — `verify_chain_from_database` gains
  `encryption_key`; the CLI gains `--encryption-key`, per §5.1/§12.5. A
  `FieldDecryptionError` from `EvidenceStore.all()` is caught and reported
  as a clean, distinct `ChainVerificationResult` naming the specific
  unreadable record, never an unhandled crash — see "Production-Readiness
  Review" below for the one real plumbing detail the design's own prose
  underspecified here.
- **`retention/purge_expired_records.py`** (new package) — the retention
  CLI, per §5.2: `compute_cutoff`, `purge_shadow_findings`,
  `purge_protected_attribute_resolutions`, `run_purge` (each table its own
  transaction), and `main` (`--database-url` required, retention windows
  read from `Settings`). A table with no configured window is skipped
  entirely, logged as such. Idempotent: a re-run against an already-purged
  table deletes zero rows.
- **Migrations `0025`/`0026`** — `0025` extends `evidence_chain`'s own
  `REVOKE UPDATE, DELETE` lockdown to `systems`, `model_versions`,
  `decision_events`, `findings`, `verdicts`, `verdict_findings`, per §5.3;
  `0026` revokes `DELETE`/`UPDATE` from `gov_platform_app` on
  `shadow_findings`/`protected_attribute_resolutions` and adds the two
  indexes the retention CLI's own cutoff scans need, per §5.2/§5.3/§6.
  Regrouped by risk profile exactly as designed: `0025` alone needs a
  maintenance window.
- **`api/app.py`** — builds one `FieldEncryptor` from
  `Settings.FIELD_ENCRYPTION_KEY`, threads it into every repository that
  needs it, and logs a `WARNING` (not `INFO`) on every startup where the
  key is unset, per §5.1/§9.
- **No new plugin port, no new API endpoint, no new external dependency,
  no encryption of `decision_events.protected_attribute_refs`/`decision_output`,
  no retention for `evidence_chain`/`population_findings` or the six newly
  locked operational tables** — §1/§3, as designed.

## Production-Readiness Review

Performed after implementation, before freeze — mirroring M5–M10's own
finalization passes, with the same "assume it's wrong until proven
otherwise" discipline applied to the *implementation* this time, not the
design. Three real, implementation-time findings surfaced; none is a
design contradiction. All three are documented in full in the CHANGELOG's
own "Fixed" section for this milestone; summarized here:

1. **`EvidenceStore.all()`'s pre-existing eager, list-returning contract
   means a decrypt failure can't be caught *inside* `verify_chain()`'s own
   per-record loop the way §5.1's prose read at a literal level — the loop
   never starts if the fetch itself raises first.** Not a design
   contradiction: the design's *outcome* requirement (a clean, distinct,
   specific `ChainVerificationResult`, never an unhandled crash) is fully
   met — `verify_chain_from_database` catches `FieldDecryptionError`
   around the whole `store.all()` fetch instead, with the specific failing
   record's `sequence_number` named in the exception message itself (set
   by `EvidenceStore._to_model`). The one honest gap against a maximally
   literal reading: `checked_count` is `0` in this path, since no
   hash-verification could run before the fetch itself failed, rather than
   reflecting how many records *would* have verified first. Classified:
   **implementation-time finding**, resolved without reopening any
   approved design decision.
2. **Writing real Postgres integration tests for encrypted
   `evidence_chain` rows surfaced a genuine test-isolation hazard that
   predates M11 but had never been exercised before it: `EvidenceStore.all()`/
   `verify_chain_from_database` scan the *entire*, shared, cumulative
   `evidence_chain` table with no per-test scoping.** A test-only encrypted
   row left behind under a one-off throwaway key would have silently
   broken every *other* test's own keyless or differently-keyed
   verification call against that same table, including the pre-existing
   `test_verify_chain_postgres.py` suite (which has always assumed the
   whole table is a validly-decryptable, unbroken chain — true by
   construction before M11, since nothing ever wrote a `"gpenc1:"`-marked
   row). Classified: **pre-existing characteristic exposed by new test
   coverage**, not a defect in the frozen design or in M11's own
   production code. Fixed at the test-suite level, not the design or
   implementation level: every M11 test that writes an actually-encrypted
   `evidence_chain` row now cleans it up via the elevated
   `admin_db_engine` connection before returning (`evidence_chain` has had
   no `DELETE` grant for the ordinary role since migration `0008`,
   unrelated to M11).
3. **A genuine implementation bug, found by direct reproduction, not
   reasoning alone: `FernetFieldEncryptor.decrypt_token` called
   `token.encode("ascii")` with no containment around it.** §5.1 already
   discloses that a `resolution_notes`/`proxy_basis` value colliding with
   the `"gpenc1:"` marker (free text submitted before encryption was ever
   enabled) fails Fernet's own `InvalidToken` check once encryption is
   later turned on — but a colliding value that also contains non-ASCII
   characters (entirely plausible free text) raised an uncaught
   `UnicodeEncodeError` *before* ever reaching Fernet's decrypt logic,
   bypassing `FieldDecryptionError` and, with it, every caller's
   per-record containment — the exact "crashed list response instead of a
   `[unreadable]` placeholder" failure mode §5.1/§12.15 was designed to
   prevent. Reproduced directly (`decrypt_field("gpenc1:héllo wörld...",
   encryptor)` raised `UnicodeEncodeError`, confirmed empirically before
   and after the fix). Classified: **implementation bug**. Fixed:
   `UnicodeEncodeError` is now caught at the same point and wrapped into
   `FieldDecryptionError`, identically to `InvalidToken`; a regression
   test was added.

No other implementation-time bug, pre-existing issue, or out-of-scope
discovery surfaced. `population_engine/window.py`, `GovernanceEngine`,
every per-event `Policy`/`Adapter`, both ingestion routes, and every
existing Admin API response shape remain byte-for-byte untouched — verified
directly (unchanged imports, unchanged call sites) rather than assumed.

**What could not be verified this session:** this sandbox has no local
Postgres and no working Docker daemon (confirmed directly — `docker ps`
fails to reach a daemon). Every Postgres-dependent integration test written
for this milestone (`test_m11_encryption_postgres.py`,
`test_purge_expired_records_postgres.py`, and the M11 additions to
`test_privilege_enforcement.py`) is therefore **written and believed
correct, reviewed carefully against Postgres's and SQLAlchemy's own
documented semantics, but not empirically executed in this session** — the
identical situation M9's own finalization pass disclosed for the same
reason. Everything checkable without a live database — lint, strict
mypy on `src`, and the full local pytest run — is clean.

## Verdict

M11 is implemented exactly as the frozen design specifies, across every
item in the approval checklist (§13, items 1–23), with zero deviation
forced by a genuine implementation-time architectural contradiction. Three
real implementation-time findings were made and resolved: two mechanical
consequences of code shapes the design's own prose didn't spell out to
this level of detail (`EvidenceStore.all()`'s eager-fetch contract, and a
test-isolation hazard in the shared `evidence_chain` table), and one real
bug in the encryption module's own error handling (an uncaught
`UnicodeEncodeError` on a non-ASCII marker-collision value, found by direct
reproduction and fixed with a regression test) — none a reversal of an
approved decision. `population_engine/window.py`,
`GovernanceEngine`, every per-event `Policy`/`Adapter`, both ingestion
routes, and every M6–M10 endpoint remain completely untouched; the full
pre-M11 test suite continues to pass/skip unmodified against the M11
codebase.

**Unlike M5–M8, and the same as M9, this milestone's own finalization pass
could not verify its Postgres-dependent behavior against a real database
in this session** — no Docker daemon was reachable throughout, confirmed
directly rather than assumed. Everything checkable without a live
database (lint, strict types, and the 271 tests that don't touch Postgres)
is clean. The new Postgres-dependent tests — including the ones directly
targeting this milestone's most novel mechanisms (encrypt/decrypt round
trips and decrypt-failure containment for all four encrypted columns,
`verify_chain --encryption-key`'s clean-failure path, retention's
skip/purge/idempotency behavior, and the extended six-plus-two-table
privilege enforcement) — are written, reviewed carefully against
Postgres's, SQLAlchemy's, and `cryptography`'s own documented semantics,
and believed correct, but **not yet empirically proven**. This milestone
should not be considered fully verified, in the sense every prior
milestone's own "Verdict" used that word, until those tests actually run
against a real Postgres — in CI, or in a follow-up session with Docker
available — and the result is folded back into this document.

## Revision note (hostile-review pass)

This document has been through a hostile-review pass (assume-it's-wrong-
until-proven-otherwise, the identical discipline M5–M10 each went through
before their own implementations began) — the same discipline this
document's own opening paragraph already commits to. Ten findings came out
of it. Three were severe enough to reverse part of the proposed
architecture rather than just annotate it, and are folded in below, in
place, rather than kept as a separate errata section, mirroring exactly
how M6/M8/M9 each folded in their own hostile-review corrections:

1. **§4.1/§5.1 reversed — `reviewer` is removed from the encrypted-field
   set, on both `verdict_reviews` and `population_finding_reviews`.** The
   first draft's own safety check (§4.1: "never referenced in any
   `WHERE`/`GROUP BY` clause") was performed against the wrong layer —
   `api/admin/verdict_reviews.py`/`api/admin/population_finding_reviews.py`
   never filter on `reviewer`, but `db/repositories/verdict_review.py`'s and
   `db/repositories/population_finding_review.py`'s own `resolve()` methods
   do, as a conditional `UPDATE ... WHERE ... AND reviewer = :reviewer` —
   M9's own identity-continuity concurrency mechanism
   (`docs/milestones/M9.md` §3.3/§9.6). Fernet ciphertext is non-
   deterministic (a fresh IV every call), so a stored ciphertext value can
   never equal an incoming plaintext comparison value — encrypting
   `reviewer` would make every legitimate `resolve()` call fail with
   `rowcount == 0`, permanently, the moment `FIELD_ENCRYPTION_KEY` is set.
   This is not a degraded feature; it is a deleted one — the Human Review
   Workflow's own terminal action would stop working entirely. See the
   corrected §4.1/§5.1 below.
2. **§4.1/§5.1 reversed — `protected_attribute_resolutions.attribute_name`
   is removed from the encrypted-field set, for the identical root cause at
   lower severity.** `db/repositories/protected_attribute_resolution.py`'s
   `list_by_decision_event` does `.order_by(...attribute_name)` — a clause
   the first draft's WHERE/GROUP BY-only check never considered. Ciphertext
   byte order bears no relationship to plaintext order; encrypting this
   column would not break anything outright, but would silently destroy
   this method's deterministic, human-legible ordering. `proxy_basis` (never
   ordered or filtered anywhere) is unaffected and remains in scope.
3. **§5.1/§12.5 reversed — `audit/verify_chain.py` does *not* need "zero
   code changes."** The first draft's claim was true only for the hash-
   recomputation *logic* (which already operates on the decrypted
   `EvidenceRecord.payload` dict) and false for the module as a whole:
   `verify_chain_from_database` constructs `EvidenceStore(engine)` with no
   other argument, and neither `EvidenceStore.__init__` nor `verify_chain.py`'s
   bare-`argparse` `main()` has any mechanism today to obtain
   `FIELD_ENCRYPTION_KEY` from anywhere. As literally documented, running
   `verify_chain.py` against an encryption-enabled deployment would not
   fail gracefully — `EvidenceStore._to_model`'s `json.loads` would raise an
   unhandled `json.JSONDecodeError` on the first ciphertext row it hit. See
   the corrected §5.1 below for the minimal plumbing this actually requires.

Beyond these three, seven further findings are folded in as amendments —
real gaps that don't change the overall two-tier-encryption/two-table-
retention/privilege-lockdown shape, but do change its details: the
migration-lock discussion for privilege changes against `decision_events`
and its five siblings is corrected to name a real availability risk
migration `0026`'s own risk analysis never got applied to (§6/§8); retention's
silent interaction with M7's already-shipped, frozen `?since` metric is
disclosed rather than left for a future session to discover the hard way
(§5.2/§9); the retention-period defaults are removed rather than presented
as considered when they were not (§5.2); Fernet's plaintext-length leakage
is named as a real, if narrow, limitation of tier two specifically for
this schema's low-entropy columns (§5.1/§9); decrypt-failure handling is
specified using the identical per-record containment philosophy M9 already
established for its own reconciliation tool, rather than left unspecified
(§5.1); the reasoning behind reusing the migration-owner credential for
retention is expanded to weigh a recurring, scheduled job's different risk
profile from a one-time migration's (§12.11); and the risk of a silent
regression to plaintext storage if `FIELD_ENCRYPTION_KEY` is ever removed
after having been enabled is named explicitly, with a disclosure-based
mitigation, rather than left as an unstated edge case of the "opt-in, no
ephemeral fallback" design (§5.1/§9).

A third hostile-review pass, run after this document's own second revision
was otherwise approval-ready, found four further issues — none severe
enough to reopen this milestone's scope or reverse an approved
architectural decision, but real enough that leaving them unaddressed
would have meant approving a document that either mischaracterized its own
privilege model or left a genuine implementation ambiguity for whoever
built this milestone to discover the hard way:

1. **§1/§5.3 corrected — the claim that the application role "holds no
   deletion capability over anything in this schema at all" was false, not
   merely imprecise.** Six ordinary admin-configuration tables
   (`plugin_registrations`, `policy_bindings`, `protected_attribute_rules`,
   `population_policy_bindings`, `verdict_reviews`,
   `population_finding_reviews`) retain the full `DELETE` grant given at
   their own originating migration (`0010`/`0011`/`0012`/`0014`/`0023`/`0024`
   respectively) — confirmed directly against each file. M11 never revokes
   it, and should not: none of these six is retention-eligible or
   evidentiary. The prior text asserted both "unchanged by this milestone"
   and "never deletable by it" about the same six tables in the same
   sentence — those two claims cannot both be true, and the second one was
   the error. §1 and §5.3 now scope the privilege claim to exactly the ten
   tables this milestone actually classifies (eight permanently
   append-only, two deletable only through the retention tool's own
   connection), not to "this schema" as a whole.
2. **§4/§5.2 amended — retention's "nothing irreplaceable is lost" premise
   for `protected_attribute_resolutions` was never checked against M5's own
   architecture.** The M2-era claim this document quoted ("derived,
   reconstructible data... re-running the resolver reproduces it") predates
   M5's switch to a live, DB-backed `protected_attribute_rules` table —
   granted `UPDATE`/`DELETE` (migration `0012`) and, unlike
   `population_findings`, carrying no `classification_snapshot`-equivalent.
   Nothing in today's Admin API exercises that mutability (§12.16), but the
   document's own "reconstructible, so deletion is safe" reasoning was
   stated as settled when it was actually conditional on a fact — the
   ruleset never changing — this document never checked. New §4.4 names
   this plainly; §5.2/§9/§11/§12.16 disclose it consistently, the same
   "disclose, don't reopen a settled boundary" discipline §4.3 already
   applies to the `?since` interaction.
3. **§5.1 amended — `FIELD_ENCRYPTION_KEY`'s encoding was never specified,
   and the "structurally identical to `SIGNING_PRIVATE_KEY`" framing
   actively pointed toward the wrong one.** `SIGNING_PRIVATE_KEY` is a
   hex-encoded raw Ed25519 seed; `Fernet` requires its key as 32
   url-safe-base64-encoded bytes — `Fernet.generate_key()`'s own output
   format, not a hex string. §5.1 now states this explicitly and points at
   `Fernet.generate_key()` directly, needing no bespoke generation helper
   the way signing needed `generate_private_key_hex()`.
4. **§5.1/§12.5 amended — the default, no-key "no-op" encryptor's behavior
   against a `"gpenc1:"`-prefixed row was underspecified.** A literal
   pass-through would reproduce the exact unhandled `json.JSONDecodeError`
   this document's second pass already corrected `verify_chain.py` to
   avoid. §5.1 now states plainly that marker detection is unconditional —
   it happens before any encryptor is consulted, regardless of which one is
   wired in — so the no-key case fails the same specific, catchable way
   every other unreadable-ciphertext case does, never by falling through to
   `json.loads` on raw ciphertext.

None of the four changes this milestone's overall shape — no new table, no
new dependency, no reversed architectural decision. All four are folded in
below, in place, the same convention every prior pass in this document
already used.

This section records that the design below is the **corrected** design —
every subsection that follows already reflects the reversals and
amendments from all three passes above, the same convention M6/M8/M9 each
used for their own hostile-review passes.

## TL;DR

M11 completes architecture §13 ("Audit System") with the three things every
milestone since M0 has pointed at by the same three-word phrase and never
built: **encryption at rest**, **retention tiers**, and **privilege
classification for the Evidence Store**. Unlike M6–M10, this milestone adds
no new computation and almost no new persisted state — its job is to change
*how existing data is protected and eventually removed*, not to compute
anything new.

Three findings, made by tracing this codebase's actual SQL and actual
privilege grants rather than assumed from the citation trail alone, are
severe enough to shape this document's entire recommendation rather than
being footnotes:

1. **Two `decision_events` columns cannot receive application-level
   encryption without breaking M6/M8's entire population-policy
   computation.** `population_engine/window.py` casts
   `protected_attribute_refs` and `decision_output` to `jsonb` **inline, in
   SQL**, and groups by their content directly in Postgres (confirmed
   directly against that module and against M6's own production-readiness
   review, which verified this exact cast "against real seeded data, not
   just reasoned about"). An opaque, application-encrypted ciphertext blob
   in either column is not `jsonb`-castable and cannot be grouped by — every
   `PopulationPolicy` this platform has (`adverse-impact-ratio`,
   `disparity-significance-test`) would silently stop working, with no
   error at ingestion time and a hard failure the next time
   `population_engine/run_policies.py` runs. This is the headline
   architectural finding of this document (§5.1, §12.2) — the two columns
   whose contents are the single most sensitive data this platform holds
   (real protected-attribute values, not just labels) are exactly the two
   columns application-level encryption cannot touch under the current
   Event Lake design.
2. **Retention (real deletion) is fundamentally incompatible with the hash
   chain, and — once this document's own privilege-classification fix
   ships — with the rest of the Evidence Store too.** `evidence_chain` is
   hash-chained; deleting any row breaks `previous_hash` continuity for
   every row after it, silently defeating the entire tamper-evidence
   guarantee this platform's core value proposition rests on. Once M9
   §9.5's disclosed gap is closed (§5.3, §12.7) — extending
   `REVOKE UPDATE, DELETE` to `systems`, `model_versions`,
   `decision_events`, `findings`, `verdicts`, `verdict_findings`, matching
   `evidence_chain`/`population_findings`'s existing treatment — those six
   tables become just as undeletable as the two they already couldn't
   touch. Retention tiers in this document therefore apply to exactly two
   tables (`shadow_findings`, `protected_attribute_resolutions`) — the only
   tables in this schema that are simultaneously non-evidentiary and
   already privilege-unlocked — not to "old data" in general (§5.2, §12.8).
3. **The ephemeral-key fallback M5 built for signing would be actively
   dangerous if reused unchanged for encryption.** A process with no
   configured signing key generates a fresh one per process and signs
   fine — the only cost is that a different process can't cross-verify
   that signature, an inconvenience, not data loss. A process with no
   configured encryption key that generated a fresh one the identical way
   would encrypt real data with a key that exists nowhere else, and lose
   the ability to decrypt that same data the moment it restarts — an
   unrecoverable, self-inflicted data-loss bug, not a graceful degradation.
   These two "no key configured" fallbacks look identical on the surface
   and must not be built the same way (§5.1, §12.4).

No new plugin port, no new API endpoint, no new domain-computation module.
The `cryptography` package this platform already depends on (added at M5
for Ed25519 signing) is sufficient for everything this document proposes —
**zero new external dependencies**, the same discipline M0 (stdlib JSON
logging), M6 (no dedicated analytical store), M7 (no Prometheus/
OpenTelemetry), and M8 (stdlib `statistics.NormalDist`) have each already
applied to their own milestone's temptation to reach for infrastructure.

A second hostile-review pass, performed after this document's first draft
was otherwise approval-ready, found that the encrypted-field list and the
"no code changes to `verify_chain.py`" claim were both wrong in ways that
would have broken real functionality rather than merely being incomplete —
see the revision note above. Neither correction changes this document's
overall shape (still two encryption tiers, still retention scoped to
exactly two tables, still a privilege lockdown closing M9 §9.5's gap); both
narrow what tier two actually covers and specify plumbing the first draft
asserted away rather than designed.

A third hostile-review pass, run against this now-corrected design, found
four further issues — a privilege-model claim in §1/§5.3 that was flatly
contradicted by the migrations it described, an unchecked assumption
behind retention's inclusion of `protected_attribute_resolutions`, and two
underspecified implementation details (`FIELD_ENCRYPTION_KEY`'s required
encoding, and the no-key encryptor's behavior against ciphertext it can't
read). See the revision note above for all four. None reopens this
milestone's scope, reverses an approved decision, or adds new
infrastructure — three are documentation corrections, and one
(`protected_attribute_resolutions`'s reconstruction caveat) is a disclosed,
not-fixed limitation, the same treatment §4.3 already gives the `?since`
interaction.

## 1. Scope

**M11 owns:**

- **Encryption at rest for a fixed, named set of application-level fields**
  that are never filtered, compared, or ordered by their own content in any
  SQL statement this codebase issues — anywhere in the codebase, not just
  the API router layer (§4.1, §5.1, corrected by this document's own
  hostile-review pass) — implemented via the already-present `cryptography`
  dependency, a single static symmetric key, no rotation, no KMS/HSM,
  mirroring M5's own signing-key scope boundary exactly.
- **A documented, verified-at-deploy-time requirement that the external
  Postgres instance's storage be encrypted** (§5.1) — the literal, standard
  reading of "at rest" for the primary datastore, satisfied at the
  infrastructure layer this repository does not itself provision
  (`infra/docker/docker-compose.yml` runs only the application container;
  Postgres is external, per architecture §17 — confirmed by reading that
  file directly, not assumed).
- **Retention tiers for `shadow_findings` and `protected_attribute_resolutions`**
  — a new, explicitly-invoked, idempotent purge tool, mirroring
  `population_engine/run_policies.py`'s and
  `human_review/backfill_reviews.py`'s existing CLI shape, running under a
  separate, more-privileged database connection than the app's own runtime
  role (§5.2).
- **Privilege classification for the Evidence Store** — extending
  `REVOKE UPDATE, DELETE` to `systems`, `model_versions`, `decision_events`,
  `findings`, `verdicts`, and `verdict_findings` (§5.3), closing the exact
  gap `docs/milestones/M9.md` §9.5 disclosed and left for "a dedicated
  review of exactly which tables should gain the lockdown" — and,
  consistently, revoking the ordinary app role's `DELETE`/`UPDATE` on the
  two retention-eligible tables too, so no table this milestone classifies
  as evidentiary or retention-eligible — ten tables in total — can ever be
  deleted from by the continuously-running application process; only the
  retention tool's own separately-credentialed connection can ever delete
  a row from `shadow_findings`/`protected_attribute_resolutions`, and no
  connection the running app itself uses can delete from any of the other
  eight (§5.3, corrected by this document's own third hostile-review pass
  — see the revision note above). This is a narrower, more precisely
  scoped claim than "the application holds no deletion capability over
  anything in this schema": six ordinary admin-configuration tables
  (`plugin_registrations`, `policy_bindings`, `protected_attribute_rules`,
  `population_policy_bindings`, `verdict_reviews`,
  `population_finding_reviews`) retain the full `DELETE` grant they were
  given at their own originating migration, unchanged and un-revisited by
  M11, because they are legitimately admin-mutable operational config, not
  evidentiary output — see §5.3.

**M11 explicitly does not own** — each backed by a finding in §4/§5, not a
judgment call made unilaterally:

- **Pruning or archiving the hash chain itself, or `population_findings`.**
  Real retention for either requires a chain-checkpointing/segmentation
  mechanism this document does not design (§4.2, §5.2, §12.9) — a genuine,
  disclosed, deferred gap, not silently built around.
- **Key rotation or KMS/HSM-backed custody** for either the existing
  Ed25519 signing key or the new symmetric encryption key — unchanged from
  M5's own scope boundary for signing, applied consistently to encryption
  (§5.1, §12.3).
- **Retroactive encryption of any pre-M11 row.** Encryption applies going
  forward only, the identical "signing applies going forward only, no
  retroactive signing of M0–M4 evidence" precedent M5 already established
  (§8, §12.6).
- **Multi-tenancy or per-tenant retention/encryption policy.** This
  platform has one domain (`FINANCE`) and no tenant concept at all — a
  single, global retention period per table and a single, global encryption
  key are the right amount of configurability for a platform with no second
  case to design plurality against, the same discipline M5 applied to
  Policy Bindings' `adapter_id` key and M6 applied to a single population
  domain.
- **Authentication of any kind.** Still `M13` — the ninth consecutive
  milestone naming this exact gap (M0's own predecessor concern) M10 named
  itself the eighth instance of. Encrypting `resolution_notes` (and
  `reviewer`, which this milestone cannot encrypt at all — see §4.1/§5.1)
  does not address who can write or read them via the Admin API in the
  first place (§10).
- **A new Admin API surface of any kind** — no endpoint to view retention
  status, trigger a purge, or report encryption configuration. Mirrors
  `run_policies.py`/`backfill_reviews.py`'s existing "explicitly-invoked
  CLI, no admin trigger" precedent (§7, §12.10).

address, because M0–M10 were each building the platform's ability to
compute and persist a governance fact in the first place, not managing the

## 4. Architectural analysis

### 4.1 Why "encryption at rest" cannot mean "encrypt every sensitive column uniformly"

The naïve reading — wrap every TEXT/String column holding potentially
sensitive data in the same encrypt-before-write/decrypt-after-read
helper — fails for a reason specific to this codebase, not a generic
security concern: **this schema has at least two columns whose content is
read directly by SQL, not only by the application after a row is
fetched.** `population_engine/window.py`'s Event Lake read (M6, extended by
M8) issues a `GROUP BY` over `protected_attribute_refs`' and
`decision_output`'s **parsed JSON content**, computed entirely inside
Postgres — the whole reason M6 could recommend "no new storage, a new read
pattern over existing tables" (M6 §13.2) was that Postgres could already
answer "how many decisions had `race=Black` and a favorable outcome" via a
plain aggregate query. An opaque ciphertext blob defeats that cast
entirely — Postgres cannot `jsonb`-cast or group by the contents of an
AES/Fernet token, and would either error outright (`CAST` failure) or, if
the cast is applied loosely, silently return meaningless grouped counts.
Either failure mode is severe: the first breaks `run_policies.py`
outright the next time it runs; the second would silently corrupt every
future adverse-impact-ratio and disparity-significance-test finding,
undetectably, for a platform whose entire purpose is producing correct
bias findings.

This is not a reason to abandon application-level encryption — it is a
reason to scope it precisely to columns this codebase's own SQL never
reaches into, checked at the layer that actually issues SQL, not the layer
that merely calls into it.

**Corrected by this document's own hostile-review pass: checking only the
API router layer's `WHERE`/`GROUP BY` clauses is not sufficient, and the
first draft's list was wrong twice over as a result.** The first draft
confirmed `verdict_reviews`/`population_finding_reviews`'s `reviewer` and
`protected_attribute_resolutions.attribute_name` were safe by reading
`api/admin/verdict_reviews.py`/`api/admin/population_finding_reviews.py`
(which indeed never filter on either) — but never read the *repository*
layer underneath them, which is where this codebase's actual SQL lives.
Two real breakages follow directly from that gap:

- **`db/repositories/verdict_review.py::resolve()`** (and the identical
  method on `db/repositories/population_finding_review.py`) issues a
  conditional `UPDATE ... WHERE id = :id AND status = 'IN_REVIEW' AND
  reviewer = :reviewer` — M9's own identity-continuity check
  (`docs/milestones/M9.md` §3.3/§9.6), the one non-authentication integrity
  mechanism this platform's Human Review Workflow has. This is an equality
  comparison between the *stored* column value and an *incoming* plaintext
  parameter, evaluated inside Postgres. Fernet — like every practical
  symmetric-encryption scheme with a random IV — produces different
  ciphertext for the same plaintext on every call. There is no way to make
  `VerdictReviewRow.reviewer == reviewer` (ciphertext-vs-plaintext) succeed
  for a genuinely matching value without either decrypting inside the
  database (this platform has no `pgcrypto` extension enabled and adding
  one is out of scope, per §5.1's own "zero new dependencies" bar) or
  switching to a deterministic/blind-indexed scheme for this one column
  specifically (a different cryptographic primitive this document does not
  design, since `reviewer` is being removed from scope entirely rather than
  given a bespoke mechanism — see below). Encrypting `reviewer` would make
  every legitimate `resolve()` call fail with `rowcount == 0` and raise
  `ValueError`, translated by the Admin API into a permanent `409` — not
  intermittently, not under contention, but always, the moment
  `FIELD_ENCRYPTION_KEY` is set. This does not degrade the Human Review
  Workflow; it deletes its own terminal action.
- **`db/repositories/protected_attribute_resolution.py::list_by_decision_event`**
  does `.order_by(ProtectedAttributeResolutionRow.attribute_name)`. Nothing
  crashes here — but ciphertext byte order bears no relationship to
  plaintext order, so encrypting `attribute_name` would silently replace
  this method's deterministic, human-legible ordering with effectively
  random output, with nothing anywhere signaling the regression.

**The corrected, safe list** — re-verified against every repository method
that touches each candidate column, not only the API layer above it:

- `evidence_chain.payload` — read only whole, in Python, via `json.loads`
  (`EvidenceStore._to_model`); never filtered, grouped, or ordered by SQL.
- `verdict_reviews.resolution_notes`, `population_finding_reviews.resolution_notes`
  — free text, never referenced in any `WHERE`/`GROUP BY`/`ORDER BY` clause
  anywhere in either repository or either Admin API router.
- `protected_attribute_resolutions.proxy_basis` — read via
  `decision_event_id` joins only; never filtered, grouped, or ordered by
  its own value (unlike its sibling `attribute_name`, above).

**Removed from scope, not merely re-labeled "excluded like `protected_attribute_refs`":**
`verdict_reviews.reviewer`, `population_finding_reviews.reviewer`, and
`protected_attribute_resolutions.attribute_name`. This has a real,
disclosed consequence worth stating plainly rather than glossing over:
`reviewer` — a self-asserted human name tied to a real bias-finding
judgment — is precisely the value M9's own production-readiness review
called the most sensitive thing this platform persists (*"the first
milestone where an unauthenticated caller can fabricate a specific, named
person's professional judgment about a real bias finding"*), and it is
exactly the one column this milestone's chosen mechanism cannot protect at
the application layer without a different, bespoke cryptographic
construction this document does not build. `reviewer` remains plaintext,
protected only by tier one (storage-level encryption) and by nothing else
— named as a real, disclosed gap in §9/§11, not silently accepted.

`decision_events.input_features` sits in a different category from any of
the three removed above — never SQL-filtered, grouped, or ordered today,
but structurally the same kind of column `window.py` already reaches into
for one sibling field (`protected_attribute_refs`) on the same row; §12.2
still treats it as a judgment call rather than an obvious inclusion, given
how easily a future milestone could extend the Event Lake to key on model
input features too.

### 4.2 Why retention cannot mean "delete anything past a certain age"

`evidence_chain` is not merely privilege-locked against deletion — it is
**structurally** incapable of tolerating it. Each row's `record_hash`
commits to `previous_hash`, the prior row's own `record_hash`
(`audit/hash_chain.py: compute_hash(previous_hash, payload_json)`).
Deleting row N does not just lose row N's content — it makes row N+1's
`previous_hash` point at a hash with no corresponding row anywhere in the
table, an unrecoverable break `verify_chain`'s own re-derivation logic
would report as tamper (correctly — from the chain's own perspective, a
missing link and a forged link are indistinguishable, which is exactly
hash-chaining's point). Deleting the *newest* rows first (truncating the
tail) would preserve the remaining chain's internal consistency but is the
opposite of what "retention" (removing *old* data) means. There is no way
to delete an *interior or oldest* row from a hash chain and have the
remainder still verify against `GENESIS_HASH`, full stop, without a
mechanism this document does not build: a **checkpoint** — a
periodically-recorded, independently-attested "as of row N, the chain up to
here is known-good" marker that lets a future verifier treat row N+1 as a
new starting point rather than requiring the unbroken original genesis
link. Building that correctly (deciding what a checkpoint attests to, how
it is itself protected from tampering, and how `verify_chain`'s CLI
consumes one) is a real, separate cryptographic design problem — this
document declines to invent it speculatively, with no concrete legal
retention-period requirement or storage-cost pressure forcing the question
yet, the same "no second case yet" discipline this project has applied to
every other piece of unbuilt infrastructure (M5's KMS, M6's analytical
store, M7's metrics stack).

`population_findings` is not hash-chained (M6 §13.5's own decision — a
parallel, non-chained table, deliberately), so it does not share this
specific structural problem, but it is `REVOKE UPDATE, DELETE`-locked for
an equally load-bearing reason (M6 §13.16: a signed, evidentiary,
point-in-time-pinned record). Deleting an old `population_finding` would
not corrupt anything *else's* verifiability the way an `evidence_chain`
deletion would, but it would still destroy the one thing this table exists
to be — proof of what was reported at the time. This document treats it the
same as `evidence_chain` for retention purposes: not because deleting it
is structurally impossible, but because doing so contradicts the table's
entire reason to exist, absent the same kind of "we've decided this
evidentiary guarantee has a bounded shelf life" policy decision a
checkpoint mechanism would formalize for the hash chain.

Once §5.3 closes M9 §9.5's gap, the same reasoning extends to `verdicts`,
`findings`, `decision_events`, `model_versions`, `systems`, and
`verdict_findings` — not because any of them are individually
hash-chained, but because they are the **normalized record of exactly what
`evidence_chain.payload` already embeds**. Deleting a `decision_events` row
while its full content survives unencrypted-or-encrypted-consistently
inside `evidence_chain.payload` forever does not reduce this platform's
actual data-retention footprint — it only reduces which tables a direct SQL
query can reach the same data through. This is worth stating with the same
plainness this project applied to M6 §13.16's own "the underlying
recommendation is unchanged, only how honestly its risk is described": **a
retention tier over the normalized operational tables alone would be
largely cosmetic**, and this document does not build one, rather than
building a feature that would look like data minimization without being
one.

### 4.3 A disclosed, not fixed, interaction with M7's own frozen `?since` metric — found during this document's own hostile-review pass

`observability/metrics.py`'s `_SHADOW_DISAGREEMENT_SQL` (backing
`GET /v1/admin/metrics`'s `shadow_disagreement_rate_by_policy`, M7) reads
`FROM shadow_findings ... WHERE sf.evaluated_at >= :since`, and M7's own
design places no upper bound on how far back a caller may set `?since` (the
*default* is 24 hours; the parameter itself is not capped — M7 §13.15's own
language is "a bounded, recent window," describing the default, not a
ceiling). Retention (§5.2) purges `shadow_findings` rows past a configured
age. The two facts compose into a real, previously-undisclosed
consequence: **once retention has run, `GET /v1/admin/metrics?since=` for
a window older than the configured retention period silently
undercounts** — not because no shadow-policy disagreement occurred in that
period, but because the evidence for it no longer exists, with nothing in
the response distinguishing "zero disagreement" from "evidence purged."

**This document does not fix this by reopening M7's endpoint.** Capping
`?since` at the shortest configured retention window, or annotating the
response when a query window exceeds it, would mean modifying a module
frozen since M7 for a concern introduced by an unrelated, later milestone
— the identical "don't reopen a frozen module for unrelated new state"
discipline M8 §13.14 and M9 §9.1 already applied to `GET /v1/admin/metrics`
and to `Policy`/`GovernanceEngine` respectively. **Recommendation:
disclose, don't fix** — named explicitly here, in §9 (production-readiness),
and in §11 (deferred items), as a real, accepted limitation an operator
must know about (an old `?since` query against a system with retention
enabled cannot be trusted to reflect true historical shadow-disagreement
activity), not silently left for a future session to rediscover the hard
way. If a future milestone ever needs `GET /v1/admin/metrics` to account
for retention explicitly (e.g., surfacing "data unavailable before
`<date>`" in the response), that is real, additive scope for whichever
milestone owns it next — not implied or begun here.

### 4.4 A disclosed, not fixed, gap in retention's own "reconstructible" premise for `protected_attribute_resolutions` — found during this document's own third hostile-review pass

§5.2 scopes retention to `protected_attribute_resolutions` partly on the
strength of that table's own M2 docstring: *"this table is derived,
reconstructible data... re-running the resolver over the same
`DecisionEvent` reproduces it"* (quoted in full in §2). That claim was true
when M2 wrote it — the resolver's only ruleset source was
`protected_attributes/classification.py`, a static, in-code dict with no
runtime mutation path at all. It has not been re-verified since M5 changed
what the *live* resolver actually consults: `EvidenceStore` constructs
`ProtectedAttributeResolver(engine=engine)` (`audit/evidence_store.py`,
confirmed directly), which resolves against the DB-backed
`protected_attribute_rules` table, not `classification.py`'s static copy.
That table is granted `SELECT, INSERT, UPDATE, DELETE` for
`gov_platform_app` (`infra/migrations/0012_create_protected_attribute_rules.sql`,
confirmed directly) and carries no equivalent of
`population_findings.classification_snapshot` — the exact mechanism M6
built (§13.16, quoted in §2) because a live, unversioned ruleset makes
"recompute to reproduce" false the moment the ruleset changes.
"Re-running the resolver reproduces it" is therefore only true as long as
`protected_attribute_rules` hasn't changed for the domain/attribute in
question since the original resolution — a condition this document never
checked before citing the M2 claim as settled.

**This is a real gap, not a hypothetical one, but a narrow one under
today's actual code.** The Admin API for `protected_attribute_rules`
(`api/admin/protected_attribute_rules.py`, confirmed directly) exposes
only `POST`/`GET` — `create()` raises a conflict rather than upserting
when a `(domain, attribute_name)` pair already exists, and no endpoint
anywhere updates or deletes an existing rule. Under the *application's*
current code paths, a rule's classification is therefore practically
immutable once set, and "reconstructible" holds in practice today. What it
does not hold against is (a) direct database access exercising the
`UPDATE`/`DELETE` grant this table already has, independent of anything
M11 does, and (b) a plausible future milestone adding a rule-correction
endpoint — an obvious, natural admin feature ("fix a misconfigured
classification") — with nothing in this schema to stop it from silently
invalidating every `protected_attribute_resolutions` row retention has
since purged, for exactly the reason M6 built `classification_snapshot` to
prevent for `population_findings`.

**This document does not fix this by adding a snapshot mechanism to
`protected_attribute_resolutions`.** Doing so would mean either adding a
new column to an existing table (a real schema change this document's own
"no `ALTER` of any existing table" discipline, §6, does not currently call
for) or building versioning for `protected_attribute_rules` itself — real,
separate scope no milestone has asked for, the same "no preemptive
scaffolding without a concrete forcing case" discipline §12.9 already
applies to chain-checkpointing. **Recommendation: disclose, don't fix, and
don't reverse retention-eligibility.** `protected_attribute_resolutions`
remains in retention scope (§5.2) — the *raw* attribute values this
classification was computed over are never at risk regardless: they
persist forever in `decision_events.protected_attribute_refs` and
`evidence_chain.payload`, neither of which retention ever touches, so
nothing this platform's evidentiary guarantees depend on is actually lost;
what a retention-purged row loses is specifically the *original,
point-in-time classification decision*, which a re-run of the resolver
reproduces faithfully only if the ruleset hasn't since changed. Named
explicitly here, in §9 (production-readiness) and §12.16, as a real,
disclosed limitation on what "reconstructible" actually guarantees — not
silently assumed to still mean what the M2 docstring meant before M5
existed.

## 5. Proposed architecture (this review's recommendation)

### 5.1 Encryption at rest

**Two tiers, addressing two different threats, neither substituting for the
other:**

**Tier one — storage-level encryption of the Postgres data directory/volume
itself.** This is the literal, standard reading of "encryption at rest" in
most compliance frameworks (protection against a stolen disk, an
unencrypted backup, a decommissioned volume) and the one this repository
cannot implement in code at all: confirmed directly, `infra/docker/docker-compose.yml`
provisions exactly the application container, nothing else — Postgres is
external, per architecture §17, unchanged since M1. **Recommendation:**
document this as a hard, verified-at-deploy-time deployment requirement
(README.md and `infra/docker/`'s own comments) — "the Postgres instance
this application connects to must use storage-level encryption at rest
(a managed provider's own encryption-at-rest setting, or a
self-managed LUKS-encrypted volume)" — the identical "named explicitly,
not silently assumed, because this platform has no second deployment
environment to design a specific mechanism against" discipline M5 applied
to signing-key custody and M7 applied to a real metrics stack. No code.

**Tier two — application-level field encryption for a fixed, named list of
columns**, addressing a threat storage-level encryption alone does not:
anyone with a live, authenticated database connection (a leaked
credential, an SQL-injection foothold — this platform still has none of
the SQL-parameterization gaps M0–M10 introduced, but the threat model is
about credentials, not injection specifically) or an unencrypted logical
dump/backup sees plaintext under storage-only encryption, since disk
encryption is transparent to any legitimate query. Encrypted columns
remain opaque even to a party who can run arbitrary `SELECT`s against the
live database.

**The named list, and why each is safe** (traced directly against every
repository method and every SQL statement this codebase issues — the API
router layer *and* the layer underneath it, per §4.1's own corrected
methodology, not assumed and not stopped at the first layer checked):

- `evidence_chain.payload` — read only whole, in Python
  (`EvidenceStore._to_model`), never SQL-filtered, grouped, or ordered.
- `verdict_reviews.resolution_notes`, `population_finding_reviews.resolution_notes`
  — free text, never referenced in any `WHERE`/`GROUP BY`/`ORDER BY` in
  either repository or either Admin API router.
- `protected_attribute_resolutions.proxy_basis` — read via
  `decision_event_id` joins only, never filtered, grouped, or ordered by
  its own value.

**Excluded, deliberately, for two distinct reasons:**

- `decision_events.protected_attribute_refs`, `decision_events.decision_output`
  (§4.1, §12.2) — `population_engine/window.py`'s SQL casts and groups by
  these directly; encrypting either would silently break every
  `PopulationPolicy` this platform has. `decision_events.input_features` is
  a judgment call, not an automatic inclusion — see §12.2.
- `verdict_reviews.reviewer`, `population_finding_reviews.reviewer`,
  `protected_attribute_resolutions.attribute_name` (§4.1, **corrected by
  this document's own hostile-review pass — removed from the first
  draft's list, not merely reclassified**) — each participates in a
  repository-level SQL operation (an equality-checked `WHERE`, for
  `reviewer`; an `ORDER BY`, for `attribute_name`) that a non-deterministic
  cipher cannot survive. `reviewer` in particular is excluded not because
  it is safe to leave unprotected, but because this milestone's chosen
  mechanism cannot protect it without a different, bespoke construction
  (deterministic or blind-indexed encryption) this document does not
  design — see §4.1 and the disclosed gap in §9/§11.

**Mechanism: `cryptography.fernet.Fernet`**, not raw AES-GCM. Fernet is
authenticated (tamper is detected, not just confidentiality protected),
handles its own nonce/IV generation internally (removing an entire class of
nonce-reuse bugs a hand-rolled AES-GCM wrapper could introduce), and is
already available from the `cryptography` dependency this platform added
at M5 — zero new external dependency, the same bar M8 held stdlib
`statistics.NormalDist` to over scipy/numpy.

**A real, disclosed limitation of tier two specifically — Fernet does not
hide plaintext length** (found during this document's own hostile-review
pass). Fernet's ciphertext length is a deterministic function of plaintext
length, modulo AES block-size rounding; it protects content, not size. This
matters for exactly the columns this section names, because several draw
from a small, fixed vocabulary — `protected_attribute_resolutions.classification`
(a sibling of `proxy_basis`, not itself encrypted, but illustrative of the
table's own vocabulary: `DIRECT`, `PROXIED`) is a handful of distinct
strings with visibly different lengths. A reader with direct database
access — precisely the threat tier two exists to defend against, per this
section's own opening — can sometimes distinguish which of a small set of
plausible values a row holds from ciphertext length alone, without the
key. This is a well-known, generally-accepted characteristic of any
block-cipher-based column encryption, not a defect specific to this
design's choices, and it does not argue against encrypting these columns
— tier two still removes the much larger risk of a casual `SELECT`
returning the value verbatim. It is named here as a genuine, if narrow,
ceiling on what tier two actually guarantees for low-entropy content,
alongside the chain-verification-distributability cost already disclosed
below, rather than left for an operator to assume "encrypted" means
"length is hidden too."

**Key management, deliberately diverging from M5's signing-key precedent**
(§12.4, the highest-stakes finding in this document): `Settings` gains
`FIELD_ENCRYPTION_KEY: str | None = None`, matching `SIGNING_PRIVATE_KEY`'s
shape (an optional string, sourced the same `GOV_PLATFORM_`-prefixed
environment-variable way) but differing from it in two respects, not
one — **its required encoding, and its fallback behavior when unset, both
specified/corrected by this document's own third hostile-review pass,
which found the first version's "structurally identical... in every way
except one" framing actively misleading.**

**Encoding (new, specified by this document's own third hostile-review
pass — earlier versions never said).** `SIGNING_PRIVATE_KEY` is a
hex-encoded raw 32-byte Ed25519 seed (`audit/signing.py`'s own
`generate_private_key_hex`). `FIELD_ENCRYPTION_KEY` is not that: `Fernet`
requires its key as 32 url-safe-base64-encoded bytes —
`Fernet.generate_key()`'s own output format, a different encoding than the
signing key's. An operator or implementer who followed the "structurally
identical" framing literally and supplied a hex string here would have
`Fernet(key)` raise at first use — a startup or first-write crash, not a
subtle bug. **Recommendation: `FIELD_ENCRYPTION_KEY` is the raw output of
`Fernet.generate_key()`** (a `bytes` value; stored/passed as its own
`str`/env-var form via `.decode()`), needing no bespoke generation helper
the way signing needed `generate_private_key_hex()` — `Fernet.generate_key()`
already produces a ready-to-use, correctly-encoded value on its own, and
this document builds nothing new on top of it (§12.17).

**Fallback behavior — there is no ephemeral,
auto-generated fallback when it is unset.** If `FIELD_ENCRYPTION_KEY` is
`None`, encryption is simply off: the named columns above are stored and
read as plaintext, exactly as every milestone before this one already
does, with a loud, explicit startup log line naming this, logged at
**`WARNING`, not `INFO`** — a deliberate choice, see below. Encryption is
opt-in, not "on by default with a self-defeating fallback." The reasoning
is asymmetric with signing on purpose: a fresh, per-process signing key
that nobody else can verify against is an inconvenience; a fresh,
per-process **encryption** key that nobody else (including a future
instance of this same process, after a restart) can decrypt against is
irrecoverable data loss for every row written under it. Reusing M5's
pattern unchanged here would be applying a precedent to a case its own
underlying safety argument does not cover — named explicitly so a future
reader does not assume "we already solved this exact problem at M5" and
copy the wrong half of that solution.

**A related, narrower risk the "no ephemeral fallback" fix does not itself
prevent — a silent regression to plaintext if the key is removed after
having been enabled** (found during this document's own hostile-review
pass). The fix above correctly prevents the catastrophic case (a
silently-generated key nobody can ever reproduce). It does not prevent a
distinct, quieter one: an operator who has been running with
`FIELD_ENCRYPTION_KEY` set, and later unsets it — a configuration mistake,
a bad rollback, a secret-rotation step scoped to the wrong variable — gets
no hard failure. Per this section's own design, "unset" is a valid,
silently-accepted state; the application would simply resume writing *new*
rows to the same columns as plaintext, alongside historical ciphertext
rows, with only a startup log line marking the transition. **Recommendation:
log this specific state at `WARNING` severity, unconditionally, every time
the process starts with `FIELD_ENCRYPTION_KEY` unset** — not because
"encryption is off" is inherently a warning-worthy state on a fresh
deployment that has never used it, but because this platform has no way to
distinguish "encryption has never been configured" from "encryption was
just disabled" without adding a new, persisted marker this document
declines to build (the identical "no preemptive scaffolding for a problem
without a concrete forcing case" reasoning §12.9 already applies to chain-
checkpointing). A `WARNING`-level line on every affected startup is the
cheapest available mitigation that doesn't invent new infrastructure: it
does not prevent the regression, but it makes it far less likely to pass
unnoticed in whatever log-monitoring an operator already has, compared to
the `INFO`-level line the first draft proposed. Named explicitly as a
real, disclosed, only-partially-mitigated risk in §9 — not solved, flagged.

**Hash-chain interaction: hash-then-encrypt, not encrypt-then-hash** (§4/
§12.5). `EvidenceStore.append` computes `record_hash =
compute_hash(previous_hash, canonical_json(payload))` exactly as it does
today, over the **plaintext** payload dict — unchanged. Only the resulting
JSON string is then encrypted before being written to the `payload`
column. On read, `EvidenceStore._to_model` decrypts first (detecting
whether the stored value is ciphertext at all — see the backward-
compatibility marker below — falling through to treating it as plaintext
for a pre-M11 row), then proceeds to `json.loads` exactly as today.
**`verify_chain`'s own hash-recomputation *logic* needs zero changes** — it
already operates on `EvidenceRecord.payload`, the already-decrypted dict,
never on raw column bytes, confirmed directly against that module in §2.

**Corrected by this document's own hostile-review pass — this is not the
same as "`audit/verify_chain.py` needs zero code changes," which the first
draft claimed and which is false.** Traced directly against the actual
module: `verify_chain_from_database` constructs `EvidenceStore(engine)`
with no other argument, and neither `EvidenceStore.__init__` (which reads
no `Settings` and no environment variable itself — every existing
collaborator is either passed in explicitly by its caller or falls back to
a context-free default) nor `verify_chain.py`'s own bare-`argparse` `main()`
(two flags today: `--database-url`, `--public-key`) has any mechanism to
obtain `FIELD_ENCRYPTION_KEY` from anywhere. Left exactly as the first
draft specified, running `verify_chain.py` against an encryption-enabled
deployment does not degrade gracefully — `EvidenceStore._to_model`'s
`json.loads` raises an unhandled `json.JSONDecodeError` on the first
ciphertext row it reaches, a confusing crash, not a clear "this chain is
encrypted, provide a key" result.

**The minimal plumbing this actually requires**, specified now rather than
discovered at implementation time:

1. `EvidenceStore.__init__` gains a fourth optional collaborator,
   `encryptor: FieldEncryptor | None = None`, following the identical
   pattern `signer`/`resolver` already use — passed in explicitly by
   whichever caller has a real key to give it, defaulting to a no-op
   passthrough (never an auto-generated key — see this section's own
   "no ephemeral fallback" decision, which this parameter's default must
   not quietly reintroduce; see point 5 below for exactly what "no-op"
   means here) when not given.
2. `create_app()` constructs the real encryptor from
   `Settings.FIELD_ENCRYPTION_KEY` and passes it into `EvidenceStore(...,
   encryptor=...)`, the same two-line addition pattern every prior
   milestone's own composition-root wiring already follows (mirroring
   exactly how `load_signer(resolved_settings.SIGNING_PRIVATE_KEY, ...)`
   is wired today).
3. `verify_chain.py`'s `main()` gains a new, optional
   `--encryption-key` argument, threaded through
   `verify_chain_from_database(database_url, *, public_key_hex=None,
   encryption_key=None)` into the `EvidenceStore(engine, encryptor=...)`
   it constructs — the same shape `--public-key` already has, not a new
   argument-parsing pattern.
4. **A decrypt failure must raise a specific, catchable exception type**
   (e.g. `FieldDecryptionError`), never let Fernet's own `InvalidToken` or
   the resulting `json.JSONDecodeError` propagate raw. `verify_chain`'s own
   per-record loop (which already reports `first_corruption_at` for the
   first hash mismatch it finds, rather than crashing uncontrolled) can
   then catch this specific error and report "record N: cannot be read —
   `FIELD_ENCRYPTION_KEY` missing or incorrect" as its own, distinct
   `ChainVerificationResult.detail`, clearly distinguished from an actual
   hash-mismatch tamper finding. This is evidentiary content — unlike the
   free-text fields addressed below, a decrypt failure here must never be
   silently papered over with a placeholder value (that would mean lying
   about what the evidence chain contains); it must surface as a loud,
   specific, actionable failure, not an inscrutable crash.
5. **Marker detection happens before any encryptor is consulted, and is
   unconditional — specified precisely by this document's own third
   hostile-review pass, which found the first version's "no-op passthrough"
   description ambiguous enough to reintroduce the exact bug it was meant
   to fix.** `EvidenceStore._to_model` checks for the `"gpenc1:"` prefix
   itself, on every row, regardless of which `encryptor` was injected — a
   value with no prefix is always treated as legacy/unencrypted plaintext
   and never handed to the encryptor at all; a value *with* the prefix is
   always handed to `encryptor.decrypt(...)`, including when `encryptor`
   is the default no-key passthrough. That passthrough's `decrypt` method
   must therefore itself raise `FieldDecryptionError` for any input, never
   return it unchanged — a literal "pass the string straight through"
   no-op would silently hand raw ciphertext bytes to `json.loads`,
   reproducing the exact unhandled `json.JSONDecodeError` this document's
   second pass already corrected `verify_chain.py` to avoid (§12.5).
   "No-op" describes *no decryption capability*, not *no awareness of
   ciphertext* — the distinction earlier versions of this list left
   unstated.

None of this changes the underlying design decision (hash over plaintext,
encrypt the resulting string) — it corrects the claim that no code
follows from it. The one real, new **operational** cost, unaffected by
this correction and already worth naming plainly: **once encryption is
enabled, verifying the chain requires the symmetric decryption key, not
just the optional public signing key** — a materially more sensitive
credential requirement than today (an asymmetric public key is safe to
distribute broadly; a symmetric decryption key is not). A third party who
previously could verify this platform's chain integrity holding only the
public key can no longer do so once encryption is turned on, without also
being trusted with the confidentiality key. Recorded as a named
production-readiness consequence in §9, not hidden.

**Backward compatibility: a version-prefix marker, not a try/decrypt-and-
catch guess.** Every application-encrypted value is stored as
`"gpenc1:" + fernet_token`, never the bare token. A read path checks for
that literal prefix; its absence means "this value predates M11 (or
encryption was never enabled), read it as plaintext" — an explicit,
self-describing distinction, the same "make the record self-contained
rather than inferred" discipline `classification_snapshot` (M6) and
`parameters_used` (M8) already established, applied here to distinguishing
ciphertext from legacy plaintext rather than to a computation's inputs. No
backfill, no migration rewriting existing rows — encryption applies going
forward only, identical to M5's own "no retroactive signing of M0–M4
evidence" decision (§8, §12.6).

**Decrypt-failure containment for the free-text fields — specified using
M9's own established philosophy, not left open** (added by this document's
own hostile-review pass; the first draft never specified this at all). The
marker scheme is not perfectly collision-safe against the two remaining
encrypted free-text columns specifically (`resolution_notes` on both review
tables), because — unlike `evidence_chain.payload` (application-controlled
JSON) or `proxy_basis` (a small, application-controlled vocabulary) —
`resolution_notes` accepts arbitrary text from a caller, and M9's own
review named these endpoints as still unauthenticated. Nothing stops a
caller from submitting a value that happens to start with the literal
`"gpenc1:"` marker while encryption is off (or before it is ever turned
on); once encryption is later enabled, the read path would misidentify
that legacy plaintext as ciphertext and fail Fernet's own integrity check
(`InvalidToken`) when it tries to decrypt it. **Recommendation: contain
this exactly the way M9 already contains an analogous, unrelated failure**
— `_queue_verdict_review`'s own docstring: *"logged and swallowed, never
propagated."* A decrypt failure on `resolution_notes` specifically (never
`payload` — see the verifier-side containment above, which is deliberately
stricter, because that column *is* the evidentiary content, not a display
field) is logged (row id, table, no key material or partial ciphertext in
the log line) and the field is returned as a fixed placeholder (e.g.
`"[unreadable]"`) for that one row, never allowed to raise past the
repository boundary and take down an entire `GET /v1/admin/verdict-reviews`/
`GET /v1/admin/population-finding-reviews` list response over one bad
row. This mirrors the identical "one record's failure is logged and
counted, never allowed to abort reconciling the rest" discipline
`human_review/backfill_reviews.py` already holds itself to (`docs/milestones/M9.md`
§3.5) — applied here to a read-time decrypt failure instead of a write-time
reconciliation failure, but the same underlying principle: a failure in
this non-essential subsystem (rendering one free-text field) must never
take down what matters more (the rest of the list, and the review
workflow's other, correctly-stored fields).

### 5.2 Retention tiers

**Scope: exactly two tables, `shadow_findings` and
`protected_attribute_resolutions`** — the only tables in this schema that
are simultaneously (a) not part of the hash chain or any other
tamper-evident guarantee, and (b) not, after §5.3 ships, locked against
deletion at the database-privilege level. `shadow_findings` was never
evidentiary by design (M3: "a shadow policy's output can never be mistaken
for one that actually governed a decision"); `protected_attribute_resolutions`
is, by its own M2 docstring, "derived, reconstructible data" — re-running
the resolver over the same (still-present) `DecisionEvent` reproduces it,
**so long as `protected_attribute_rules` hasn't changed for that domain/
attribute since the original resolution — a real, disclosed caveat on this
claim, not an unconditional guarantee; see §4.4, added by this document's
own third hostile-review pass.** The *raw* attribute values this
classification was computed over are never at risk regardless — they
persist forever in `decision_events.protected_attribute_refs` and
`evidence_chain.payload`, neither of which retention ever touches — so a
purged row always remains re-derivable in the sense that matters most for
this platform's evidentiary guarantees, even on the rare path where it
would not reproduce byte-for-byte identically to what was originally
computed.

**Explicitly not in scope, per §4.2**: `evidence_chain`, `population_findings`,
and — once §5.3 locks them down — `systems`, `model_versions`,
`decision_events`, `findings`, `verdicts`, `verdict_findings`. Deleting old
rows from the normalized operational tables while `evidence_chain.payload`
retains a full, permanent copy of the same content would not reduce this
platform's actual data footprint, only its queryable surface — this
document declines to build that half-measure and call it "retention"
(§4.2).

**Mechanism: a new, explicitly-invoked CLI**, `python -m
gov_platform.retention.purge_expired_records`, mirroring
`population_engine/run_policies.py`'s and
`human_review/backfill_reviews.py`'s existing shape exactly: no daemon, no
in-process scheduler — this platform has zero always-running background
processes anywhere today, and M6 §13.4/M7 §13.6 have already each declined
to introduce the first one for their own milestone's batch/aggregation
needs. Real scheduling (cron, a Kubernetes `CronJob`) remains
deployment-topology scope, architecture §17/M13, unchanged.

**Per-table, configurable retention windows** via new `Settings` fields —
`RETENTION_DAYS_SHADOW_FINDINGS: int | None = None`,
`RETENTION_DAYS_PROTECTED_ATTRIBUTE_RESOLUTIONS: int | None = None` — **no
numeric default, corrected by this document's own hostile-review pass.**
The first draft proposed `90`/`365` as "sane, documented defaults" without
citing anything they were sane *relative to* — a real inconsistency with
this project's own standing discipline: every other governance-sensitive
numeric constant this platform has ever shipped cites a real external
standard (the EEOC four-fifths ratio and its `_MINIMUM_GROUP_SIZE = 30`
floor, M6; the CFPB 0.43 debt-to-income threshold, M4, whose own design
doc warned that an invented number would repeat "the exact governance
smell M2's review flagged"; the *Castaneda*-convention `z_critical = 2.0`,
M8). No such standard exists for "how long may a shadow-policy comparison
or a protected-attribute classification legitimately persist" — this is an
operational/legal/business decision specific to a real deployment, not
something this review can source a defensible number for. **Recommendation:
both settings are optional with no default; retention for a given table is
simply disabled (the purge tool's own CLI, invoked with no configured
window for that table, is a no-op for it, logged as such) until an
operator explicitly sets a value** — the identical "no key configured
means the feature is off, not silently guessing" shape §5.1 already uses
for `FIELD_ENCRYPTION_KEY`, applied here to a retention period instead of
an encryption key, for internal consistency within this same document
rather than a second, different convention for "unconfigured."

This mirrors the same "admin-configurable, with a documented fallback"
shape M8 established for population-policy parameters in spirit (a
process-wide setting rather than a per-binding one — no
`PopulationWindow`-style per-invocation threading is needed, since there is
no per-system or per-policy variation to this decision, matching the "no
second case to justify plurality" reasoning in §1) but not in the specific
detail of *what* the fallback is: M8's policies fall back to a real,
cited default (the EEOC ratio, the Castaneda z-critical); retention has no
equivalent to fall back to, so its "documented fallback" is "disabled,"
not a guessed number.

**This interacts with the disclosure in §4.3**: once a retention window is
configured and the purge tool has run, `GET /v1/admin/metrics?since=` (M7)
can silently undercount shadow-policy disagreement for any query window
older than that setting — named there, not repeated in full here, but the
two sections should be read together before an operator configures a
retention period for `shadow_findings` specifically.

**Privilege model — the tool runs under a separate, more-privileged
connection, never the app's own runtime role** (§5.3, §12.11): mirrors
`db/migrate.py`'s and `Settings.DATABASE_URL`'s own already-established
precedent for exactly this kind of ops-time, elevated-privilege operation.
`purge_expired_records`'s CLI takes `--database-url` as an explicit
argument (not a `Settings` field, the identical reasoning
`Settings.DATABASE_URL`'s own docstring already gives for keeping migration
credentials out of the app's runtime configuration), pointed at a
connection with `DELETE` privilege on the two retention-eligible tables —
operationally, the same owner/migration-privileged credential this
platform's operators already hold for `db/migrate.py`, not a new,
fourth credential tier.

**Idempotency and safety**: for each table with a configured retention
window, each invocation deletes rows strictly older than
`now() - retention_days`; a table with no configured window is skipped
entirely, logged as such, not silently defaulted to some assumed period.
Every run logs a structured summary (row count, table, cutoff timestamp —
mirroring `observability/logging.py`'s existing JSON-formatted convention),
and is safe to re-run at any cadence — a run against an already-purged
table is a clean no-op, the identical idempotency bar
`human_review/backfill_reviews.py` already holds itself to. No new
persisted "last purged at" state is created — the operation is naturally
idempotent from its own cutoff-timestamp logic alone, so nothing extra
needs tracking.

### 5.3 Privilege classification for the Evidence Store

**Extend `REVOKE UPDATE, DELETE` to `systems`, `model_versions`,
`decision_events`, `findings`, `verdicts`, and `verdict_findings`** — the
exact fix `docs/milestones/M9.md` §9.5 disclosed and explicitly deferred,
implemented now as this milestone's own named job. Verified directly, not
assumed, that no existing code path issues an `UPDATE` or `DELETE` against
any of these six tables (every write to them happens exactly once, inside
`EvidenceStore.append`'s single INSERT-only transaction, and no repository
anywhere exposes an update/delete method for any of them) — this lockdown
changes zero application behavior, the identical "verified this is a strict
tightening with no existing caller affected" discipline M1 originally
applied to `evidence_chain` itself.

**Also revoke `DELETE` (and, since neither table is ever updated after
insertion either, `UPDATE`) from the ordinary `gov_platform_app` role on
`shadow_findings` and `protected_attribute_resolutions`** — a deliberate
tightening beyond what M2/M3 originally granted, not a correction of a
defect in those milestones (their "ordinary, admin-mutable operational
table" grant was the right call at the time; neither table had a retention
mechanism yet to reserve deletion capability for). The continuously
running, unauthenticated-everywhere (still `M13`) application process
should hold no deletion capability over any evidentiary or
retention-governed table — only the retention tool's own
separately-credentialed connection can ever delete a row from
`shadow_findings`/`protected_attribute_resolutions`, and no connection the
running app itself uses can delete from any of the other eight. This
completes "privilege classification" as a real, load-bearing security
property rather than a documentation exercise, over the specific set of
tables this milestone actually classifies: by the end of this milestone,
every table this document treats as evidentiary-or-retention-governed (ten
tables total) is either (a) permanently append-only for the running
application (the eight evidentiary/Evidence-Store tables) or (b)
mutable-but-never-deletable by the running application, deletable only
through the retention tool's own connection (`shadow_findings`,
`protected_attribute_resolutions`).

**Corrected by this document's own third hostile-review pass: this is not
the same claim as "the application role holds no deletion capability
anywhere in this schema," which earlier versions of this section stated
and which is false.** Six ordinary admin-configuration tables —
`plugin_registrations`, `policy_bindings`, `protected_attribute_rules`,
`population_policy_bindings`, `verdict_reviews`, `population_finding_reviews`
— retain the full `DELETE` grant given at their own originating migration
(`0010`, `0011`, `0012`, `0014`, `0023`, `0024` respectively), confirmed
directly against each file; M11 does not touch any of those grants, and
does not need to — none of these six is retention-eligible or
evidentiary, each is genuinely admin-mutable operational config (even
though, per §12.16, no code path exercises `DELETE` against any of them
today), and revoking `DELETE` from any of them would be an unrequested,
out-of-scope tightening this milestone's own citation trail gives no basis
for. "Unchanged by this milestone" and "never deletable" cannot both be
true of the same six tables — earlier versions of this section asserted
both at once. The corrected claim is scoped to exactly the ten tables this
milestone actually classifies as evidentiary or retention-governed, not to
"this schema" as a whole.

## 6. Database schema changes

**No new table.** Still two migrations — **regrouped, not increased in
count, corrected by this document's own hostile-review pass**: the first
draft bundled all eight `REVOKE` statements (six high-risk, two low-risk)
into `0025` and left `0026` as indexes only; the corrected grouping moves
the two low-risk `REVOKE`s into `0026` alongside its own indexes, so each
file's statements share one risk profile, not two (see §6/§8's
migration-lock discussion below for why the grouping itself, not merely
the SQL, needed to change) — each single-purpose within its own risk
profile, matching the one-migration-one-change convention M6/M7/M8
established:

```sql
-- 0025_lock_down_evidence_store_tables.sql
-- Closes docs/milestones/M9.md §9.5's disclosed gap: these six tables
-- write exactly once per governed decision (inside EvidenceStore.append's
-- single transaction) and are never updated or deleted by any existing
-- code path -- verified directly, not assumed. Matches evidence_chain's
-- (migration 0008) and population_findings' (migration 0015) own
-- privilege treatment.
--
-- OPERATOR NOTE (see docs/milestones/M11.md §6/§8): GRANT/REVOKE on a
-- table takes an ACCESS EXCLUSIVE lock in PostgreSQL -- the same class of
-- lock ordinary ALTER TABLE DDL takes -- conflicting with every concurrent
-- statement against that table, including plain SELECT, and (per
-- PostgreSQL's lock-queue ordering) blocking new transactions that arrive
-- while it waits. decision_events specifically is touched by every single
-- ingestion request this platform serves. Apply this migration during a
-- planned, low-traffic maintenance window, the same operational discipline
-- any ACCESS-EXCLUSIVE-requiring DDL against a request-path table needs --
-- not silently assumed to be as cheap as an ordinary additive migration.
-- Kept as one transaction deliberately, not split per table: a partially
-- applied lockdown (some of the six tables locked, some not) is a worse,
-- more confusing intermediate state than a single, scheduled, atomic cutover.
REVOKE UPDATE, DELETE ON systems FROM gov_platform_app;
REVOKE UPDATE, DELETE ON model_versions FROM gov_platform_app;
REVOKE UPDATE, DELETE ON decision_events FROM gov_platform_app;
REVOKE UPDATE, DELETE ON findings FROM gov_platform_app;
REVOKE UPDATE, DELETE ON verdicts FROM gov_platform_app;
REVOKE UPDATE, DELETE ON verdict_findings FROM gov_platform_app;
```

```sql
-- 0026_harden_retention_eligible_tables.sql
-- Regrouped from the first draft's separate "0025 tail" and "0026" files:
-- these two tables share the same low-risk profile (bounded, low-write-
-- volume operational tables -- shadow comparison output and per-decision
-- attribute resolutions, not decision_events-scale ingestion traffic), so
-- their own privilege tightening and their own new indexes belong together,
-- deliberately separate from migration 0025's much higher-risk lockdown
-- above. Safe to apply at any time, no maintenance window required.
--
-- Retention-eligible tables keep INSERT/SELECT for the running app, but
-- lose DELETE (and UPDATE, since neither is ever updated post-insert
-- either) -- only the retention tool's own, separately-credentialed
-- connection may ever delete a row from either (see docs/milestones/M11.md
-- §5.2/§5.3).
REVOKE UPDATE, DELETE ON shadow_findings FROM gov_platform_app;
REVOKE UPDATE, DELETE ON protected_attribute_resolutions FROM gov_platform_app;

-- Supports "delete rows older than :cutoff" for the new retention CLI --
-- neither table has an index shaped for a time-bounded scan today, the
-- identical situation M6 §6/M7 §6 were each in for their own new query
-- patterns.
CREATE INDEX idx_shadow_findings_evaluated_at
    ON shadow_findings (evaluated_at);
CREATE INDEX idx_protected_attribute_resolutions_resolved_at
    ON protected_attribute_resolutions (resolved_at);
```

No `ALTER` of any column type or nullability, no constraint change, no
data rewrite. This is the smallest schema footprint of any milestone since
M4 ("no schema changes are needed" — M4 §6) — everything M11 adds is
privilege grants and indexes, not new structure. Application-level
encryption (§5.1) requires **no migration at all**: the encrypted value
(a `"gpenc1:"`-prefixed Fernet token) is still a string, and every column
§5.1 names is already `TEXT` or unbounded `String` — no length constraint
anywhere in this schema forces a column-width change to accommodate the
size overhead Fernet's authenticated-encryption framing adds.

## 8. Migration strategy

Two purely additive migrations (§6), applied in the same numbered,
idempotent-runner sequence every migration since M1 has used
(`db/migrate.py`, no Alembic). Both are safe to apply against a live,
already-populated database with zero data-loss or *steady-state* behavior
change for any existing code path — but the two migrations carry
meaningfully different **transient** risk, corrected and separated in this
document's own hostile-review pass (the first draft applied `0026`'s lock/
blast-radius scrutiny to its own low-volume-table indexes and never applied
the equivalent scrutiny to `0025`'s privilege change against this
platform's actual highest-throughput tables):

- **`0025`'s `REVOKE` statements** affect only which SQL statements
  `gov_platform_app` is permitted to issue going forward — they do not
  touch a single existing row, and (per §5.3's direct verification) no
  existing code path ever issues the now-forbidden statements against any
  of the six affected tables, so *once applied*, this migration changes
  zero observable application behavior for any request that succeeded
  before it and will still succeed identically after. **What the first
  draft omitted: applying it.** `GRANT`/`REVOKE` on a Postgres table
  acquires an `ACCESS EXCLUSIVE` lock — the most restrictive lock mode
  available, conflicting with every other lock mode including the plain
  `ACCESS SHARE` an ordinary `SELECT` takes. `decision_events`,
  `findings`, and `verdicts` are this platform's actual highest-write-
  volume, request-path-critical tables — `decision_events` specifically is
  written by every single ingestion request this platform serves. Applying
  `0025` against a live, actively-serving deployment can therefore stall
  in-flight and newly-queued requests against these tables for the
  migration's transaction duration, exactly the class of availability risk
  `0026`'s own analysis (below) already reasons about for its own,
  much smaller tables. **Recommendation, corrected: apply `0025`
  during a planned, low-traffic maintenance window**, the same discipline
  any ACCESS-EXCLUSIVE-requiring DDL against a request-path table already
  requires in ordinary Postgres operational practice — named here as an
  explicit deployment requirement, not left implicit the way the first
  draft left it unstated entirely. This is also why `0025` stays one
  migration/one transaction across all six tables rather than being split
  further: a scheduled, atomic, all-six-at-once cutover is a better outcome
  than a partially-locked-down intermediate state achieved by splitting the
  six `REVOKE`s across separate migrations, even though splitting them
  would reduce any single transaction's peak lock footprint.
- **`0026`'s `REVOKE` statements and new indexes** are regrouped,
  deliberately, away from `0025` — `shadow_findings` and
  `protected_attribute_resolutions` are bounded, low-write-volume
  operational tables (shadow comparison output and per-decision attribute
  resolutions), not `decision_events`-scale ingestion traffic, so the
  identical `ACCESS EXCLUSIVE` lock these statements also require is a
  non-event in practice — the same reasoning M8 §4.4 already accepted for
  `population_policy_bindings`' own index. No maintenance window required
  for this migration specifically. `db/migrate.py`'s own single-transaction-
  per-migration design makes `CREATE INDEX CONCURRENTLY` illegal here
  regardless, the identical constraint M8 §4.4 already verified directly
  against that runner's code.

Encryption (§5.1) needs **no migration of its own** and, critically, **no
backfill of any existing row** — every pre-M11 value in every column §5.1
names remains exactly as it is today (plaintext, no `"gpenc1:"` prefix)
until it is next written, which for `evidence_chain`/`verdict_reviews`/
`population_finding_reviews`/`protected_attribute_resolutions` never
happens again after the row's initial insert (all four are write-once by
design). This means, stated plainly: **turning on `FIELD_ENCRYPTION_KEY`
for the first time encrypts nothing that already exists — only rows
written from that point forward.** An operator wanting every historical
row encrypted would need a separate, explicit re-encryption tool this
document does not build (the identical "a genuine 'recompute under new
rules' capability is a legitimate, different feature, explicitly not
built here" boundary M6 §13.16 drew for population findings, applied here
to encryption instead of classification rules) — named as a real,
disclosed limitation in §11, not silently implied to be comprehensive.

Retention's own migrations are the only schema changes this milestone
needs; the purge tool itself requires no migration to run — it is
ordinary CLI application code operating through a connection string
supplied at invocation time, the same as `db/migrate.py` and
`human_review/backfill_reviews.py` already are.

## 9. Production-readiness implications

- **Encryption is opt-in and off by default** — a real deployment must
  explicitly set `FIELD_ENCRYPTION_KEY` to get any confidentiality benefit
  from §5.1's tier two; the storage-level requirement (tier one) must be
  separately verified by whoever provisions the external Postgres instance.
  Neither happens automatically, and this document does not pretend
  otherwise — mirroring `README.md`'s own existing "synthetic data only"
  caveat discipline (extended to name this milestone's own gap explicitly,
  not silently folded into the existing sentence).
- **`reviewer` (on both `verdict_reviews` and `population_finding_reviews`)
  is never encrypted, and cannot be under this milestone's chosen
  mechanism** (§4.1/§5.1, corrected by this document's own hostile-review
  pass) — protected only by tier one (storage-level encryption), the same
  as every column not in §5.1's named list. This is worth stating with the
  same plainness M9's own review used for the identical value: `reviewer`
  is *"a specific, named person's professional judgment about a real bias
  finding"* — the single most sensitive value this table holds — and it is
  exactly the one this milestone's mechanism cannot protect at the
  application layer without a different, bespoke construction
  (deterministic or blind-indexed encryption) this document does not
  build. Named as a real, disclosed limitation, not a cost-free exclusion.
- **A real, named cost to chain-verification distributability** (§5.1,
  §12.5): once encryption is enabled, `verify_chain`'s CLI needs the
  symmetric decryption key to read anything at all (via the new
  `--encryption-key` argument specified in §5.1), a materially more
  sensitive credential requirement than today's optional, safely-shareable
  public signing key. An operator who previously distributed the public
  key to a third-party auditor for independent chain verification cannot
  continue that practice unchanged once encryption is on, without also
  extending trust in the confidentiality key.
- **Fernet does not hide plaintext length** (§5.1) — a real, if narrow,
  ceiling on tier two's confidentiality guarantee for the low-entropy,
  small-vocabulary columns this milestone protects. A direct-database
  reader can sometimes infer which of a small set of plausible values a
  row holds from ciphertext length alone, without the key. Named as a
  disclosed limitation of the chosen mechanism, not a reason to reject it.
- **Migration `0025` requires a planned maintenance window, not a routine
  additive-migration deploy** (§6/§8, corrected by this document's own
  hostile-review pass) — its `REVOKE` statements against `decision_events`,
  `findings`, `verdicts`, and their three siblings acquire `ACCESS
  EXCLUSIVE` locks against this platform's actual highest-throughput,
  request-path tables, and can stall live ingestion traffic for the
  migration's duration if applied without one. Migration `0026`'s own
  privilege/index changes carry no equivalent risk and need no such window.
- **Retention on `shadow_findings` silently degrades M7's own
  `GET /v1/admin/metrics?since=` for query windows older than the
  configured retention period** (§4.3, found during this document's own
  hostile-review pass) — a real, disclosed, not-fixed interaction between
  two otherwise-independent milestones. An operator who configures
  retention for `shadow_findings` should not treat old `?since` queries
  against `shadow_disagreement_rate_by_policy` as trustworthy once
  retention has actually purged the underlying rows.
- **Retention on `shadow_findings`/`protected_attribute_resolutions` is a
  genuine, if partial, reduction in this platform's PII footprint** — the
  first milestone since M0 to actually delete anything, ever, from this
  schema, and (corrected by this document's own hostile-review pass) only
  once an operator explicitly configures a retention window for a given
  table — there is no default period, per §5.2's own corrected reasoning.
  Stated with equal plainness: retention on the normalized operational
  tables (`decision_events` et al.) was considered and explicitly declined
  (§4.2) because `evidence_chain.payload`'s permanent embedded copy would
  make it cosmetic — an operator should not read this milestone as having
  solved "how do we ever actually delete an applicant's data," only "how
  do we bound the two tables where deletion is both safe and complete."
- **A decrypt failure on a free-text field degrades to a placeholder for
  that one row, never a crashed list response** (§5.1) — specified using
  the identical per-record containment philosophy M9's reconciliation tool
  already established, rather than left unspecified. A decrypt failure on
  `evidence_chain.payload` specifically is handled differently and more
  strictly — it is evidentiary content, so it surfaces as a loud, specific,
  catchable error (distinguished from an actual tamper finding), never a
  silently-substituted placeholder.
- **A silent regression to plaintext if `FIELD_ENCRYPTION_KEY` is removed
  after having been enabled** (§5.1, found during this document's own
  hostile-review pass) — an operator configuration mistake, not a code
  defect, but one this platform has no way to detect without new,
  out-of-scope machinery. Mitigated only by logging this state at
  `WARNING` (not `INFO`) severity on every affected startup — a partial,
  disclosure-based mitigation, not a prevention.
- **No authentication anywhere** — unaffected by this milestone, still
  `M13`, now a ninth-consecutive-milestone gap (M10 named itself the
  eighth). Named again because encrypting `resolution_notes` addresses
  confidentiality against a compromised database, not against the standing
  fact that any caller, authenticated or not, can already read that value
  (and `reviewer`, never encrypted at all — see above) through the
  existing, unauthenticated Admin API endpoints that return them in
  plaintext over HTTP. Encryption at rest and authorization to read are
  orthogonal controls; this milestone builds only the former.
- **The retention tool's elevated credential is a new, real operational
  secret this platform's deployment story must manage — and, unlike the
  migration-owner credential it reuses, one that must now be available on
  a recurring schedule, not only at deploy time** (§12.11, expanded by this
  document's own hostile-review pass). A migration credential is used
  rarely, transiently, under direct supervision; retention (§5.2) is
  designed to run on a recurring cron/`CronJob` cadence, meaning this same
  schema-owning secret must live persistently in whatever system runs that
  schedule — a materially larger, more routine exposure window than the
  document's original complexity-avoidance framing considered. See §12.11
  for the full, expanded reasoning and why this document still does not
  mandate a narrower role.
- **Chain-checkpointing for `evidence_chain`/`population_findings` retention
  remains completely unbuilt** (§4.2, §12.9) — the single largest
  disclosed gap this document leaves open, and the most likely reason a
  future milestone would need to revisit this one specifically, should a
  concrete legal retention-period requirement or a real storage-cost
  pressure ever force the question.
- **The application role's privilege lockdown applies to exactly ten
  tables, not to this schema as a whole** (§1/§5.3, corrected by this
  document's own third hostile-review pass) — the eight evidentiary
  Evidence-Store tables are permanently append-only for the running
  application, and `shadow_findings`/`protected_attribute_resolutions` are
  deletable only through the retention tool's own separate connection. Six
  ordinary admin-configuration tables (`plugin_registrations`,
  `policy_bindings`, `protected_attribute_rules`,
  `population_policy_bindings`, `verdict_reviews`,
  `population_finding_reviews`) retain the full `DELETE` grant given at
  their own originating migration, unchanged — a deliberate, correct scope
  boundary, not a gap, but one earlier versions of this document
  mischaracterized as "no deletion capability over anything in this
  schema at all."
- **Retention's inclusion of `protected_attribute_resolutions` rests on a
  "reconstructible" premise that is conditional, not absolute** (§4.4,
  found during this document's own third hostile-review pass) — true only
  as long as `protected_attribute_rules` hasn't changed for the relevant
  domain/attribute since the original resolution. Nothing in today's Admin
  API exercises that mutability, so the practical risk is low today, but
  it is real: a future rule-correction endpoint, or direct database access
  exercising the `UPDATE`/`DELETE` grant `protected_attribute_rules`
  already has, would silently make a retention-purged row's original
  classification unrecoverable, with no snapshot mechanism (unlike
  `population_findings.classification_snapshot`) to fall back on. The raw
  attribute values remain permanently recoverable regardless (§4.4).
- **`FIELD_ENCRYPTION_KEY` requires a specific encoding
  (`Fernet.generate_key()`'s own base64 output), not the hex convention
  `SIGNING_PRIVATE_KEY` uses** (§5.1, found during this document's own
  third hostile-review pass) — an implementation detail earlier versions
  of this document left unspecified while actively implying the two keys
  were interchangeable in shape.

## 12. Architectural ambiguities, each with a recommendation and justification

### 12.1 — Is "encryption at rest" satisfied by storage-level encryption alone, application-level field encryption alone, or both? **(the highest-stakes call in this document)**

Options: **(a)** storage/volume-level only — the standard, literal reading,
requires zero application code, but this repository does not itself
provision the Postgres instance to encrypt (§2, §4/§5.1), so "building" it
here means only documentation. **(b)** application-level field encryption
only — protects against a compromised credential/leaked backup regardless
of the underlying disk's own encryption state, but (per §4.1) cannot cover
every sensitive column without breaking the Event Lake. **(c)**
(recommended) both, each covering a threat the other does not: storage-level
as a documented, verified-at-deploy-time requirement (the honest ceiling of
what this repository's own code can guarantee, given it doesn't provision
Postgres); application-level for the fixed, named, SQL-safe subset of
columns, as genuine defense in depth against a scenario storage encryption
alone does not address (a live, credentialed reader).

**Recommendation: (c).** Neither tier alone satisfies what "encryption at
rest" is generally understood to mean for a platform handling real
protected-attribute data, and this platform's own citation trail (§0) never
narrows the phrase to one specific mechanism, leaving room to combine both
without contradicting anything already committed. **This requires your
explicit sign-off** — if a real `ARCH-GOV-002` document specifies a single,
particular mechanism (e.g., mandates a specific KMS-integrated column
encryption product), that is the one finding in this document most likely
to require a materially different design, not a parameter tweak.

### 12.2 — Should `decision_events.input_features` receive application-level encryption alongside the other named fields?

Unlike `protected_attribute_refs`/`decision_output`, `input_features` is
never referenced by any existing SQL query today — confirmed directly.
Options: **(a)** include it in §5.1's encrypted list — the safe, "encrypt
everything not proven unsafe" reading. **(b)** (recommended) exclude it,
deliberately, alongside its two siblings on the same row. **Recommendation:
(b).** `input_features` sits on the exact same `decision_events` row as the
two columns the Event Lake already reaches into by SQL, and a future
milestone extending `population_engine/window.py` to key on model input
features (a plausible, not far-fetched, extension — e.g., a fairness check
scoped to a specific feature range) would hit the identical breakage §4.1
found for its siblings, except silently, since nothing today would flag
that this column was ever encrypted. Treating all three `decision_events`
JSON columns identically — none application-encrypted, all covered only by
storage-level encryption — is a more conservative, more consistent
posture than encrypting two-thirds of a row's sensitive columns and
leaving the third exposed to a different future failure mode. This is a
real, disclosed reduction in defense-in-depth coverage for `input_features`
specifically, not a cost-free decision — flagged for your explicit
awareness rather than presented as an obvious inclusion or exclusion either
way.

### 12.3 — Does the new encryption key need rotation or KMS/HSM-backed custody, given signing already declined this?

**Recommendation: no**, unchanged from M5 §13.8's own reasoning for the
signing key, applied consistently: this platform has no second deployment
environment to design real key custody against, and a single, static,
env-loaded secret is the same scope boundary every other credential in this
codebase already accepts (the signing key itself, database credentials).
Building rotation for the *new* key while the *existing* signing key still
has none would be an inconsistent, arbitrary hardening of one secret over
an equally sensitive other.

### 12.4 — Should the encryption key have an ephemeral, auto-generated fallback when unset, mirroring the signing key's own precedent? **(found during this document's own hostile-review pass — the most severe finding in it)**

Already argued in full in §5.1/TL;DR finding 3. **Recommendation: no
ephemeral fallback, ever.** A signing key with no configured value
generates fresh and signs fine within one process's lifetime — the only
cost is an inability to cross-verify across processes, a real but bounded,
recoverable limitation. An encryption key with the identical fallback would
encrypt real data under a key that exists nowhere durable, and lose access
to that same data on the next process restart — an unrecoverable,
self-inflicted data-loss bug masquerading as a graceful default. **This
does not require your sign-off in the sense of a genuine open question** —
it is a direct, mechanical consequence of the two features' different
failure semantics, the same category of "does not need approval, it is the
only safe answer" M10 §8.6 already used for its own construction-failure
containment finding — but it is flagged this prominently because it is the
one place in this document where blindly reusing an already-approved prior
milestone's own pattern would have been actively wrong, worth a reader's
explicit attention even without a real decision to make.

**A related, narrower gap this fix does not close on its own, found during
this document's own second hostile-review pass**: "no ephemeral fallback"
prevents silent key *generation*, not a silent key *removal* after
encryption has already been enabled — see §5.1/§9's disclosed, only-
partially-mitigated downgrade risk (a `WARNING`-level startup log is the
recommended mitigation, not a prevention). Recorded here rather than as a
separate ambiguity, since it is the same underlying key-lifecycle question
this item already owns, just at its other end.

### 12.5 — Does encrypting `evidence_chain.payload` require any change to `audit/verify_chain.py`? **(reversed from the first draft — hostile-review pass)**

**The first draft's "no" was wrong, not merely incomplete.** The
hash-recomputation *logic* is correctly untouched — `verify_chain`'s
existing recomputation already operates on the decrypted
`EvidenceRecord.payload` dict, never on raw column bytes, confirmed
directly against that module (§2) — but the module as a whole is not
"unchanged": `verify_chain_from_database` constructs `EvidenceStore(engine)`
with no other argument, and neither that constructor nor `verify_chain.py`'s
own bare-`argparse` `main()` has any mechanism today to obtain
`FIELD_ENCRYPTION_KEY`. Run exactly as the first draft specified, this
tool does not fail gracefully against an encryption-enabled deployment —
`EvidenceStore._to_model`'s `json.loads` raises an unhandled
`json.JSONDecodeError` on the first ciphertext row it reaches.

**Recommendation: yes, three specific, minimal changes** (detailed in
§5.1): `EvidenceStore.__init__` gains an optional `encryptor` collaborator,
following the exact pattern `signer`/`resolver` already use;
`verify_chain.py`'s `main()` gains a new, optional `--encryption-key`
argument, threaded through to that collaborator, the same shape
`--public-key` already has; and a decrypt failure raises a specific,
catchable exception type rather than letting `InvalidToken`/
`JSONDecodeError` propagate raw, so `verify_chain`'s own per-record loop
can report "record N: cannot be read" as a distinct result from an actual
hash-mismatch tamper finding. None of this changes what a *correctly-keyed*
verification run reports, or reopens any decision about the hash-chain
algorithm itself (`audit/hash_chain.py` is untouched) — it is new,
necessary plumbing for a code path the first draft asserted needed none.
The real, named operational cost is unchanged by this correction and
remains real: `verify_chain_from_database`'s CLI now needs
`FIELD_ENCRYPTION_KEY` (or the new `--encryption-key` argument) supplied
whenever encryption is enabled, since it constructs a real `EvidenceStore`
to read `payload` at all — a genuinely more sensitive credential
requirement than today's optional public-key-only verification, named
plainly in §9, not hidden as a footnote.

### 12.6 — Does M11 retroactively encrypt or re-sign any existing row?

**Recommendation: no**, mirroring M5's own "signing applies going forward
only, no retroactive signing of M0–M4 evidence" decision exactly (§8). A
signature/encryption asserts something true about the moment a record was
written; computing either retroactively over data that predates the
mechanism's existence would assert something false, or (worse, for
encryption specifically) require decrypting nothing and encrypting
already-plaintext historical rows in place — a real, invasive rewrite of
supposedly-immutable evidentiary tables this document has no reason to
attempt, especially now that §5.3 locks several of them against `UPDATE`
entirely.

### 12.7 — Does closing M9 §9.5's privilege gap belong in M11, or does it deserve its own dedicated milestone?

M9 §9.5 itself recommended "a dedicated review of exactly which tables
should gain the lockdown" without naming which future milestone that
would be. **Recommendation: M11**, on direct textual grounds: M11's own
citation trail names "privilege classification for the Evidence Store" as
its third pillar, and the six tables M9 §9.5 flagged are precisely "the
Evidence Store" in the operational sense — the normalized tables
`EvidenceStore.append` writes to every time it runs. Treating this as a
separate, later milestone would mean inventing a tenth architecture-section
citation with no textual basis, when M11's own name already covers it
directly.

### 12.8 — Given the privilege lockdown, can retention still apply to `decision_events`/`findings`/`verdicts` via the retention tool's own elevated connection (which bypasses the ordinary role's revoked privileges anyway)?

A real question: the retention tool's elevated connection could
technically `DELETE` from any table, including the six newly-locked ones —
the `REVOKE` in §6 only restricts `gov_platform_app`, not the
migration-privileged role the retention tool uses. **Recommendation: no —
deliberately do not exercise that technical capability.** The privilege
lockdown in §5.3 is a statement about what these tables *are*
(append-only evidentiary records, matching `evidence_chain`), not merely
about which role happens to hold which grant — using a different,
more-privileged connection to delete from them anyway would defeat the
entire point of classifying them this way in the first place, and would
recreate exactly the cosmetic-retention problem §4.2 already rejected (a
`decision_events` row's deletion doing nothing to remove the same data
still embedded in `evidence_chain.payload`). The elevated connection exists
specifically and only for `shadow_findings`/`protected_attribute_resolutions`
— using it more broadly is explicitly out of scope, not merely unbuilt.

### 12.9 — Should M11 build any preliminary scaffolding toward future chain-checkpointing (e.g., a placeholder `checkpoint` table, an unused column), so a later milestone has less to design from scratch?

**Recommendation: no.** This would be exactly the "add a preemptive,
unused column/table just in case" pattern M5 §9 explicitly declined for
signing ("no preemptive, unused `signature`/`signing_key_id` columns are
added to either table now 'just in case'... a future milestone that does
decide to sign resolutions gets its own migration then") — applied here to
a checkpoint mechanism instead of signing. Building scaffolding for a
design this document has not actually worked out (what a checkpoint
attests to, how it is itself protected, how a partial-chain verifier
consumes one) risks locking in the wrong shape before a concrete forcing
requirement exists to design correctly against. The gap is named loudly in
§9/§11 instead — a disclosed absence, not a guessed-at partial solution.

### 12.10 — Does M11 need a new Admin API endpoint to trigger retention on demand, or report encryption/retention configuration?

**Recommendation: no**, mirroring `run_policies.py`/`backfill_reviews.py`'s
own precedent exactly (§1, §7): both are explicitly-invoked CLI tools with
no HTTP trigger, and this project has never added an Admin endpoint whose
only purpose is to kick off an existing CLI's own logic a second way. A
future `GET /v1/admin/metrics` addition reporting "rows pending purge" or
"encryption enabled: true/false" is a plausible, small follow-up (the same
category of addition M7 §13.12's staleness metric was for M6's own async
plane) — not built here, absent a concrete operational need demonstrating
this milestone's own CLI output/logs are insufficient.

### 12.11 — Should the retention tool's elevated database connection be a distinct new Postgres role, or reuse the existing migration-owner credential? **(reasoning expanded by this document's own hostile-review pass)**

**Recommendation, unchanged in conclusion: reuse the existing migration-
owner/superuser credential operators already hold for `db/migrate.py`** —
no new Postgres role is created by this milestone. Inventing a fourth
credential tier (application role, migration-owner role, and now a
retention-specific role) for a capability that is already a strict subset
of what the migration-owner role can already do would be complexity with
no corresponding safety benefit this document can point to.

**The reasoning above was incomplete, not wrong, and needed a real
addition, found during this document's own hostile-review pass**: it
weighs *complexity* (avoiding a fourth credential tier) without weighing
*usage pattern*. A migration credential is provisioned for rare,
supervised, deploy-time events — used transiently, then idle. Retention
(§5.2) is explicitly designed to run on a **recurring** schedule (an
operator's own cron/`CronJob`). Reusing a full schema-owning credential for
a routinely-scheduled automated job is a materially different exposure
than "used once during a deploy": that secret must now live persistently
in whatever system runs the schedule, not just be handed to a human or a
gated CI step for the duration of a migration. This is a real difference
in risk profile the first draft's complexity-focused analysis did not
weigh at all.

**The recommendation stands anyway, with this now made explicit rather
than assumed away**: this document still does not *mandate* a narrower
role, for the same reason as before (no new, required Postgres role this
milestone invents), but an operator who provisions a scoped-down role —
`SELECT`+`DELETE` only, on exactly `shadow_findings` and
`protected_attribute_resolutions`, for the retention job specifically,
distinct from the migration-owner role reserved for deploy-time schema
changes — is not merely "free to," as the first draft's phrasing
suggested, but **actively encouraged to, precisely because of the
recurring-schedule exposure named above.** This is a stronger, more
specific recommendation than the first draft made, without inventing any
new mandatory infrastructure this milestone would have to build or verify
(provisioning a Postgres role is a one-line `CREATE ROLE`/`GRANT` an
operator runs themselves, the same ops-time, config-deliberately-out-of-
scope category `Settings.DATABASE_URL`'s own docstring already places
migration credentials in).

### 12.12 — Where does the new encryption code live: a new top-level package, or an existing one?

**Recommendation: `audit/encryption.py`**, alongside `audit/signing.py` and
`audit/hash_chain.py` — not a new top-level `security/` package. Mirrors
the exact correction M10's own hostile-review pass made for its static
assets ("this project reaches for a new top-level package only when
nothing existing is a natural home"): encryption-at-rest is, per
`architecture-mapping.md` §13's own row, unfinished business of the
**same** "Audit System" architecture section `audit/` already implements
(hash-chaining, signing, verification) — not a new architectural concern
needing its own home.

### 12.13 — Where does the new retention code live?

**Recommendation: a new, small top-level package, `retention/`** — unlike
encryption, retention has no single existing package that naturally owns
both `shadow_findings` (plugin/sandbox-adjacent) and
`protected_attribute_resolutions` (protected-attributes-adjacent). This
mirrors M9's own justification for `human_review/` earning a new top-level
package: a standalone CLI tool whose subject matter spans more than one
existing package, with nowhere more natural to live, meets the bar this
project has consistently required before reaching for a new package
(unlike, e.g., M10's dashboard assets, which did have a natural existing
home and were corrected to live there instead).

### 12.14 — Does this milestone need a formal, extensible "field sensitivity classification" mechanism, or is a fixed list in code/documentation sufficient?

Options: **(a)** a `protected_attribute_rules`-style database table
classifying every column in this schema by sensitivity tier, admin-
configurable without a redeploy. **(b)** (recommended) a fixed, named list,
stated directly in this document (§5.1) and in `audit/encryption.py`'s own
docstring/constant, with no admin-facing configuration surface at all.
**Recommendation: (b).** This schema has a small, fixed, rarely-changing
set of columns, and no second "kind" of classification need has appeared
yet to justify the plurality a database-backed, admin-configurable
mechanism would provide — the identical "no abstraction without a second,
real, concrete use case already in hand" discipline M2 applied to
`ProtectedAttributeResolver` staying a concrete class rather than a new
port, and M4 applied to `GovernanceEngine`'s aggregation rule staying a
plain `any(...)` rather than a configurable engine. Revisit only if a
second, genuinely different sensitivity-classification need (e.g., a
future domain beyond `FINANCE` with its own, different sensitive-field
list) actually appears.

### 12.15 — Does a decrypt failure on one row raise, crash the whole response, or degrade per-row? **(new — discovered during this document's own hostile-review pass)**

Nothing in the first draft specified this at all, for either category of
encrypted field. The marker scheme (`"gpenc1:"` prefix, §5.1) is not
perfectly collision-safe against `resolution_notes` specifically, since —
unlike `payload`/`proxy_basis` — it accepts arbitrary text from a caller,
and M9's own review already named these endpoints unauthenticated: nothing
stops a caller from submitting a value that happens to start with the
literal marker before encryption is enabled, which then fails Fernet's own
integrity check once encryption is later turned on and that legacy row is
read back. Options: **(a)** let the exception propagate — simplest to
implement, but means one bad row (accidental or deliberately crafted)
takes down an entire `GET /v1/admin/verdict-reviews`/`GET
/v1/admin/population-finding-reviews` list response, including every
other, correctly-stored row in it. **(b)** (recommended for free-text
fields) catch the failure per row, log it (row id, table, no key material
or ciphertext fragment), and substitute a fixed placeholder for that one
field, leaving the rest of the row and every other row in the response
intact. **(c)** (recommended for `evidence_chain.payload` specifically,
which is evidentiary, not cosmetic, content) raise a specific, catchable
exception type distinct from a hash-mismatch tamper finding, letting
`verify_chain`'s own per-record loop (and any other caller) report a clear
"cannot be read" result — never silently substitute placeholder content
for evidence.

**Recommendation: (b) for `resolution_notes`, (c) for `payload` — the two
columns need different containment, not the same policy applied
uniformly.** (b) mirrors the exact "one record's failure is logged and
counted, never allowed to abort reconciling the rest" discipline
`human_review/backfill_reviews.py` already holds itself to
(`docs/milestones/M9.md` §3.5) — a failure in rendering one non-essential
display field must never take down what matters more (the rest of the
list). (c) mirrors `verify_chain`'s own existing design (a per-record loop
that reports the first problem it finds, rather than crashing
uncontrolled) and this platform's standing discipline of never silently
papering over a question about the evidentiary record's own integrity —
the same reasoning that keeps a hash mismatch a loud, reported failure
rather than a skipped row. Neither policy is new machinery; both reuse
patterns this codebase already has for an analogous problem.

### 12.16 — Does retention's inclusion of `protected_attribute_resolutions` require `protected_attribute_rules` to gain versioning first? **(new — found during this document's own third hostile-review pass)**

Options: **(a)** block `protected_attribute_resolutions` from retention
scope until `protected_attribute_rules` gains a versioning/snapshot
mechanism — the safest reading, but reopens M5's own architecture for a
risk this milestone's own citation trail never asked it to fix, and
removes retention from the one table besides `shadow_findings` this
document can build it for at all, leaving M11 with a single-table
retention story. **(b)** build a minimal snapshot column onto
`protected_attribute_resolutions` now, mirroring
`population_findings.classification_snapshot` — real, additive scope this
milestone's own "no `ALTER` of any existing table" boundary (§6) does not
currently call for, and a schema change to a table this document elsewhere
treats as needing none. **(c)** (recommended) retain
`protected_attribute_resolutions` in retention scope, disclose the
conditional nature of "reconstructible" plainly (§4.4/§9), and defer the
versioning fix (§11) until a concrete need appears — the identical
"disclose, don't reopen a settled boundary" discipline §4.3 already
applies to the `?since` interaction, and the identical "no preemptive
scaffolding without a concrete forcing case" discipline §12.9 already
applies to chain-checkpointing.

**Recommendation: (c).** The practical risk today is low — no Admin API
path mutates an existing rule — and the raw values this classification was
computed over are never actually lost (§4.4). Blocking or redesigning
retention over a risk with no current exploitation path and no concrete
forcing requirement would repeat the exact "solve a problem before a real
case demands it" pattern this document has declined elsewhere (§12.3,
§12.9, §12.14). If a future milestone adds rule-editing to the Admin API,
that milestone should also add the versioning this ambiguity defers — not
retrofit it after the fact.

### 12.17 — What encoding does `FIELD_ENCRYPTION_KEY` need, and does it need its own generation utility like `generate_private_key_hex`? **(new — found during this document's own third hostile-review pass)**

**Recommendation: `Fernet.generate_key()`'s own output** — 32
url-safe-base64-encoded bytes, not the hex convention
`SIGNING_PRIVATE_KEY` uses. No bespoke helper is needed: unlike raw
Ed25519 key generation (which has no self-describing, ready-to-use string
encoding of its own, hence `generate_private_key_hex`), `Fernet.generate_key()`
already returns a directly usable key in exactly the form `Fernet(key)`
expects. Building a wrapper around it would be redundant machinery this
document declines to add, the same "don't build what the dependency
already provides" discipline every other use of `cryptography` in this
codebase already follows.

**Every item below reflects this document's own second and third
hostile-review passes, folded in — see the revision note near the top for
what changed and why. Items 4 and 9 are corrected/reversed from the first
draft; items 3, 6, 7, 12, and 13 carry an amendment from the second pass;
item 21 corrects a factual overclaim the first two drafts made, and items
22–23 are new additions, all three from the third pass.**

   by two tiers together: a documented, verified-at-deploy-time

   encryption (no code, since this repository does not provision

7. §5.1/§12.5 — **(reversed from the first draft)** `evidence_chain.payload`
