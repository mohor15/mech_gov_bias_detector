    below it.** Checked directly against how this method is actually
    called: the Admin API handler (§5.3) already runs its own
    `get(session, binding_id)` pre-check immediately before invoking
    `set_lifecycle_state`, so that row is already loaded in the session's

    already-loaded object from that map without a fresh database read

    race this milestone exists to close (M9 §9.6) — a second transaction
    committing a conflicting transition between the handler's pre-check
    and this method's own `UPDATE` — the unpatched branch would have
    returned the *stale*, pre-race `lifecycle_state` the earlier
    pre-check loaded, not the row's true state, directly contradicting

    *unchanged* — still a separate step run before `set_lifecycle_state`
    is called at all. Only `set_lifecycle_state`'s own internal shape
    collapsed (its own `get()`-then-`flush()` two-step became one atomic
    `UPDATE`); the outer gap between the router's pre-check and the write
    is not narrowed by this milestone. `PolicyBinding` also has no
    "revocation" concept — only `ACTIVE`/`INACTIVE` transitions;
    "revoke" is `Principal`'s vocabulary (M13), and its appearance here
    was a copy-paste artifact. **Corrected (§5.3):** the claim is
    removed rather than restated, since the race it described has no
    practical consequence either way — no code path in this codebase
    ever issues a `DELETE` against `policy_bindings` (confirmed directly),
    so the row a concurrent revocation could act on cannot disappear.
12. **Amended — the test plan (§1 item 4, §9) cited only a sequential
    conflict-test precedent for the concurrency fix, not a genuine
    concurrent one.** `test_claim_on_an_already_claimed_review_is_409`'s

    clause's correctness, not the atomicity property under real

    milestone exists to do (§1 item 2, §4.8), a sequential test alone
    cannot verify it. **Corrected (§1 item 4, §9):** the test plan now
    commits to a genuine concurrent test for `set_lifecycle_state`,
    mirroring the established threaded pattern.

## TL;DR

M14 closes two small, concrete, already-disclosed defects in this
platform's Policy Bindings surface (architecture §7/§8, M5) — not a new
capability, not a response to any newly-named architecture gap, and
explicitly not an attempt to claim the number 14 for any of the several
larger, more obvious-looking candidates (multi-tenancy/mTLS/multi-plane
deployment, real scheduling, key rotation, rate limiting, pagination,
chain-checkpointing) that this document's own architectural analysis
(§4) finds and rejects, each for a reason already stated somewhere in
this project's own record.

**Defect one (`docs/milestones/M8.md` §13.20):** `population_policy_bindings`
was fixed at M8 so that deactivating a binding and creating a new one for
the identical `(system_id, population_policy_id)` pair — the only way
this platform lets an admin change a binding's parameters, since there is
no `PATCH`/update endpoint — actually works: a partial unique index
scoped to `ACTIVE` (migration `0022`) plus a new,
lifecycle-aware `get_active_by_identity` lookup. `policy_bindings`, the
structurally identical table `PolicyBindingRepository` manages, was
found at the same time to have the *same* underlying problem — a plain
`UNIQUE (adapter_id, policy_id)` constraint (migration `0011`) and a
lifecycle-blind `get_by_identity` conflict check — and was explicitly
"deliberately left unfixed inside M8... flagged as a candidate for a
small, dedicated follow-up," since fixing another milestone's table was
out of that milestone's own scope. **Confirmed, by reading the current
repository directly, still unfixed**: an admin can deactivate a
`PolicyBinding` to change its `severity`, then discover the identical
`(adapter_id, policy_id)` pair can never be re-bound again, with no
schema-level or application-level path to recover short of picking a
different, unused pair.

**Defect two (`docs/milestones/M9.md` §9.6):** `set_lifecycle_state`, the
method both `PolicyBindingRepository` and `PopulationPolicyBindingRepository`
use for `activate`/`deactivate`, is a plain `session.get(...)`, mutate the
attribute, `flush()` — no conditional `WHERE` clause, no row-count check.
Two concurrent `activate`/`deactivate` calls against the same binding can
both "succeed," last write silently wins, with no conflict signal to
either caller — found as a byproduct of M9's own design work, which
needed (and built) a materially stronger pattern for `VerdictReview`/
`PopulationFindingReview`'s own `claim`/`release`/`resolve`, and confirmed
this platform's two pre-existing lifecycle methods never received the
same treatment. **Confirmed still unfixed in both repositories** — and
cited as still-live precedent as recently as `docs/milestones/M13.md`'s
own `PrincipalRepository.revoke`, which explicitly uses the *stronger*
pattern specifically to avoid repeating this exact, still-open gap a
third time.

**The fix reuses mechanisms this codebase has already built and proven,
twice — no new dependency, no new infrastructure, no new endpoint, no new
`Settings` field.** One purely-mechanical migration (mirroring migration
`0022`'s own shape exactly, for `policy_bindings` instead of
`population_policy_bindings`); one new repository method
(`PolicyBindingRepository.get_active_by_identity`, mirroring
`PopulationPolicyBindingRepository`'s own M8 addition); and one repository-
method rewrite, applied identically to both `PolicyBindingRepository.set_lifecycle_state`
and `PopulationPolicyBindingRepository.set_lifecycle_state`, converting
each from a read-then-write to a single conditional `UPDATE ... WHERE ...
RETURNING`, checked by row count — the exact shape
`VerdictReviewRepository.claim`/`release`/`resolve` (M9) and
`PrincipalRepository.revoke` (M13) already use.

**One genuine value judgment is held for your explicit approval (§12.1)**,
the same way M11/M12/M13 each held their own single highest-stakes call:
whether a redundant `activate`-on-already-`ACTIVE` or `deactivate`-on-
already-`INACTIVE` call should become a `409` (full consistency with
every other conditional-`UPDATE` method this codebase has ever shipped)
or keep today's actual, silent `200` no-op (preserving byte-for-byte
backward compatibility for that one specific case). Everything else in
this document is this review's own confident recommendation.

## 1. Scope

M14 modifies exactly two existing repositories
(`src/gov_platform/db/repositories/policy_binding.py`,
`src/gov_platform/db/repositories/population_policy_binding.py`), the two
Admin API routers built directly on them
(`src/gov_platform/api/admin/policy_bindings.py`,
`src/gov_platform/api/admin/population_policy_bindings.py`), and adds one
new migration. It touches no other module, no other table, no other
endpoint, and no cross-cutting platform concern (authentication,
encryption, retention, reporting) at all.

**In scope:**

1. `policy_bindings` gains the identical "recreate after deactivate"
   capability `population_policy_bindings` already has — a new partial
   unique index (migration `0029`) and a new
   `PolicyBindingRepository.get_active_by_identity` method, wired into
   `create_policy_binding`'s existing conflict pre-check in place of the
   lifecycle-blind `get_by_identity` it uses today.
2. `PolicyBindingRepository.set_lifecycle_state` and
   `PopulationPolicyBindingRepository.set_lifecycle_state` are each
   rewritten from a read-then-write two-step to a single conditional
   `UPDATE ... WHERE id = :id [AND ...] RETURNING *`, checked by row
   count — closing the concurrent-transition race named at M9 §9.6 for
   both repositories that share it.
3. `activate_policy_binding`/`deactivate_policy_binding` and their
   `population_policy_bindings` twins gain an explicit
   `except ValueError as exc: raise HTTPException(409, ...)` around the
   now-conflict-capable `set_lifecycle_state` call — the identical
   pattern `admin/verdict_reviews.py`/`population_finding_reviews.py`'s
   `claim`/`resolve` handlers already use for their own conditional-
   `UPDATE` repository calls, not a new error-handling idiom.
4. New unit/integration tests exercising every changed code path,
   mirroring the exact shape of the tests M8 added for
   `population_policy_bindings`' own recreate-after-deactivate fix and M9/
   M13 added for their own conditional-`UPDATE` conflict paths — **and**,
   for `set_lifecycle_state` specifically, a genuine concurrent test, not
   only a sequential one (Revision note item 12, §9).

**Out of scope**, argued in full at §4:

- Architecture §17 (multi-tenancy, mTLS, multi-plane deployment) —
  unassigned, unchanged from M13 §4.2/§12.2.
- Real scheduling for this platform's three recurring batch CLIs —
  unassigned, unchanged from four consecutive prior milestones' own
  conclusion (M6/M8/M11/M12), reaffirmed by M13 §4.2/§13.3.
- Key rotation / KMS/HSM custody for any of this platform's secret types
  — unassigned, unchanged from M5/M11/M13.
- Per-principal rate limiting or any other comprehensive request-abuse
  protection — unassigned, unchanged from M0/M13 §13.5.
- List-endpoint pagination — unassigned, unchanged from M10 §8.3/M12
  §12.15.
- `evidence_chain`/`population_findings` chain-checkpointing — unassigned,
  unchanged from M11 §4.2/§12.9.
- Any change to `PolicyBinding`'s or `PopulationPolicyBinding`'s public
  field shape, to `severity` semantics, to which roles may call which
  endpoint (M13's `require_role` wiring is untouched), or to any other
  table in this schema.

## 2. Relationship to previous milestones

M14 is a direct, narrow continuation of a defect this project's own
record has already fully investigated twice and explicitly deferred both
times, not a new architecture decision.

- **M5** built `policy_bindings` and `PolicyBindingRepository` — the
  original `UNIQUE (adapter_id, policy_id)` constraint (migration `0011`)
  and the original, lifecycle-blind `get_by_identity`/`set_lifecycle_state`
  shape M14 now revises both trace back to this milestone. Nothing about
  M5's own scoping decisions (severity on the binding, not the policy;
  `adapter_id`-keyed, not `System.domain`-keyed) changes.
- **M6** built `population_policy_bindings` and
  `PopulationPolicyBindingRepository` as a deliberate structural mirror of
  M5's `policy_bindings` — including, unintentionally, the identical
  defect shape M14 now closes in both places.
- **M8**, generalizing `population_engine` and making a population
  policy's parameters admin-configurable, discovered that
  `population_policy_bindings`' plain uniqueness constraint made a
  binding's parameters *not actually changeable* without recreating the
  binding — and that recreation was itself blocked by the same
  constraint. Fixed for `population_policy_bindings` (migration `0022`,
  `get_active_by_identity`). Found, named, and **explicitly left unfixed**
  for `policy_bindings` — "a genuinely pre-existing, previously-
  undiscovered defect... deliberately left unfixed inside M8 (M5's scope,
  not the Evaluation Framework)... flagged as a candidate for a small,
  dedicated follow-up" (`docs/milestones/M8.md` §13.20). M14 is that
  follow-up.
- **M9**, building `VerdictReview`/`PopulationFindingReview`'s `claim`/
  `release`/`resolve` and needing a materially stronger concurrency
  pattern than either binding repository had, checked the existing
  precedent first and found `set_lifecycle_state`'s read-then-write shape
  in both `PolicyBindingRepository` and `PopulationPolicyBindingRepository`
  — "confirmed real, verified directly against the repository's actual
  code... confirmed pre-existing, not introduced by M9... Recommendation:
  do not fix inside M9... documented here and at §7/§8 as a verified,
  outstanding candidate for a small, separate follow-up"
  (`docs/milestones/M9.md` §9.6). M14 is that follow-up, for both
  repositories.
- **M11** is direct proof this project does eventually return to and
  close items named this way: M9 §9.5 (a separate, related finding —
  `verdicts`/`findings`/`decision_events`/`model_versions`/`systems`/
  `verdict_findings` lacking the append-only privilege lockdown
  `evidence_chain`/`population_findings` already had) was closed by M11's
  migration `0025`, two milestones after M9 named it. M14 is the
  identical shape of return for M9 §9.6/M8 §13.20's own, still-open
  companion findings, three and four milestones later respectively.
- **M13** is the most recent evidence these two defects are still live
  and still relevant: `PrincipalRepository.revoke`'s own docstring
  explicitly cites `PopulationPolicyBindingRepository.set_lifecycle_state`'s
  read-then-write shape as "a genuine, documented pre-existing race —
  `docs/milestones/M9.md` §9.6" and deliberately does *not* repeat it,
  using the conditional-`UPDATE`-by-row-count pattern instead. M13 chose
  not to fix the pre-existing gap it was citing (correctly — a fourth
  milestone's own scope is not the place to retroactively patch a second
  and third milestone's tables), but its own code is the freshest,
  clearest confirmation that the pattern this document proposes is
  already this platform's own established convention for exactly this
  problem, not a new idiom M14 invents.

No prior milestone's approved architectural decision is revised,
weakened, or reopened by this document. `PolicyBinding.severity`'s
meaning, `policy_bindings`' `adapter_id` key, `ACTIVE`/`INACTIVE`'s two-

## 3. Explicit non-goals

- **Not a new capability from an end-user's perspective beyond "a
  previously-blocked action now succeeds."** No new endpoint, no new
  request field, no new response field, no new role.
- **Not a general "audit every repository for this defect shape"
  initiative.** §4.8/Revision note item 8 confirms, by direct inspection,
  that exactly two repositories carry this defect and every other
  lifecycle-carrying table in this schema was built correctly from the
  start. This document does not propose a standing review process or
  tooling to catch a future instance — the same "no infrastructure
  without a concrete, current forcing case" restraint this project
  applies everywhere else. A future milestone that introduces a new
  lifecycle-carrying table is responsible for using the now-established
  pattern from the start, the same way M9 and M13 already did.
- **Not a change to `severity`'s meaning or to how `GovernanceEngine`
  resolves a `GoverningPolicy`.** `list_active_for_adapter`/
  `list_active_for_system` — the methods the request-path/batch-path
  actually depend on for policy resolution — are untouched.
- **Not a `PATCH`/update endpoint for either binding type.** "Deactivate
  and recreate" remains this platform's only mechanism for changing a
  binding's `severity`/`parameters` — M14 makes that mechanism actually
  work for `policy_bindings`, it does not replace it with a different
  one. A general update endpoint remains unbuilt, unchanged from M5/M6/M8.
- **Not a fix for the list-endpoint pagination gap**, even though this
  milestone touches two of the routers pagination would eventually need
  to change — see §4.6/§12 for why bundling it in here would repeat this
  project's own precursor mistake to M13.
- **Not a retroactive correction of any already-recorded `PolicyBinding`/
  `PopulationPolicyBinding` row.** Every existing row's `id`, `severity`/
  `parameters`, and `lifecycle_state` are read and written exactly as
  before; the new partial index is, by construction, strictly less
  restrictive than the constraint it replaces (§8), so no existing row
  can violate it.

## 4. Architectural analysis

### 4.1 What "M14" inherits from this project's own record

§ Sourcing note above establishes the fact: nothing. This section works
through every candidate this document considered before settling on
Policy Binding Lifecycle Hardening, applying the same two tests each
time — **(a) does this platform's own record show a concrete, current
forcing case for building it now**, the discipline M5 (signing custody),
M7 (metrics infrastructure), M11 (encryption), M12 (PDF rendering), and
M13 (OAuth2/OIDC) each already applied to decline a superficially-
reasonable-looking scope expansion; and **(b) is this actually one
coherent concern, or does it bundle several unrelated ones the way
architecture §17 and the historical use of the string "M13" both did**,
the specific failure mode this document's own instructions named.

### 4.2 Why not architecture §17 (multi-tenancy, mTLS, multi-plane deployment)

This is the most obvious candidate on a purely numerical reading — the
one remaining explicitly-numbered architecture section (§17) with real,
undelivered scope, and the one M13 itself came closest to touching.
Fails both tests. **Test (a):** `docs/milestones/M13.md` §4.2 already
established, directly against this platform's own record, that none of
the three has a concrete forcing case — "this platform's schema has no
tenant-scoping concept anywhere today... a real design question with
zero concrete case in this platform's record to design against" for
multi-tenancy; "this platform has exactly one deployment plane today...
meaning there is no second plane yet for mTLS to secure trust between"
for mTLS; nothing in this project's record between M13's approval and now
introduces a second tenant, a second deployment plane, or a corporate
identity-federation requirement. **Test (b):** §17 is not one concern, it
is three (multi-tenancy, mTLS, multi-plane deployment) — the exact
bundling shape that made "M13" unusable as a citation until this
project's own discipline unbundled it. Proposing "M14 = §17" would
recreate that problem one milestone later, not avoid it.

### 4.3 Why not real scheduling for the three recurring batch CLIs

Fails test (a) by this project's own repeated, explicit conclusion — not
a new finding, a restated one. `docs/milestones/M6.md` §13.4,
`docs/milestones/M8.md` §4.1, `docs/milestones/M11.md` §5.2,

### 4.5 Why not per-principal rate limiting

The one candidate whose disqualification required the closest reading,

`docs/milestones/M10.md` §8.3 names this precisely — "a real, verified

### 4.8 What actually survives both tests

Two defects, both already fully investigated and named by this project's
own hostile-review discipline, both confirmed — by reading
`src/gov_platform/db/repositories/policy_binding.py` and
`population_policy_binding.py` directly against their own docstrings and
migration `0011`/`0022` — to still be present exactly as described:

- **M8 §13.20**: `policy_bindings` never received the "recreate after
  deactivate" fix `population_policy_bindings` got in the same milestone.
  This is a real, present-tense defect, not future infrastructure — it is
  wrong *today*, at any scale, the first time an admin deactivates a
  binding intending to rebind it with a different `severity`.
- **M9 §9.6**: `set_lifecycle_state`'s read-then-write shape, shared by
  both repositories, has no conditional-update protection against a
  concurrent transition — also a real, present-tense defect (M9's own
  risk assessment calls the concrete race "rare," not nonexistent; §9
  below preserves that same honest framing rather than overstating the
  risk to justify the fix).

Both pass test (a): the forcing case is not a hypothetical future
requirement, it is a bug that exists in the shipped code right now,
independent of scale, deployment topology, or tenancy. Both pass test
(b): they are one coherent concern — `PolicyBindingRepository`'s
lifecycle-transition mechanics never receiving the hardening this
project's own established pattern (partial unique index +
lifecycle-aware lookup + conditional-`UPDATE`-by-row-count) already gave
every sibling repository — not several unrelated things sharing a
milestone number. This is the scope §5 proposes.

## 5. Proposed architecture (this review's recommendation)

### 5.1 `PolicyBindingRepository.get_active_by_identity` — mirrors M8's own fix, exactly

A new method, added alongside the existing `get_by_identity` (left
unchanged — `plugins/seed_registry.py`'s `seed_policy_binding` depends on
its current, lifecycle-blind meaning for its own idempotent-seed check,
confirmed by reading `src/gov_platform/plugins/seed_registry.py` directly;
changing `get_by_identity`'s meaning would silently break that caller,
exactly the risk `population_policy_binding.py`'s own docstring already
flags for why *its* M8 fix was additive, not a change to the existing
method):

```python
def get_active_by_identity(
    self, session: Session, *, adapter_id: str, policy_id: str
) -> PolicyBinding | None:
    """Like `get_by_identity`, additionally scoped to
    `lifecycle_state == ACTIVE` -- `None` if the only binding(s) for this
    key are all deactivated, even though `get_by_identity` would still
    find one. Mirrors `PopulationPolicyBindingRepository.get_active_by_identity`
    (M8) exactly. See docs/milestones/M14.md."""
```

`create_policy_binding`'s existing conflict pre-check
(`src/gov_platform/api/admin/policy_bindings.py`) switches from
`get_by_identity` to `get_active_by_identity` — the one-line change that
actually makes recreation after deactivation possible; the schema change
alone (§8) is necessary but not sufficient, the identical lesson M8
§4.4/§13.19 already recorded for `population_policy_bindings`.

### 5.2 `set_lifecycle_state` — conditional `UPDATE`, checked by row count

Both `PolicyBindingRepository.set_lifecycle_state` and
`PopulationPolicyBindingRepository.set_lifecycle_state` change from:

```python
row = session.get(BindingRow, binding_id)
if row is None:
    raise ValueError(...)
row.lifecycle_state = lifecycle_state.value
session.flush()
return self._to_model(row)
```

to the shape `VerdictReviewRepository.claim` (M9) and
`PrincipalRepository.revoke` (M13) already establish:

```python
statement = (
    update(BindingRow)
    .where(
        BindingRow.id == binding_id,
        BindingRow.lifecycle_state != lifecycle_state.value,
    )
    .values(lifecycle_state=lifecycle_state.value)
)
result = session.execute(statement)
assert isinstance(result, CursorResult)
if result.rowcount == 0:
    row = session.get(BindingRow, binding_id, populate_existing=True)
    if row is None:
        raise ValueError(f"no {binding kind} with id {binding_id!r}")
    return self._to_model(row)  # already in the requested state -- see §12.1
session.flush()
row = session.get(BindingRow, binding_id, populate_existing=True)
assert row is not None
return self._to_model(row)
```

**Both branches use `populate_existing=True`, not only the success
branch** — corrected by this document's own second, independent
hostile-review pass (Revision note item 10), against a first draft that
omitted it from the `rowcount == 0` branch specifically. `Session.get()`
returns an object straight from the session's identity map, without a
fresh database round trip, if that primary key is already loaded in the
current session — and it already is: the calling Admin API handler
(§5.3) runs its own `get(session, binding_id)` pre-check immediately
before calling this method. Without `populate_existing=True`, the exact
concurrent-race scenario this milestone exists to fix (M9 §9.6) — a
second transaction committing a conflicting transition between the
handler's pre-check and this `UPDATE` attempt — would make the
`rowcount == 0` branch return the *stale*, pre-race object the earlier
pre-check loaded, not the row's true state at the moment this `UPDATE`
ran. Both branches now force a fresh read, so the returned
`lifecycle_state` is always accurate, regardless of what raced against
it in between.

The `lifecycle_state != :target` condition, not an
`lifecycle_state == :specific_expected_prior_state` condition, is
deliberate: the existing `activate`/`deactivate` endpoints take no
"expected current state" parameter from the caller (unlike `resolve`'s
`reviewer` field, which *does* have a caller-supplied value to check
against), so the only meaningful condition available is "this call would
actually change something." This closes the disclosed defect precisely
as named — an atomic, row-locked transition instead of a non-atomic
read-then-write — while leaving open exactly one judgment call, resolved
at §12.1: what a caller should see when the row *was already* in the
requested state at the moment the `UPDATE` ran (rowcount 0, but not
because of a lost race — because there was nothing to change). The
pseudocode above shows the backward-compatible branch (§12.1 option (b));
§12.1 option (a)'s alternative is a one-line change (raise `ValueError`
in that branch instead of returning the current state).

### 5.3 Admin API — `ValueError` → `409`, the existing idiom, not a new one

`activate_policy_binding`/`deactivate_policy_binding`
(`api/admin/policy_bindings.py`) and
`activate_population_policy_binding`/`deactivate_population_policy_binding`
(`api/admin/population_policy_bindings.py`) each wrap their existing
`set_lifecycle_state` call in the identical `try`/`except ValueError as
exc: raise HTTPException(status.HTTP_409_CONFLICT, detail=str(exc)) from
exc` shape `claim_verdict_review`/`resolve_verdict_review` already use
today — not a new exception-handling pattern, and not routed through
`api/app.py`'s global `ValueError → 422` handler (that handler exists for
client-input-shape problems, e.g. an unrecognized protected attribute;
this is a state-conflict problem, the same distinction M9 already drew
for `claim`/`resolve`). The existing `get(session, binding_id) is None`
pre-check (→ `404`) that runs before `set_lifecycle_state` today is
unchanged — it continues to own "the binding does not exist at all";
`set_lifecycle_state`'s own `ValueError` (§5.2) is now reachable only for
"the binding exists" cases the pre-check already let through.

**Corrected by this document's own second, independent hostile-review
pass (Revision note item 11)**: a first draft of this section claimed the
fix additionally "closes a... TOCTOU gap... the `get()` pre-check and the
write are no longer two separate round trips a concurrent revocation
could land between." Checked directly against the surrounding text two
sentences above — the router's own pre-check is explicitly *unchanged*,
still a separate step run before `set_lifecycle_state` is ever called;
only `set_lifecycle_state`'s **own internal** shape collapsed (its own
`get()`-then-`flush()` two-step became one atomic `UPDATE`, §5.2). The
router-level gap between "check it exists" and "write to it" is not
narrowed by this milestone at all. That claim also borrowed the wrong
vocabulary — `PolicyBinding` has no "revocation" concept (only
`ACTIVE`/`INACTIVE` transitions; "revoke" is `Principal`'s term, M13).
Both corrected here by removing the claim rather than restating it more
carefully: it described a race with no practical consequence regardless
of wording, since no code path in this codebase ever issues a `DELETE`
against `policy_bindings` — the row this pre-check might theoretically
race against disappearing simply cannot disappear.

## 6. Database/schema implications

**One migration**, `0029`, purely mechanical and directly modeled on
migration `0022`'s own, already-reviewed shape:

```sql
-- Relax policy_bindings' uniqueness to a partial index scoped to
-- ACTIVE -- architecture §7/§8, M14. Closes docs/milestones/M8.md
-- §13.20's own disclosed, deliberately-deferred defect: population_policy_bindings
-- received this exact fix at M8 (migration 0022); policy_bindings never
-- did. See docs/milestones/M14.md §6/§8 for the full reasoning --
-- identical to 0022's, applied to the sibling table it was always meant
-- to also cover.
--
-- Safe for every existing row, for the identical reason 0022 was: the
-- new partial index is strictly less restrictive than the plain
-- constraint it replaces -- any row set satisfying "at most one row per
-- (adapter_id, policy_id), full stop" trivially satisfies "at most one
-- *ACTIVE* row per (adapter_id, policy_id)".
ALTER TABLE policy_bindings
    DROP CONSTRAINT policy_bindings_adapter_id_policy_id_key;

CREATE UNIQUE INDEX one_active_policy_binding_per_adapter
    ON policy_bindings (adapter_id, policy_id)
    WHERE lifecycle_state = 'ACTIVE';
```

`policy_bindings_adapter_id_policy_id_key` is Postgres's default-generated
name for migration `0011`'s inline `UNIQUE (adapter_id, policy_id)`
constraint — implementation must confirm this against the actual, live
schema (`\d policy_bindings`) before this migration is finalized, the
same verification migration `0022`'s own author performed for its own
sibling constraint, rather than assumed from convention alone.

**No `ALTER` of any column, no data rewrite, no change to any other
table.** Plain `CREATE UNIQUE INDEX`, not `CONCURRENTLY` — identical
reasoning to migration `0022`: `db/migrate.py`'s `apply_migrations` wraps
every migration file in one transaction, and `CREATE INDEX CONCURRENTLY`
is illegal inside a transaction block. `policy_bindings` is bounded,
low-write-volume admin configuration (one row per real `(adapter, policy)`
pair, no request-path write traffic — the request path only ever
*reads* `policy_bindings` via `list_active_for_adapter`), so the brief
`ACCESS EXCLUSIVE` lock this incurs is a non-event in practice, the same
conclusion migration `0022` reached and materially different from
migration `0025`'s own maintenance-window requirement (which touched
this platform's actual highest-throughput, request-path-critical tables
— `policy_bindings` is not one of them). Apply during a low-admin-activity
window as a documented precaution regardless, matching `0022`'s own
stated caution.

**No new table, no new column, no privilege (`GRANT`/`REVOKE`) change** —
`gov_platform_app`'s existing `SELECT, INSERT, UPDATE, DELETE` grant on
`policy_bindings` (migration `0011`) already covers everything the
revised `set_lifecycle_state`/`get_active_by_identity` need.

`population_policy_bindings` needs **no schema change** — its partial
unique index and `get_active_by_identity` already exist from migration
`0022`/M8; only its repository method (`set_lifecycle_state`, §5.2) and
Admin API handler (§5.3) change.

## 7. Public API changes

No new endpoint, no new router, no new request or response field, no
change to any role gate M13 already wired onto these eight endpoints
(`create`/`activate`/`deactivate` remain `ADMIN`-only on both routers;
`list`/`get` remain any authenticated principal). Two response-code
deltas, both narrow and both detailed further in §10 (Backward
compatibility):

1. **`POST /v1/admin/policy-bindings`, previously-deactivated pair**:
   `409` → `201`. A binding for an `(adapter_id, policy_id)` pair whose
   *only* existing row is `INACTIVE` can now be created — a strict
   widening of what succeeds; no request that used to succeed can now
   fail.
2. **`POST /v1/admin/{policy-bindings,population-policy-bindings}/{id}/{activate,deactivate}`,
   redundant call**: `200` → `409`, **if and only if** §12.1 is resolved
   toward full consistency with this codebase's other conditional-`UPDATE`
   methods (option (a)). If §12.1 is resolved toward preserving today's
   idempotent behavior (option (b)), this response code does not change
   at all. This is the one item in this document not yet decided.

No change to `PolicyBindingResponse`/`PopulationPolicyBindingResponse`'s
field shape in either case — every successful response's body is
byte-for-byte identical to today's.

## 8. Migration strategy

Single migration (`0029`, §6), applied the same way every migration in
this platform's history has been — `python -m gov_platform.db.migrate
--database-url <admin-connection>`, no application downtime required, no
maintenance window required beyond the general "avoid concurrent
admin-heavy activity" caution §6 already states (materially lighter than
migration `0025`'s own requirement, which this document does not repeat
since it does not touch a request-path table).

No data migration, no backfill — every existing `policy_bindings` row
already satisfies the new partial index by construction (§6). No
coordinated deploy ordering beyond this platform's own existing
convention (migrations apply before the new application code that
depends on them starts serving traffic) — nothing about the repository/
API-layer changes in §5 depends on anything migration `0029` does not
already guarantee once applied.

Rollback, if ever needed, is the exact inverse — `DROP INDEX
one_active_policy_binding_per_adapter; ALTER TABLE policy_bindings ADD
CONSTRAINT policy_bindings_adapter_id_policy_id_key UNIQUE (adapter_id,
policy_id);` — safe only if no row created after `0029` applied would
violate the restored plain constraint (i.e., no `(adapter_id, policy_id)`
pair was ever recreated after a deactivation in the interim); this is the
identical, already-accepted rollback risk migration `0022` itself carries
for `population_policy_bindings`, not a new risk class this document
introduces.

## 9. Production-readiness implications

**What this closes, concretely.** An admin who deactivates a
`PolicyBinding` intending to rebind the same `(adapter_id, policy_id)`
pair at a different `severity` — the only way this platform lets that
judgment call change, since there is no update endpoint — has, since M5,
silently been unable to do so: `create_policy_binding` would reject the
attempt with a `409` ("already exists"), even though the existing
binding's own `lifecycle_state` shows `INACTIVE` in the very same list
response. At this platform's actual observed scale (two adapters, a
handful of bindings, `docs/milestones/M8.md` §13.20's own framing) this
has likely never been reported precisely because it has likely never
been hit — but it is a real, confusing, silent dead end for the first
operator who does hit it, not a theoretical one.

**What this closes, with an honestly bounded risk assessment.** The
`set_lifecycle_state` race M9 §9.6 names requires two concurrent
`activate`/`deactivate` calls against the *same* binding within
milliseconds of each other — M9's own assessment ("a lifecycle-activation
race requires two admins acting on the same binding within milliseconds
of each other — rare") is not revised upward by this document; this fix
closes a real but low-probability gap, not a frequently-observed one.
The value of closing it now is that the fix is nearly free (an existing,
already-proven pattern, applied to two more call sites) and the pattern
is now consistent everywhere this codebase does a lifecycle-style
transition, not that the risk has grown.

**No performance implication.** Both tables remain small,
admin-configuration-scale (row count bounded by real adapter/system ×
policy pairs, not by request or decision volume); a conditional `UPDATE`
checked by row count costs the same single round trip the current
`get()` + `flush()` pair already does, and `create_policy_binding`'s
conflict check trades one index lookup (`get_by_identity`) for another,
functionally identical one (`get_active_by_identity`) — no additional
query, no additional table scan.

**No security implication.** This is an internal data-integrity/API-
correctness fix; it does not touch `require_role`, `Principal`, or any
M13 authentication/authorization mechanism, and does not change which
role may call which endpoint.

**No coverage regression expected.** New tests are additive, mirroring
the exact shape `test_population_policy_bindings_postgres.py`'s own M8-
era tests already established for `get_active_by_identity`/recreate-
after-deactivate, plus the exact shape
`test_verdict_reviews_postgres.py`'s M9-era tests already established for
a conditional-`UPDATE` conflict path (`test_claim_on_an_already_claimed_review_is_409`
and its siblings) — no existing test asserts today's actual "recreate
after deactivate silently fails" or "no conflict signal on a redundant
activate/deactivate call" behavior as a *feature* (confirmed by reading
`tests/integration/test_policy_bindings_postgres.py` and
`tests/integration/test_admin_policy_bindings_api.py` directly:
`test_deactivating_and_reactivating_a_binding` toggles the same binding's
own state back and forth, it does not attempt to recreate a deactivated
one, and no test exercises a concurrent pair of calls at all), so no
existing test needs to be deleted or weakened to land this fix, only
extended.

**Corrected by this document's own second, independent hostile-review
pass (Revision note item 12)**: a sequential conflict test
(`test_claim_on_an_already_claimed_review_is_409`'s own shape — call
once, call again, assert `409`) verifies the `WHERE` clause's
correctness, but not the atomicity property under genuine concurrent
load — the actual, already-established precedent for verifying *this*
exact defect class (a lifecycle-transition race, M9 §9.6's own origin) is
a real multi-threaded test, confirmed present for the structurally
identical `claim` race in both `tests/integration/test_verdict_reviews_postgres.py`
(ten concurrent `threading.Thread`-based claim attempts) and
`tests/integration/test_population_finding_reviews_postgres.py` (the
identical pattern). A first draft of this milestone's own test plan cited
only the sequential shape. **Corrected (§1 item 4):** the new test suite
also includes a genuine concurrent test for `set_lifecycle_state` on at
least one of the two repositories, mirroring `test_verdict_reviews_postgres.py`'s
own threaded pattern exactly, since closing "the concurrent-transition
race" (§1 item 2) is half of what this milestone exists to do and cannot
be verified by a single-threaded test alone.

## 10. Backward compatibility

- **No response body shape changes for any existing successful call** —
  `PolicyBindingResponse`/`PopulationPolicyBindingResponse` are unchanged.
- **`create_policy_binding` for a previously-deactivated `(adapter_id,
  policy_id)` pair: `409` → `201`.** Strictly widening — every request
  that succeeds today still succeeds identically; a request that used to
  fail now succeeds. No caller that depends on today's rejection exists
  in this codebase (confirmed: `plugins/seed_registry.py`'s own
  `seed_policy_binding` uses lifecycle-blind `get_by_identity` for its
  idempotent-seed check, unaffected by this change, and does not depend
  on recreation ever being rejected).
- **`activate`/`deactivate` on an already-in-the-requested-state binding:
  `200` → `409`, conditional on §12.1's resolution.** If resolved toward
  option (a) (full consistency), this is a real, disclosed, narrow
  behavioral break — any caller that today relies on redundant
  `activate`/`deactivate` calls succeeding idempotently (e.g., a retried
  request after a client-side timeout, unsure whether the first attempt
  landed) would need to treat a `409` here as "already done," not as a
  failure, the same interpretation every other `409` this platform's
  conditional-`UPDATE` methods already produce requires. No such caller
  exists inside this codebase today (confirmed: no test, CLI, or
  first-party integration calls `activate`/`deactivate` more than once
  per binding in sequence); a real external operator's automation, if any
  exists, is the only plausible affected caller, and is exactly the
  audience §12.1 asks you to weigh before approving option (a).
- **No `ALTER` of any pre-existing row's data** — every `PolicyBinding`/
  `PopulationPolicyBinding` created before this milestone reads back with
  an identical `id`, `severity`/`parameters`, `lifecycle_state`, and
  `created_at` to what it had before.
- **No change to which credential/role may call which endpoint** — every
  M13 `require_role` dependency on these routers is untouched.
- **No change to `list_active_for_adapter`/`list_active_for_system`** —
  the request-path/batch-path policy-resolution query every ingestion
  route and `population_engine/run_policies.py` actually depends on is
  byte-for-byte unchanged.

Restated from §1/§4 for completeness, each with its own already-argued

## 12. Architectural ambiguities, each with a recommendation and justification

### 12.1 — Should a redundant `activate`/`deactivate` call (binding already in the requested state) return `409` or a silent `200`? **(this document's own highest-stakes call — held for your explicit approval)**

**Option (a): `409 Conflict`**, for full consistency with every other
conditional-`UPDATE`-by-row-count method this codebase has ever shipped —
`VerdictReviewRepository`/`PopulationFindingReviewRepository`'s `claim`/
`release`/`resolve` (M9) and `PrincipalRepository.revoke` (M13) all treat
"the row wasn't in the state this operation requires" as a conflict,
never a silent no-op, regardless of whether the "wrong" state happens to
already equal the caller's own goal.

**Option (b): a silent `200`, current binding state returned** —
preserves today's actual, live behavior byte-for-byte for this specific
case; the pseudocode in §5.2 implements this option directly. No response
code change at all if chosen.

**Recommendation: (a), with a full and honest accounting of the cost.**
This document leans toward (a) for one reason: the disclosed defect this
milestone exists to close (M9 §9.6) is specifically "no conflict signal
to either caller" — an admin who calls `deactivate` on a binding that a
concurrent call has *just* activated, and who happens to observe the
binding already sitting in some state, deserves a `409` telling them
their call did not do what they asked, not a `200` that could be
misread as "your deactivation just happened" when it did not. Option (b)
closes the *torn-write* half of M9 §9.6's defect (the atomicity problem)
but not the *signaling* half (the actual sentence M9 §9.6 uses:
"no conflict signal to either caller") — a caller whose own no-op request
happened to already match the current state is not the caller M9 §9.6 was
worried about; a caller whose request was overtaken by someone else's is,
and under option (b) that caller still gets an unqualified `200`, which
is precisely the silence M9 §9.6 named as the problem. Option (a) is
therefore the more complete fix, at the cost of the narrow, disclosed
`§10` behavioral change to redundant calls.

**This is not a unilateral call this document makes for you.** Unlike
every other decision in this document, reasonable people could weigh
"more precise conflict reporting" against "an idempotent-retry-friendly
API" differently, and no citation anywhere in this project's record
settles it either way for policy binding lifecycle transitions
specifically. Approve (a) or (b) explicitly before implementation
begins — see §13, item 1.

### 12.2 — Should the concurrency fix (§5.2) apply to `population_policy_bindings` too, given it already received its own M8 mutability fix separately?

**Recommendation: yes, apply to both.** `population_policy_bindings`
already has `get_active_by_identity` and its partial unique index (M8) —
it does *not* already have a conditional-`UPDATE` `set_lifecycle_state`;
that specific defect (M9 §9.6) was named against *both* repositories
identically and has been fixed in *neither*. Applying §5.2's fix to only
`policy_bindings` would leave `population_policy_bindings` with the
identical, already-named race it has carried since M6, for no reason
other than this document choosing not to finish a fix it was already
touching the exact right file to complete. This is not scope creep — M9
§9.6 named this defect once, against a single method shared by two
repositories; treating it as "half-closed" by fixing only one instance
would be an artificial, unjustified split of one finding into two.

### 12.3 — Should M14 also close the M10 §8.3 pagination gap, since this document is already touching two of the eight-router Admin API surface?

**Recommendation: no**, for the identical reason M10 itself gave when it
found this same gap and declined to fix it: "a real, verified gap, found
as a byproduct of a later milestone's own design work, that belongs to
an *earlier* milestone's surface, not the one that happened to notice
it" (`docs/milestones/M10.md` §8.3). Neither `policy-bindings` nor
`population-policy-bindings` is one of the three endpoints M10 §8.3
actually names (`population-findings`, `verdict-reviews`,
`population-finding-reviews`) — this document touching adjacent-looking
routers does not make their unrelated pagination gap this milestone's
problem, any more than M13 touching every router in this codebase made
M10 §8.3 M13's problem. Named again here, still not fixed here, still
not silently absorbed — the exact treatment this project's own
discipline has consistently given it since M10.

### 12.4 — Should `policy_bindings`' migration also add a `CHECK` constraint on `severity`/`lifecycle_state`, since M14 is already touching this table's schema?

**Recommendation: no.** `docs/milestones/M13.md`'s own Revision note item
11 already settled this question platform-wide, for `principals.role`:
no enum-backed column in this schema has ever had a database-level
`CHECK` constraint, validation lives at the Pydantic layer only
(`PolicySeverity`, `PolicyBindingLifecycleState`), and introducing one
now — for a column this migration is not otherwise touching the meaning
of — would be exactly the kind of incidental scope creep §3 already
disclaims. `severity`/`lifecycle_state` themselves are untouched by this
migration; only the *uniqueness* constraint changes.
